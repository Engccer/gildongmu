# 안드로이드 앱 출시 준비 조사 (2026-09-15)

> 조사 기록물이라 시점 고정이다. 정책·버전 수치는 조사 시점 기준이며, 결론이 뒤집히면 이 머리에 한 줄로 표기한다.
>
> 범위: 길동무 안드로이드판을 낼 때 필요한 전 과정(개발 환경, 기기, 기술 경로, 개발자 계정, 배포, 접근성 검증). 코드는 아직 한 줄도 쓰지 않는 단계의 조사다.

## 0. 한 줄 결론

**지금 이 컴퓨터로 안드로이드 앱 개발과 출시가 가능하다.** 막는 요소는 기술이 아니라 두 가지 실무 조건이다. 하나는 디스크 여유 15GB이고(정리하거나 설치 범위를 줄이면 해결된다), 다른 하나는 개발자 계정 유형 선택이다(개인 계정이면 출시 전에 테스터 12명을 14일간 모아야 한다).

가장 중요한 발견은 **한소네 7이 그냥 안드로이드 15 기기**라는 점이다. 개발용 시험 기기이자 동시에 한국 시각장애인 실사용 환경 그 자체다. 아이폰 개발 때는 없던 조건이다.

## 1. 지금 이 컴퓨터로 되는가 (실측)

2026-09-15에 이 컴퓨터에서 직접 확인한 값이다. 추정이 아니다.

| 항목 | 실측값 | 판정 |

| 메모리 | 16GB | 권장치 충족 |

### 1.1 디스크 15GB 문제

일반적인 안드로이드 개발 권장 여유 공간은 30GB에서 40GB다. 지금 15GB로는 "전부 설치"가 안 된다. 다만 **전부 설치할 필요가 없다.**

용량을 먹는 주범은 세 가지인데, 그중 가장 큰 하나를 뺄 수 있다.

| 구성요소 | 대략 용량 | 꼭 필요한가 |
|---|---|---|
| 에뮬레이터 + 시스템 이미지 | 8GB에서 12GB | **불필요**. 실기기(한소네)가 있다 |
| Android Studio 본체 | 2.5GB에서 3GB | 선택. 아래 §1.3 |
| 커맨드라인 SDK(platform-tools, build-tools, platform API) | 300MB에서 500MB | 필수 |
| Gradle 배포판 + 빌드 캐시 | 프로젝트당 1GB에서 2GB | 필수 |

**결론: 에뮬레이터를 빼면 약 2GB에서 3GB로 개발이 가능하다.** 15GB 안에 들어간다. 다만 빌드 캐시가 계속 자라므로 여유를 만들어 두는 편이 안전하다. 디스크 정리를 권한다.

### 1.2 JDK 25가 설치돼 있는데 그대로 쓰면 안 될 수 있다

설치된 Java는 25다. 그런데 안드로이드 빌드 도구(Android Gradle Plugin)가 공식 지원하는 것은 통상 JDK 17 또는 21이다. 최신 Java가 오히려 빌드를 깨뜨리는 구간이 있다.

대응은 간단하다. Java를 여러 개 깔아 두고 안드로이드 프로젝트에서만 17이나 21을 가리키게 하면 된다. 기존 JDK 25는 건드리지 않는다.

```bash
brew install --cask temurin@21
# 프로젝트의 gradle.properties 에 다음 한 줄
# org.gradle.java.home=/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home
```

착수 시점에 그때의 AGP 지원 표를 확인해 17과 21 중 고른다.

### 1.3 Android Studio를 꼭 깔아야 하는가: 아니다

이것이 이 조사에서 가장 실질적인 결론 중 하나다.

Android Studio는 IntelliJ 기반 GUI 개발 도구다. 그런데 안드로이드 빌드는 전부 명령줄로 된다.

```bash
./gradlew assembleDebug      # 시험용 앱 만들기
./gradlew bundleRelease      # 스토어 제출용 파일 만들기
./gradlew test               # 테스트
adb install app-debug.apk    # 기기에 설치
```

iOS를 Xcode GUI 없이 Claude Code와 명령줄로 개발해 온 것과 **같은 방식이 안드로이드에도 그대로 성립한다.** 오히려 안드로이드가 더 낫다. Xcode는 프로젝트 파일(pbxproj) 편집이 까다로워 XcodeGen 같은 도구를 끼워야 했지만, 안드로이드는 빌드 설정 자체가 원래 텍스트 파일(`build.gradle.kts`)이라 편집이 자연스럽다.

Android Studio를 깔면 좋은 유일한 이유는 **Layout Inspector**(화면 구조를 들여다보는 도구)인데, 이것도 접근성 트리 확인에는 `adb`의 `uiautomator dump`가 더 직접적이다(§7.2).

**권고: 처음에는 커맨드라인 SDK만 설치한다.** 디스크도 아끼고 화면 없는 작업 흐름과도 맞는다. 필요해지면 그때 추가한다.

```bash
brew install --cask android-commandlinetools
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"
```

## 2. 한소네 7이라는 시험 기기

### 2.1 실측으로 확인된 것

USB 장치 목록에 다음이 잡힌다.

```
H732B
  Manufacturer: SELVAS
  USB Vendor ID: 0x045e
  USB Product ID: 0x940a
```

`H732B`는 한소네 7의 32셀 모델이다. 제조사가 SELVAS로 확인된다. 블루투스 페어링 목록에는 `BrailleSense6_2079`와 `BrailleSense-150`도 남아 있으나 현재 연결 상태는 아니다.

Vendor ID가 `0x045e`(마이크로소프트)로 보이는 것은 오류가 아니다. **HID Braille 표준**을 따르는 점자 디스플레이는 이 식별자 체계를 쓴다. 덕분에 드라이버 없이 운영체제가 바로 인식한다.

### 2.2 기기 사양 (조사)

| 항목 | 값 |
|---|---|
| 운영체제 | **Android 15** |
| 프로세서 | 옥타코어 최대 3.35GHz |
| 메모리 / 저장공간 | 8GB LPDDR5X / 256GB UFS 4.0 |
| 점자 셀 | 20셀, 32셀, 40셀 라인업 (보유 기기는 32셀) |
| 화면 | LCD 있음. 점자 디스플레이와 내용이 동기화됨 |
| 연결 | Wi-Fi a/b/g/n/ac, 블루투스 5.3, USB-C 2개, USB-A 2개, HDMI 출력 |
| 기타 | 후면 카메라 20MP, GPS 듀얼밴드, Gemini 통합 |
| 출시 | 2026년 9월 |

**Android 15**라는 점이 중요하다. 구글 플레이 최신 요구치(§5.3)를 만족하는 최신 기기이며, 요즘 기능을 실기기로 검증할 수 있다.

**LCD 화면이 있다는 점도 중요하다.** 점자 사용자와 눈으로 보는 사람이 같은 화면을 공유하도록 설계된 제품이라, 화면 스크린샷을 떠서 시각적 배치를 검증하는 것도 가능하다.

### 2.3 개발 연결 완료 (2026-09-19 후속 실측)

```bash
$ adb devices
List of devices attached
000000000150    device
```

한소네 7 32셀 모델 H732B가 이 맥에 USB로 연결됐다. 개발자 옵션과 USB 디버깅이 켜져 있고(`settings global adb_enabled=1`, `development_settings_enabled=1`), 위원장이 이 맥의 ADB 접속을 허용했다. Android 15(API 35), 사용자 빌드(`ro.build.type=user`)라 root는 없으며 앱의 minSdk 31을 충족한다. Google Play Store(`com.android.vending`)와 TalkBack(`com.google.android.marvin.talkback`)도 설치돼 있다.

USB 디버깅을 켠 채 로그를 회수하는 동안에도 점자 출력은 정상이었다. 아래 초판의 “USB 역할 전환 시 점자 연결이 끊길 가능성”은 이 기기에서는 재현되지 않았다. 따라서 현재 실기기 판정의 선행 조건은 연결이 아니라 판정 대본 실행이다.

**USB 개발 연결**
개발자 옵션과 USB 디버깅이 활성화된 상태다. USB 연결로 ADB와 점자 출력을 함께 사용한다. 이번 실측은 설정값과 실제 연결 상태를 확인했으며, 설정 화면의 세부 진입 순서는 기록하지 않았다.

**무선 디버깅**
안드로이드 11 이상이므로 필요하면 Wi-Fi ADB도 사용할 수 있지만, 현재 USB ADB와 점자 출력이 함께 정상이라 선행 조건이 아니다.

```bash
# 한소네: 설정 > 개발자 옵션 > 무선 디버깅 > 페어링 코드로 기기 페어링
adb pair 192.168.219.XXX:YYYYY   # 기기가 알려주는 주소와 포트, 6자리 코드 입력
adb connect 192.168.219.XXX:ZZZZZ
adb devices                       # 여기서 잡히면 성공
```

### 2.4 미러링에 관하여: 아이폰 미러링과 결정적으로 다르다

질문하신 "사소한 팁" 중 이것이 가장 중요하므로 따로 적는다.

안드로이드 화면 미러링의 표준 도구는 **scrcpy**다(`brew install scrcpy`). 무료이고, 기기에 앱을 설치할 필요도 루팅도 필요 없다. USB와 Wi-Fi 모두 된다.

**그런데 scrcpy는 스크린 리더로 읽을 수 없다.** 이것이 아이폰 미러링과의 결정적 차이다.

| | 아이폰 미러링 | scrcpy (안드로이드) |
|---|---|---|
| 맥에 나오는 것 | 조작 가능한 화면 | **영상 스트림 한 장** |
| VoiceOver로 읽히는가 | 읽힘 | **안 읽힘** |
| 이유 | 접근성 정보가 맥으로 전달됨 | 화면을 그냥 비디오로 그리기만 함 |

아이폰 미러링은 애플이 접근성 정보까지 맥으로 넘겨주도록 만든 기능이다. scrcpy는 그런 통로가 없다. 화면을 영상으로 받아 창에 그릴 뿐이라, 맥 입장에서는 그림 한 장이다. VoiceOver가 읽을 내용이 존재하지 않는다.

**그래서 scrcpy는 이 작업에서 주력 도구가 아니다.** 쓸모가 있는 경우는 딱 하나, 눈으로 보는 사람에게 화면을 보여줘야 할 때다(예: 시각적 디자인 검토 요청, 시연 녹화).

**대신 쓸 도구는 따로 있다.** 안드로이드에는 화면의 내용을 텍스트 구조로 그대로 뽑아 주는 명령이 있다.

```bash
adb exec-out uiautomator dump /dev/tty
```

이 한 줄이 현재 화면의 모든 요소를 XML로 내보낸다. 각 요소의 글자, 접근성 설명(content description), 눌리는지 여부, 화면 위치까지 전부 들어 있다. **스크린 리더가 읽는 것과 같은 정보를 텍스트로 받는 것이다.** iOS에서 xcodebuildmcp 스냅샷으로 라벨을 확인하던 것과 정확히 같은 자리를 메운다.

다만 함정이 하나 있다. 화면에 애니메이션이 계속 돌면 이 명령이 응답을 기다리며 멈춘다. 기기 쪽에 시간 제한을 걸어 피한다.

```bash
adb exec-out timeout 10 uiautomator dump /dev/tty
```

**그리고 진짜 검증은 한소네 자체에서 한다.** 한소네에 앱을 설치하고 점자로 직접 읽어 보는 것이, 미러링을 거치는 어떤 방법보다 정확하다. 이것이 실사용 환경이기 때문이다.

## 3. 어떻게 만들 것인가: 세 갈래 길

길동무는 이미 두 개의 구현체가 있다. 웹(Next.js, `src/lib` 아래 순수 로직 201파일 29,017줄)과 iOS(Swift 263파일 44,744줄)다. 안드로이드판을 낼 때 이 자산을 얼마나 재사용하느냐로 경로가 갈린다.

### 경로 1. 웹을 그대로 포장한다 (TWA)

이미 만들어 둔 웹 앱을 안드로이드 앱 껍데기에 넣어 스토어에 올리는 방식이다. 구글이 공식 지원하는 경로이며 **Trusted Web Activity**라고 부른다. 포장 도구는 구글이 만든 **Bubblewrap**이다.

중요한 점은 이것이 흔히 말하는 "웹뷰 앱"과 다르다는 것이다. 웹뷰는 앱 안에 축소판 브라우저를 넣는 것이지만, TWA는 **크롬 본체가 그대로 돌아간다.** 주소창만 안 보일 뿐 성능과 기능이 크롬과 동일하다. 접근성도 크롬의 접근성을 그대로 물려받는다.

| 항목 | 내용 |
|---|---|
| 재사용 | 웹 코드 100퍼센트. **새로 짜는 코드가 사실상 없다** |
| 준비물 | **거의 전부 충족됨**. 아래 §3.1 참조 |
| 도메인 소유 증명 | `assetlinks.json`을 `/.well-known/`에 올린다 |
| 비용 | 개발자 등록비 25달러 외 없음 |
| 예상 기간 | **며칠 단위** |
| 약점 | 웹이 못 하는 것은 앱도 못 한다. 백그라운드 위치 추적, 실시간 음성 안내 세션 유지 등 |

**iOS와 달리 이 길이 열려 있다는 점이 핵심이다.** 애플은 웹사이트를 그대로 포장한 앱을 거부하지만, 구글은 TWA를 공식 경로로 제공한다.

#### 3.1 TWA 요건 실측 (2026-09-15)

착수 전에 막힐 자리가 있는지 확인한 결과, **준비물이 사실상 전부 갖춰져 있다.**

| 요건 | 상태 | 근거 |
|---|---|---|
| HTTPS 제공 | 충족 | gildongmu.dodoplanet.space |
| manifest.json | 충족 | `src/app/manifest.ts`가 생성 |
| `name` / `short_name` | 충족 | "길동무 Gildongmu" / "길동무" |
| `start_url` / `scope` | 충족 | 둘 다 `/` |
| `display: standalone` | 충족 | 주소창 없는 앱 형태의 필수 조건 |
| `theme_color` | 충족 | `#1d4ed8` |
| 아이콘 192x192 | 충족 | `public/icons/icon-192.png` |
| 아이콘 512x512 | 충족 | `public/icons/icon-512.png` |
| **maskable 아이콘** | **충족** | `public/icons/icon-maskable-512.png` |
| 서비스워커 | 충족 | `public/sw.js` (45줄, 수제) |
| Digital Asset Links | **미충족** | 유일하게 새로 만들어야 하는 것 |
| Lighthouse 80점 이상 | 미측정 | 실측 필요 |

**maskable 아이콘이 이미 있다는 점은 특기할 만하다.** 안드로이드는 런처마다 아이콘을 원형이나 둥근 사각형으로 잘라내는데(적응형 아이콘), maskable 아이콘이 없으면 잘린 자리에 흰 여백이 생기거나 로고가 잘린다. iOS에 없는 요건이라 보통 이 지점에서 한 번 막힌다. 이미 갖춰져 있다.

**남은 것은 사실상 하나다.** 도메인 소유를 증명하는 파일을 웹에 올리는 일이다.

```
/.well-known/assetlinks.json
```

이 파일에 앱의 패키지 이름과 서명키 지문을 적으면, 크롬이 "이 앱과 이 웹사이트는 같은 개발자의 것"이라고 확인하고 주소창을 숨긴다. 이것이 없으면 앱 안에 주소창이 그대로 보인다.

⚠ 이 파일 배포는 웹 배포를 수반한다. **심사 동결 기간(2026-09-22 09:00 KST까지)에는 할 수 없다.** TWA 착수는 동결 해제 이후로 잡는다. 그 전까지는 계정 개설과 기기 연결 확인(§8의 0단계에서 3단계)을 진행한다.

### 경로 2. 안드로이드 네이티브로 새로 만든다 (Kotlin + Jetpack Compose)

iOS판과 대등한 앱을 안드로이드용으로 새로 작성한다.

| 항목 | 내용 |
|---|---|
| 재사용 | 화면·로직 코드 재사용 0. 다만 **설계와 판정 규칙은 전부 재사용**된다 |
| 강점 | 백그라운드 위치, 실시간 안내, 점자 최적화 등 제약 없음 |
| 약점 | Swift 44,744줄에 대응하는 분량을 다시 써야 한다 |
| 예상 기간 | **수개월 단위** |

다만 실제 부담은 줄 수만큼은 아니다. 길동무의 어려운 부분은 이미 풀려 있다. 이탈 판정, 톤 계층, 도착 추정 같은 규칙은 순수 함수로 정리돼 있고 웹과 Kit에 미러링된 상태다. 안드로이드는 **세 번째 미러**가 된다. 설계를 다시 하는 게 아니라 옮겨 적는 작업에 가깝다.

### 경로 3. 코틀린 멀티플랫폼 (KMP)

로직을 코틀린으로 한 벌 써서 안드로이드와 iOS가 함께 쓰는 방식이다. 2026년 기준 프로덕션 사용 가능 단계로 평가된다(넷플릭스, 캐시앱 등 사용).

**그러나 길동무에는 권하지 않는다.** iOS가 이미 Swift로 완성돼 있기 때문이다. KMP의 이득은 "두 플랫폼을 함께 시작할 때" 나온다. 이미 완성된 Swift 44,744줄을 코틀린으로 옮기는 것은 안드로이드판을 새로 만드는 것보다 비싸다. 멀쩡히 돌아가고 App Store 심사를 통과한 코드를 흔드는 위험도 있다.

### 권고: 두 단계로 간다

```
1단계 (지금): TWA로 웹 앱을 올린다
  목적 - 계정 개설, 심사 통과, 첫 사용자 확보를 며칠 안에 끝낸다
  효과 - "안드로이드에서 안 된다"는 요청에 즉시 답한다
  부가 - 배포 절차와 스토어 정책을 몸으로 익힌다

2단계 (이후): 네이티브 앱으로 교체하거나 병행한다
  조건 - 실시간 안내처럼 웹으로 안 되는 기능이 안드로이드에도 필요해질 때
  방식 - 같은 패키지 이름으로 업데이트하면 사용자는 이어서 쓴다
```

1단계의 진짜 값어치는 앱 자체가 아니라 **계정 개설과 심사 통과를 미리 끝내 두는 것**이다. 개인 계정이면 테스터 12명 14일이 걸리는데(§5.2), 이 시계를 네이티브 개발과 동시에 돌릴 수 있다.

**권고: 먼저 순수 adb와 gradle로 시작하고, 반복 작업이 실제로 쌓이면 그때 자작 스킬로 만든다.** 자가 학습 루프 원칙(같은 시행착오를 두 번 겪지 않는다)에 맞고, 검증 안 된 서드파티 MCP에 의존하지 않아도 된다.

## 5. 개발자 계정

### 5.1 기본

| 항목 | 내용 |
|---|---|
| 비용 | **25달러, 일회성**(애플은 연 99달러이므로 훨씬 싸다) |
| 절차 | 구글 계정 준비 → 등록 및 결제 → 개발자·결제 프로필 → 신원·주소 인증 → 2단계 인증 |
| 신원 확인 | 법적 이름의 국가 발급 신분증, 신용카드. 주소 증명은 주민등록등본, 공과금 고지서, 카드사 명세서 등 |

### 5.2 결정이 필요한 갈림길: 개인 계정인가 조직 계정인가

**이것이 이 조사에서 유일하게 위원장 판정이 필요한 항목이다.** 출시 일정이 여기서 몇 주 갈린다.

**개인 계정으로 등록하면**, 2023년 11월 13일 이후 만든 계정이므로 다음이 강제된다.

> 12명 이상의 테스터가 이전 14일 동안 연속으로 비공개 테스트에 참여

즉 앱을 만들어도 **바로 못 낸다.** 테스터 12명을 모아 각자 설치하게 하고, 그 상태를 14일간 유지해야 프로덕션 출시를 신청할 수 있다. 신청 후 구글 검토도 별도로 걸린다. 앱 단위로 적용되는 조건이다.

추가로 개인 계정은 **Play Console 모바일 앱으로 실제 안드로이드 기기 접근을 인증**해야 한다는 조건도 있다. 한소네에 Google Play Store가 설치된 것은 확인했지만 Play Console 모바일 앱의 동작 여부는 아직 확인하지 않았다(O5, §9).

**조직 계정으로 등록하면** 이 요건 범위 밖이다. 대신 **D-U-N-S 번호**(국제 기업 식별번호)가 필요하고, 등록한 단체 정보와 일치해야 한다. 발급은 무료이며 통상 며칠에서 2주가량 걸린다.

**장교조 명의로 조직 계정이 가능하다면 그쪽이 빠르다.** 노동조합도 고유번호증이나 사업자등록이 있으면 D-U-N-S 발급 대상이 된다. 다만 단체 명의 계정은 소유권이 단체에 귀속되므로, 길동무를 개인 프로젝트로 유지할지 단체 사업으로 둘지의 판단이 선행한다.

역설적이지만, **개인 계정의 12명 요건이 길동무에는 오히려 유리할 수도 있다.** 장애인 교원 커뮤니티와 시각장애인 사용자층이 있으므로 12명 모으기가 어렵지 않고, 그 14일이 실제 베타 테스트 기간이 된다. iOS에서 TestFlight로 하던 일을 강제로 하게 되는 셈이다.

### 5.3 기술 요건 마감일

**2026년 8월 31일부터 신규 앱과 업데이트는 Android 16(API 36) 이상을 대상으로 해야 한다.**

이 날짜는 **이미 지났다**(오늘 2026-09-15). 따라서 지금 새로 만드는 앱은 처음부터 API 36을 대상으로 해야 한다. 연장 신청 제도가 있으나 2026년 11월 1일까지이고, 새로 시작하는 앱에는 해당 사항이 없다.

새로 만드는 프로젝트라 문제가 되지 않는다. 기본값이 최신이면 된다. 한소네가 Android 15이므로 API 36을 대상으로 하되 Android 15에서 도는 앱이 되며, 이는 정상 구성이다.

## 6. 배포 절차

iOS와 대응시켜 정리한다.

| 단계 | iOS | 안드로이드 |
|---|---|---|
| 제출 파일 | `.ipa` 아카이브 | **`.aab`**(Android App Bundle) |
| 서명 | 인증서 + 프로비저닝 프로파일 | **keystore 파일**(직접 생성·보관) |
| 서명 위탁 | 자동 관리 | **Play App Signing**(구글이 최종 서명키 보관) |
| 시험 배포 | TestFlight | **내부 테스트 트랙** |
| 심사 | App Review | Play 검토 |
| 심사 기간 | 수일 | 통상 더 짧으나 신규 계정 첫 앱은 길어질 수 있음 |
| 개인정보 신고 | 영양 라벨 + PrivacyInfo.xcprivacy | **데이터 안전성 섹션** |

배포 트랙은 넷이다.

```
내부 테스트   최대 100명, 즉시 배포, 검토 거의 없음   <- 여기서 시작
비공개 테스트 초대한 사람만. 12명 14일 요건을 채우는 곳
공개 테스트   누구나 참여 가능한 베타
프로덕션     정식 출시
```

### 서명키 주의

**keystore 파일을 잃어버리면 그 앱을 영원히 업데이트할 수 없다.** 안드로이드에서 가장 흔하고 치명적인 사고다. Play App Signing을 쓰면 구글이 최종 서명키를 보관하므로 업로드 키만 관리하면 되고, 업로드 키는 분실 시 재발급이 가능하다. **처음부터 Play App Signing을 켠다.**

keystore는 `~/gildongmu-private/`처럼 저장소 밖에 두고 절대 커밋하지 않는다.

### 데이터 안전성 섹션

iOS의 개인정보 3자 일치 불변식이 안드로이드에도 그대로 적용된다. 수집·전송 항목을 바꾸면 다음을 **동시에** 갱신해야 한다.

```
웹 /{locale}/privacy 카피
iOS PrivacyInfo.xcprivacy
App Store Connect 영양 라벨
Play Console 데이터 안전성 섹션   <- 여기가 추가된다
```

불일치는 심사 거절 사유다. 4자 일치로 확장되는 셈이다.

## 7. 접근성 검증

### 7.1 안드로이드 접근성 지형

| iOS | 안드로이드 |
|---|---|
| VoiceOver | **TalkBack** (최신 17.0.1, 2026-06-04) |
| accessibilityLabel | contentDescription |
| accessibilityTraits | Compose semantics |
| Accessibility Inspector | Accessibility Scanner / Layout Inspector |

**점자 지원이 중요하다.** 안드로이드 13부터 TalkBack에 점자 디스플레이 지원이 내장됐다. 예전에 필요했던 BrailleBack 앱은 더 이상 필요 없다. 한소네를 다른 안드로이드 기기에 연결해 점자로 쓰는 것도, 한소네 자체에서 TalkBack으로 앱을 쓰는 것도 가능하다.

### 7.2 검증 수단 세 층

**1층. 자동 검사 (매 커밋)**
Accessibility Test Framework가 Accessibility Scanner와 Espresso 접근성 검사의 공통 기반이다. Compose 1.8.0부터 Compose 테스트에서도 이 검사를 돌릴 수 있다. 접근 가능한 이름 누락, 터치 타깃 크기 부족, 대비 부족 등을 잡는다.

웹에서 axe가 하는 자리와 같다. 웹 쪽 실브라우저 접근성 게이트가 아직 비어 있는 상태(PORTS.md 열린 항목)인데, 안드로이드는 처음부터 이 레인을 깔 수 있다.

**2층. 화면 구조 확인 (개발 중)**
```bash
adb exec-out timeout 10 uiautomator dump /dev/tty
```
스크린 리더가 읽는 정보를 텍스트로 받는다. "한 줄 = 한 접근성 객체" 규칙이 지켜졌는지, 라벨이 시각 텍스트를 덮지 않는지를 눈이 아니라 구조로 확인한다.

**3층. 실기기 실사용 (판정)**
한소네에서 TalkBack과 점자로 직접 쓴다. 접근성 헌장이 말하는 "정적 감사 통과로 닫지 않는다"가 그대로 적용된다. 특히 과잉 ARIA에 해당하는 안드로이드 쪽 문제(불필요한 contentDescription, 중복 낭독)는 자동 검사가 잡지 못한다.

### 7.3 TWA 경로의 접근성

TWA는 크롬 본체로 웹을 띄우므로 **웹의 접근성이 그대로 앱의 접근성이 된다.** 길동무 웹은 이미 시각장애인 사용을 전제로 만들어져 있으므로 출발점이 좋다.

다만 두 가지는 확인이 필요하다. 하나는 브라우저 주소창이 사라진 상태에서 뒤로 가기 동작이 어떻게 들리는가이고, 다른 하나는 TalkBack에서의 낭독이 iOS VoiceOver와 다르게 들리는 지점이 있는가다. 같은 HTML이라도 스크린 리더마다 읽는 방식이 다르다.

## 8. 착수 순서 제안

```
0단계. 판정 (위원장)
   개인 계정인가 조직 계정인가 (§5.2)
   이 결정이 일정을 몇 주 가른다

1단계. 계정 개설 (반나절)
   25달러 결제, 신원·주소 인증, 2단계 인증
   조직 계정이면 D-U-N-S 발급이 선행 (며칠에서 2주)

2단계. 기기 연결 확인 [완료 2026-09-19]
   한소네 개발자 옵션·USB 디버깅 활성화 확인
   USB adb devices 에서 H732B device 상태 확인
   디버깅 중 점자 출력 정상 확인

3단계. 환경 구성 (1시간)
   JDK 21 설치, 커맨드라인 SDK 설치
   디스크 정리

4단계. TWA로 첫 앱 (1일에서 2일)   [심사 동결 해제 후]
   assetlinks.json 배포 (아이콘·manifest·서비스워커는 이미 충족)
   Bubblewrap 으로 aab 생성, keystore 생성 및 백업
   내부 테스트 트랙 업로드
   한소네에 설치해 점자로 실사용 검증

5단계. 테스트 트랙 운영 (개인 계정이면 14일)
   테스터 모집, 비공개 테스트
   이 기간에 네이티브 개발 착수 가능

6단계. 프로덕션 신청
```

**2단계와 4단계 사이가 실제 작업이고, 나머지는 대기와 행정이다.** 그래서 계정 개설을 먼저 시작하는 것이 합리적이다.
