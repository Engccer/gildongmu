# 순서 바꾸기 로터 액션: 고정한 최근 항목(E67)과 탭 순서(E66, 실험판)

2026-10-05. 백로그 `docs/BACKLOG.md` E67·E66의 설계 정본이다(위원장 판정은 백로그 본문, 이 문서는 그것을 구현 계약으로 옮긴다). 범위는 iOS뿐이다. 안드로이드 이식은 E67이 iOS 실기기 판정 뒤, E66은 대상 밖이다. 웹은 대상 밖이다(로터 등가물이 없다).

> 설계 리뷰 판정: 함. 새 저장 불변식 하나(고정 블록 순서가 사용자 지정 순)와 저장값 복구 규칙 하나(탭 순서)가 들어가 적대적 설계 리뷰 1회 대상이다. 결과는 §0.

## 0. 설계 리뷰 결과

적대적 설계 리뷰 1회(fable, 2026-10-05, 대상 `308a3c5a`). 판정: 수정 후 통과. 불변식 전수표(§2.1)와 복구 규칙(§3.1)은 성립했고, 위원장 판정을 바꾸는 지적은 없었다. 처리:

| 지적 | 처리 |
|---|---|
| (중) "화면 밖으로 갈 수 있는 이동은 맨 위로뿐"은 거짓: 토글로 자리를 유지하던 행은 어느 이동이든 채택 순간 고정 블록으로 뛴다. 길찾기 탭엔 가시화 수단이 없다 | §2.3 재시도는 이동 종류와 무관하게 가시화 → 대입. 길찾기 탭에 `ScrollViewReader`를 더했다 |
| (중) 이동마다 저장 + 앱 루트 `.id` 재생성이면 설정 아래 탭이 이동 횟수만큼 초기화되고, 남은 길찾기 프리필이 재생성마다 경로 조회를 다시 돌린다 | §3.2 순서는 화면 안 초안, 화면을 떠날 때(또는 백그라운드) 한 번 저장. 재생성은 복구된 순서가 실제로 바뀐 때만, 프리필 소거와 한 갱신에 묶는다 |
| (중) 되돌리기가 기본 순서를 명시 저장하면 "미지정"이 사라져 뒤에 늘어난 탭이 끝에 붙는다 | §3.1 기본 순서와 같으면 키를 비운다 |
| (낮) 즉시 재대입은 이동이 값을 바꾸지 않아 효과가 없다 | 뺐다. 복구는 재시도 단계만 |
| (낮) `applyPinnedOrder` 동일 판정·남는 값 미명세 | §2.2에 적었다(목록의 dedupe 술어, 값은 저장본) |
| (낮) 새 Kit 파일의 미러 등록부 | FOUNDATION은 `pending`을 허용하지 않아 `:kit` `Reorder.kt`로 이식해 `ported`(§2.1) |
| (낮) 한 행에 `.accessibilityActions`와 `swipeActions`를 함께 다는 선례 없음 | §1 실기기 확인 항목을 "두 집합이 모두 보이는가"부터로. 가려지면 고정·삭제도 `.accessibilityActions`로 옮기고 `swipeActions`는 시각 전용으로 둔다 |
| (낮) 탭 화면의 「맨 위로」는 E66 문면과 다르다 | 위원장 판정 2026-10-05(코디네이터 경유): 둔다 |
| (낮) `.onMove` 기제 미명세 | §3.2 편집 모드를 켜지 않는다(길게 눌러 끌기) |
| (낮) `AppTab.order` static과 `@AppStorage` 두 읽기 | `AppTab.order(stored:)` 순수 함수로, 저장소 직접 읽기는 시작 탭(`initial`)뿐 |
| (낮) 서수 없는 문장꼴, 안드로이드 K1 드리프트, 문서 분배 자리 | §1·§3.3에 적었다 |

## 1. 공용 계층: 이동 셋과 할 수 있는 이동

두 화면이 같은 조작법이라 판정은 Kit 한 파일 `Reorder.swift`(순수 함수, 테스트 `ReorderTests.swift`)에 둔다.

- `ReorderMove` = `toTop`(맨 위로) · `up`(위로) · `down`(아래로).
- `Reorder.availableMoves(index:count:)`: 항목이 2개 미만이면 없음. `toTop`은 index ≥ 2(둘째 행의 맨 위로는 위로와 같다), `up`은 index ≥ 1, `down`은 index < count − 1. 순서는 위에서 아래로(맨 위로, 위로, 아래로).
- `Reorder.moved(_:from:_:)`: 배열에서 한 항목을 옮긴 새 배열. 범위 밖·이동 불가(맨 위의 위로 등)는 원본 그대로.
- 문자열 키도 한 벌이다: `ios.reorder.toTop`·`ios.reorder.up`·`ios.reorder.down`(액션 이름), `ios.reorder.moved`(「{position}번째로 옮겼습니다」, 위원장 판정 2026-10-05). Kit 해석기는 ICU `plural`만 풀고 서수(`selectordinal`)가 없어 en·es·fr·it는 서수 접미사 없는 꼴로 짓는다("Moved to position {position}").
- 액션은 `.accessibilityActions`로 단다(로터 전용). `swipeActions`에 넣지 않는다: 눈으로 쓰는 사람에게 밀어서 보이는 버튼이 다섯이 되고, 끝까지 밀기가 첫 버튼을 실행한다. `.accessibilityActions` 빌더는 선언 역순으로 노출되므로(메모 `swiftui-accessibility-actions-reverse-order`) 아래로 → 위로 → 맨 위로 순으로 선언해 맨 위로 → 위로 → 아래로로 들리게 한다. 한 행에 `.accessibilityActions`와 `swipeActions`를 함께 다는 선례가 저장소에 없다. 실기기에서 먼저 두 집합이 모두 로터에 보이는지, 그다음 상대 순서를 본다(SwiftUI가 정하고 코드로 고정할 수 없다. 의도는 "이동 셋 → 고정 해제 → 삭제"). 한쪽이 가려지면 고정·삭제도 `.accessibilityActions`로 옮기고 `swipeActions`는 시각 전용으로 둔다(BACKLOG §2 E67 행).

## 2. E67: 고정 블록의 순서

### 2.1 불변식

저장 배열 = [고정 블록(**사용자 지정 순**, 새 고정은 블록 끝)] + [비고정 최신순, cap 20]. 종전 "고정 시점 순"은 "사용자가 한 번도 옮기지 않았을 때의 사용자 지정 순"과 같으므로 저장 형식·키·기존 데이터는 그대로다.

기존 쓰기 전수(Kit `RecentSearchStore`, 세 목록 공통 코어):

| 쓰기 | 고정 블록에 하는 일 | 새 불변식과 |
|---|---|---|
| `partitionPinned`(읽기 정규화) | 고정끼리의 저장 순서 유지(안정 분할) | 부딪히지 않음 |
| `appendKeepingPins`(재기록) | 같은 고정 항목은 제자리 교체, 그 밖은 블록 뒤 삽입 | 부딪히지 않음 |
| `setPinnedIn(pinned: true)` | 블록 맨 뒤로 | "새 고정은 블록 끝" 그대로. ⚠ 이미 고정인 항목에 다시 부르면 맨 뒤로 옮긴다. 화면은 토글(반대 값)만 부르므로 닿지 않는다 |
| `setPinnedIn(pinned: false)` | 블록에서 빼 비고정 맨 앞으로, 나머지 고정 순서 유지 | 부딪히지 않음 |
| `remove*`·`clear*` | 필터만(순서 유지) | 부딪히지 않음 |

시간·이름으로 고정 블록을 다시 정렬하는 자리는 없다. 웹 `src/lib/recent-searches.ts`도 같은 다섯 연산이 같은 방식이라(정렬 없음) 파급이 없다. `:kit` `RecentSearchStore.kt`도 같다. 이 판정을 공유 fixture로 잠그는 자리는 없고(세 벌이 각자 테스트), 미러 등록부는 파일 실재만 본다. 그래서 `:kit` `RecentSearchStore.kt`는 고치지 않고 등록부 `note`에 미이식 함수(`applyPinnedOrder`·`reorderPinned*`)를 적는다. 새 Kit 파일 `Reorder.swift`는 FOUNDATION 그룹이 `pending`을 허용하지 않아 `:kit` `Reorder.kt`(+ 테스트)로 이식해 `ported`로 둔다(순수 함수 셋이라 이식이 등재보다 싸다).

### 2.2 이동은 "화면에 보이는 고정 순서"를 기준으로 한다

화면 배열은 고정 토글 때 자리를 유지하고 정렬은 다음 로드부터 한다(스펙 2026-08-12 §4: 토글 순간 행이 화면 밖으로 가면 포커스가 유실된다). 그래서 한 화면 방문 안에서는 **화면의 고정 순서와 저장의 고정 순서가 어긋날 수 있다**: Y를 고정한 뒤 그보다 위에 보이는 Z를 고정하면 저장은 `…, Y, Z`, 화면은 `…, Z, …, Y`다. 사용자가 듣는 순서는 화면 순서이므로 이동의 기준도 화면이다.

- Kit 공용 코어 `applyPinnedOrder(_:to:)`: 넘긴 순서대로 고정 블록을 다시 세운다. 동일 판정은 그 목록의 dedupe 술어(텍스트·좌표 4자리·`sameRoute`)이고, 결과에 남는 값은 저장본이다(넘긴 값의 라벨·pinned는 쓰지 않는다). 넘긴 목록에 없는 고정 항목은 저장 순서대로 뒤에 붙고, 넘긴 목록의 비고정·없는 항목·중복은 무시한다. 비고정 블록은 그대로다. 공개 진입점은 목록마다 하나(`reorderPinnedQueries`·`reorderPinnedEndpoints(_:scope:)`·`reorderPinnedRoutes`).
- 화면 핸들러: 화면 배열의 고정 부분열에서 그 행의 자리 i를 찾고 → `Reorder.moved`로 옮긴 순서를 → `reorderPinned*`에 넘기고 → **돌려받은 저장 배열을 화면 배열로 채택**한다. 채택은 다른 행의 "자리 유지" 상태도 함께 정렬하므로 이동 뒤 화면 = 저장 순서다(고정 블록이 위로 모인다). 통지하는 자리 = 채택한 배열에서 그 행의 index + 1(고정 블록이 맨 위라 고정 안에서의 자리와 목록 안의 자리가 같다).
- 할 수 있는 이동은 화면 배열의 고정 부분열에서 계산한다(`availableMoves(index: i, count: 고정 수)`). 비고정 행엔 없다.

### 2.3 포커스와 통지

- 행 정체성은 순서와 무관하다(`Identifiable` id = dedupe 축). 이동은 같은 id의 행을 옮기는 것이라 SwiftUI는 삭제+삽입이 아니라 이동으로 처리한다. 포커스 바인딩 값(`pinned` 포함 Hashable)도 이동으로는 바뀌지 않는다.
- 이동은 행 정체성도 포커스 값도 바꾸지 않으므로 커서가 그 행에 남아 있으면 할 일이 없다(즉시 재대입은 같은 값 대입이라 효과가 없어 두지 않는다). 채택으로 행이 화면 밖으로 뛰면 커서가 떨어질 수 있다: 토글로 자리를 유지하던 행은 **어느 이동이든** 고정 블록 자리로 뛴다. 그래서 600ms 뒤 커서가 그 행에 없으면 가시화(`scrollTo`) → 300ms → 대입을 1회 한다(목록 포커스 정본 순서). 세 화면 모두 `ScrollViewReader`를 갖는다(길찾기 탭은 이번에 더했다).
- 통지 「{position}번째로 옮겼습니다」는 `.high`다: 로터 액션 활성화 응답이고, 커서가 같은 행에 남아 라벨이 다시 읽히지 않으므로 이 통지가 이동의 유일한 증거다(PATTERNS "iOS 통지 우선순위의 판별선" 둘째 판별선). 고정 토글이 라벨 변화만으로 상태를 알리는 것과 다른 이유: 이동은 라벨이 바뀌지 않는다.

## 3. E66: 탭 순서 (실험판만)

### 3.1 저장과 복구

- 키 `tabOrder.v1`, 값은 탭 `rawValue` 배열의 JSON 문자열(`["chat","search","directions","nearby"]`). 문자열인 이유: 앱 루트가 `@AppStorage`로 관찰해야 탭 바가 다시 그려지고, `@AppStorage`는 배열을 받지 않는다. **기본 순서와 같으면 키를 비운다**(빈 문자열 = 미지정): 기본 순서를 명시 저장하면 뒤에 늘어난 탭이 기본 자리가 아니라 끝에 붙는다.
- 복구 `Reorder.restoredOrder(saved:defaultOrder:)`(Kit 순수 함수): 저장값을 앞에서부터 읽어 기본 순서에 있는 값만 처음 한 번씩 남기고, 빠진 탭은 기본 순서대로 뒤에 붙인다. 파싱 실패·빈 값·전부 모르는 값이면 기본 순서다. 탭이 늘면 새 탭은 끝에 붙고, 줄면 그 값은 버려진다(저장값이 다른 탭을 가리키는 일이 없다: `rawValue`는 이름 기반).
- 기본 순서 = 채팅 · 검색 · 길찾기 · 내 주변(정식판과 같다). `AppTab.order(stored:)`(순수 함수) = 실험판이면 저장값 복구, 정식판이면 기본 순서 고정. 앱 루트는 `@AppStorage` 관찰값을 넘기고, 저장소를 직접 읽는 것은 런치·리셋의 시작 탭 `AppTab.initial`(= 순서[0], 맨 앞 탭이 시작 탭)뿐이다.
- `AppConfig.experimentalTabOrderEnabled`의 뜻이 "고정 순서 분기"에서 "설정 노출 + 저장값 사용"으로 바뀐다. K1 고정 순서 실험(검색 맨 앞)은 사라진다: 실험판도 저장값이 없으면 기본 순서다.

### 3.2 화면

- 설정 일반 묶음, 언어 다음에 `NavigationLink` 한 줄 「탭 순서」(실험판만). 가드 `settings-topic-sections.test.ts` 묶음표에 더한다.
- 탭 순서 화면(새 파일 `TabOrderView.swift`): 한 줄 = 한 탭(탭 이름 한 텍스트). 로터 액션은 §1 그대로(맨 위로 포함: 셋째·넷째 줄을 시작 탭으로 올리는 한 동작이다. 위원장 판정 2026-10-05). 눈으로 쓰는 사람은 `.onMove`로 길게 눌러 끌기(편집 모드를 켜지 않는다: 켜면 행마다 재정렬 핸들이 별도 접근성 객체로 붙어 "한 줄 = 한 객체"가 깨진다). 맨 아래 「기본 순서로 되돌리기」 버튼: 누르면 기본 순서가 되고 「기본 순서로 되돌렸습니다」를 `.high`로 통지한다(커서는 버튼에 남고 화면 변화를 듣지 못하므로 통지가 유일한 증거). 이미 기본 순서여도 같은 통지다(결과 상태를 말한다).
- 순서는 화면 안의 초안이고 **화면을 떠날 때(또는 앱이 백그라운드로 갈 때) 한 번 저장**한다. 앱 루트는 `@AppStorage("tabOrder.v1")`를 관찰하고, **복구된 순서가 실제로 바뀐 때만** 세대를 올려 탭 트리 `.id`를 바꾼다: `ForEach` 순서 변경만으로 `TabView`가 탭 바를 다시 배치하는지 iOS 18·26에서 보장이 없어, 언어 전환과 같은 재생성으로 결정론을 택한다. 대가는 탭 콘텐츠 초기화(방문당 최대 1회)이고, 설정 시트·안내 세션·채팅 모델은 `.id` 밖이라 그대로다. 선택 탭은 값으로 남는다. 같은 갱신에서 길찾기 프리필(`directionsPrefill`)을 비운다: 남아 있으면 재생성된 길찾기 탭이 순서만 바꿨는데 경로 조회를 다시 돈다(`resetSession`과 같은 이유). ⚠ 언어 전환 재생성에도 같은 구멍이 있다(이번 범위 밖, 보고에 적는다).

### 3.3 탭 순서에 기대는 자리 점검

`AppTab` 케이스 순서·`order` 인덱스에 기대는 소비자: `GildongmuApp`의 `ForEach(AppTab.order)`와 `initial`뿐이다. 띠바 착지(`bandFocusedTab: AppTab?`)·단축어 진입(`selectedTab = .search` 등)·`refreshCurrentTab`은 탭 값으로 가른다. `guidance-gate-drift.test.ts`는 탭을 보지 않는다. 열린 채 순서가 바뀌는 화면은 탭 순서 화면 자신뿐이고, 행 정체성이 탭 값이라 순서 변경이 행을 파괴하지 않는다(A51의 피커 함정과 무관: 피커가 없다). 언어는 이 화면이 열린 채 바뀌지 않는다(언어 피커는 설정 루트에 있다).

안드로이드 실험판은 K1 고정 순서(검색 맨 앞, `android/.../nav/AppTab.kt`)를 그대로 둔다(E66 안드로이드 대상 밖, 별도 판정). 그래서 두 실험판의 기본 순서가 갈린다. 문서 분배에서 낡는 자리: BACKLOG §2 K1 탭 순서 행(E66 행으로 교체), `CLAUDE.md`의 실험 플래그 줄(코디네이터 반영 요청), `docs/PATTERNS.md`의 K1 탭 순서 서술.
