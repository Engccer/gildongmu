### 1.2 착수 게이트 판정 — `barvlDt`의 심야 해석

**CLAUDE.md의 "`barvlDt`를 슬롯형으로 환산하면 운행종료에도 비0이라 오발화" 경고는 지하철에도 성립한다.** 시간형이 아닌 행 **65행**이 비0 `barvlDt`를 가진다(`전역 출발` 25 · `전역 도착` 24 · `전역 진입` 8 · `{역} 도착` 4 · `{역} 진입` 2 · `전전역 출발` 1 · `{역} 전역출발` 1). ⚠ 첫 집계의 71행은 분류 정규식이 `^(\d+)분`이라 **초만 있는 시간형**(`15초 후 (불암산)`)을 비시간형으로 센 과다 계상이었다(코디네이터 독립 재현으로 정정, 결론은 불변). 백로그 E37 표의 "시간형이 아닌 행은 전부 0"은 20건 표본의 우연이었다. 극단 표본: 2026-09-12 **00:30** 서울역 `전역 출발`이 `barvlDt = 1200`(20분) — 바로 앞 역을 떠난 열차에 20분은 뜻이 없고, 이것을 환산해 "20분 후 도착"이라 말하면 그것이 오발화다. 00~02시대 183행 중 비0 비시간형은 `전역 출발/도착/진입`·`{역} 진입/도착/전역출발` 계열이고 값은 60~1200초로 흩어진다.

▶ **불변식 I1.** 시간형 조립의 게이트는 **`arvlMsg2`의 시간 문법 인식**이고, 초 수는 **그 문장에서 읽는다**. `barvlDt`(`arrivalSeconds`)와 `arvlCd`(`arrivalCode`)는 판정에도 값에도 쓰지 않는다. (`arvlCd`를 게이트로 쓰면 8호선 심야 `[N]번째 전역`이 코드 1로 와서 가장 난반한 문법이 원문으로 남는다 — §1.1의 24행.)

### 1.3 `arvlMsg3`의 뜻은 문법마다 다르다 — 역명은 관계가 확인된 자리에만 문장에 넣는다

| 문법 | `arvlMsg3`의 실제 관계 | 근거 |
|---|---|---|
| `전역 진입/도착/출발` | 조회 역의 **바로 앞 역** | (역, 노선, 방향) 28개 조합 전부 인접역(서울역 1호선 상행 남영 · 하행 시청, 강남 2호선 내선 역삼 · 외선 교대 …) |

▶ **불변식 I2.** 역명을 싣는 것은 **그 역이 열차 위치임이 실측으로 확인된 문법뿐이다**(`전역 …` = 1정거장 전, `[N]번째 전역 (X)` = N정거장 전, `N분( M초) 후 (X)`). `전전역 출발`과 `{X} 전역출발`은 문장에도 꼬리에도 역명을 싣지 않고 출발 사실만 말한다(`2정거장 전에서 출발.`·`1정거장 전에서 출발.`). 근거의 성격이 둘로 갈린다: 뒤의 것은 X가 **조회 역 자신**이라는 구조적 사실이라 단단하고(12/12, 문장에 그 이름이 박혀 온다), 앞의 것은 **관측이 얇아 뜻을 모른다**(쓸 수 있는 1행에서 `arvlMsg3`가 한 역 앞을 가리켰고 문장의 "두 역 앞"과 어긋난다). ⚠ **근거가 얇다는 것이 싣지 않는 쪽을 지지한다** — 그 역이 열차 위치라는 증거가 없는데 실으면 3-state의 unknown을 "있음"으로 바꾸는 것이다. 착수 프롬프트 초안 `2정거장 전 미사에서 출발.`과 문안 1판의 `현재 강일.` 꼬리가 모두 이 이유로 기각됐다(위원장 확인 2026-09-13).

## 2. 판정 계층 — 파싱 → 문장 계획 (웹 ↔ Kit 미러, 공유 fixture)

순수 함수 `subwayArrivalProse(message, currentLocation) → Plan | null`. 웹 `src/lib/place-lines/station-arrivals.ts` ↔ Kit `SubwayArrivalLine.swift`. 공유 fixture `src/lib/__tests__/fixtures/subway-arrival-prose-cases.json`이 두 구현을 한 표로 잠근다(A32 선례 `subway-arrival-tail-cases.json`과 같은 자리·같은 로더).

### 2.1 인식 문법과 계획

| 원문 모양 | Plan | 문장의 역 | 꼬리 `nowAt` |
|---|---|---|---|
| `{S} 진입` / `{S} 도착` / `{S} 출발` (S = `arvlMsg3`) | `stationEvent(verb, station)` | S | 없음 |
| `전역 진입` / `전역 도착` / `전역 출발` | `prevStationEvent(verb, station: arvlMsg3)` | `arvlMsg3` **필수** | 없음 |
| `{X} 전역출발` | `departedStopsBack(count: 1)` | 없음 | **없음**(§1.3) |
| `전전역 출발` | `departedStopsBack(count: 2)` | 없음 | **없음**(§1.3) |
| `[N]번째 전역 (X)` (N ≥ 1, **괄호 필수**) | `stopsAway(count: N, station: X)` | X | 없음 |
| `N분 후` / `N분 M초 후` / `M초 후` (+ ` (X)`) | `eta(minutes?, seconds?)` | 없음 | `X ?? arvlMsg3` |
| 같은 시간 문장 + `(K번째 전)`·`[K번째 전]` (구 문법) | `eta(…, stops: K)` | 없음 | `arvlMsg3` |
| 그 밖 | `null` → §2.3 원문 경로 | | |

- 정규식은 **문장 전체**에 건다(`^…$`). 서버 영문 행렬(`subway-arrival-en.ts`)과 같은 모양이고 이쪽이 상위집합(`{X} 전역출발`·`전전역 출발`·`M초 후`·구 문법이 더 있다). 정확 일치(`전역 …`·`전전역 출발`)를 먼저 보고 패턴을 본다.
- ⚠ **문자 클래스 안의 `[`는 양쪽 다 이스케이프한다**(`[(\[]`). ICU(Swift)는 `[([]`를 중첩 집합의 시작으로 읽어 패턴이 통째로 어긋나고 JS는 문자로 읽으므로, **웹만 통과하고 iOS는 시간형 전량을 놓친다**(구현 중 공유 fixture가 검출).
- 범위: 분 ≥ 1 또는 초 ≥ 1, 초 ≤ 59, N ≥ 1, K ≥ 1. 밖이면 `null`.
- ⚠ **`[N]번째 전역`의 괄호는 필수다.** 코퍼스 254행이 전부 괄호를 다는데, 괄호 없는 변형에서 `arvlMsg3`를 역으로 삼으면 그 역이 열차 위치라는 보장이 없다 — `{X} 전역출발`의 X가 조회 역 자신인 것과 같은 계열일 수 있어 사용자가 서 있는 역을 "3정거장 전"이라 낭독하게 된다(I2가 막으려던 실패 모드, 설계 리뷰 MAJOR-2).
- ⚠ **당역 문법은 `arvlMsg3`와 값이 같을 때만 인정한다.** `{무엇} 도착` 모양은 역명이 아닌 말도 통과시켜 `곧 도착`의 "곧"을 역으로 읽는다(구현 중 테스트가 검출). 코퍼스의 이 문법 228행은 전부 `arvlMsg3`와 같은 값이라 실측 손실 0이다.
- **모순은 원문이다**: 문장에서 읽은 역(S·X)과 `arvlMsg3`가 **둘 다 있고 다르면** `null`. 서버 `enrichArrivalEn`의 "둘이 다르면 부재"와 같은 축.
- `prevStationEvent`는 `arvlMsg3`가 없으면 `null`(역을 지어내지 않는다 — 코퍼스 부재 0/858, 3-state의 unknown은 원문).
- 비교 전 양끝 공백만 다듬는다(A32와 같은 trim 규율).
- **키 선택은 한 자리다**(`arrivalProseSegments` ↔ `subwayArrivalProseSegments`) — 계획이 같아도 두 플랫폼이 다른 문장을 고르면 화면이 갈리므로, 공유 fixture의 `keys` 열이 조각 키와 꼬리 키를 함께 잠근다.

### 2.2 렌더 — 한 줄 = 한 접근성 객체

**꼬리의 유무는 계획이 정하고 역명은 표기일 뿐이다**(`plan.nowAt`에서 유도) — 호출자가 넘긴 역으로 가르면 `nowAt` 없는 계획에서 en 줄에만 꼬리가 붙어 같은 항목의 ko·en이 다른 주장을 한다(설계 리뷰 MINOR-4).

조각은 두 가지로 이어진다. `joined`(구 문법의 정거장 조각 + 시간 문장)는 **쉼표**로, `tail`(`nowAt`)은 앞 문장과 **공백**으로 잇는다. 쉼표 결합과 정거장을 앞에 두는 순서는 버스 안내 상태 문장(E39 §2.2 `1정거장 전, 약 4분 후 도착.`)과 같다. 기존 `subwayArrival.currentLocation`(`현재 {location}`, 마침표 없음)은 §2.3 원문 경로의 쉼표 결합용으로 남고, 문장형 꼬리는 새 키 `subwayArrival.nowAt`(`현재 {station}.`)이다.

⚠ 영문 역명이 마침표로 끝나면(`Seogang Univ.`) 문장 끝 마침표와 겹쳐 `… at Seogang Univ..`가 된다. 낭독은 달라지지 않고, 고치려면 로케일마다 다른 종결 부호를 문자열에서 떼어내야 해 이득이 없다 — 그대로 둔다.

### 2.3 원문 경로(폴백) — 현행 A32 그대로 + A38

`Plan`이 `null`이면 종전 코드 그대로: `arvlMsg2` 원문 + A32 꼬리 판정(`subwayShowsCurrentLocationTail`), en 계열은 서버 `messageEn` + 영문 꼬리. **바뀌는 것은 A38 하나**(§3).

## 3. 언어 — 줄 원자성과 A38

### 3.1 문장형 줄의 언어
문장 틀은 사용자 언어(UI 로케일)로 조립하고, 역명만 데이터 언어를 따른다(`prefersEnglish(locale)`이면 `currentLocationEn`, 아니면 한국어 역명).

⚠ **영문 화면에서 역명이 필요한데 `currentLocationEn`이 없으면 문장형을 버리고 원문 경로로 떨어진다.** 영어 문장에 한국어 역명을 끼우면 한 줄 안에서 언어가 섞이고(E27), 문장 틀이 UI 번역기 하나뿐이라 "그 줄만 한국어 문장형"을 만들 수단이 없기 때문이다. 원문 경로는 `pickLine`이 종전대로 한국어 원문 + `lang="ko"`를 낸다. (구현 중 이 자리가 `Arriving in 6 min. Now at 강일.`을 냈고 테스트가 검출했다.)

역을 요구하지 않는 계획(`departedStopsBack`, 꼬리 없는 `eta`)은 영문 역명 없이도 UI 언어 줄이 선다.

iOS는 편성·메시지가 **한 접근성 객체**라 같은 판정이 편성 조각에도 걸린다 — `lineEn`·`directionEn`·`trainLineNmEn` 중 하나라도 결측이면 문장형을 쓰지 않고 원문 경로로 떨어진다(그 줄 전체가 한국어).

문장형 줄은 UI 템플릿이라 `lang` 태그를 달지 않는다(ja 화면의 문장은 일본어이고, 역명 한 낱말 때문에 `lang="en"`을 달면 문장 전체가 영어 음성으로 낭독된다).

### 3.2 A38 — 영문 자리의 결측 판정을 ko 값에서 뗀다
원문 경로의 영문 현재역 자리는 종전 `a.currentLocation ? a.currentLocationEn : ""`(ko가 없으면 영문도 버린다)에서 **`a.currentLocationEn ?? (a.currentLocation ? undefined : "")`**로 바뀐다: 영문 값이 있으면 그 값, 없고 ko도 없으면 자리 표시, 없는데 ko는 있으면 결측(줄 전체 ko). "판정에 먹이는 값이 곧 렌더되는 값"(A32 계약)은 그대로다 — 이 한 변수가 꼬리 판정과 `enParts` 양쪽에 들어간다. 문장형 경로는 §3.1이 같은 축(영문 줄은 `currentLocationEn` 자신)으로 세워져 A38이 구조로 닫힌다.

## 6. 접근성
- 메시지 줄은 종전과 같이 **한 접근성 객체**(`<div>` 하나 / `Text` 하나). 문장과 꼬리를 시각용 span으로 쪼개지 않는다.
- 낭독 정정(`spokenDistanceUnits` 류)은 두지 않는다 — "분·초·정거장"은 실기기 오독 확인이 없다.
- 두 문장이 마침표로 나뉘어 TTS가 자연 휴지를 둔다(`4분 후 도착. 현재 삼각지.`).
