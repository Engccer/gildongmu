## 1. 문제

현재 위치의 유일한 소스가 클라이언트 측위다. 세 겹으로 부족하다.

| # | 현행 | 귀결 |
|---|---|---|
| ① | 측위가 실패하면 대안이 없다 | 웹 `geolocation.ts:107-112`가 권한 거부·`POSITION_UNAVAILABLE`·`TIMEOUT`을 `denied` 하나로 합류시키고, `useNearbyFetch.ts:159-166`이 그것을 "브라우저에서 위치 접근을 허용해 주세요"로 낸다. **실내 측위 실패 사용자는 허용해 놓고도 같은 문구를 듣고, "내 주변" 10종이 통째로 죽는다** |
| ② | 라벨을 역지오코딩이 정한다 | 서울 무작위 30점 실호출에서 건물명 37%, 도로명 13%, **지번만 50%**. 사용자가 "태양마트"에 있어도 "강동구 길동 363-1"로 낭독될 확률이 절반 |
| ③ | 사용자가 아는 것을 앱에 말할 수 없다 | 사용자는 자기가 어디 있는지 알지만 입력 경로가 없다 |

**왜 심각한가**: 셋 다 시각장애 사용자가 **화면으로 반증할 수 없다.**

**이미 세 조각이 흩어져 있다.** 이 설계는 새 기능이 아니라 그 통합이다.

| 조각 | 위치 | 한계 |
|---|---|---|
| `{label, lat, lng}` 영구 저장 + 이름 지오코딩 | CLI `config.ts:8`, `resolve-location.ts:32-58` | headless 표면에만 존재 |
| 좌표 고정 주입 | 웹 `useNearbyFetch.ts:136-139`(`kind:"place"`), iOS `NearbyLoadCore.swift:39-43`(`.fixed`) | 장소 상세의 "이 장소 주변"에 갇힘 |
| 사람이 읽는 현위치 라벨 | `directions.currentLocationNear`(6로케일), `/api/geocode/reverse` 3단 체인 | 길찾기 출발지 필드 한 곳만 소비 |

## 2. 범위 밖

- **원격지 조회.** "지금 있지 않은 곳의 주변을 본다"는 이미 `PlaceAnchor`/`.fixed`가 담당한다. 이 설계는 **"내가 있는 곳을 정확히 말한다"**뿐이다.
- **즐겨찾기 저장소.** 검색 모달의 최근 목록을 재사용한다(YAGNI).
- **최근접 POI 라벨링 — 금지한다.** §6.2의 실측이 근거다.
- **백그라운드 지오펜스.** "항상 허용" 권한을 요구해 심사·프라이버시 비용이 크다.
- **실시간 안내에 수동 위치 적용.** §4.4가 타입으로 차단한다.
- **서버·API 변경.** 라우트는 좌표를 받을 뿐 출처를 모른다.

## 3. 계층 선택 (왜 자동 해제를 유지하는가)

adversarial-review 20건 중 **7건이 이동 판정 한 계층에 몰렸다**(§8). 이 저장소의 규율은 "동일 계층 지적이 2회 이상 반복되면 계층 선택 자체를 의심"이므로 대안을 검토했다.

| 안 | 내용 | 판정 |
|---|---|---|
| A. 자동 해제 폐기 | 명시 해제까지 유지, 표시줄만 상시 노출 | **기각.** 판정 계층이 통째로 사라지지만, 위원장이 명시 요구한 "이동 후 열면 GPS로 복귀"를 버린다 |
| B. 해제 대신 질문 | 이동 감지 시 "계속 쓸까요?" 확인 | **기각.** 마찰이 늘고, SR 사용자에게 복귀마다 확인이 걸린다 |
| C. 자동 해제 유지 + 정밀도 보강 + **결과 통지** | 판정을 정확하게 만들고, 판정 결과를 사용자에게 알린다 | **채택** |

**계층 자체는 옳았고, 빠져 있던 것은 "판정 결과를 사용자에게 알린다"는 한 축이었다.** 그 축이 없으니 오판정이 조용한 실패가 되고, 그래서 판정 정밀도에 감당 못 할 부담이 걸렸다. 통지를 넣으면 오판정이 "알려진 실패"가 되어 사용자가 즉시 재지정할 수 있고, 판정은 완벽하지 않아도 된다.

## 4. 채택 설계

### 4.1 데이터 모델

```
ManualLocation = {
  revision: Int          // 단조 증가. 판정 CAS용
  label:    String       // 사용자가 고른 장소 이름
  lat, lng: Double       // 그 장소의 좌표
  origin:   Fix?         // 지정 시점의 적격 실측 fix. 없을 수 있다
  setAt:    Double       // epoch seconds
}
Fix = { lat, lng, accuracy: Double, at: Double }
```

- iOS `UserDefaults`, 웹 `localStorage`. 해제 축이 앱 생명주기가 아니므로 영속 저장이 맞다.
- **검증 상태는 저장하지 않고 파생한다**: `origin == nil` → `unverifiable`, 아니면 `verifiable`.
- 저장 경계에서 **스키마 검증**(웹 zod, iOS `Codable` + 수동 검증): 좌표 유한·범위 내, `accuracy > 0`, `label` 공백 제거 후 비어 있지 않음. 실패는 조용히 폐기한다(손상된 저장값을 복원하면 `haversine`이 NaN을 내고 모든 비교가 false가 되어 영구 유지된다).

⚠ **기준점은 `origin`이지 `{lat,lng}`가 아니다.** 초판은 "사용자가 장소를 지정하는 것이 곧 거기 있다는 주장"이라며 장소 좌표를 기준점으로 삼았는데, **장소 검색 결과 좌표는 건물 중심이나 대표 출입구**라 사용자가 서 있는 지점과 100m 이상 떨어질 수 있다(지하철역·대형 병원·공원·쇼핑몰). 정확도 10m fix가 들어오면 **같은 자리에 있는데 이동으로 판정**된다.

초판이 `origin` 방식을 기각한 근거는 "지정 시점 fix가 없으면 영구 유지(미해제)가 되고, 미해제가 오해제보다 나쁘다"였다. **그 전제가 틀렸다** — 미해제가 나쁜 이유는 "조용해서"이고, §4.5의 검증 상태 노출이 그 조용함을 없앤다. 나쁨의 크기는 상수가 아니라 설계가 정하는 값이었다.

### 4.2 이동 판정 — 순수 함수, 웹 ↔ Kit 미러

```
judgeManualLocation(manual, fix) -> .keep | .drop | .undecidable

  manual.origin == nil        → .undecidable   (기준점 없음)
  fix == nil                  → .undecidable   (측위 실패·권한 없음)
  !eligible(fix)              → .undecidable   (아래)
  separation > MOVED_M        → .drop
  otherwise                   → .keep

  eligible(fix) =
       fix.accuracy.isFinite && fix.accuracy > 0 && fix.accuracy <= JUDGE_CEILING_M
    && fix.lat/lng 유한 && 좌표 범위 내
    && (now - fix.at) <= FIX_MAX_AGE_S

  separation = haversine(fix, manual.origin) - fix.accuracy - manual.origin.accuracy
```

| 상수 | 값 | 근거 |
|---|---|---|
| `MOVED_M` | 100 | **"100m가 최근접 정류소 순위를 뒤집는다"는 실측**이 `LocationFix.swift:11-12`·`:27-28`에 두 번 기록돼 있다. 답이 달라지는 거리가 곧 "이동했다"의 정의다 |
| `JUDGE_CEILING_M` | 100 | `LocationFixPolicy.storeCeiling`과 같은 값·같은 취지("셀·Wi-Fi 측위의 km급 좌표는 어떤 용도로도 위치가 아니다") |
| `FIX_MAX_AGE_S` | 10 | `LocationFixPolicy.acceptAge`와 같은 값. `force:true`가 신선도를 보장하지 않는다 — iOS는 매니저 시작 직후 캐시 fix를 먼저 전달할 수 있다 |

⚠ **두 100m는 값만 같고 축이 다르다**(답이 달라지는 거리 / 판정 자격). 상수를 나눠 선언한다.

⚠ **양쪽 정확도를 차감한다.** 거리 101m·정확도 100m는 수동 좌표가 fix의 오차 원 안에 있다는 뜻이라 이동의 증거가 아니다. `JUDGE_CEILING_M`은 fix의 **사용 자격**만 가를 뿐 이동을 **증명**하지 않는다. `separation`은 "두 오차 원이 겹치지 않고도 남는 거리"이므로 그것이 100m를 넘어야 이동이다.

⚠ **`accuracy > 0` 검사가 필수다.** iOS `horizontalAccuracy`는 무효 fix에 **음수**를 준다. 음수를 그대로 빼면 `separation`이 커져 거짓 이동이 된다.

### 4.3 판정 트리거 — 세 곳

| # | 트리거 | 막는 결함 |
|---|---|---|
| ① | 포그라운드 복귀 (iOS `scenePhase` → `.active`, 웹 `visibilitychange` → visible) | 기본 경로 |
| ② | **`force = true`인 위치 조회**(새로고침·"현재 위치 사용" 등) | 앱을 켠 채 걸어가면 ①이 영영 안 돈다. 새로고침은 "지금 어디 있는가"를 다시 묻는 행동이므로 수동 위치라도 판정을 동반한다 |
| ③ | **수동 위치가 있는 상태의 앱·탭 시작** | 웹은 탭을 닫으면 모듈 싱글턴이 `idle`로 초기화되는데 `localStorage`의 수동 위치는 남는다. 시작 시 판정하지 않으면 **부산에서 길동 결과가 정상 응답처럼 나오고 영원히 교정되지 않는다** |

각 트리거는 실측위를 시도하고(웹 `awaitGeolocation({force:true})`, iOS `currentCoordinate(force:true)`), 도착한 fix로 §4.2를 돌린다.

⚠ **캐시를 읽으면 판정이 성립하지 않는다.** 웹 공유 스토어는 TTL이 없어 `ready` 좌표가 세션 최초 값이고, iOS `coordinateForDisplay()`는 `freshTTL` 60초를 넘기면 nil이다. 둘 다 `.keep`/`.undecidable`로 귀결해 이동을 놓친다.

⚠ **지정 직후에는 판정하지 않는다.** 세 트리거 중 어느 것도 지정 시점에 발화하지 않으므로 유예가 저절로 성립한다.

⚠ **CAS로 경쟁 상태를 막는다.** 판정 시작 시 `manual.revision`을 캡처하고, fix 도착 시점의 `revision`과 같을 때만 `.drop`을 반영한다. 다르면 폐기한다. 판정 왕복 중에 사용자가 새 위치를 지정하면 늦게 온 옛 판정이 **방금 지정한 위치를 지운다**(`useNearbyFetch`의 요청 ID latest-wins, `NearbyLoadCore`의 취소 게이트와 같은 패턴).

⚠ **"복귀 시 권한 팝업 금지"를 약속하지 않는다.** 초판은 웹 스토어의 `ready`를 권한 증명으로 삼았는데, `ready`는 "이번 세션에 측위가 성공했다"는 뜻이라 ⓐ콜드 스타트에서 항상 false이고 ⓑ이후 권한이 철회돼도 true로 남는다. 측위 시도는 **앱의 기존 정책을 그대로 따른다**(웹은 홈 마운트에서 이미 fire-and-forget 측위로 팝업을 띄운다). 권한이 없으면 결과는 `.undecidable`이고 §4.5가 그것을 노출한다.

### 4.4 적용 경계 — 타입으로 봉인한다

초판은 함수 이름 분기(`awaitGeolocation` vs `awaitEffectiveLocation`)로 막겠다고 했으나 **이름은 값의 출처를 따라가지 못한다.** 길찾기 조회에서 얻은 수동 좌표가 route state에 저장되면, 안내 시작 함수 자체에 `awaitEffectiveLocation` 호출이 없어도 그 state를 재사용하는 경로로 수동 좌표가 안내에 들어간다. 소스 스캔은 통과한다.

**출처를 값에 부여한다.**

```
RealFix           = Fix & { readonly __source: "real" }      // 실측위만 생산
EffectiveLocation = { lat, lng, source: "gps" | "manual" }
```

| 소비자 | 받는 타입 | 실패 규칙 |
|---|---|---|
| 안내 시작 · 이탈 재조회 · 자동차 ETA | **`RealFix`만** | 실측위 실패 시 **fail-closed** — 기존 경로 기하를 재사용하지 않고 안내 시작을 실패시킨다 |
| 내 주변 10종/11화면 · 검색 거리 · 채팅 앵커 · 길찾기 출발지 · 현위치 정위 | `EffectiveLocation` | 수동 위치 우선 |

⚠ **브리핑과 실시간 안내의 위치 요구가 다르다.** GPS가 안 잡혀 수동 위치로 브리핑까지 성공한 사용자가 안내 시작을 누르면 `RealFix`를 얻지 못해 실패한다. 침묵하거나 "경로를 찾을 수 없습니다"로 뭉개면 사용자가 원인을 알 수 없다. (갱신 2026-08-17: 전용 오류 문구 `실시간 안내는 실제 위치가 필요합니다`는 폐기. 시작 순간의 통지 "현재 위치에서 안내를 시작합니다"가 먼저 나가므로, 뒤따르는 안내 자체의 측위 실패 문구(`guide.detailNoLocation` 등 "현재 위치를 확인하지 못했습니다")만으로 원인이 이어진다.)

**단일 관문 덕에 호출부 수정이 적다.**

| 플랫폼 | 관문 | 자동 반영 |
|---|---|---|
| 웹 | `useNearbyFetch.ts:143` | "내 주변" 10종 전부 |
| iOS | `LocationService.nearbyCoordinateSource()` | 11개 화면 전부 |

**길찾기 출발지는 코드 수정이 없다.** `DirEndpoint`는 `{kind:"current"}` 토큰만 저장하고 좌표는 조회 시점에 해석한다. 다만 **해석 결과에 `source`가 실린다**(위 fail-closed 규칙의 판정 근거).

**우선순위 계약**: `장소 앵커 > 수동 위치 > GPS`.
- iOS `.fixed(place)`와 웹 `source:{kind:"place"}`는 **수동 위치보다 항상 우선**한다. 수동 위치는 `.current`/`{kind:"current"}` 해석에만 개입한다. 이 계약이 없으면 "이 장소 주변"이 웹에서는 그 장소를, iOS에서는 수동 위치를 조회한다.
- 채팅: `placeContext` > 수동 위치 > GPS. **채팅 페이로드의 `userLocation`은 `EffectiveLocation`이다.** 기존 불변식("장소 앵커가 있어도 길찾기 출발지는 `userLocation`")은 *장소 앵커 vs 사용자 위치* 축이라 유지되며, 수동 위치는 사용자 위치의 한 형태다. ⚠ **채팅에 실시간 안내를 시작하는 도구를 추가하면 이 필드를 `RealFix`와 분리해야 한다.** 현재는 그런 도구가 없어 단일 필드로 족하다.

**실시간 추적 fix는 애초에 이 계층을 안 지난다**(웹 `watchPosition`, iOS `startBeaconUpdates`).

**커버리지 마커는 좌표 출처와 무관하게 적용된다**(`NearbyLoadCore.swift:125-129`). 추가 처리 없음.

### 4.5 상태 노출 — 3-state를 UI까지 끌고 간다

§4.2의 세 판정 결과가 사용자에게 구분되어 도달해야 한다.

| 판정 | 표시줄 | 통지 |
|---|---|---|
| `.keep` | `지정한 위치, 길동 카페` | 없음 |
| `.drop` | `현재 위치, …` (GPS로 복귀) | **polite 1회**: `이동이 감지되어 지정한 위치를 해제했습니다` |
| `.undecidable` | `지정한 위치, 길동 카페(위치 확인 불가)` | 없음 |

⚠ **자동 해제는 반드시 통지한다.** 초판은 "표시줄이 첫 줄에서 말하니 통지가 잉여"라고 판단했는데 **틀렸다.** ⓐ포커스 밖 텍스트 변경을 VoiceOver는 읽지 않는다 — "첫 줄이 말한다"는 사용자가 그 줄로 돌아갈 때만 성립한다. ⓑ표시줄이 없는 화면(장소 상세·길찾기)에서 복귀하면 아예 만나지 못한다. ⓒ "뻔한 꼬리 문장" 판정선은 *"뒷문장이 새 정보를 주는가"*인데, **사용자가 이동한 사실과 앱이 저장 상태를 바꾼 사실은 다른 정보다.**

⚠ **`.undecidable`을 `.keep`과 뭉개지 않는다.** 권한을 철회하고 부산으로 이동한 사용자에게 `지정한 위치, 길동 카페`만 말하면, "내 주변"이라는 이름 아래 길동 데이터가 정상 응답으로 나오고 검증이 실패했다는 신호가 없다. 3-state 불변식의 이 기능 판이다.

**시맨틱과 포커스 계약**:
- 표시줄은 **형제 버튼 둘**이다: `위치 지정`(항상) + `지정 해제`(수동일 때만). **중첩 인터랙티브 금지** — 행 전체를 버튼으로 만들고 안에 해제 버튼을 넣지 않는다.
- 상태 텍스트(`지정한 위치, 길동 카페`)는 `위치 지정` 버튼의 접근 가능한 이름에 포함한다(한 줄 = 한 객체).
- `onTapGesture`/`div onClick` 금지. 네이티브 `Button`/`<button>`. 44×44px 이상.
- 해제 후 포커스는 남아 있는 `위치 지정` 버튼으로 이동한다(자기를 없애는 버튼의 포커스 이탈 방지, 헌장 §5).
- 지정 완료 후 포커스는 `위치 지정` 버튼으로 이동한다(라벨이 곧 결과 신호이므로 별도 통지 없음).

**저장소와 런타임 상태를 분리한다.** 정본은 **단일 observable store**이고 `UserDefaults`/`localStorage`는 그 뒤의 영속 매체다. 웹은 `storage` 이벤트(다른 탭) + 같은 탭 내부 구독을 함께 처리한다(기존 `geolocation.ts` 싱글턴 패턴 재사용). iOS는 `@Observable` 단일 소유자. set·clear·auto-clear가 모든 소비자에 원자적으로 전파되어야 한다.

**탭하면 열리는 것**: 장소 검색 모달.
- iOS: `DirectionsEndpointSearchView` 재사용. `target == .from` 조건(`:163-166`)을 일반화하고 `onSelect` 콜백을 그대로 쓴다. "현재 위치 사용" 항목은 이 맥락에서 **해제**를 뜻한다.
- 웹: `EndpointField`가 `DirectionsView.tsx:968`의 비공개 인라인 컴포넌트다. **추출 범위를 좁힌다**(초판의 6축 일반화는 세 번째 소비자 하나를 위한 과잉이고, 옵션 조합에 따라 기존 길찾기 검색의 포커스 복원·오류 통지가 빠질 위험이 있다):
  1. **먼저 주소→좌표 해석 순수 로직만 공용화한다.** 이것은 이미 홈(`PlaceSearch.tsx:581-608`)과 길찾기(`DirectionsView.tsx:1131-1156`)에 **복붙 2벌**로 존재한다. 반환은 성공 결과만이 아니라 오류 계약까지 포함한다: `results | empty | failed | resolving | invalidSelection`. upstream 502를 "검색 결과가 없습니다"로 뭉개면 안 된다.
  2. 수동 위치 선택기는 그 로직 위의 **전용 얇은 래퍼**로 만든다.
  3. UI 컴포넌트 일반화는 세 표면의 렌더 계약이 같다는 증거가 생긴 뒤에 한다.

### 4.7 문구

| 상태 | 표시줄 | 길찾기 출발지 |
|---|---|---|
| GPS + 주소 확보 | `현재 위치, 강동구 성내로 12 부근` | `출발지, 현재 위치(강동구 성내로 12 부근)` |
| GPS + 주소 미확보 | `현재 위치` | `출발지, 현재 위치` |
| GPS 실패 | `위치를 확인할 수 없습니다` | 기존 `directions.geoError` |
| 수동 (verifiable) | `지정한 위치, 길동 카페` | `출발지, 지정한 위치, 길동 카페` |
| 수동 (unverifiable) | `지정한 위치, 길동 카페(위치 확인 불가)` | `출발지, 지정한 위치, 길동 카페` |

- 수동일 때 **"현재 위치"라는 표현을 어디서도 쓰지 않는다.** GPS가 알아낸 위치와 사용자가 지정한 위치는 다른 것이고, 시각장애 사용자는 화면으로 구분할 수 없다.
- **"현위치 정위"(where-am-i) 화면**은 수동일 때 헤더가 `지정한 위치`가 된다. 산문은 그 좌표를 설명하므로 내용 변경 없음.
- **안내 시작 통지**: 이 결과의 **출발지**가 수동 위치였을 때만(`originSource === "manual"` ↔ iOS `resultsUsedManualOrigin`) 안내 시작 버튼의 직접 응답으로 `현재 위치에서 안내를 시작합니다`(`manualLocation.guideStartsFromCurrent`)를 통지한다. iOS는 `.high`(시트가 떠 포커스가 옮겨가므로), 웹은 길찾기 뷰의 단일 polite 채널(같은 문장 재통지는 텍스트 노드 재삽입). "실제 위치"가 아니라 "현재 위치"인 이유: 앱 어휘에서 GPS 위치는 "현재 위치", 수동은 "지정한 위치"이고 안내 문구(`guide.*`)도 전부 "현재 위치"다. "지정한 위치가 아니라" 같은 대비 앞머리는 붙이지 않는다 — "현재 위치"만으로 상황이 설명되며 사족이다(위원장 판정 2026-08-17). ⚠ 결과 화면 상시 고지(구 `manualOriginNoticeText`·웹 settled 합산 통지 병기)는 폐기 — 그 정보로 갈리는 행동은 안내 시작뿐이라 안내를 시작하지 않는 사용자에겐 매 조회 잡음이었다.
- 6개 로케일 × 웹(`messages/*.json`) · iOS(`Localizable.xcstrings`).

## 5. 검증 계획

### 5.1 게이트 테스트 (매 커밋)

| 대상 | 내용 |
|---|---|
| `judgeManualLocation` | 3-state 전부. `origin` 부재 / fix 부재 / 정확도 음수·NaN·초과 / fix 나이 초과 / `separation` 경계 99·100·101m / 양쪽 정확도 차감. **웹↔Swift 공유 fixture 대조** |
| 저장 스키마 | 잘못된 JSON·범위 밖 좌표·빈 label·NaN이 폐기되는가(양 플랫폼 동일 fixture) |
| 트리거 3종 | 복귀·`force:true` 조회·앱/탭 시작에서 각각 판정이 도는가. 지정 직후에는 돌지 않는가 |
| CAS | 판정 왕복 중 새 지정이 들어오면 늦게 온 `.drop`이 폐기되는가 |
| 타입 봉인 | 안내 3경로(`start`·`requestReroute`·`refreshCarEta`)가 `RealFix`만 받는가(타입 레벨). 실측위 실패 시 fail-closed인가 |
| 우선순위 | 장소 앵커 > 수동 > GPS. 웹·iOS 동일 fixture |
| 통지 | `.drop`이 polite 통지를 정확히 1회 내는가. `.keep`·`.undecidable`은 통지하지 않는가 |
| 문구 | 수동 상태에서 `"현재 위치"`가 표시 경로에 등장하지 않는가(6로케일). `unverifiable` 접미가 붙는가 |
| 다중 탭 | 웹 `storage` 이벤트로 다른 탭의 해제가 전파되는가 |
| i18n | 신규 키 6로케일 존재(`i18n-messages.test.ts` 기존 게이트) |

**변이 주입으로 검출력을 실측한다**([[mutation-proves-test-detection-power]]):
① `MOVED_M` 100→1000 ② `separation`에서 정확도 차감 제거 ③ `accuracy > 0` 검사 제거 ④ 안내 경로가 `EffectiveLocation`을 받도록 완화 ⑤ 판정 시점을 지정 직후로 이동 ⑥ 트리거 ③(앱 시작) 제거 ⑦ CAS 제거 ⑧ `.undecidable`을 `.keep`으로 병합 ⑨ `.drop` 통지 제거. 아홉 전부 red가 되어야 한다.

⚠ **"두 상수를 하나로 병합"은 변이 목록에서 뺀다.** 값이 우연히 같아 런타임 출력이 변하지 않으므로, red로 만들려면 소스 형태를 검사하는 취약한 테스트가 필요하고 정상 리팩터링까지 실패시킨다. 대신 **두 축이 독립적으로 조정 가능한지**를 서로 다른 값으로 검증한다.

### 5.2 리뷰로 대체할 수 없는 게이트

- **실기기 VoiceOver**: 표시줄 두 버튼이 각각 이름을 갖는가, 검색 탭에서 위치→마이크 순서가 자연스러운가, 해제 후 포커스가 이탈하지 않는가, `.drop` 통지가 실제로 발화되는가.
- **실보행**: 지정 후 100m 이상 이동해 복귀했을 때 GPS로 돌아가는가. 같은 자리에서 앱을 여러 번 여닫아도 유지되는가. **`.undecidable` 비율이 실사용에서 얼마나 되는가**(높으면 `origin` 확보 경로를 재검토).
- **실사용**: 위원장이 집·직장에서 며칠 써 보고 재지정 빈도가 견딜 만한지.

| MAJOR | 안내 시작 시 실측위 실패 동작 미정의 | 수용 → §4.4 fail-closed + 전용 오류 문구 |
| MAJOR | 웹 `ready`는 권한 증명이 아님 | 수용 → §4.3 팝업 금지 약속 철회 |
| MAJOR | "유지"와 "검증 불가 유지"가 뭉개짐 | 수용 → §4.2 `.undecidable` + §4.5 노출 |
| MAJOR | fix 시각·값 유효성 계약 없음 | 수용 → §4.2 `eligible()` |
| MAJOR | 저장 데이터 검증·마이그레이션 없음 | 수용 → §4.1 스키마 검증 |
| MAJOR | iOS `.fixed`와 수동 위치 우선순위 미명시 | 수용 → §4.4 우선순위 계약 |
| MAJOR | 다중 탭·반응성 계약 없음 | 수용 → §4.6 단일 observable store |
| MAJOR | 표시줄 시맨틱·포커스 계약 없음 | 수용 → §4.6 형제 버튼 둘 |
| MAJOR | 검색 0건과 지오코딩 실패 미구분 | 수용 → §4.6 오류 계약 5-state |
| MINOR | `EndpointField` 6축 일반화 과잉 | 수용 → §4.6 추출 범위 축소(순수 로직 우선) |
| MINOR | "두 상수 병합" 변이 무효 | 수용 → §5.1 변이 목록 교체 |

**가장 큰 교훈**: 초판 §3.1의 실패 방향 분석이 **"미해제는 조용하다"를 상수로 가정**했다. 조용함은 설계가 정하는 값이고, §4.5의 상태 노출이 그 값을 바꾼다. 전제를 고정값으로 놓고 트레이드오프를 계산하면 잘못된 축에서 최적화한다.

## 9. 열린 판정

- **`.undecidable` 비율**(§5.2 실보행). 높으면 `origin` 확보 경로를 재검토한다(예: 지정 직후 짧은 창 안에 도착한 첫 적격 fix를 `origin`으로 지연 확정).
- **웹 표시줄을 장소 상세·길찾기 뷰에도 둘지.** 현재는 홈·허브 2곳이다. 실사용 후 판정.
