# 현위치 수동 지정 설계 (2026-08-09)

> 웹·iOS 동시. 서버 변경 없음(좌표만 다르게 실린다). CLI/MCP는 이미 같은 계약을 갖고 있어 범위 밖.
>
> 실시간 안내(E4)와 독립이며 그 봉인 해제 여부와 무관하게 성립한다. App Store 1.4에 `Release` 구성으로 실린다.

## 1. 문제

현재 위치의 유일한 소스가 클라이언트 측위다. 세 겹으로 부족하다.

| # | 현행 | 귀결 |
|---|---|---|
| ① | 측위가 실패하면 대안이 없다 | 웹 `geolocation.ts:107-112`가 권한 거부·`POSITION_UNAVAILABLE`·`TIMEOUT`을 `denied` 하나로 합류시키고, `useNearbyFetch.ts:159-166`이 그것을 "브라우저에서 위치 접근을 허용해 주세요"로 낸다. **실내 측위 실패 사용자는 허용해 놓고도 같은 문구를 듣고, "내 주변" 10종이 통째로 죽는다** |
| ② | 라벨을 역지오코딩이 정한다 | 서울 무작위 30점 실호출에서 건물명 37%, 도로명 13%, **지번만 50%**. 사용자가 "태양마트"에 있어도 "강동구 길동 363-1"로 낭독될 확률이 절반 |
| ③ | 사용자가 아는 것을 앱에 말할 수 없다 | 사용자는 자기가 어디 있는지 알지만 입력 경로가 없다 |

**왜 심각한가**: 셋 다 시각장애 사용자가 **화면으로 반증할 수 없다.** GPS가 200m 어긋난 좌표를 주면 정상 응답이 오고, 그 응답이 틀렸다는 신호가 어디에도 없다.

**이미 세 조각이 흩어져 있다.** 이 설계는 새 기능이 아니라 그 통합이다.

| 조각 | 위치 | 한계 |
|---|---|---|
| `{label, lat, lng}` 영구 저장 + 이름 지오코딩 | CLI `config.ts:8`, `resolve-location.ts:32-58` | headless 표면에만 존재 |
| 좌표 고정 주입 | 웹 `useNearbyFetch.ts:136-139`(`kind:"place"`), iOS `NearbyLoadCore.swift:39-43`(`.fixed`) | 장소 상세의 "이 장소 주변"에 갇힘 |
| 사람이 읽는 현위치 라벨 | `directions.currentLocationNear`(6로케일), `/api/geocode/reverse` 3단 체인 | 길찾기 출발지 필드 한 곳만 소비 |

## 2. 범위 밖

- **원격지 조회.** "지금 있지 않은 곳의 주변을 본다"는 이미 `PlaceAnchor`/`.fixed`가 담당한다. 이 설계는 **"내가 있는 곳을 정확히 말한다"**뿐이다. 두 축을 합치면 판정선이 사라진다(§3.2가 이동 판정으로 자기 위치 주장을 검증하는데, 원격지 조회는 그 검증이 성립하지 않는다).
- **즐겨찾기 저장소.** 검색 모달의 최근 목록(웹 `recent-searches.ts`, iOS `DirectionsEndpointSearchView` "최근 장소")을 재사용한다. 이동 판정이 붙으면 재지정 자체가 드물어져 별도 저장소의 값이 낮다(YAGNI).
- **최근접 POI 라벨링 — 금지한다.** §4.2의 실측이 근거다.
- **백그라운드 지오펜스.** `CLCircularRegion` 감시는 "항상 허용" 권한을 요구해 심사·프라이버시 비용이 크다. 포그라운드 복귀 1회 측위로 족하다.
- **실시간 안내에 수동 위치 적용.** §3.3이 구조로 차단한다.
- **서버·API 변경.** 라우트는 좌표를 받을 뿐 출처를 모른다.

## 3. 채택 설계

### 3.1 데이터 모델 — 저장 항목은 하나

```
ManualLocation = { label: string, lat: number, lng: number }
```

- iOS `UserDefaults`, 웹 `localStorage`. 해제 축이 앱 생명주기가 아니므로(§3.2) 영속 저장이 맞다.
- 웹은 `sessionStorage`가 아니다. 탭을 닫았다 여는 것이 이동을 뜻하지 않는다.
- CLI `config.location`과 같은 모양이다. 지금은 공유하지 않지만 나중에 합칠 때 변환이 없다.

**지정 시점 GPS 좌표를 기준점으로 따로 저장하지 않는다.** 사용자가 "길동 카페"를 지정하는 것이 곧 **"나는 길동 카페에 있다"는 주장**이므로, 그 좌표 자체가 이동 판정의 기준점이다.

⚠ **이 선택에는 실패 방향의 비대칭이 있고, 그것이 채택 근거다.**

| 기준점 | 오해제(안 움직였는데 해제) | 미해제(움직였는데 유지) |
|---|---|---|
| **수동 위치 좌표(채택)** | Wi-Fi 측위가 정확도를 좋게 보고하며 100m+ 틀릴 때 발생 | **발생하지 않음** |
| 지정 시점 GPS(기각) | 발생하지 않음 | 지정 시점에 fix가 없던 사용자는 기준점이 없어 **영구 유지** |

오해제는 표시줄이 즉시 "현재 위치"로 바뀌어 **보인다.** 미해제는 표시줄이 상태를 말하지만 사용자가 매번 확인한다는 보장이 없고, 틀린 답이 그럴듯하게 나온다. 이 저장소가 이미 겪은 실사고의 기제가 정확히 후자다("오류도 빈 결과도 아니라 그럴듯한 응답이 와서 실패가 보이지 않는다", CLAUDE.md 위치 싱글턴 동결). **덜 나쁜 실패를 고른다.**

부수 효과 둘: 지정 시점 권한이 없던 사용자도 판정 대상이 되고, 사용자가 자기 위치를 잘못 지정하면 GPS가 교정한다.

### 3.2 이동 판정 — 순수 함수, 웹 ↔ Kit 미러

```
keepManualLocation(manual, fix) -> Bool
  fix == nil                       → true   (측위 실패·권한 없음: 증거 부재)
  fix.accuracy > JUDGE_CEILING_M   → true   (판정 자격 미달)
  haversine(fix, manual) > MOVED_M → false  (이동 확정)
  otherwise                        → true
```

| 상수 | 값 | 근거 |
|---|---|---|
| `MOVED_M` | 100 | **"100m가 최근접 정류소 순위를 뒤집는다"는 실측**이 `LocationFix.swift:11-12`·`:27-28`에 두 번 기록돼 있다. 답이 달라지는 거리가 곧 "이동했다"의 정의다 |
| `JUDGE_CEILING_M` | 100 | `LocationFixPolicy.storeCeiling`과 같은 값·같은 취지("셀·Wi-Fi 측위의 km급 좌표는 어떤 용도로도 위치가 아니다"). 실내 측위가 튀어서 오해제되는 것을 막는다 |

⚠ **두 100m는 값만 같고 축이 다르다**(답이 달라지는 거리 / 판정 자격). 상수를 나눠 선언하고 한쪽을 바꿔도 다른 쪽이 따라가지 않게 한다. 값이 같다는 이유로 하나로 합치면 다음 사람이 한 축만 조정하려다 둘 다 바꾼다.

**판정 시점**: 포그라운드 복귀 1회.
- iOS: `scenePhase` → `.active` 전이.
- 웹: `visibilitychange`에서 `visible` 전이 + 최초 로드.

⚠ **지정 직후에는 판정하지 않는다.** 지정은 포그라운드에서 일어나므로 위 시점 정의가 유예를 저절로 만든다. 앱을 벗어났다 돌아와야 판정이 돈다. 지정하자마자 사라지는 경험을 구조로 막는다.

⚠ **판정용 측위는 강제 재취득이다. 캐시를 읽으면 판정이 성립하지 않는다.**

| 계층 | 캐시를 읽었을 때 | 귀결 |
|---|---|---|
| 웹 공유 스토어 | TTL이 없어 `ready` 좌표가 **세션 최초 값**이다(CLAUDE.md 동결 실사고, `useRouteGuide.ts:622-627`이 같은 이유로 `force` 기본값을 없앴다) | 이동을 영영 감지 못 함 |
| iOS `coordinateForDisplay()` | `freshTTL` 60초를 넘기면 nil | 백그라운드 체류가 길수록 판정 불가로 떨어짐 |

둘 다 **미해제**로 귀결하는데, §3.1이 정한 대로 그것이 더 나쁜 실패 방향이다. 그래서 웹 `awaitGeolocation({force:true})`, iOS `currentCoordinate(force:true)`를 쓴다. 복귀 1회이므로 정밀 재취득 비용을 받아들인다.

**부수 효과(의도된 이득)**: 복귀 시점마다 공유 스토어가 신선해진다. TTL 부재 때문에 세 곳에서 각각 독립적으로 방어해야 했던 문제(`useRouteGuide.ts:622-627`·`:719-720`·`:1480-1481`)가 복귀 경로에서 완화된다.

⚠ **권한 팝업을 띄우면 안 된다.** 거부한 사용자에게 복귀마다 팝업이 뜨는 것은 이 기능이 구제하려던 사용자를 정확히 괴롭히는 일이다. 판정은 **이미 권한이 부여된 상태에서만** 돈다.

- 웹: `getGeolocationSnapshot().status === "ready"`일 때만. `ready`는 성공한 fix가 이미 있었다는 뜻이므로 권한 보유가 증명된 상태다. Permissions API를 쓰지 않는다(Safari 지원 편차를 끌어들일 이유가 없다).
- iOS: `authorizationSnapshot`이 `.authorizedWhenInUse`/`.authorizedAlways`일 때만.
- `idle`/`denied`/`.notDetermined`면 **판정하지 않고 유지**한다(증거 부재).

**공유 fixture**로 웹 `src/lib/manual-location.ts` ↔ Kit `ManualLocation.swift`의 동조를 강제한다(기존 `route-guide` fixture 관례).

### 3.3 적용 경계 — 이름으로 가른다

수동 위치를 `awaitGeolocation`에 그냥 끼우면 **실시간 안내까지 오염된다.** `fetchGuideRoute`가 같은 함수를 쓰기 때문이다(`useRouteGuide.ts:644`). 함수를 둘로 가른다.

| 함수 | 동작 | 소비자 |
|---|---|---|
| `awaitGeolocation(opts)` / iOS `currentCoordinate(force:)` | **항상 실좌표** | 안내 시작(`useRouteGuide.ts:1275`), 이탈 재조회(`:1482`), 자동차 ETA(`:721`), iOS `BeaconModel` |
| `awaitEffectiveLocation(opts)` / iOS `effectiveCoordinate(force:)` | 수동 위치 있으면 그것, 없으면 위 함수에 위임 | 내 주변 10종/11화면, 검색 거리 블렌딩, 채팅 앵커, 길찾기 출발지, 현위치 정위 |

**이름으로 가르는 이유**: 안전 판단을 기본값이나 옵션으로 두면 새 호출 지점이 건너뛴다. `fetchGuideRoute(force)`가 기본값을 없앤 것과 같은 기법이다([[no-default-for-safety-parameters]]). 6개월 뒤 새 "내 주변" 도메인을 붙이는 사람이 어느 함수를 부를지 고민하는 그 순간이 설계가 판단을 강제하는 지점이다.

**단일 관문 덕에 호출부 수정이 적다.**

| 플랫폼 | 관문 | 자동 반영 |
|---|---|---|
| 웹 | `useNearbyFetch.ts:143` | "내 주변" 10종 전부 |
| iOS | `LocationService.nearbyCoordinateSource()`(`NearbyLoadState.swift:63-83`) | 11개 화면 전부 |

**길찾기 출발지는 코드 수정이 없다.** `DirEndpoint`는 `{kind:"current"}` 토큰만 저장하고 좌표는 조회 시점에 해석한다(웹 `DirectionsView.tsx:438`, iOS `DirectionsTabView.swift:202`). 그 해석이 새 함수를 부르면 끝이다.

**실시간 추적 fix는 애초에 이 계층을 안 지난다**(웹 `watchPosition` `useRouteGuide.ts:1259`, iOS `startBeaconUpdates`). 구조가 이미 격리돼 있다.

**안내 시작 시 경로 재조회는 이미 있다.** `useRouteGuide.ts:1273-1274`가 "시작 조회는 정밀 재취득이다 — 길찾기 조회 이후 이동해 있으면 낡은 출발점 기하로 즉시 이탈·오투영이 난다"고 명시한다. 수동 위치로 브리핑한 경로와 안내 경로의 출발지가 달라지는 것은 이 재조회가 이미 처리하는 사례이며, 시작 통지에 문장 하나를 더한다(§3.5).

**커버리지 마커는 좌표 출처와 무관하게 적용된다**(iOS `NearbyLoadCore.swift:125-129`가 `.fixed`에도 동일 적용). 수동 위치가 한국 밖이면 기존 `outOfCoverage` 경로를 그대로 탄다. 추가 처리 없음.

**채팅 앵커 우선순위**: 장소 앵커(`placeContext`) > 수동 위치 > 실좌표. `anchorOf(ctx)` 불변식은 그대로이고 `userLocation` 자리에 수동 위치가 들어간다.

- 웹: `EndpointField`가 `DirectionsView.tsx:968`의 비공개 인라인 컴포넌트라 **추출이 선행된다.** 뜯을 것 6가지: `export` 추가, `FieldState`/`DirEndpoint` → 중립 `{label, lat, lng}` 콜백, `t` 네임스페이스 주입(현재 `"directions"` 하드코딩), 최근목록 옵셔널화, `announce`/`focusAfterResolve` 옵셔널화, 결과 렌더 슬롯화.

⚠ **추출은 중복을 하나 줄이는 김에 한다.** 홈 검색(`PlaceSearch.tsx:581-608`)과 길찾기 검색(`DirectionsView.tsx:1131-1156`)의 **주소→좌표 지오코딩 25줄이 이미 복붙 2벌**이다. 세 번째 소비자를 만들면 3벌이 된다. 추출 시 이 함수를 공용으로 올린다.

### 3.5 문구 — "현재 위치"를 쓰지 않는다

GPS가 알아낸 위치와 사용자가 지정한 위치는 다른 것이고, 시각장애 사용자는 화면으로 구분할 수 없다. 3-state 불변식의 이 기능 판이다.

| 상태 | 표시줄 | 길찾기 출발지 |
|---|---|---|
| GPS + 주소 확보 | `현재 위치, 강동구 성내로 12 부근` | `출발지, 현재 위치(강동구 성내로 12 부근)` |
| GPS + 주소 미확보 | `현재 위치` | `출발지, 현재 위치` |
| GPS 실패 | `위치를 확인할 수 없습니다` | (기존 `directions.geoError`) |
| 수동 | `지정한 위치, 길동 카페` | `출발지, 지정한 위치, 길동 카페` |

- 표시줄은 **한 줄 = 한 접근성 객체**다. `joinText`(웹)·단일 `Text`(iOS)로 합친다.
- 수동일 때만 **해제 버튼**이 따라 나온다. 버튼은 별도 접근성 객체가 정상이다.
- 해제하면 GPS로 돌아간다. 그 시점 GPS가 실패 상태면 위 3행 문구가 된다(정직한 3-state).
- **자동 해제 시 별도 음성 통지를 하지 않는다.** 표시줄이 첫 줄에서 상태를 말하고, 이동은 사용자가 아는 사실이라 통지가 새 정보를 주지 않는다(CLAUDE.md "뻔한 꼬리 문장" 판정선).
- **"현위치 정위"(where-am-i) 화면**은 수동일 때 헤더가 `지정한 위치`가 된다. 산문은 그 좌표를 설명하므로 내용 변경 없음.
- **안내 시작 통지**에 수동 위치가 켜져 있을 때만 한 문장을 더한다: `실제 위치에서 안내를 시작합니다`.
- 6개 로케일 × 웹(`messages/*.json`) · iOS(`Localizable.xcstrings`).

## 4. 실측 근거

### 4.1 역지오코딩 라벨 커버리지 (2026-08-09, 카카오 `coord2address` 실호출)

서울 무작위 30점: 건물명 **37%**(11) · 도로명까지 13%(4) · **지번만 50%**(15) · 없음 0.

랜드마크 6점: `태양마트`·`서울특별시청`·`경복궁` 확보, 강동역·강남역·홍대입구역은 **null**. 셋 다 `road_address` 자체가 null인 좌표다(CLAUDE.md가 기록한 "도로명 건물 미매핑 좌표, GPS 빈발" 현상).

→ **"건물명·상호로 보여 달라"는 요구는 GPS 경로에서 절반 이하만 충족된다. 수동 지정 경로에서만 100%다.** 사용자가 고른 장소의 이름을 그대로 쓰기 때문이다.

### 4.2 최근접 POI 라벨링 — 금지 근거 (같은 날 실호출)

| 실제 위치 | `coord2address` | 최근접 POI |
|---|---|---|
| 강동역 | (null) | `언톨드(56m)` 카페 |
| 강남역 | (null) | `마리김밥(5m)` |
| 홍대입구역 | (null) | `마라공간마라탕 홍대점(9m)` |
| 길동 주택가 | `태양마트` | `말랑오븐(32m)` **(불일치)** |

`coord2address`의 `building_name`은 **그 좌표가 속한 건물**을 주지만, 최근접 POI는 **다른 건물**을 준다. "지금 마리김밥에 있습니다"를 시각장애 사용자는 반증할 수 없다. [[agentic-llm-fabricates-unstated-fields]]와 같은 계열이라 **어떤 폴백으로도 도입하지 않는다.**

### 4.3 Release 구성 빌드 (2026-08-09)

```

```

`#if EXPERIMENTAL`은 4개 파일에만 있고(`AppConfig`·`AppLanguage`·진단 2종), 봉인 지점은 `DirectionsTabView` 게이트 4종뿐이다(`AppConfig.swift:31`). Release plist에 `UIBackgroundModes` 없음, Experimental만 `[location, audio]`. **실험판은 브랜치가 아니라 빌드 구성이라 브랜치 드리프트가 발생할 자리가 없다.**

## 5. 검증 계획

### 5.1 게이트 테스트 (매 커밋)

| 대상 | 내용 |
|---|---|
| `keepManualLocation` 순수 함수 | fix 부재 / 정확도 초과 / 경계 99·100·101m / 정상 유지, 웹↔Swift **공유 fixture 대조** |
| 함수 분기 | 안내 3경로(`start`·`requestReroute`·`refreshCarEta`)가 **수동 위치를 절대 보지 않음**. 소스 스캔 가드로 `awaitEffectiveLocation` 호출 부재 강제 |
| 관문 통과 | `useNearbyFetch`가 수동 위치를 실을 때 fetch URL의 lat/lng가 수동 좌표 |
| 문구 | 수동 상태에서 `"현재 위치"` 문자열이 표시 경로에 등장하지 않음(6로케일) |
| i18n | 신규 키 6로케일 존재(`i18n-messages.test.ts` 기존 게이트) |
| 판정 시점 | 지정 직후에는 판정이 돌지 않음 |
| 판정용 측위 | 복귀 판정이 **캐시가 아니라 `force:true`**를 호출함(캐시를 읽으면 이동을 영영 감지 못 함) |
| 권한 | 권한 미보유(`idle`·`denied`·`.notDetermined`)면 측위를 시도하지 않고 수동 위치를 유지함 |

**변이 주입으로 검출력을 실측한다**([[mutation-proves-test-detection-power]]): ① `MOVED_M`을 100→1000 ② 부등호 뒤집기 ③ 정확도 게이트 제거 ④ 안내 경로를 `awaitEffectiveLocation`으로 교체 ⑤ 판정 시점을 지정 직후로 이동 ⑥ 두 상수를 하나로 병합 ⑦ 판정용 측위를 `force:false`로 강등. 일곱 전부 red가 되어야 한다.

### 5.2 리뷰로 대체할 수 없는 게이트

- **실기기 VoiceOver**(iOS): 표시줄이 한 객체로 읽히는가, 검색 탭에서 위치→마이크 순서가 자연스러운가, 해제 버튼 포커스가 사라진 뒤 이탈하지 않는가.
- **실보행**: 지정 후 100m 이상 이동해 복귀했을 때 GPS로 돌아가는가. 같은 자리에서 앱을 여러 번 여닫아도 유지되는가. **실내에서 오해제가 잦은지**(§3.1 트레이드오프의 실측 검증 — 잦으면 `JUDGE_CEILING_M` 재검토).
- **실사용**: 위원장이 집·직장에서 며칠 써 보고 재지정 빈도가 견딜 만한지.

## 6. 릴리스

App Store **1.4**(현재 1.3.0, 빌드 9, `READY_FOR_SALE` 2026-08-06). `Release` 구성이므로 실시간 안내는 자동으로 빠진다.

⚠ **1.4에 실릴 것이 이 기능만은 아니다.** 1.3 이후 iOS 커밋 대부분은 안내 축(게이트 뒤)이지만 `130f6e3`(빠른하차)·`2a3fbbe`(도보 브리핑 계단 회피)·`6f28a08`(비한국어 문 번호)처럼 Release 노출분이 섞여 있다. 릴리스 노트 작성 시 **게이트 안팎을 커밋 단위로 가른다.**

⚠ **병렬 세션 파일 충돌.** 이 작업은 `LocationService.swift`·`DirectionsTabView.swift`를 건드리고 실시간 안내 작업도 같은 파일을 쓴다. 브랜치 드리프트가 아니라 index 공유 문제다. `git commit -- <경로>` 원자화와 `git show HEAD --stat` 검증을 지킨다([[commit-stage-explicit-files]]).

## 7. 열린 판정

- **오해제 빈도**(§5.2 실보행). 잦으면 `JUDGE_CEILING_M`을 낮춰 판정 자격을 좁힌다(해제가 덜 일어남). 상수 하나로 조정 가능하게 설계돼 있다.
- **웹 표시줄을 장소 상세·길찾기 뷰에도 둘지.** 현재는 홈·허브 2곳이다. 웹은 뷰 스택이라 상세에서 돌아오면 홈의 표시줄을 다시 만난다. 실사용 후 판정.
