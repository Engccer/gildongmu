# E72 로터 동작을 화면에서도 쓰게 한다: 설계 (2026-10-17, iOS)

판정 정본은 `docs/BACKLOG.md` E72(위원장 판정 1~4, 2026-10-17). 이 문서는 그 판정을 코드 자리에 앉히는 방법만 정한다. 웹·안드로이드는 범위 밖(iOS 실기기 판정 뒤).

설계 리뷰 판정: 새 상태 머신·외부 계약·저장 포맷·안전 판정이 없는 표시 계층 변경이라 codex 적대적 리뷰 대상이 아니다(CLAUDE.md 리뷰 게이트 ①~④ 해당 없음). 대신 별도 컨텍스트 opus 리뷰어 한 번으로 spec을 본다. 정본 판정은 실기기 VoiceOver다(§6).

## 2. 규칙 1·2: 장소 목록 행은 밀기 버튼

### 2.1 묶음은 하나, 그리는 방식만 둘

`SearchView.swift`의 `PlaceRowActions`가 묶음의 정본으로 남는다(E60 가드가 이 파일을 읽는다). 묶음은 네 동작이고 보유한 데이터만 낸다(죽은 동작 금지, 종전 그대로):

- 주소 복사(`ios.place.copyAddress`, 도로명이 있을 때)
- 여기까지 길찾기(`directions.toHere`, 늘)
- 전화 걸기(`ios.place.call`, 번호가 있을 때)
- 물어보기(`ios.place.askAbout`, 화면이 채팅 진입을 넘길 때)

카카오맵·네이버 지도 딥링크는 묶음에서 빠진다(판정 2). 두 딥링크는 장소 상세의 보조 출구로 남는다(CLAUDE.md "딥링크는 장소 상세의 보조 출구다"와 정합).

그리는 방식은 호스트가 고른다.

- **`List` 행**: `.placeRowSwipeActions(place, onAskAbout:)`. 밀기 버튼은 **행의 뿌리 뷰**(행이 `NavigationLink`면 그 링크)에 단다. `swipeActions`는 `List` 행에 붙어야 동작하므로 `PlaceRow` 안(링크 라벨 안쪽)에 두지 않는다. 그래서 `PlaceRow`는 더 이상 스스로 동작을 달지 않고, 행을 만드는 호출부가 단다.
- **`List` 밖(채팅 카드, `ScrollView`)**: `.placeRowActions(place, onAskAbout:)`(로터). 같은 네 동작, 같은 순서.

판별선은 "그 행이 `List` 행인가"이고 화면 종류가 아니다.

### 2.2 밀기 방향별 배치

| 쪽 | 버튼(가장자리부터) | 끝까지 밀면 실행되는 첫 버튼 |
|---|---|---|
| 왼쪽으로 밀기(trailing) | 주소 복사 → 여기까지 길찾기 | 주소 복사(클립보드를 덮어쓴다, 데이터가 사라지지 않는 동작으로 본다). 도로명이 없어 첫 버튼이 여기까지 길찾기면 끈다(`allowsFullSwipe: !place.roadAddress.isEmpty`): 프리필은 길찾기 탭을 새로 만들어 앞서 조회한 경로를 지우고 최근 도착지에 기록하며 자동 조회(유료 호출 포함)를 낸다 |
| 오른쪽으로 밀기(leading) | 전화 걸기 → 물어보기 | 없음(`allowsFullSwipe: false`). 전화는 되돌릴 수 없고, iOS가 앱의 `tel:` 열기에 확인창을 띄우는지는 버전에 따라 달라 왔다(10.3 도입 뒤 제거·재등장 보고). 버튼을 보고 눌러야만 실행된다 |

끝까지 밀어 실행되는 첫 버튼은 되돌릴 수 있는 것만 둔다(판정 "착수 시 확인할 것"). 전화가 든 쪽은 끝까지 밀기 실행을 끈다(번호가 없어 그 쪽이 물어보기 하나여도 같은 값). 버튼 글자는 종전 로터 라벨 그대로다(「○○에 관해 물어보기」처럼 이름이 든 라벨은 밀기 폭에서 시각만 잘릴 수 있다. 밀기 버튼의 VoiceOver 이름은 버튼 글자라 줄이면 낭독도 바뀌므로 이번엔 바꾸지 않는다). 시각 버튼은 글자만 쓴다(아이콘만 있는 버튼은 뜻이 모호하고 VoiceOver 이름은 어차피 글자다). 이모지 금지.

**VoiceOver 동작 목록 순서**: E60이 정한 들리는 순서는 "주소 복사 → 여기까지 길찾기 → (딥링크 둘) → 전화 → 물어보기"이고, 딥링크를 뺀 목표는 **주소 복사 → 여기까지 길찾기 → 전화 걸기 → 물어보기**다. **한쪽 안의 순서는 선언 순서 그대로 오른다**(`2026-08-12-recent-pinning-design.md` §7, 실기기 확정 — `accessibilityActions`의 역순 노출과 다르다). 모르는 것은 **두 묶음 중 어느 쪽이 먼저 오르는가** 하나이고 실기기 VoiceOver만 판정한다(§6 ①). 이 축은 선언 순서로 고칠 수 없다. 오른쪽 묶음이 먼저 오르면 선택지는 ⓐ두 묶음의 자리를 맞바꾼다(끝까지 밀기 규칙은 버튼을 따라 옮긴다) ⓑ들리는 순서를 "전화 → 물어보기 → 주소 복사 → 여기까지 길찾기"로 다시 판정받는다이고, 위원장 판정이다(판정 요청 질문 2, 추천 ⓐ). 역 제목(상세 보기·길찾기 | 전화)도 같은 축이다.

`accessibilityActions`와 `swipeActions`를 한 행에 같이 두지 않는다(같은 동작이 동작 목록에 두 번 선다).

### 2.3 역·정류소 제목

- 역 제목(`SubwayNearbyView` `StationTitleActions`): 왼쪽 밀기 = 상세 보기 → 여기까지 길찾기(허용될 때), 오른쪽 밀기 = 전화 걸기. 목표 VoiceOver 순서는 E65 그대로 상세 보기 → 여기까지 길찾기 → 전화. 끝까지 밀면 왼쪽은 상세 보기(화면 이동)가 실행되고, 오른쪽(전화)은 끝까지 밀기 실행이 꺼져 있다(§2.2). 좌표 없는 응답이면 셋 다 없다(종전 그대로). 제목은 머리말 trait를 유지한다.
- 역 전화가 번호 없음·찾는 중·실패로 끝나면 통지는 VoiceOver에만 가므로, 눈으로 쓰는 사람에게 밀기 버튼이 무반응이 된다. **VoiceOver가 꺼져 있을 때만 같은 문장을 알림창으로 띄운다**(`callStationPhone`의 `onNotice`, VoiceOver 사용자는 종전과 똑같이 통지만 듣는다). 판정 요청 질문 1의 기본값이다.
- 정류소 제목(`BusNearbyView` `stopTitle`): 왼쪽 밀기 = 여기까지 길찾기 하나(허용될 때만, 아니면 밀기 버튼 자체가 없다). 끝까지 밀기는 끈다(첫 버튼이 프리필이라 §2.2와 같은 이유).
- 전화 번호 미리 조회 `.task`(역 제목)는 종전 자리 그대로.

### 2.4 앵커 목록·「주변 확인」

- 장소 상세 "이 장소 주변" 앵커 목록의 `directionsEntryAllowed`(E65 계약)는 그대로 밀기 버튼에도 적용된다.
- 안내 시트 「주변 확인」(버튼형 `SurroundingsSceneSection`)은 종전처럼 동작이 없다(`rowActionsAskAbout` nil).

## 3. 규칙 3: 줄 안 대상은 이름만 링크

### 3.1 한 벌의 도우미

새 파일 `ios/Gildongmu/InlineTargets.swift` 하나가 세 소비자(둘러보기 문장·브리핑 줄·채팅 블록)를 맡는다.

- 범위 판정은 Kit 순수 함수 `inlineTargetSpans(in:names:avoiding:)`(`InlineTargetSpans.swift`, `swift test`로 잠근다, 안드로이드 미러 등록부엔 `pending`): 각 이름의 모든 등장을 `Character` 오프셋으로 낸다. **피할 낱말(`avoiding`)의 등장을 먼저 막고**(브리핑 줄 맨 앞의 노선 이름 「신림선」 안의 「신림」), **긴 이름부터** 걸며 이미 잡힌 범위와 겹치면 건너뛴다(「강남구청」 안의 「강남」). 못 찾은 이름은 범위가 없고 로터만 남는다.
- 앱 `InlineTargets.linked(_:names:avoiding:)`는 그 오프셋에 자체 스킴 링크(`gildongmu-inline-target:///<순번>`)와 밑줄을 입힌다. 밑줄은 링크를 색에만 맡기지 않기 위해서다(WCAG 1.4.1). 인라인 링크는 목표 크기 기준(2.5.8)의 인라인 예외라 헌장 §1의 44pt와 충돌하지 않는다.
- `.inlineTargetTaps(_ handlers: [() -> Void])`: `openURL` 환경을 가로채 순번으로 처리한다. 자체 스킴이 아니면 `.systemAction`.
- 로터는 소비자가 종전 그대로 단다(역순 선언 관례 유지). 링크와 로터는 같은 대상 목록에서 나온다.

순번만 URL에 싣는다(이름·id에 URL에 안전하지 않은 문자가 있을 수 있다, 종전 채팅 관례). 채팅의 `gildongmu-place-mention` 스킴은 이 도우미로 흡수한다.

### 3.2 한 줄 = 한 접근성 객체

줄은 `Text` 하나로 남고 낭독 라벨(`accessibilityLabel`)도 종전 그대로다. 링크 속성은 시각 탭 경로일 뿐이다. 줄 글자 안에 "버튼"을 넣지 않는다. **`Text` 안 링크가 VoiceOver 객체를 쪼개는지, 줄에 "링크"를 덧붙여 읽는지, 줄을 두 번 탭하면 링크가 열리는지는 실기기 판정이다**(§6 ②). 처방은 미리 정해 두고 실측 전에는 넣지 않는다(종전 채팅 2개 이상 갈래의 판정과 같다): 쪼개지면 1순위 `.accessibilityElement(children: .combine)`, 그래도 쪼개지면 2순위 `.accessibilityElement(children: .ignore)` + 종전 낭독 라벨 + 로터(헤딩 블록은 `.isHeader`를 그 뒤에 다시 단다). 두 번 탭의 갈래별 수용: 아무 일 없음 = 판정 3 그대로 / 첫 링크가 열림 = 대상 하나인 줄은 받아들이고 둘 이상인 줄은 위원장 판정 / "링크"가 덧붙음 = 위원장 판정.

**출시 문턱**: 채팅의 지배적 경우(언급 1개 블록, 실호출 표본 27개 중 26개)가 실기기로 검증된 블록 버튼 길에서 미검증 링크 길로 옮겨 간다. 그래서 §6 ②(한 객체로 읽히는가) 판정 전에는 정식판(Release) 아카이브에 싣지 않는 것을 권고한다(코디네이터·위원장 결정, 실험판 설치로 판정할 수 있다).

### 3.3 소비자별

- **둘러보기 「한눈에 보기」**: 대상은 Kit `overviewDetailTargets(bullet, lang:)` 그대로, 링크 이름은 `target.name`. 줄은 `bilingualLine(visible:accessible:)`이 그리는데 시각 쪽만 링크를 받는다. 로터 라벨·역순은 종전 그대로.
- **경로 브리핑 지하철 구간 줄과 그 앞 도보 줄·하차 줄**(`BriefingStationRow`, 길찾기 탭의 `stationEntry` 옵트인일 때만): 링크 이름은 `BriefingStationAction.name`(그 줄의 언어, E45). 구간 줄은 노선 이름을 피할 낱말로 넘긴다. 도보 줄의 이름(「강남」)은 시각 문자열(「강남역」)의 일부에만 걸릴 수 있다. 링크 = 상세 열기. 전화는 링크가 아니고 로터에만 남는다(전화 라벨이 상태로 갈리는 E45 판정 ④ 그대로). 링크는 대상 줄 `Text`(구간 줄·하차 줄)의 시각 문자열에 걸리므로, 줄 뷰가 링크를 받을 수 있게 `transitLegRow`·하차 줄이 이름 목록을 인자로 받는다. 옵트인이 꺼진 소비자(안내 조망 "다른 경로")는 링크도 로터도 없다.
- **채팅 산문 블록**(§4).

## 4. 규칙 4: 채팅 산문 블록

`ChatConversationView.blockView`: 언급 0개면 평문, **1개 이상이면 언제나** 이름 링크 + 로터 「○○ 상세 보기」(역순 선언). 언급 1개의 블록 버튼 갈래와 "링크색만 칠하기" 갈래는 지운다. 포커스 복원 키(`focusedOriginKey`)는 종전처럼 블록에 단다. 헤딩 블록은 `.isHeader`가 버튼에 감싸이지 않고 `Text`에 그대로 남는다(종전 판정 대기 항목 하나가 사라진다).

채팅은 `ScrollView`라 밀기 버튼이 없다(판정 "착수 시 확인할 것"). 장소 카드는 §2.1 로터 묶음.

## 5. VoiceOver 읽기 순서 (목표)

| 자리 | 커서가 앉으면 | 동작 목록(위/아래 쓸기) |
|---|---|---|
| 장소 목록 행 | "이름, 분류·주소·거리" 한 객체(행이 링크면 "버튼") | 주소 복사 → 여기까지 길찾기 → 전화 걸기 → 물어보기(있는 것만) |
| 역 제목 | "역명, 노선, 거리, 머리말" | 상세 보기 → 여기까지 길찾기 → 전화 걸기 |
| 정류소 제목 | "정류소명, 번호, 거리, 머리말" | 여기까지 길찾기 |
| 한눈에 보기 문장 | 문장 한 객체 | 문장에 나온 순서로 「○○ 상세 보기」 |
| 브리핑 지하철 줄 | 줄 한 객체 | 「승차역 상세 보기」 → 「승차역에 전화 걸기」 → 「하차역 상세 보기」 → 「하차역에 전화 걸기」 |
| 브리핑 도보 줄·하차 줄 | 줄 한 객체 | 그 줄의 역 하나의 「상세 보기」 → 「전화 걸기」 |
| 채팅 블록 | 블록 한 객체 | 산문 순서로 「○○ 상세 보기」 |

언급 1개 채팅 블록은 종전 "…, 버튼"·두 번 탭으로 상세가 열리던 것이 동작 목록 한 칸으로 바뀐다(판정 4가 받아들인 대가). 두 번 탭이 링크를 여는지는 §3.2의 실기기 판정이다.

## 6. 검증

- **소스 가드**(웹 vitest, `test:run`): E60 순서 가드(`ios-location-ui.test.ts`)를 밀기 배치로 갈아 쓴다(왼쪽 = 주소 복사·여기까지 길찾기 선언 순, 오른쪽 = 전화·물어보기, 딥링크 키가 묶음에 없다, 묶음에 `accessibilityActions`가 없다). E65 가드(`e65-nearby-rotor-guard.test.ts`)·E45 가드(`briefing-station-entry-guard.test.ts`)를 링크·밀기 구조로 갈아 쓴다. `List` 행 호출부가 전부 행 뿌리에 밀기 수정자를 다는지, `PlaceRow` 본문에 동작 수정자가 없는지 센다.
- **빌드**: Kit `swift test`, 앱 Release·Experimental.
- **Kit**: `InlineTargetSpansTests`(피할 낱말·긴 이름 우선·못 찾음·Character 오프셋).
- **시뮬레이터 레인(1차, 정본 아님)**: 시뮬레이터 하나에서 둘러보기 문장·언급 1개 채팅 블록·장소 행 하나를 띄워 접근성 트리로 링크 자식 분리와 장소 행 동작 목록 존재를 본다. 결과는 완료 보고에 적는다.
- **실기기 판정**(BACKLOG §2에 새로 만드는 E72 행, FIELD-TEST §4-7에 새로 더하는 E72 행): ①`NavigationLink` 행·머리말 `Text` 행 각각에서 밀기 버튼이 동작 목록에 **모두 오르는가**, 그다음 순서가 §5와 같은가(오르지 않으면 처방은 VoiceOver 동작을 `accessibilityActions`로 두고 밀기 버튼은 시각용으로 남기는 것이다 — 오르지 않으니 중복도 없다. 순서가 어긋나면 §2.2의 위원장 판정) ②링크를 단 줄(한눈에 보기·브리핑·채팅)이 한 객체로 읽히고 "동작 사용 가능"이 들리는가, "링크"가 덧붙는가, 두 번 탭하면 무엇이 일어나는가 ③시각: 왼쪽·오른쪽 밀기에 버튼이 보이고, 왼쪽은 끝까지 밀면 첫 버튼이 실행되고 오른쪽(전화)은 실행되지 않는가 ④역 제목 머리말 trait가 밀기 버튼과 함께 남는가 ⑤헤딩 채팅 블록이 머리말 로터에 잡히는가.
