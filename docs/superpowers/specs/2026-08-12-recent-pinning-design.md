# 최근 목록 고정 (Recent Pinning) 설계

> 2026-08-12 위원장 승인. 대상: 웹 + iOS 동시(배포판·실험판 공통 — `#if EXPERIMENTAL` 게이트 없음).
> 최근 목록 4종(검색어·출발지 장소·도착지 장소·경로)의 각 항목에 "고정/고정 해제" 액션을 추가해
> 자주 가는 장소·자주 다니는 경로를 목록 상단에 유지한다. 기반 스펙:
> `2026-07-26-recent-searches-design.md`(3목록) + `2026-08-10-recent-routes-and-release-notes-design.md`(경로).

## 1. 목적

- 자주 쓰는 항목이 최근 20개 cap에 밀려나거나 최신순에 묻히지 않게 상단에 붙잡아 둔다.
- 스크린 리더 사용자의 위치 근육 기억("위에서 두 번째가 집")이 성립하도록 고정 항목의 자리를 안정시킨다.

## 2. 데이터 계약 (양 플랫폼 공통)

각 항목에 `pinned: boolean` 플래그를 내장한다.

| 목록 | 모델 변경 | 저장 키 |
|---|---|---|
| 검색어 | `string` → `{ text, pinned }` 구조체 | **v2로 상향** + v1 자동 승계 |
| 장소(from/to) | `RecentEndpoint`에 `pinned` 추가 | 기존 v1 유지(관용 디코딩) |
| 경로 | `RecentRoute`에 `pinned` 추가 | 기존 v1 유지(관용 디코딩) |

- **관용 디코딩**: `pinned` 부재(기존 데이터)는 `false`. 구버전 앱이 신버전 데이터를 읽는 방향은
  미지 필드 무시로 안전(JSON 디코더 공통 동작).
- **검색어 마이그레이션**: v2 키가 비어 있고 v1이 있으면 v1을 `pinned:false`로 감싸 승계한다.
  v1 키는 지우지 않는다(롤백 안전, 부가 기능이라 이중 보관 무해).
- ⚠ `RecentRoute.from/to`에 실리는 `RecentEndpoint.pinned`는 **무의미하다**(경로의 고정은 경로
  자체의 `pinned`). 항상 `false`로 저장하고 판정에 쓰지 않는다.
- dedupe 판정(`sameCoord`·`sameRoute`·검색어 완전 일치)은 `pinned`를 **보지 않는다** — 같은
  장소의 고정본과 비고정본이 공존하면 안 된다.

## 3. 정렬 불변식

저장 배열 = **[고정 블록] + [비고정 최신순]**. 모든 연산이 이 불변식을 보존한다.

| 연산 | 동작 |
|---|---|
| 고정 | `pinned=true`, 고정 블록 **맨 뒤**로 이동(먼저 고정한 항목이 항상 위 — 자리 안정) |
| 고정 해제 | `pinned=false`, 비고정 블록 **맨 앞**으로 |
| 재기록(재사용) | 고정 항목이면 **자리 유지**(장소는 최신 라벨로 교체만), 비고정이면 기존대로 비고정 블록 맨 앞 |
| cap 20 | **비고정 블록에만** 적용(고정 항목은 축출 면제) |
| 모두 지우기 | **비고정만** 삭제(위원장 확정 2026-08-12). 고정만 남으면 섹션은 계속 노출 |
| 개별 삭제 | 고정 여부 무관 삭제(명시 행동) |

## 4. UI·접근성 계약

- **항목 라벨**: 고정 항목은 `joinText(기존 라벨, "고정됨")` — 시각 표시와 접근명이 같은 단일
  텍스트, 쉼표 구분(헌장 "한 줄 = 한 객체"). 별도 헤딩·섹션 분리 없음(위원장 지시).
- **액션 순서**: 고정/고정 해제가 삭제보다 **상위**(위원장 지시 2026-08-12).
  - iOS: `swipeActions`에 [고정 토글, 삭제] 순 선언. full swipe가 고정 토글이 되는 것은 수용
    (비파괴·가역이라 삭제보다 안전). ⚠ VoiceOver 로터 노출 순서는 `.accessibilityActions`
    역순 함정([[swiftui-accessibility-actions-reverse-order]])이 swipeActions에도 적용되는지
    미확정 — **실기기 검증 항목**(§7). 뒤집혀 들리면 선언 순서만 교정.
  - 웹: 항목별 기존 삭제 버튼 **앞에** 고정 토글 버튼(DOM 순서 = 접근 순서). 접근명은 기존
    삭제 버튼 관례(항목명 포함)를 따른다.
- **토글 직후 (핵심)**: **즉시 재정렬하지 않는다.** 화면상 그 자리에서 `pinned`·라벨만 갱신하고,
  상단 정렬은 다음 목록 표시(재로드)부터 적용. 근거: 토글 순간 항목이 화면 밖으로 이동하면
  VO 포커스 유실(오프스크린 행 컬링) + 탐색 맥락 파괴.
  - iOS: 토글 후 갱신된 항목 값으로 포커스 재확정 → VO가 새 라벨을 낭독하는 것이 성공 신호
    (헌장 §5 "라벨이 곧 상태 신호", 별도 통지 없음). `pinned`가 항목 정체성에 포함되므로 재대입이
    같은 값 no-op이 되지 않는다(검색어도 구조체 전환으로 같은 기제 성립).
  - 웹: 기존 삭제와 같은 관례로 polite 통지("고정됨"/"고정 해제됨"). 포커스는 토글 버튼에 그대로
    (버튼이 사라지지 않음), 버튼 라벨은 고정↔고정 해제로 전환.
- 기록 시점·표시 조건(검색 전 초기 상태에만 등)·웹 상위 5건 표시 관례는 전부 기존 유지.
  웹 endpoint 5건 절단은 정렬 후 절단이므로 고정이 표시를 선점한다(의도).

## 5. i18n

`recent` 네임스페이스 4키 × 6로케일(ko/en/es/fr/it/ja): `pin`("고정"), `unpin`("고정 해제"),
`pinned`("고정됨" — 라벨 접미사 겸 웹 통지), `unpinned`("고정 해제됨" — 웹 통지).
iOS는 messages→xcstrings 파이프라인 재생성.

## 6. 테스트

- 양 플랫폼 store 단위 테스트: 고정 우선 정렬 불변식, cap 비고정 한정, 모두 지우기 보존,
  검색어 v1→v2 승계, 재기록 시 고정 자리 유지·라벨 교체, dedupe가 pinned 무시.
- 웹 컴포넌트 테스트(`DirectionsView.test.tsx` 등): 고정 버튼 순서(삭제보다 앞)·라벨 접미사·통지.
- 게이트: `npm run test:run` + GildongmuKit 테스트 + i18n 키 일관성 테스트(자동).

## 7. 실기기 검증 항목 (머지 후)

- [ ] 로터 커스텀 액션 순서: 고정이 삭제보다 위인가(뒤집히면 선언 역전만).
- [ ] 토글 후 새 라벨("…, 고정됨") 낭독이 실제로 발화되는가(침묵이면 `.high` 통지 보강).

## 8. 리뷰 판정

설계 단계 적대적 리뷰 **생략**: 신설 판정 계층·외부 통합·안전 크리티컬 축 없음. 저장 포맷 변경이
있으나 기기 로컬 부가 기능(파싱 실패 = 빈 목록 복구 계약 기존 유지)이라 비가역·고파급에 해당하지
않는다. 구현 단계 서브에이전트 리뷰 + 테스트가 잔여 리스크를 커버한다.
