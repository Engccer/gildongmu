# 지하철 빠른하차 출입문 병치 설계 (백로그 E5)

> 상태: 설계 확정(2026-08-08, 위원장 판정 3건 반영). 선행 조사·계약 확정은 `PROGRESS.md` 라운드1 M5 절, 상위 스펙은 `2026-08-04-transit-guidance-design.md`.

## 1. 배경과 목표

대중교통 안내는 "어느 열차를 타는가"까지 답하지만 **"몇 번째 칸에 타는가"**는 답하지 않는다. 시각장애 사용자에게 이 차이는 크다. 하차역에서 계단·엘리베이터가 승강장 어디에 있는지 모르면, 내린 뒤 승강장을 끝에서 끝까지 흰지팡이로 훑어야 한다.

서울교통공사 빠른하차 정보(data.go.kr 15143840)가 **하차역·방향별로 어느 칸 어느 문이 계단·엘리베이터에 가장 가까운지**를 준다. 이 값을 승차 전에 알려 주면 그 탐색이 사라진다.

⚠ 상위 스펙 §9는 이 항목을 "출입문·출구 번호 안내(**데이터 없음**)"으로 비범위에 두었다. 그 전제가 2026-08-06 API 발굴로 깨져 E5가 열렸다. **출구 번호는 여전히 데이터가 없다** — 이 스펙은 칸·문 번호와 시설 종류까지다.

**성과 지표**: 실승차에서 위원장이 하차 후 계단·엘리베이터를 찾는 데 드는 탐색이 줄어드는가(실사용 판정).

## 3. 데이터 계층 — 정적 seed

### 3.1 왜 seed인가

| 축 | 값 |
|---|---|
| 전체 크기 | **2,358행** (전량 1회 수집 확인) |
| 갱신 주기 | `crtrYmd` 전 행 `20241231` — **연 1회 스냅숏** |
| 커버 | 서울교통공사 **1~8호선만**, 276개 (역·노선), 543개 (역·노선·방향) |

대중교통 안내 세션은 이미 세션당 150~210콜을 쓰고(상위 스펙 §7 쿼터 산술), 그 쿼터는 백로그 C4가 관측 대상으로 걸어 둔 `DATA_GO_KR_API_KEY` 공유분이다. 연 1회 바뀌는 2,358행을 세션 중에 조회할 이유가 없다. **seed로 두면 쿼터 소비 0, 지연 0, 장애 노출 0**이다.

선례는 `subway-stations`·`audio-signals`·`tago-cities`·`congestion-areas` 넷이고 이 항목이 그중 가장 작다.

### 3.2 빌드 스크립트

`scripts/build-subway-quick-exit.mjs` → `src/lib/data/subway-quick-exit.json`(서버 전용 import).

⚠ **이 엔드포인트의 JSON 파라미터는 `dataType=json`이다.** 우리 다른 data.go.kr provider 9종이 전부 쓰는 `_type=json`은 **무시되고 XML이 온다**(`resultCode 00`에 실데이터가 실려 오므로 키 문제로 오진하기 쉽다). `type=json`·`resultType=json`도 XML이다. 실호출로만 알 수 있는 차이라 이 줄이 그 기록이다.

**투영**: 원본 14필드 중 seed에 남기는 것은 `stnNm`·`lineNm`·`upbdnbSe`·`drtnInfo`·`qckgffVhclDoorNo`·`plfmCmgFac`뿐이다. `facNo`·`elvtrNo`·`qckgffMngNo`는 내부 관리번호라 낭독에 쓸 수 없고, `facPstnNm`·`fwkPstnNm`는 §5 문장에 쓰지 않는다(아래 비범위).

**정제 2건**:
- **완전 중복 228조합 제거**. 원본에 같은 (역·노선·방향·방면·문·시설)이 두 번 들어 있는 행이 있다.
- **`qckgffVhclDoorNo`가 `NA-NA`인 행 폐기**(1건, 창동 4호선 상행 계단). 정보 없음을 문자열로 채운 것이라 그대로 실으면 "NA-NA 문"이 낭독된다. 같은 방향에 정상 계단 2개(3-4·7-3)가 있어 폐기해도 손실이 없다. ⚠ **가드로 고정**: 새 스냅숏에서 `NA` 행이 늘어나면 조용히 늘지 않도록 개수를 기록하고, 그 방향에 다른 정상 문이 없으면 빌드를 세운다.
- **`"3-2,3-3 사이"` 형태 4건은 보존**(전부 엘리베이터). 두 문 사이라는 정당한 위치 정보다. 거리 계산에는 앞 문(`3-2`)을 앵커로 쓰고 **표시는 원문 그대로**.

**빌드 가드**(하나라도 어긋나면 빌드 중단):
1. 노선이 정확히 `1호선`~`8호선` 8종
2. (역·노선) 276 이상 — 줄면 upstream 부분 장애를 의심한다([[upstream-outage-disguised-as-zero]])
3. **우리 역 seed와 조인 100%** — 부역명 괄호 정규화 후 276/276이 현재 값이다. 1건이라도 미일치면 중단(역명 개정·신설역 감지)
4. **두 방향의 `drtnInfo` 교집합 0** — §4.1 판정의 전제다. 깨지면 방향 판정이 무력해지므로 중단

### 3.3 우리 역 seed와의 조인

빠른하차 API는 부역명이 없고(`강변`) 우리 seed는 정식 표기다(`강변(동서울터미널)`). 후행 괄호를 벗기면 **276/276 완전 일치, 중복 0**이다. 정규화는 `station-match.ts`의 기존 함수를 쓰고 자체 정규화를 만들지 않는다(CLAUDE.md 역명 매칭 규칙).

## 4. 판정 계약 — 순수 함수 `src/lib/quick-exit.ts`

```ts
export function findQuickExit(input: {
  stationName: string;   // 하차역(ODsay 표기)
  lineName: string;      // 노선(ODsay 표기)
  previousStopName: string | null;  // 경로상 하차역 직전 정차역
}): QuickExit | null;

export interface QuickExit {
  elevatorDoor?: string;  // "6-4" 또는 "3-2,3-3 사이"
  stairsDoor?: string;
}
```

### 4.1 방향 판정 — `drtnInfo`가 진행 방향의 다음 역이다

`drtnInfo`는 **그 방향으로 갈 때 다음 역**의 이름이다(강동 5호선 상행 → `천호`). 우리 경로는 하차역에 **직전역에서** 도착하므로:

> **직전역과 같은 `drtnInfo`를 가진 방향이 반대 방향이다. 남은 쪽이 우리 방향.**

이 규칙이 성립하는 근거는 **두 방향의 `drtnInfo` 교집합이 543개 조합 전부에서 0**이라는 실측이다(§3.2 가드 4가 이를 고정한다).

경계 셋이 전부 자연히 처리된다:

- **종점**: 종착 방향의 `drtnInfo`는 **자기 역명**이다(방화 5호선 상행 → `방화`, 마천 → `마천`, 오금 3호선 하행 → `오금`). 방화에 개화산에서 도착하면 하행(`개화산`)이 배제되고 상행이 남는다 — 방화행 열차로 방화에 내리는 것이 맞다.
- **분기역**: 강동 5호선 하행은 방면이 `길동`·`둔촌동` 둘이다(응암 6호선 하행도 `새절`·`역촌`). 천호에서 도착하면 상행(`천호`)이 배제되고 하행이 남으며, **하행 두 방면의 시설을 합집합**한다. 같은 승강장이므로 합치는 것이 옳다. 전체 543 중 이 경우는 **2건뿐**이다.
- **단방향**: 6호선 응암순환 구간(역촌·불광·독바위·연신내·구산)과 한양대 2호선 등 **9개 조합**은 한 방향만 존재한다 → 그것을 쓴다. ⚠ 응암 6호선 상행은 `drtnInfo`가 `null`이라 대조에서 무매칭으로 취급된다(단방향 분기가 먼저 잡는다).

**판별 실패는 null이다.** 직전역이 없거나(경로 이상), 양쪽 다 매칭되거나(가드가 막지만 방어), 어느 쪽도 매칭되지 않으면 **필드를 싣지 않는다**. 틀린 방향의 문 번호는 없는 것보다 나쁘다.

⚠ **이 규칙은 `serviceWayCode`(ODsay wayCode)에 의존하지 않는다.** 상위 스펙 §5.1이 "2호선 내선/외선 ↔ wayCode 대응은 실호출로 확정한다"고 남겨 둔 항목이 백로그 F-a의 아침 게이트에 아직 열려 있다. **미확정 계약 위에 기능을 얹지 않는 것이 이 선택의 값**이다.

### 4.2 시설 선택 — 쌍 최적화

한 (역·노선·방향)에 계단이 최대 5개, 엘리베이터가 최대 3개 있다(계단 2개 이상 349건, 엘리베이터 2개 이상 30건). 원본에 우선순위 필드가 없으므로 규칙이 필요하다.

> **엘리베이터와 계단의 모든 쌍 중 서로 가장 가까운 쌍을 고른다.** 거리는 (칸 차이, 문 차이) 사전순, 동률이면 문 번호가 작은 쪽.

**근거는 목적이지 미학이 아니다.** 두 시설을 병기하는 이유는 사용자가 *도착해서* 고르게 하려는 것인데, 둘이 멀면 *승차 전에* 이미 골라야 해서 병기의 의미가 사라진다. 실측 대조(둘 다 보유 478조합):

| 규칙 | 칸 차이 0~1 | 3칸 이상 |
|---|---|---|
| **쌍 최적화** | **435 (91.0%)** | 19 (4.0%) |
| 각자 최저 문번호 | 264 (55.2%) | 151 (31.6%) |

서울역 1호선 하행이 전형이다. 각자 최저는 엘베 4-4·계단 1-1로 3칸이 벌어지지만, 쌍 최적화는 **계단 4-2를 골라 같은 칸**에 떨어진다.

**한쪽만 있는 경우**(계단만 21조합·엘리베이터만 43조합)는 그 시설의 **최저 문번호**를 쓴다. 쌍을 이룰 상대가 없어 최적화할 축이 없다.

**둘 다 없는 경우**(1조합, 에스컬레이터만 보유) → null.

## 5. 전달 계약

### 5.1 서버가 값을, 클라이언트가 문장을

`TransitLeg`에 additive 필드를 싣는다.

```ts
/** 하차역 빠른하차 문 번호(서울교통공사 1~8호선). 판정 불가·미커버면 필드 부재 */
quickExit?: { elevatorDoor?: string; stairsDoor?: string };
```

⚠ **도보 경로와 규칙이 다른 이유**: 도보는 provider 원문 문장을 서버가 재작성하므로 "서버가 문장을 만든다"가 정본이다(CLAUDE.md, 2026-08-07 판정). 여기는 provider가 문장을 주지 않고 **구조화된 값 두 개**를 줄 뿐이라, 로케일별 문장은 i18n의 몫이다. 값을 서버에서 확정하고 문장을 클라이언트가 만드는 것이 두 규칙 모두와 정합한다.

### 5.2 `includeStops`와 무관하게 항상 계산한다

방향 판정에 직전역이 필요한데, 그것은 ODsay `passStopList`에 있고 **`includeStops`는 방출만 통제한다**(provider `toLeg`가 플래그와 무관하게 원본을 갖는다). 따라서 `quickExit`는 옵트인 없이 계산해 항상 싣는다.

이 선택의 실질은 **CLI·MCP·iOS가 아무 변경 없이 값을 받는다**는 것이다(현재 `includeStops=1`을 보내는 소비자는 웹 `DirectionsView` 하나뿐이다). 응답 크기 증가는 지하철 leg당 최대 두 문자열이라 무시할 수준이다.

### 5.3 문장

i18n 키 하나, 6로케일. 위원장이 승인한 형태 그대로:

```
{station} 하차, 엘리베이터 {elevator} 문, 계단 {stairs} 문.
```

한쪽만 있으면 그 절만 남긴다(`여의도 하차, 엘리베이터 6-4 문.`). **한 줄 = 한 접근성 객체**이므로 시각 강조용 인라인 `<span>`으로 쪼개지 않고 단일 텍스트로 만든다(`joinText` 관례).

⚠ **"빠른 하차" 같은 라벨을 앞에 붙이지 않는다.** 문장이 이미 무엇인지 말한다.

## 6. 노출 지점

| 지점 | 위치 | 비고 |
|---|---|---|
| 웹 브리핑 | `TransitRouteBriefing.tsx` 지하철 leg | leg 문장 뒤 별도 줄 |
| iOS 브리핑 | 대응 SwiftUI 뷰 | 동형 |
| CLI·MCP | `packages/cli` transit 포매터 | ⚠ 카탈로그 항목이 아니라 기존 포매터 확장이므로 `formatter-coverage` 대상 아님 |
| 안내 세션 | 웹 `TransitGuidePanel` · iOS 세션 시트, **승차 대기 국면** | 열차 선택 목록 위 |

**통지는 만들지 않는다.** 정적 정보라 상태 변화가 없고, live region은 변화를 알리는 채널이다. 세션 대기 화면의 텍스트로 존재하는 것으로 충분하다(§5.1 "대기 중 자동 낭독은 선택 후에만" 계약과도 정합).

**환승 구간에서 자연히 여러 번 나온다** — 지하철 leg마다 자기 하차역 기준으로 계산되므로, 환승역에서도 "어느 칸에 타야 환승이 빠른가"가 답해진다. 별도 처리가 필요 없다.

## 7. 3-state

- **필드 부재 = 정보 없음.** 9호선·신분당선·경의중앙·수인분당·인천 등 서울교통공사 밖 노선, 방향 판정 실패, 미수록 역이 전부 여기 해당한다.
- **"빠른 하차 정보가 없습니다" 문구를 넣지 않는다.** 서교공 밖 노선에서 매번 울릴 잉여이고, 사용자 행동을 바꾸지 않는다([[honesty-disclosures-belong-to-api-layer]]). 커버리지 한계는 API 응답의 필드 부재로만 표현한다.
- **한쪽 시설만 있으면 있는 것만** 말한다. 없는 시설을 "없음"으로 명시하지 않는다.

## 8. 테스트·게이트

1. **빌드 가드 4종**(§3.2) — 스크립트 자체가 실호출이므로 seed 재생성이 곧 실호출 검증이다.
2. **방향 판정 단위 테스트 6케이스**: 일반(여의도) · 종점(방화) · 분기 합집합(강동 하행) · 단방향(연신내) · 부역명 정규화(강변) · 판별 실패(직전역 null).
3. **시설 선택 단위 테스트 5케이스**: 쌍 최적화(서울역 1호선 하행이 4-2를 고르는가) · 엘베 복수(창동) · 계단만 · 엘베만 · 둘 다 없음.
4. **정제 테스트**: `NA-NA` 폐기 · `"3-2,3-3 사이"` 보존 · 완전 중복 제거.
5. **스키마 계약**: `quickExit` 미보유 응답이 기존과 byte-호환인지(additive 확인).
6. **변이 주입**: 방향 판정을 반대로 뒤집는 변이와 쌍 최적화를 각자 최저로 바꾸는 변이가 **검출되는지** 확인한다([[mutation-proves-test-detection-power]]). 후자는 fixture가 두 규칙이 갈리는 역(서울역 1호선 하행)을 포함해야만 잡힌다.
7. **실사용 판정(위원장)**: 실승차에서 칸 번호가 실제 승강장 표기와 맞는지, 문장이 대기 화면에서 방해가 되지 않는지, 환승역 반복 노출이 과한지.

## 9. 비범위

- **에스컬레이터**(위원장 제외 판정). 데이터는 seed에 넣지 않는다 — 쓰지 않을 값을 싣지 않는다(YAGNI).
- **출구 번호**: 원본에 없다. `facPstnNm`("천호 방면8-4")·`fwkPstnNm`("강동 B4")는 층·방면 정보이지 출구가 아니고, **계단 행에는 아예 없다**(1,259행 전부 null). 문장에 쓰지 않는다.
- **역 상세 화면 노출**: 방향 선택 UI가 따로 필요해 범위를 넘는다. 실사용 판정 후 재검토.
- **버스**: 해당 데이터가 없다.
- **9호선·신분당선 등 서교공 밖 노선**: 운영기관이 다르고 공개 API가 확인되지 않았다.
