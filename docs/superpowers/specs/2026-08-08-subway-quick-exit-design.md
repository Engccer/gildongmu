# 지하철 빠른하차 출입문 병치 설계 (백로그 E5)

> 상태: 구현 완료(2026-08-08). 위원장 판정 3건 + codex 적대적 리뷰 24건 판정 반영(§10) + 구현 중 실측 정정 4건(§11). 실호출 게이트 결과는 `PROGRESS.md`. 선행 조사·계약 확정은 `PROGRESS.md` 라운드1 M5 절, 상위 스펙은 `2026-08-04-transit-guidance-design.md`.

## 1. 배경과 목표

대중교통 안내는 "어느 열차를 타는가"까지 답하지만 **"몇 번째 칸에 타는가"**는 답하지 않는다. 시각장애 사용자에게 이 차이는 크다. 하차역에서 계단·엘리베이터가 승강장 어디에 있는지 모르면, 내린 뒤 승강장을 끝에서 끝까지 흰지팡이로 훑어야 한다.

서울교통공사 빠른하차 정보(data.go.kr 15143840)가 **하차역·방향별로 어느 칸 어느 문이 계단·엘리베이터에 가장 가까운지**를 준다. 이 값을 승차 전에 알려 주면 그 탐색이 사라진다.

⚠ 상위 스펙 §9는 이 항목을 "출입문·출구 번호 안내(**데이터 없음**)"으로 비범위에 두었다. 그 전제가 2026-08-06 API 발굴로 깨져 E5가 열렸다. **출구 번호는 여전히 데이터가 없다** — 이 스펙은 칸·문 번호와 시설 종류까지다.

**성과 지표**: 실승차에서 위원장이 하차 후 계단·엘리베이터를 찾는 데 드는 탐색이 줄어드는가(실사용 판정).

## 3. 데이터 계층 — 정적 seed

### 3.1 왜 seed인가

| 축 | 값 |
|---|---|
| 전체 크기 | **2,358행** (전량 1회 수집 확인, 정제 후 채택 1,806행) |
| 갱신 주기 | `crtrYmd` 전 행 `20241231` — **연 1회 스냅숏** |
| 커버 | 서울교통공사 **1~8호선만**, 276개 (역·노선), **542개** (역·노선·방향 — §11 정정) |

대중교통 안내 세션은 이미 세션당 150~210콜을 쓰고(상위 스펙 §7 쿼터 산술), 그 쿼터는 백로그 C4가 관측 대상으로 걸어 둔 `DATA_GO_KR_API_KEY` 공유분이다. 연 1회 바뀌는 2,358행을 세션 중에 조회할 이유가 없다. **seed로 두면 쿼터 소비 0, 지연 0, 장애 노출 0**이다.

선례는 `subway-stations`·`audio-signals`·`tago-cities`·`congestion-areas` 넷이고 이 항목이 그중 가장 작다.

### 3.2 빌드 스크립트

`scripts/build-subway-quick-exit.mjs` → `src/lib/data/subway-quick-exit.json`(서버 전용 import).

⚠ **이 엔드포인트의 JSON 파라미터는 `dataType=json`이다.** 우리 다른 data.go.kr provider 9종이 전부 쓰는 `_type=json`은 **무시되고 XML이 온다**(`resultCode 00`에 실데이터가 실려 오므로 키 문제로 오진하기 쉽다). `type=json`·`resultType=json`도 XML이다. 실호출로만 알 수 있는 차이라 이 줄이 그 기록이다.

**투영**: 원본 14필드 중 seed에 남기는 것은 `stnNm`·`lineNm`·`upbdnbSe`·`drtnInfo`·`qckgffVhclDoorNo`·`plfmCmgFac`뿐이다. `facNo`·`elvtrNo`·`qckgffMngNo`는 내부 관리번호라 낭독에 쓸 수 없고, `facPstnNm`·`fwkPstnNm`는 §9 근거로 제외한다. `stnNo`는 §3.3 가드에만 쓰고 seed에는 싣지 않는다.

**정제 3건**:
- **완전 중복 제거**(같은 역·노선·방향·방면·문·시설이 두 번 들어 있다). 전체 기준 228조합이지만 그중 213이 에스컬레이터라 제외 뒤에는 **15행**이다.
- **`qckgffVhclDoorNo`가 `NA-NA`인 행 폐기**(현재 1건, 창동 4호선 상행 계단). 정보 없음을 문자열로 채운 것이라 그대로 실으면 "NA-NA 문"이 낭독된다. 같은 방향에 정상 계단 2개(3-4·7-3)가 있어 손실이 없다.
- **에스컬레이터 행 전량 제외**(확정 판단 1). 쓰지 않을 값을 싣지 않는다.

**문법 화이트리스트 — 미지 형태는 빌드 중단**:

| 필드 | 허용 | 처리 |
|---|---|---|
| `qckgffVhclDoorNo` | `N-M`(N=1~10, M=1~4) · `N-M,N-M 사이` · `NA-NA` | 앞 둘은 채택, `NA-NA`는 폐기, **그 밖은 빌드 중단**. ⚠ **범위까지 정규식으로 강제한다** — 자릿수만 보면 `1-5`와 `2-1`이 선형 위치 5로 충돌한다(§11 정정 5) |
| `plfmCmgFac` | `계단` · `엘리베이터` · `에스컬레이터` | 그 밖은 빌드 중단 |
| `upbdnbSe` | `상행` · `하행` | 그 밖은 빌드 중단 |

문 번호를 관용적으로 파싱하면 새 스냅숏의 전각 문자·공백·범위 표기가 `NaN` 정렬이나 원문 오발화로 조용히 새어 나간다. 모르는 형태는 **빌드를 세우는 것이 정답**이다.

### 3.3 빌드 가드 (구현은 11종 — §11 정정)

하나라도 어긋나면 빌드를 중단한다. 아래 번호는 설계 시점 열거이고, 구현은 문법 화이트리스트 3종을 별도 가드로 세어 **총 11종**이다(`scripts/build-subway-quick-exit.mjs`의 G1~G11). 가드는 순수 함수로 내보내 테스트가 변이를 주입한다 — 가드가 있다는 사실과 가드가 잡는다는 사실은 다르다.

**수집 완전성**(부분 응답 차단):
1. 모든 페이지의 `resultCode`가 정상이고, 수집 행 수 == `totalCount`
2. 페이지 간 `qckgffMngNo` 중복·누락 0
3. `crtrYmd`가 단일 값 — 여러 값이 섞이면 스냅숏 경계가 불분명하다

**구조 불변식**:

4. 노선이 정확히 `1호선`~`8호선` 8종
5. **우리 역 seed와 조인 100%**(부역명 괄호 정규화 후 현재 276/276). 1건이라도 미일치면 중단 — 역명 개정·신설역 감지
6. **두 방향의 `drtnInfo` 교집합 0** — §4.1 판정의 전제
7. **`drtnInfo`가 `stnNo` 인접역과 일치**(현재 2,207건 검사 중 2,192 일치 + 화이트리스트 4건). ⚠ 인접역이 서교공 목록 밖이면(서울역→남영, 청량리→회기 등 코레일 구간) 검사에서 제외한다 — 그 42건이 예외가 아니라 **검사 대상이 아니라는** 뜻이다. 지선 번호(`211-1`·`P549`)도 증감이 정의되지 않아 대상 밖이다
8. (7과 같은 검사다 — `상행`=`stnNo`−1·`하행`=`stnNo`+1이 7의 인접 정의다.) ⚠ **예외 0이 아니라 4건**이다(§11 정정): 응암순환 3(응암 610 하행 새절·구산 615 하행 응암·새절 616 상행 응암)과 강동 5호선 548 하행 둔촌동. 전부 번호 순서와 선로 위상이 다른 곳이라 화이트리스트로 두고 **목록 밖 어긋남만** 빌드를 세운다

**이전 스냅숏 대비 비교**(가드 4~8은 한쪽이 통째로 비어도 자명하게 참이 될 수 있다):

9. (역·노선·방향) 집합·시설별 행 수를 직전 seed와 대조해 **감소를 보고**하고, 감소가 있으면 빌드를 중단한다. 사람이 확인해 의도된 변화면 기준선을 갱신한다.

**신선도**:

10. `crtrYmd`와 빌드 일자를 seed 메타에 기록한다. ⚠ **운영기관 문의는 외부 발신이라 자율 진행 대상이 아니다** — 자동 만료 차단 대신 기록을 남기고, 연 1회 재빌드 때 가드 9가 변화를 보고하는 것으로 갈음한다. 승강장 공사로 문 위치가 바뀌었는데 스냅숏이 그대로인 위험은 **실사용 판정(§8-8)이 유일한 검출 수단**이고, 이것이 이 기능의 알려진 한계다.

### 3.4 우리 역 seed와의 조인

빠른하차 API는 부역명이 없고(`강변`) 우리 seed는 정식 표기다(`강변(동서울터미널)`). 후행 괄호를 벗기면 **276/276 완전 일치, 중복 0**이다. 정규화는 `station-match.ts`의 기존 함수를 쓰고 자체 정규화를 만들지 않는다(CLAUDE.md 역명 매칭 규칙).

## 4. 판정 계약 — 순수 함수 `src/lib/quick-exit.ts`

```ts
export function findQuickExit(input: {
  stationName: string;              // 하차역(ODsay 표기)
  lineName: string;                 // 노선(ODsay 표기 — "수도권 5호선")
  previousStopName: string | null;  // 경로상 하차역 직전 정차역
}): QuickExit | null;

export interface QuickExitDoor {
  /** "6-4" 또는 두 문 사이면 ["3-2","3-3"] */
  kind: "door" | "between";
  doors: string[];
}
export interface QuickExit {
  elevator?: QuickExitDoor;
  stairs?: QuickExitDoor;
}
```

### 4.0 노선명 정규화

⚠ **ODsay는 `"수도권 5호선"`, 이 API는 `"5호선"`이다**(실호출 확정). 역명 조인 100%는 정적 역 seed와의 관계만 증명하며 **런타임 ODsay 표기를 증명하지 않는다**.

`"수도권 "` 접두를 벗겨 seed 키로 대조한다. **노선 화이트리스트는 두지 않는다**(§11 정정): 커버 범위의 정본은 seed 키 하나여야 하고, 화이트리스트를 병치하면 관측되지 않는 채로 seed와 어긋날 수 있으며 노선이 늘 때 두 곳을 고쳐야 한다(변이 주입에서 검출 불가로 확인). 9호선·신분당선·경의중앙선은 키가 없어 걸러지고, 1호선 코레일 구간(부천·수원 등)은 노선명이 통과해도 **역명이 seed에 없어** 걸러진다.

⚠ **급행은 노선명 접미로 실린다**(실측: `"수도권 9호선(급행)"`). 접두만 벗기면 `"9호선(급행)"`이 되어 어떤 seed 키와도 맞지 않으므로, 급행은 §4.1의 방향 판정에 닿기 전에 **구조적으로 침묵**한다.

### 4.1 방향 판정 — 긍정 확정만

`drtnInfo`는 **그 방향으로 갈 때 다음 역**의 이름이다. 근거는 추론이 아니라 실측이다:

- `drtnInfo`가 `stnNo` 인접역과 일치: **2,207건 검사 중 2,192 일치**(나머지 4종 15행은 응암순환·강동 분기라 위상이 번호와 다르다 — §3.3 가드 7의 화이트리스트). 서교공 목록 밖 인접역 42건·지선 번호·자기 종착은 검사 대상 밖

판정 규칙:

> 하차역의 방향 그룹 중 **`drtnInfo`가 직전역과 같은 쪽을 배제**한다. 정확히 하나가 남고 **그 방향의 방면이 하나로 확정**될 때만 채택하며, 그 밖의 모든 경우는 null이다.

⚠ **"배제로 살아남은 것"과 "확인된 것"은 다르다**(§11 정정). 방면이 비어 있는 방향(응암 6호선 상행, `drtnInfo` null)은 어떤 직전역과도 대조되지 않아 **영원히 배제되지 않는다** — 반대편이 배제되면 홀로 남아 조용히 선택된다. 그래서 남은 방향의 `toward`가 정확히 1개일 때만 진행한다. 이 조항이 분기역 null(아래 경계)까지 함께 처리한다.

⚠ 대조는 양쪽 모두 `normalizeStationName`을 통과시킨다(부역명·`역` 접미·공백·괄호). 정규화 없이 비교하면 방향 판정이 조용히 사라진다.

**"한 방향만 있으면 그것을 쓴다"는 조항을 두지 않는다.** 한 방향만 수록된 (역·노선)이 9건인데, 그중 **어느 것이 실제 단방향이고 어느 것이 데이터 결측인지 데이터로 구분되지 않는다** — 응암순환 5역(역촌·불광·독바위·연신내·구산)은 진짜 단방향이지만 한양대 2호선·남위례 8호선은 양방향 본선역이라 결측이다. 그 조항이 있으면 **하행 승객에게 상행 문 번호를 낭독**한다.

긍정 확정 규칙만으로 이것이 저절로 안전해진다. 한양대에 하행으로 도착하는 승객의 직전역은 왕십리인데 유일하게 수록된 상행 행의 `drtnInfo`가 왕십리라 배제되고, 남는 행이 없어 null이 된다. 반대로 상행 승객(직전역 뚝섬)은 배제되지 않아 정상 동작한다. 응암순환 5역도 같은 규칙으로 통과한다. **특례를 지우는 것이 특례를 정교하게 다듬는 것보다 안전했다.**

**경계**:

- **종점**: 종착 방향의 `drtnInfo`는 자기 역명이다(방화 상행 → `방화`). 개화산에서 방화에 도착하면 하행(`개화산`)이 배제되고 상행이 남는다.
- **분기역은 null이다**(강동 5호선 하행 = 방면 `길동`·`둔촌동`, 응암 6호선 하행 = `새절`·`역촌`). 두 방면이 같은 승강장인지 데이터로 확인할 수 없고, 서로 다른 방면의 엘리베이터와 계단을 쌍으로 묶으면 **어느 열차에서도 성립하지 않는 조합**이 나온다. 543 중 **2건**이라 침묵의 비용이 작다. ⚠ 세션 국면에서는 사용자가 고른 열차의 행선지로 방면을 확정할 수 있으나, 브리핑에는 그 정보가 없어 소비자별로 답이 갈린다 — 통일을 위해 둘 다 null로 둔다(백로그 후보).
- **급행 통과역**: `drtnInfo`는 물리적 인접역이고 `passStopList`는 정차역이라, 급행이면 둘이 어긋나 어느 방향도 배제되지 않는다 → **null(안전 침묵)**. 서교공 1~8호선 본선에 급행이 없다는 것을 §8-5 게이트로 확인하고, 있으면 그 노선의 실동작을 기록한다. 폴백은 만들지 않는다(YAGNI — 안전 실패가 이미 보장된다).

### 4.2 시설 선택 — 선형 위치 기준 쌍 최적화

한 (역·노선·방향)에 계단이 최대 5개, 엘리베이터가 최대 3개 있다(계단 복수 349건, 엘리베이터 복수 30건). 원본에 우선순위 필드가 없으므로 규칙이 필요하다.

**거리는 열차 선형 위치로 잰다.** 서울 지하철 전동차는 칸당 문 4개이고(실측: 문 번호 분포가 1~4뿐), 칸 번호는 1~10이다.

```
pos("N-M") = (N - 1) * 4 + M
pos(between "A","B") = (pos(A) + pos(B)) / 2
```

⚠ **(칸 차이, 문 차이) 사전순은 물리 거리가 아니다.** `1-4`와 `2-1`은 칸이 다르지만 실제로는 **바로 옆 문**(선형 4와 5)인데, 사전순으로는 같은 칸의 `2-1`·`2-4`(선형 5와 8)보다 멀다고 판정된다.

> **엘리베이터와 계단의 모든 쌍 중 선형 거리가 최소인 쌍을 고른다.**
> 동률이면 **엘리베이터 위치 오름차순 → 계단 위치 오름차순** 순으로 자른다(총정렬이라 원본 행 순서가 바뀌어도 결과가 불변이다).

**근거는 목적이지 미학이 아니다.** 두 시설을 병기하는 이유는 사용자가 *도착해서* 고르게 하려는 것인데, 둘이 멀면 *승차 전에* 이미 골라야 해서 병기의 의미가 사라진다. 실측 대조(둘 다 보유 478조합, 칸 단위 근사):

| 규칙 | 칸 차이 0~1 | 3칸 이상 |
|---|---|---|
| **쌍 최적화** | **435 (91.0%)** | 19 (4.0%) |
| 각자 최저 문번호 | 264 (55.2%) | 151 (31.6%) |

서울역 1호선 하행이 전형이다. 각자 최저는 엘베 4-4·계단 1-1로 3칸이 벌어지지만, 쌍 최적화는 **계단 4-2를 골라 같은 칸**에 떨어진다.

**한쪽만 있는 경우**(계단만 21조합·엘리베이터만 43조합)는 그 시설의 **선형 위치 최소값**을 쓴다. 쌍을 이룰 상대가 없어 최적화할 축이 없다.

**둘 다 없는 경우** → null. ⚠ 에스컬레이터만 보유하던 1조합은 행 제외로 seed에서 **통째로 사라져** 그 상태가 실재하지 않는다(§11 정정 — 판정 결과는 동일한 null). ⚠ 이것을 "확인된 없음"으로 따로 표현하지 않는다: 사용자 행동이 정보 없음과 같고(둘 다 침묵) 543 중 1건이다. 빌드가 그 조합을 로그로 남겨 늘어나면 드러나게 한다.

## 5. 전달 계약

### 5.1 서버가 값을, 클라이언트가 문장을

`TransitLeg`에 additive 필드를 싣는다.

```ts
/** 하차역 빠른하차 문 위치(서울교통공사 1~8호선). 판정 불가·미커버면 필드 부재 */
quickExit?: { elevator?: QuickExitDoor; stairs?: QuickExitDoor };
```

⚠ **도보 경로와 규칙이 다른 이유**: 도보는 provider 원문 문장을 서버가 재작성하므로 "서버가 문장을 만든다"가 정본이다(CLAUDE.md, 2026-08-07 판정). 여기는 provider가 문장을 주지 않고 **구조화된 값**을 줄 뿐이라, 로케일별 문장은 i18n의 몫이다.

### 5.2 `includeStops`와 무관하게 항상 계산한다

방향 판정에 직전역이 필요한데, 그것은 ODsay `passStopList`에 있고 **`includeStops`는 방출만 통제한다**(provider `toLeg`가 플래그와 무관하게 원본을 갖는다). 따라서 `quickExit`는 옵트인 없이 계산해 항상 싣는다.

이 선택의 실질은 **모든 소비자가 옵트인 파라미터를 추가하지 않고도 값을 받는다**는 것이다(현재 `includeStops=1`을 보내는 소비자는 웹 `DirectionsView` 하나뿐이다).

⚠ **"소비자 코드 변경이 없다"는 뜻이 아니다.** Swift `Codable` 모델에는 필드를 선언해야 값이 들어오고, zod 스키마가 모르는 키를 strip할 수 있다. 각 소비자에 **디코딩부터 최종 문장까지** 통과시키는 계약 테스트를 둔다(§8-6).

⚠ `passStopList`가 모든 소비자의 실제 요청 형태에서 오는지도 게이트로 확인한다(§8-5) — 오지 않으면 웹만 동작하고 나머지는 조용히 침묵한다.

### 5.3 문장

**3분기 × 2형태**로 i18n 키를 나눈다. 변수만 비우는 방식은 `undefined`·중복 쉼표를 노출하고 로케일마다 절 순서가 달라 성립하지 않는다.

| 분기 | ko 예 |
|---|---|
| 둘 다 | `여의도 하차, 엘리베이터 6-4 문, 계단 5-4 문.` |
| 엘리베이터만 | `여의도 하차, 엘리베이터 6-4 문.` |
| 계단만 | `여의도 하차, 계단 5-4 문.` |

`between` 형태는 **별도 조각**이다. `"3-2,3-3 사이"`를 문 번호 자리에 그대로 넣으면 "엘리베이터 3-2,3-3 사이 문"이 되어 문법이 깨진다.

| 형태 | ko 예 |
|---|---|
| `door` | `엘리베이터 6-4 문` |
| `between` | `엘리베이터 3-2 문과 3-3 문 사이` |

**한 줄 = 한 접근성 객체**이므로 시각 강조용 인라인 `<span>`으로 쪼개지 않고 단일 텍스트로 만든다(`joinText` 관례). ⚠ **"빠른 하차" 같은 라벨을 앞에 붙이지 않는다** — 문장이 이미 무엇인지 말한다.

**세션 대기 화면에는 발견 경로를 명시한다.** 이 문장은 국면 전환으로 조용히 나타나므로 열차 목록 **앞**에 두어 목록으로 내려가는 길목에 놓는다(접근성 헌장 §3 "조용히 자동 등장하는 보조 섹션").

⚠ **"대기 국면 진입 시 포커스가 착지한다"는 전제는 웹에서 성립하지 않는다**(a11y 감사 확인 2026-08-08): 세션을 시작하면 트리거 버튼이 unmount되며 커서가 body로 떨어지고, 웹의 `waitingLabel` 포커스는 **목록 항목 소실 복귀** 경로에서만 호출된다. 그래서 이 자리의 근거는 "착지점 다음"이 아니라 **"목록 앞"**이다. iOS는 시트 제시가 커서를 시트로 옮겨 해당 없다. 시작 전이의 포커스 착지 부재는 이 기능이 만든 것이 아닌 **선재 결함**이라 여기서 고치지 않는다(패널 전체의 시작 전이를 다루는 별건).

**통지는 만들지 않는다.** 정적 정보라 상태 변화가 없고 live region은 변화를 알리는 채널이다(상위 스펙 §5.1 "대기 중 자동 낭독은 선택 후에만"과도 정합).

**환승 구간에서 자연히 여러 번 나온다** — 지하철 leg마다 자기 하차역 기준으로 계산되므로 환승역에서도 "어느 칸에 타야 환승이 빠른가"가 답해진다. 별도 처리가 필요 없다. 과한지는 실사용 판정(§8-8).

## 7. 3-state

- **필드 부재 = 정보 없음.** 서울교통공사 밖 노선, 방향 판정 실패(미확정·분기·급행), 미수록 역, 시설 없음이 전부 여기 해당한다.
- **"빠른 하차 정보가 없습니다" 문구를 넣지 않는다.** 서교공 밖 노선에서 매번 울릴 잉여이고 사용자 행동을 바꾸지 않는다([[honesty-disclosures-belong-to-api-layer]]).
- **한쪽 시설만 있으면 있는 것만** 말한다. 없는 시설을 "없음"으로 명시하지 않는다.

**전제 1건 추가 검증(같은 날 닫음)**: `toward`(서교공 표기) ↔ `previousStopName`(ODsay 표기)의 역명 네임스페이스 일치는 §3.4 조인이 증명하지 않는 별개 축이라 따로 쟀다 — 10경로 35개 지하철 leg에서 **불일치 0**. 집합 밖 2건은 단방향 수록 역의 **정방향 접근**(한양대 ←뚝섬, 남위례 ←복정)이라 설계대로 값을 주는 경우다. 역방향 침묵도 실데이터로 확인했다(신당→한양대·매봉→도곡 모두 `quickExit` 부재). 남위례 역방향만 이번에 걸리지 않아 실승차 판정에 남는다.
