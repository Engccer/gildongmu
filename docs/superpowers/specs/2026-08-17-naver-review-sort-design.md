# 리뷰 많은 순 정렬 (네이버 지역검색 `sort=comment`) 설계

2026-08-17 확정. 사용자 피드백 "장소 검색 결과를 리뷰·별점 순으로 보고 싶다"(검색 화면 + 채팅 자연어 둘 다)에 답한다. 조사 결과 **별점 값을 주는 소스는 우리 스택에 없고**, 네이버 지역검색의 리뷰 개수순 정렬만 실재한다. 이 문서는 그 하나를 어떻게 정직하게 노출할지의 계약이다.

## 0. 문제

요청은 "리뷰·별점 순 정렬"이지만 그 둘은 다른 것을 요구한다. **순서**는 지금 얻을 수 있고 **값**(별점 4.5, 리뷰 812개)은 얻을 수 없다. 이 비대칭이 설계 전반을 지배한다 — UI 문구·도구 설명·LLM 프롬프트가 전부 "값이 없다"를 사용자에게 정확히 전달하는 문제로 수렴한다.

시각 사용자는 화면에 별점이 없으면 없는 줄 안다. **낭독만 듣는 사용자에게는 그 부재가 보이지 않으므로**, 값이 없다는 사실 자체를 말로 전해야 한다. 그리고 LLM이 그 공백을 사전지식으로 메우면(→ [[agentic-llm-fabricates-unstated-fields]]) 검증 불가능한 거짓이 낭독된다.

## 1. 실호출 근거 (2026-08-17, 전 provider 실측)

문서가 아니라 **실제 키로 호출해 응답 필드를 직접 확인**했다.

| provider | 평점·리뷰 필드 | 정렬 축 | 판정 |
|---|---|---|---|
| 카카오 로컬 | 없음(11개 필드 전수) | `accuracy`·`distance` | 불가 |
| **네이버 지역검색** | **없음** | `random`·**`comment`(리뷰 개수순)** | **정렬만 가능** |
| Tmap POI | 없음(`desc` 소개글은 있음) | 없음 | 불가 |
| TourAPI KorService2 | 없음(25개 필드 전수) | 없음 | 불가 |

`sort=comment`가 실재하는 축이라는 근거는 **무효값이 거절된다는 것**이다. 200을 주면서 파라미터를 조용히 무시하는 API가 흔하므로(같은 repo의 빠른하차 `_type=json` 무시 선례), 값이 먹혔다는 판정에는 거절 경로 확인이 함께 필요하다.

```
sort=random   1.미도인  2.정희IFC  3.모담어반  4.유주키친  5.트라가
sort=comment  1.진주집  2.블루보틀  3.노티드   4.콘타이   5.호우섬
sort=bogus  → 200 {"errorCode":"SE04","errorMessage":"부적절한 sort값입니다."}
sort=rating → 200 {"errorCode":"SE04", …}
```

⚠ **`comment`는 별점이 아니라 카페·블로그 리뷰 *개수*다.** 맛의 순위가 아니라 화제성의 순위이고, 사용자에게 그렇게 말해야 한다.

### 1.1 제약 3종 (전부 실측)

| 제약 | 실측 | 설계 영향 |
|---|---|---|
| 값 없음 | 응답에 리뷰 수·별점 필드 0 | 행에 실을 수치가 없다 → 순서 자체가 유일한 정보 |
| 5건 상한 | `display=10` → 5로 절단, `start=6` → 무시되고 항상 1페이지 | 페이지네이션·"더 보기" 불가 |
| 좌표 무시 | `x`/`y`를 붙여도 무시. `"맛집"` 단독 질의 → 성심당(대전)·이성당(군산) | 지역명이 **질의 문자열**에 있어야 한다 |

세 번째가 채팅의 핵심 관문이다. "내 주변 맛집 리뷰순"처럼 지명이 없는 발화는 위치를 먼저 확인해 `"길동 맛집"`을 조립해야 한다.

## 2. 결정 — 리뷰순은 병합하지 않는다

`sort=review`면 카카오·네이버 병합 체인을 **통째로 우회**하고 네이버 단독으로 간다.

카카오 결과를 뒤에 이어 붙이지 않는 이유는 건수(5 → 20)가 아니라 **순서의 의미가 사라지기 때문**이다. 6번째부터는 리뷰순이 아닌데 한 목록에 있고, 화면에서는 구분선이 그 경계를 보여주지만 **낭독은 선형이라 경계가 들리지 않는다**. "리뷰순이라고 해서 들었는데 어디부터 아닌지 알 수 없는" 목록은 정렬을 안 한 것보다 나쁘다.

### 2.1 금지 2종

- ⚠ **거리 재정렬 금지.** 기존 병합에는 보강 꼬리를 거리순으로 정렬하는 `orderSupplementTail`이 있다. 리뷰순 결과에 걸면 축이 그 자리에서 파괴된다. 거리는 **표기만** 붙인다(`annotateDistances`, 정렬 없는 주석).
- ⚠ **키 부재 시 정확도순 폴백 금지.** 사용자는 리뷰순이라고 믿고 있으므로 조용한 폴백은 거짓말이다. 에러를 낸다. 실사용 도달은 게이트가 앞에서 0으로 만든다(아래 §3.1).

## 3. 서버 계약

### 3.1 정렬 축

`PlaceSearchParams`에 `sort?: "accuracy" | "review"`를 더한다. **미지정 시 기존 동작과 바이트 동일**이어야 한다(기존 테스트가 그대로 통과하는 것이 그 증거다).

`pickPlacesProvider` 분기 순서:

```
PLACES_PROVIDER 강제 (기존)
  ↓
sort === "review"  →  네이버 단독 (sort=comment, display=5)   ← 신설
  ↓
기존 체인 (en 병합 → en TourAPI → ko 병합 → 카카오 → 네이버 → mock)
```

게이트는 `hasNaverLocalKeys()`다. 키가 없으면 리뷰순 요청은 성립하지 않으므로 **소비자 쪽에서 축 자체를 노출하지 않는다**(웹·iOS 토글 미렌더, 채팅 declaration에서 `sort` 속성 제거). 서버는 그 도달 불가 경로에서 조용히 폴백하지 않고 **throw**한다 — 라우트의 기존 catch가 502로 옮긴다(새 상태 코드·마커를 만들지 않는다. 이것은 커버리지 밖도 지역 미제공도 아니라 **소비자가 부르지 말았어야 할 요청**이다).

`provider` 값은 기존 `"naver-local"`을 그대로 쓴다(새 값 불필요 — 소비자가 "무엇이 답했는가"를 알 수 있으면 충분하다).

### 3.2 라우트

`/api/places`에 `sort: z.enum(["accuracy","review"]).default("accuracy")`. 리뷰순일 때 `limit`은 무시한다(네이버가 5로 캡하므로 상한을 이중으로 두지 않는다).

⚠ 좌표 파라미터는 리뷰순에서도 계속 받는다 — **검색에는 안 쓰이고 거리 표기에만 쓰인다.** 이 비대칭이 의도이며, 좌표가 순위에 영향을 준다고 오해하지 않도록 주석으로 남긴다.

## 4. 웹 계약

### 4.1 배치 — 결과 헤더의 단일 토글

칩 행에 넣지 않는다. 기존 칩(카테고리·지역)은 **이미 받아온 결과를 거르는** 클라이언트 필터라 즉시 반응하고 건수가 고정인데, 리뷰순은 **서버를 다시 불러 결과 집합을 교체**한다. 같은 줄에 두면 같은 자리의 컨트롤이 서로 다르게 동작하는 숨은 규칙이 생긴다.

결과 목록 위 버튼 하나. **라벨이 곧 상태 신호다**: `네이버 리뷰순으로 보기` ↔ `정확도순으로 보기`.

### 4.2 상태·포커스

- 포커스는 토글에 **유지**한다. 재조회 중 `disabled` 금지(포커스가 body로 떨어진다) — `aria-disabled` + 핸들러 가드 + **in-flight ref 가드**(`useRef(false)` + `finally`).
- 건수는 **기존 결과 통지 채널**(`combinedLiveMessage`)을 재사용한다. 새 live region을 만들지 않는다.
- 라벨 변화와 건수 통지는 중복이 아니다: 라벨은 "다음에 무엇을 할 수 있나", 통지는 "지금 몇 곳인가"로 정보가 갈린다.
- URL `?sort=review`를 `replaceState`로 동기화한다(뒤로가기 엔트리를 만들지 않는다 — 정렬 전환은 화면 전환이 아니다).

### 4.3 노출 조건

`dataLocale === "ko"` **그리고** 네이버 키 보유일 때만 렌더한다. 영어 로케일에서 켜면 빈 결과가 되므로 死기능이다.

⚠ 버킷·지역 칩은 그대로 둔다. `bucketsPresent`가 결과에 실존하는 버킷만 칩으로 내므로 5건이면 칩도 자동으로 한두 개가 된다 — **별도 처리를 넣지 않는 것이 결정이다.**

## 5. 채팅 계약

### 5.1 새 도구가 아니라 인자 하나

`search_places` declaration에 `sort`를 더한다(도구 21개로 늘리지 않는다). 설명에 계약 셋을 박는다:

```
sort: "review" — 네이버 카페·블로그 리뷰 '개수'가 많은 순.
  ⚠ 별점·평점·리뷰 수의 '값'은 제공되지 않는다(순서만).
  ⚠ 최대 5곳.
  ⚠ 좌표를 쓰지 않으므로 query에 지역명을 반드시 포함할 것.
```

⚠ `sort` 속성은 **네이버 키가 있을 때만** declaration에 실린다(게이트 패턴 — 키가 없으면 LLM이 호출 자체를 못 한다). 도구 자체의 게이트는 현행 `hasKakaoKey`를 그대로 둔다 — **게이트가 둘로 갈리는 것이 정상이다**: 도구의 존재는 카카오가, 그 도구의 한 인자는 네이버가 정한다. 두 키 중 하나만 있는 상태가 실재하므로 하나로 합치면 死기능이나 호출 불가가 생긴다.

### 5.2 systemInstruction — 최소판 먼저

한 줄만 넣는다: 별점·평점을 요청받으면 그 값이 없음을 밝히고 리뷰 많은 순으로 대체 제안.

⚠ **금지문 덧대기·이중 방어를 미리 넣지 않는다**(미니멀 원칙 — 실측으로 필요가 입증될 때만). `npm run test:ab`로 실제 발화를 재고, 부족하면 그때 보강한다. 판정 축: ①값을 날조하지 않는가 ②리뷰순 호출을 실제로 하는가 ③지명 없는 발화에서 위치를 먼저 확인하는가.

### 5.3 렌더 — 두 묶음, 헤딩으로 구분

렌더 페이로드를 `{ type: "places"; places: Place[]; sort?: "review" }`로 확장한다.

카드가 이미 **렌더 배열**이고 iOS가 렌더마다 헤딩을 자동 생성하므로(`renderHeading`), 두 묶음은 새 구조가 아니라 렌더 2개다. 다만 지금은 둘 다 "장소 N곳"이라 구분이 안 되므로 **렌더가 자기 정렬 축을 알아야 헤딩이 갈린다**:

- `sort === "review"` → `네이버 리뷰순 N곳`
- 그 외 → `장소 N곳`(현행)

⚠ **정렬 축을 렌더에 싣는 것은 데이터 위생이 아니라 접근성 요구다.** 시각적으로는 묶음 사이 공백이 경계를 만들지만 낭독은 선형이라 헤딩이 유일한 경계이고, 데이터에 "무슨 순서인지"가 없으면 그 경계를 만들 재료가 없다.

## 6. iOS 계약

- Kit 렌더 디코딩에 `sort` 미러 + `renderHeading` 분기(웹 §5.3과 동일 문구 축).
- 검색 화면에 웹과 같은 토글 하나. 노출 조건 동일(ko + 키).
- 포커스는 토글에 유지한다. ⚠ `nearbyFocusOnLoad`·`landFirstRowFocus` 계열 **첫 결과 착지 계약은 적용하지 않는다** — 그 계약은 "첫 로드에만 착지"이고 정렬 전환은 사용자가 그 버튼에 커서를 둔 채 일으키는 재조회다(새로고침 버튼과 같은 계열).

## 7. 검증

| 축 | 방법 | 게이트 |
|---|---|---|
| 네이버 계약 | 실호출 — 두 정렬의 순서 차이 + 무효 sort 거절 + 5건 캡 + `start` 무시 | 머지 게이트 |
| 진입점 분기 | 단위 — `sort=review`가 병합을 우회하는가, 거리 재정렬이 **없는가**, 미지정이 기존과 동일한가 | 매 커밋 |
| 라우트 | 단위 — enum 검증, 기본값, 좌표는 표기에만 | 매 커밋 |
| 렌더 헤딩 | 단위 — `sort` 유무로 헤딩이 갈리는가 | 매 커밋 |
| 웹 UI | jsdom 계약 — 라벨 전환, ko/en·키 유무 노출 조건, 재조회 중 포커스 유지 | 매 커밋 |
| 채팅 프롬프트 | `npm run test:ab` 실호출 — §5.2 판정 축 3종 | ship 전 |
| 웹↔Kit | 드리프트 테스트 | 매 커밋 |

⚠ 실호출 게이트의 판정 술어를 헐겁게 두지 않는다(→ [[real-call-gate-weak-predicate]]). "200이 왔다"가 아니라 **"두 정렬의 상위 5건 집합이 다르다" + "무효값이 SE04로 거절된다"**를 함께 본다. 앞의 것만 보면 네이버가 정렬을 무시하고 매번 다른 결과를 주는 경우와 구분되지 않는다.

## 8. 설계 리뷰 게이트 판정

**codex 적대적 설계 리뷰 생략.** 근거: ①새 불변식·판정 계층 신설이 아니라 검증된 기존 계약(네이버 provider·검색 진입점·렌더 헤딩)의 재조합 ②새 외부 통합의 첫 계약 정의가 아님(네이버는 이미 통합돼 있고 파라미터 하나 추가) ③파급이 국소·가역 ④안전·정확성 크리티컬 축이 아님(실보행 안내가 아니다). 잔여 리스크는 구현 단계 리뷰와 §7 게이트가 덮는다.

## 9. 범위 밖

- **CLI/MCP 노출** — 이번 제외. 필요해지면 카탈로그 + `FORMATTERS` 동시 등록(→ [[cli-formatter-registration-gap]]).
- **영어 로케일** — 네이버 지역검색이 한국어 전용이라 구조적으로 불가.
- **리뷰 개수·별점 값 표시** — 소스가 없다. Google Places는 `rating` 요청 시 Enterprise SKU($35/1,000)로 올라가고 한국 리뷰가 얇아 기각(2026-08-17 조사).
- **둘러보기 항목 행 표기** — 백로그로 이관(E22). 검색·채팅 실사용 판정 뒤 착수한다.
