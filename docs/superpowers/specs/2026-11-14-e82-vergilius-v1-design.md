# E82 베르길리우스 첫 판: 설계

2026-11-14 · iOS 실험판 + 서버 · 선행 조사: `docs/research/RESEARCH-2026-11-12-e82-outing-coverage.md`, `RESEARCH-2026-11-12-e82-models-voice.md`, `RESEARCH-2026-11-14-e82-voice-latency.md` · 안내 인계는 `2026-11-14-e83-chat-route-start-design.md`의 시작 함수를 쓴다

## 1. 목표와 성과

목적지 없이 걷는 사람에게 ①지나치는 가게를 빠짐없이 먼저 말해 주고 ②말한 것을 다시 확인할 수 있게 하고 ③말로 물으면 한두 문장으로 답하고 ④답이나 기록에서 버튼 한 번으로 안내로 넘어간다. 나들이(E51)의 따라가는 엔진을 그대로 쓰고 말하는 방식과 묻는 길을 더한다.

**움직일 성과**(실보행으로 확인):
- 가게가 몰린 구간에서 앱이 알고 있던 길가 20m 안 가게가 전부 **말해지거나 기록 목록에 남는다**(10-30 세션 기준 34곳 중 13곳이 둘 다 아니었다). 「말해졌다」의 판정은 V5의 전달 신호다.
- 말한 것을 세션 안에서 다시 확인할 수 있다(지금 0).
- 주변 목록으로 답하는 질문은 질문이 끝난 뒤 답 첫 문장까지 2초 안, 조회가 끼는 질문은 실측해 기록한다.
- 묻는 동안 온 횡단보도 경고가 버려지는 일 0.

**비목표**: 길 안내 중 동작(판정 10), 잠금 중 묻기(판정 11), 실시간 음성 대화, 카메라, 날을 넘기는 기억, 말만으로 안내 시작, 정식판, 웹, 안드로이드.

## 3. 설계 결정

### 3.0 발화 전달 계약 (다른 결정이 딛는 바닥)

지금 발화 구조에는 「이 문장이 실제로 나갔는가」를 알려 주는 신호가 없고, 최신이 이기는 한 칸이 세 겹이다(모델의 미룸 칸, 톤 뒤 칸, 기기 음성 대기 칸). 그 위에서는 「빠짐없이」와 「말한 때 표시」가 성립하지 않으므로 먼저 바닥을 고친다.

| # | 결정 | 근거 |
|---|---|---|
| V0a | 게시부(`post`)는 문장이 **채널에 실렸는지**를 돌려주고, 실린 문장이 말해지기 전에 밀려나면 버려졌다는 신호를 낸다. 「말했다」 = 실렸고 버려지지 않았다 | V5·V10·V25의 시점 정의 |
| V0b | 발화 분류에 둘을 더한다: **답**(행동 문장 아래), **주변**(답 아래. 가게 묶음·도로명). 대기 칸의 서열은 안전(횡단보도·갈림길 예고) > 답 > 주변이고, 위 분류는 아래 분류의 **말하는 중인 문장을 끊는다**. 주변은 누구도 끊지 않는다. 망라 switch의 백그라운드 발화 여부는 답 「말한다(토글 무관)」, 주변 「지금 가게 문장과 같다」 | 판정 13. 지금은 횡단보도와 가게가 같은 분류라 긴 가게 문장이 30m 예고를 늦춘다 |
| V0c | **묻고 답하는 구간**(받아쓰기가 끝난 때부터 답이나 실패 문장이 끝날 때까지)의 발화는 VoiceOver가 켜져 있어도 전부 앱의 기기 음성 한 채널로 낸다. 구간 밖은 지금 규칙 그대로다. 화면 복귀 때 VoiceOver로 넘기는 인계에서 답은 뺀다 | 판정 12. 채널이 둘이면 답과 경고가 겹쳐 들리고, 버튼을 누른 직후의 VoiceOver 통지는 삼켜진다 |
| V0d | 끊긴 가게 묶음과 버려진 가게 묶음은 「말하지 않은 것」으로 되돌아간다(V4의 묶음으로). 끊긴 답은 기록에 남아 있어 다시 듣는다 | V0a의 귀결 |

### 3.1 먼저 말해 주기

| # | 결정 | 근거 |
|---|---|---|
| V1 | 지나침 판정(`OutingPassBy`)은 한 위치 갱신에서 **자격 있는 가게 전부**를 돌려준다. 「가장 가까운 한 곳만 말하고 나머지 영구 침묵」을 없앤다 | 판정 1. 누락 13곳 중 8곳의 원인 |
| V2 | 문장은 앱이 틀로 만든다: 「왼쪽에 A, B. 오른쪽에 C」, 한쪽만이면 「왼쪽에 A, B」. 한 쪽 안의 순서는 가까운 순 | 판정 1·2. 구분자는 쉼표 |
| V3 | 진행 방향을 모를 때 지나친 가게도 말한다: 「옆에 A, B」. **이때의 「지나침」**은 길가 20m 안 가게와의 거리가 줄다가 늘기 시작한 순간이고, 정지 판정 중에는 세지 않는다(서 있는 사람에게 GPS 흔들림으로 가게가 쏟아지지 않게). 상수는 10-30 세션 재생으로 정한다: 방향 상실로 빠진 5곳이 살아나고 정지 구간의 발화가 0 | 판정 3. 지금 판정은 양쪽 방위가 유효해야 해 그대로는 쓸 수 없다. 「앞」은 어느 문장에도 쓰지 않는다 |
| V4 | 아직 말하지 못한 가게는 **모델 한 곳의 묶음**에 가게 id로 쥔다. 새로 지나친 가게는 묶음에 더해진다(덮어쓰지 않고, 같은 id는 한 번만). 묶음은 채널이 빌 때만 문장으로 나가고, 뒤쪽 칸들에 미리 넣어 두지 않는다 | 최신이 이기는 칸에 문장을 넣으면 앞 문장이 사라진다 |
| V5 | 말했다는 표시(`spokenPlaces`)와 기록은 **V0a의 「말했다」가 선 때** 넣는다 | 1회성 경고 전달 계약과 같은 원리 |
| V6 | 묶음이 문장이 될 때 좌우를 **그 순간의 위치와 방향으로 다시 계산**한다. 방향을 모르면 「옆에」다. 40m 넘게 지나온 가게는 말하지 않고 기록 목록에만 남긴다(「○○카페, 지나옴」) | 자리에 묶인 문장은 늦게 말하면 거짓이다 |
| V7 | 한 문장의 가게 수에 상한을 두지 않고 시작한다. 안전 문장이 주변 문장을 끊으므로(V0b) 긴 문장이 경고를 늦추지 않는다. 갈림길 예고와 주변 문장의 간격은 주변 문장의 **끝**에서 잰다. 실보행에서 길어서 못 알아듣겠으면 그때 정한다 | 수치를 근거 없이 정하지 않는다. 판정 항목으로 넘긴다 |
| V8 | 낭독 단계(전부·이정표만·끔)와 횡단보도·갈림길·도로명·걸은 거리·자동 종료·백그라운드 유지는 바꾸지 않는다 | 판정 3(2026-11-12): 엔진은 살린다 |
| V9 | 주변 가게를 받아 오는 양은 확인 호출 결과로 정한다(§8) | 판정 15 |

### 3.2 말한 것의 기록

| # | 결정 | 근거 |
|---|---|---|
| V10 | Kit에 순수 기록 타입을 둔다. 항목은 종류(가게·횡단보도·갈림길·도로명·답)·문장 재료·시각·(가게면) id·좌표·이름. 세션 메모리에만 있고 끝나면 지운다. 디스크 로그에는 질문·답의 글과 좌표를 쓰지 않는다(길이와 종류만) | 판정 4 |
| V11 | 화면: 시트에 「방금 말한 것」 목록, 최신이 위. 한 줄 = 한 객체(예: 「○○카페, 왼쪽, 2분 전」). 목록 제목 하나만 heading이다. 가게 줄에는 동작 「도보 안내 시작」(행 뿌리의 밀기 동작 + 같은 대상의 로터, 기존 장소 행 규칙) | 판정 4·9, E72 규칙 |
| V12 | 최근 50건까지 둔다 | 세션 메모리의 상한 |
| V13 | **안내로 넘기는 길은 함수 하나다**(`acceptOutingReturn`을 일반화): 기다리던 질문 요청을 거둔다 → 베르길리우스를 끝낸다 → `GuideSession.startGuide(to:mode:)` → 시작이 거절되거나 실패하면 그 도착지를 길찾기 탭에 넘긴다. 기록 줄의 버튼(V11), 답 아래 수단 버튼(V21), 제안 버튼(V22)이 전부 이 함수를 지난다. 시작 요청은 호출자가 넘긴다: 기록 줄의 도보 시작은 길찾기 화면의 도보 시작과 같은 기본 요청(`startGuide`), 「출발점으로」는 종전 요청(줄 지정 없음) 그대로다. 시작 호출 수를 세는 가드를 함께 고친다 | 판정 9·10. 세션이 도는 채로 시작하면 「이미 안내 중」으로 거절된다 |

### 3.3 말로 묻기

| # | 결정 | 근거 |
|---|---|---|
| V14 | 시트 맨 앞에 「말로 묻기」 버튼. 받아쓰기는 기존 `SpeechService`(기기 안), 누르는 방식은 받아쓰기 설정을 따른다. 채팅과 같은 AI 동의를 거친 사람에게만 보낸다(동의 전이면 동의 화면) | 판정 11. 새 전송 경로는 동의 게이트를 우회하지 않는다 |
| V15 | 받아쓰기·요청·답의 상태는 시트가 아니라 **모델이 소유**한다(시트를 내려도 이어진다). 세션이 끝나거나 안내로 넘어가면 요청을 거두고, 세대 토큰으로 늦게 온 답과 실패 문장을 버린다 | 시트는 최소화하면 파괴된다 |
| V16 | 질문이 끝나면 대기음 → 서버에 질문 글과 재료를 보낸다 → 답을 기기 음성으로 읽는다(V0c) → 기록에 남긴다. 읽는 것은 **도구 호출이 끼지 않은 마지막 회차의 글**이고 문장이 완결되는 대로 읽기 시작한다 | 판정 6·12. 도구 호출 앞의 군말을 읽지 않는다 |
| V17 | 실패: 질문이 끝난 뒤 8초 안에 읽을 문장이 하나도 오지 않으면 「답을 받지 못했습니다」. 읽기 시작한 뒤 끊기면 「답이 끊겼습니다」. 8초는 조회가 끼는 질문의 실측에 따라 고친다. 답과 실패 문장은 백그라운드 음성 토글과 무관하게 낸다(물어서 나온 것이다) | 판정 6. 침묵과 실패를 가른다 |
| V18 | 앱이 보내는 재료는 앱이 계산한 것뿐이다: 지금 좌표, 방향을 아는지, 주변 가게(id·이름·분류·**구획(앞·옆·지나옴·모름)**·좌우·거리, 가까운 순 최대 30곳), 앞쪽 갈림길(있으면 거리와 갈래 수), 다음 횡단보도까지의 거리, 지금 걷는 길 이름, 최근 기록 20건. **모델에게 주는 글에는 좌표를 넣지 않는다**(좌표는 서버가 id로 찾는다) | 날조 금지. 「내 앞에 뭐가 있어」「직진하면 뭐가 나와」는 구획이 있어야 답한다 |
| V19 | 답의 모양(서버 지침): 한두 문장, 가게는 가까운 순 세 곳까지 이름과 좌우·거리, 수를 세지 않는다, 방향을 모르면 좌우와 「앞」을 말하지 않는다, 지나온 가게를 앞에 있다고 말하지 않는다 | 판정 7 |
| V20 | 주변 목록으로 답할 수 없는 질문(버스 번호, 수단 조합, 목록에 없는 곳까지의 길)은 서버가 기존 채팅 도구를 불러 답한다: 주변 버스·버스 노선·대중교통 경로·도보 경로·자동차 경로·장소 검색 | 판정 7 |
| V21 | 경로 도구가 낸 `route-start` 렌더만 앱에 온다(다른 렌더는 버린다). 앱은 답을 읽은 뒤 E83의 수단 버튼을 답 줄 아래에 보이고, 누르면 V13을 지난다 | 판정 9 |
| V22 | 목록이나 기록에 있는 곳으로 가자는 말에는 서버가 **제안 도구**로 그 가게의 id를 지목한다. 서버는 요청의 가게 id에 있는 값만 통과시킨다. 제안이 오면 앱은 모델의 글을 읽지 않고 **자기 틀 문장** 「○○카페로 안내할까요?」를 읽고 「도보 안내 시작」 버튼을 보인다. 이름이 여러 곳에 걸리면 지목하지 않고 되묻는다. 목록에 있는 곳을 경로 도구로 다시 검색하지 않는다(다른 지점으로 풀린다) | 판정 9. 모델이 좌표와 이름을 만들지 않는다 |
| V23 | 답변 모델은 요청의 `provider`(`openai`·`google`)로 고른다. 실험판 설정에 「답변 모델」 선택지, 처음 값 OpenAI. 서버에 키가 없는 회사는 선택지에 없다 | 판정 8. 게이트 패턴 |
| V24 | 모델 이름은 서버 코드 상수다. 처음 값은 조사에서 고른 OpenAI `gpt-6.1-terra`(추론 끔)와 Google `gemini-3.5-flash-lite`이고, 구현 때 모델 목록 API로 살아 있는지 확인한다 | latency 조사 §2~3 |

### 3.4 소리의 순서

## 4. 서버 계약

`POST /api/vergilius/ask` (NDJSON 스트림, `no-store`)

요청: `{ question, locale, provider, location: {lat,lng}, headingKnown: boolean, places: [{ id, name, category, zone: "ahead"|"beside"|"behind"|"unknown", side: "left"|"right"|"unknown", distance, lat, lng }], junctionAhead: { meters, branches } | null, nextCrosswalkMeters: number|null, roadName: string|null, log: [{ kind, text, agoSeconds, placeId? }] }`

응답 이벤트: `{type:"text", delta, final: boolean}` … `{type:"done", text, renders: RouteStartRenderPayload[], proposal: { placeId } | null}` / `{type:"error", code}`. `final`은 도구 호출이 끼지 않은 회차의 글이라는 표시이고 앱은 그 글만 읽는다. 능력 조회 `GET /api/vergilius/providers` → `{ providers: [...] }`(키가 있는 것만).

- **끝점은 공개 서버에 선다.** 「실험판」은 앱 쪽 봉인일 뿐이므로 서버가 스스로 지킨다: IP당 분당 10회(채팅과 같다), 인스턴스 하루 상한(여정의 예약 방식, 처음 값 300), 한 질문의 도구 왕복 2회, 질문 글 500자. 한국 밖 좌표는 커버리지 마커, 키 없음은 게이트.
- 도구 실행은 기존 채팅 라우터의 실행부를 그대로 부른다. 이 끝점이 실행 컨텍스트를 채운다: `userLocation` = 요청 좌표, `routeStart` 능력 켬, 장소 앵커 없음. **`router.ts`는 고치지 않는다**(도구 선언을 두 회사 형식으로 바꾸는 변환층은 새 파일이다).
- 모델에게 주는 글에는 가게의 id·이름·분류·구획·좌우·거리만 넣는다. 좌표는 서버가 `placeId`로 찾아 쓴다.
- 제안은 종결 도구 `propose_guide({ placeId })`로 받는다. `places[].id`와 `log[].placeId`에 있는 값만 통과시키고, 통과한 제안이 있으면 `done.text`는 비운다(앱이 틀 문장을 읽는다).
- 변환층 테스트 항목: Gemini 생각 서명 보존, 병렬 도구 호출의 짝 맞춤(OpenAI는 호출 id, Gemini는 이름), 스키마 타입 표기 차이.
- 지침 정본은 한 파일이고 두 회사에 같은 지침을 쓴다. 채팅 지침의 「카드로 보인다」 전제는 넣지 않는다.
- `OPENAI_API_KEY`는 서버 전용 env, 게이트 `hasOpenAiKey`. OpenAI 쪽 월 지출 상한은 콘솔에서 건다(위원장).

## 6. 불변식과 테스트

- 좌우 오답 0(나들이 기준 그대로): 좌우는 앱의 판정만 쓴다.
- 길가 20m 안에서 지나친 가게는 전부 말해지거나(V0a의 「말했다」) 기록에 「지나옴」으로 남는다(Kit fixture: 10-30 세션 재생).
- 묶음은 덮어쓰이지 않고, 같은 가게가 두 번 들지 않는다. 끊기거나 버려진 묶음은 되돌아온다(각각 변이를 넣으면 빨개진다).
- 방향을 모르는 지나침은 정지 구간에서 0건이다.
- 안전 문장은 답과 주변 문장을 끊고, 주변 문장은 아무것도 끊지 않는다.
- 받아쓰기 중 온 횡단보도 경고는 풀리는 모든 길(끝남·취소·실패)에서 답보다 먼저 나가고, 두 번 나가지 않는다.
- 안내로 넘기는 호출은 인계 함수 한 곳을 지난다(소스 가드).
- 서버: 없는 `placeId` 제안은 버린다, 모델에게 주는 글에 좌표가 없다, 키 없는 회사는 목록에 없다, 도구 왕복 상한, 하루 상한, 3-state.
- **실호출 표(S5 머지 조건)**: 일곱 질문을 두 모델에 각 5회 보내 첫 문장 시간·전체 시간·답 문장·재료 밖 이름 수·좌우 불일치 수·**지나온 가게를 앞이라 말한 수**를 표로 낸다. 셋 중 하나라도 1건 있으면 그 모델의 그 질문 유형은 열지 않는다.
- 실기기 확인(위원장): 녹음 중 진동(V27), 묻고 답하는 구간의 기기 음성과 VoiceOver 공존(V0c), 화면이 꺼진 채 온 답, 문장 길이(V7), 대기음, 「옆에」 문장의 빈도.

## 8. 확인 호출 (판정 15)

몰린 구간의 한 지점에서 카카오 분류 조회를 상한 없이(페이지를 끝까지) 받아, 지금 받는 양(분류당 15곳)에 들지 못한 가게 중 길가 20m 안에 있는 수를 센다. 결과와 V9의 결론을 여기에 적는다. 좌표와 원자료는 저장소에 두지 않는다.

- 결과(2026-11-14 실행, 10-30 세션 궤적을 50m 간격 10지점으로 다시 밟아 음식점·카페를 3쪽까지, 60회 호출): 반경 500m 안에 음식점 235~307곳, 카페 55~78곳이 있고 첫 15곳에 들지 못한 곳이 음식점 55곳, 카페 48곳이었다. 그중 **걸은 길에서 20m 안은 0곳**, 40m 안은 음식점 1곳이다.
- 결론(V9): 받는 양을 늘리지 않는다. 50m마다 다시 받는 지금 규칙이면 길가 20m 안의 가게는 첫 15곳에 든다. 누락의 원인은 말하는 규칙 쪽이다.
- 한계: 오늘의 카카오 데이터이고(10-30 당시와 다를 수 있다) 조회 지점은 궤적에서 다시 뽑은 것이다. 분류 코드가 없는 업종과 미등록 가게는 이 방법으로 세지 못한다.
