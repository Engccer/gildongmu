# 대중교통 실시간 길 안내 (묶음 B2) 설계

> 2026-08-04. 수단별 진입점 재편(B1)의 마지막 수단. 조사 정본은 `docs/research/RESEARCH-2026-08-03-mode-specific-guidance.md`(이하 "조사", 재조사 금지), 기반 자산은 B1 스펙 `2026-08-03-mode-entrypoints-car-guidance-design.md`와 E4 스펙. 위원장 확정 입력(2026-08-03): 지하철 탑승 열차 특정은 **열차 선택 목록(네이버식)**, 시작 버튼 라벨은 수단 무관 공통 "실시간 길 안내 시작"(B1 §3.1 계약). codex 적대적 리뷰(gpt-5.6-sol·high, 60건) 반영본: 반영 요지는 §11.

## 1. 배경과 목표

도보·자동차 안내는 GPS 경로 추종이지만, 대중교통은 **iOS에서 지하 구간 기기 위치가 사실상 없다**(조사 §3.1, 3사 독립 일치, 착수 금지). 신호 정본은 GPS가 아니라 **공식 실시간 도착 API의 차량·열차 식별자**다. 승객 여정의 네 국면을 안내한다:

1. **승차 대기**: 내가 탈 노선의 차량·열차가 언제 오는가(승차 정류소·역 도착 카운트다운).
2. **탑승 확정**: 무엇에 탔는가(열차 선택 목록·차량 잠금). 이때부터 그 차량만 추적한다.
3. **하차 카운트다운**: 몇 정거장 남았는가(하차 정류소·역 도착 API 폴링, 잠금 식별자 매칭).
4. **하차·전환**: 차량 도착을 관측하면 하차를 안내한다. **다음 구간 전환은 사용자 확인**이다: 차량이 정류소에 도착한 것과 사용자가 내린 것은 다른 사실이고(적대적 리뷰 최상위 지적, E4 "행동 추정 자동 전환 금지"와 정합), 전환 정보는 자동으로 주되 전환 행위는 수동으로 남긴다.

성과 지표: 위원장 실승차에서 ①탄 열차·버스가 뒤차와 섞이지 않고 ②하차 2정거장 전 알림이 실제 하차 판단에 쓸 수 있는 시점에 들리며 ③신호가 없는 구간(비수도권 지하철 등)과 신호 장애가 침묵이 아니라 정직한 상태로 들릴 것.

## 3. 진입점·세션 UI

### 3.1 시작 버튼

- 길찾기 뷰(웹 `DirectionsView`·iOS `DirectionsTabView`) 대중교통 섹션 heading 직후 첫 행, 라벨 `beacon.guideStart`("실시간 길 안내 시작") 재사용.
- **노출 게이트**: ko 데이터 로케일 ∧ 대중교통 경로 조회 성공 ∧ recommended에 탑승 leg ≥ 1(도보 전용 경로 제외). leg별 추적 가능성은 게이트 축이 아니다: 추적 불가 leg는 세션 안에서 정직 상태로 다룬다.
- B1 간략 폴백 게이트("시작 가능 안내 0개")의 계산에 대중교통 시작 가능 여부를 포함한다.

### 3.2 세션 시트·패널

- iOS: 대중교통 전용 시트(`TransitTrackingSheet`). `BeaconTrackingSheet` 재사용 아님(컨트롤 집합이 다르다). heading은 "대중교통 안내" + 목적지. **시트 닫기(스와이프·VO escape) = 세션 중지**(비콘 시트 동형 — 세션은 살아 있는데 UI만 사라지는 상태를 만들지 않는다).
- 웹: DirectionsView 안 대중교통 안내 패널(전용 컴포넌트). 웹 주 사용처가 컴퓨터라 실승차 가치는 낮지만 갭 예방 규칙(신규 도메인 동시 착수)에 따라 같은 마일스톤에 넣는다.
- **앱 백그라운드 전이**(전경 전용 계약의 구체화): 폴링만 정지하고 세션은 유지한다. 복귀 시 즉시 폴 1회 + 상태 통지("안내 재개. {현재 상태}"). 백그라운드 중 통지는 게시하지 않는다(들리지 않는 채널에 쌓지 않는다).
- 컨트롤: 공통(중지·진행 상황·잔여 상시 표시) + 국면별(§5). 시트 포커스 계약은 B1 승계(열릴 때 중지 버튼 착지, 사라지는 컨트롤의 선점 복귀).
- **세션 단일성**: 웹은 `guide-session-store` 공유(claim/release/stopActive). iOS는 현재 `BeaconModel` 단일 인스턴스가 담당하던 단일성을 앱 수준 세션 코디네이터(웹 store 동형의 싱글턴)로 올려 `BeaconModel`(도보·자동차)과 신설 `TransitGuideModel`이 상호 배제한다. **claim은 기존 세션의 동기 stop 완료 후에만 성립**하고, 통지·폴링 커밋은 세션 토큰(세대) 검증을 거친다(늦은 통지가 새 세션 채널에 섞이는 것 차단). 패널 언마운트 전이(필드 편집·스왑·재조회)의 명시 중지 + `beacon.stopped` 통지 계약도 승계.

## 4. 세션 구조와 상태 머신

### 4.1 leg 모델

recommended의 leg 시퀀스에서 **탑승 leg(bus·subway)만 국면 단위**다. 도보 leg는 국면이 아니다:

- 탑승 leg 앞의 도보 leg는 그 leg의 **승차 대기 국면 문맥**으로 흡수("도보 N분 이동 후 {승차 정류소}").
- 마지막 도보 leg는 세션 완료 통지에 병기. 완료 문구는 자기모순 금지: 마지막 도보가 있으면 "대중교통 구간이 끝났습니다. 목적지까지 도보 N분", 없으면 "도착했습니다". 도보 안내(E4)로의 자동 연결은 비범위.

### 4.2 상태 머신 (순수, 웹·Kit 미러)

신설 `src/lib/transit-guide.ts` ↔ `ios/GildongmuKit/Sources/GildongmuKit/TransitGuide.swift`. `route-guide` 리듀서와 별개다: 입력이 GPS fix가 아니라 **폴링 응답·사용자 액션·시각**이고, GuideKind 봉인 구성(walk|car)을 확장하지 않는다. E4 관례대로 공유 fixture(`transit-guide-scenarios.json`)로 웹·Kit 동조를 강제한다.

**상태 축(전부 명시적, 문구·카운터에 분산 금지)**:

- `legIndex` + `phase`: `waiting` | `riding` | `arrived`(도착 관측, 하차 확인 대기) | `done`.
- **신호 상태(배타)**: `tracking`(잠금 대상 관측 중) | `notYetVisible`(정상 미등장: 빈 결과·미커버, 오류 아님) | `signalLost`(관측되다 소실) | `upstreamFailed`(조회 실패: HTTP·봉투 오류·429) | `untrackable`(추적 불가 leg). 데이터 없음과 조회 실패를 절대 뭉개지 않는다(3-state 불변식의 세분).
- 잠금: **복합 키** `{provider, 노선 ID(busRouteId·subwayId), 방향(updnLine 원문), 차량·열차 식별자 원문 문자열}`. 식별자는 숫자 변환·트림 없이 원문 보존, 매칭은 복합 키 전 축 일치.
- `seq`(단조 요청 순번)·`phaseGen`(phase 전이마다 증가). 폴링 응답 커밋 조건: 세션 토큰 ∧ `legIndex` ∧ `phaseGen` ∧ `seq` 최신. **폴링은 세션당 단일 비행**(이전 응답 정착 전 새 요청 금지)이라 역전은 구조적으로 없고, 커밋 조건은 이중 방어다.
- 통지 래치: 사다리(§6.1) 발화 이력. 잔여가 임계를 건너뛰면(4→1) **현재 잔여 하나만** 통지하고 지나간 임계는 소비 처리. 잔여가 증가하면(데이터 정정) 래치를 되돌리지 않고 표시만 갱신.

**전이표**:

| 전이 | 트리거 | 통지 |
|---|---|---|
| 시작 → leg0 waiting | 시작 버튼 | "대중교통 안내 시작. {구간 요약}. {대기 문맥}" |
| waiting → riding | 탑승 확정(§5.1: 목록 활성화 = 탑승 선언) | "{노선} 탑승. 하차: {하차 정류소·역}, {stationCount}개 정거장" |
| riding 카운트다운 | 폴링 결과 잔여 감소 | 사다리(§6.1)에 걸릴 때만 |
| riding → arrived | 잠금 차량·열차의 하차 지점 **도착 관측**: 지하철 `arvlCd` 도착, 버스는 최종 도착 상태(실호출로 확정할 "곧 도착" 이후의 종결 신호. "곧 도착"은 임박 신호이지 도착 확정이 아니다) | "하차 지점에 도착했습니다. 내리신 뒤 '다음 구간'을 눌러 주세요. 다음: {다음 leg 요약}" |
| riding → arrived(추정) | 잠금 식별자 소실 ∧ 직전 잔여 ≤ 1 ∧ 연속 2폴 미등장 | "도착한 것으로 보입니다"(확정과 문구 구분: 3-state). 소실 후 재관측되면 riding으로 복귀(추정은 가역) |
| riding 신호 상태 전이 | tracking↔signalLost↔upstreamFailed↔notYetVisible | 상태가 바뀔 때 1회씩. 실패 통지 시점은 연속 3회 실패 또는 첫 실패 후 90초 중 먼저 |
| arrived → 다음 leg waiting(마지막이면 done) | **사용자 "다음 구간" 버튼**(하차 확인). 전환은 단일 원자 전이: legIndex 증가·잠금 해제·래치 초기화·phaseGen 증가·다음 대기 문맥 통지가 한 리듀서 스텝 | 다음 대기 문맥 |
| riding → waiting(같은 leg) | **"탑승 변경" 버튼**(잘못 잠근 차량 정정): 잠금 해제·phaseGen 증가·대기 목록 복귀 | "탑승을 다시 선택합니다" |
| 추적 불가 leg | untrackable: 폴링 없음, **"이 구간을 마치고 다음 구간으로" 버튼이 유일한 전진**(라벨이 탑승·하차를 뭉개지 않게 행위 전체를 서술) | 진입 시 1회 "이 구간은 실시간 정보가 제공되지 않습니다" |
| 중지 | 중지 버튼·시트 닫기·세션 강탈(단일성) | E4 중지 계약 승계 |

- E4 "행동 추정 자동 전환 금지"와의 정합: waiting→riding(사용자 선언), arrived→다음 leg(사용자 확인)는 사용자 행위이고, riding→arrived는 차량 신호 관측이다. 어떤 전이도 사용자 행동을 추정하지 않는다.

## 5. 국면별 신호·UX

### 5.1 승차 대기 (waiting)

- **서울 버스**: `/api/transit/track`(§7)이 승차 정류소 `getStationByUid`를 그 노선(`busRouteId` = leg `serviceRouteId`, TOPIS ID 직결)으로 필터해 슬롯 1·2(도착 문장 + `vehId`)를 준다. UI는 도착 슬롯 목록: 항목 = 완성 문장, **`vehId` 보유 슬롯만 활성화 가능**. 항목 활성화 = 탑승 선언(라벨을 "…버스에 탑승, 안내 시작" 행위구로 — 정보 열람과 탑승 선언이 낭독에서 구분되게 한다). 오선택은 "탑승 변경" 전이로 정정한다(별도 2단계 확인 대화는 두지 않는다: 마찰 과잉, §11 기각).
- **지방 버스**: TAGO 도착 목록을 노선 번호(`routeno` == leg `lineName`)로 필터해 표시. 차량 식별자가 없으므로 **"탑승" 단일 버튼**으로 확정(근사 추적 시작). 동번호 타노선 혼입 가능성은 수용하고 노선 유형을 병기.
- **지하철(수도권)**: 승차역(정식 표기, §6.3) 도착조회 → **열차 선택 목록**.
  - **노선 필터(필수)**: ODsay 노선명 ↔ `subwayId` **명시 매핑표**(SUBWAY_LINES 역방향, 실호출로 ODsay 표기 확정). `lineHintMatches`는 매핑표 미수록 표기의 폴백일 뿐 1차 수단이 아니다(부분 매칭 오포함 차단).
  - **방향 판정(보조)**: `updnLine` 원문 ↔ leg `serviceWayCode` 매핑 + `trainLineNm` 방면 토큰 ↔ 경유 정류장 두 번째 역명 대조를 결합한 판정기. 2호선 내선/외선 ↔ wayCode 대응은 실호출로 확정한다. **판정 성공 항목이 1건 이상이면 그것만, 0건이면 노선 필터만 적용해 전체 표시**하되 목록 앞에 "방면을 확인해 주세요" 1문장을 병기한다: 오필터로 탈 열차를 숨기는 것이 전부 보여주는 것보다 나쁘고, 각 항목에 방면·행선 원문이 있어 사용자가 판단할 수 있다(선택 주체는 사용자).
  - **종착(단축 운행) 검사**: 행선지(`bstatnNm`)가 경유 정류장 목록 안에서 하차역보다 앞이면 그 열차는 하차역에 가지 않는다. 결정적 판정이므로 항목에 "{종착}행, {하차역}까지 가지 않습니다"를 병기하고 활성화를 막는다.
  - **급행 라벨**: `btrainSttus` 급행이면 "급행: {하차역} 정차 여부를 확인해 주세요"를 병기한다(정차역 패턴 데이터가 없어 결정 판정 불가 — 차단하지 않고 정보로 노출). 급행을 잠갔는데 하차역을 통과하면 하차역 도착 API에 미등장 → `notYetVisible`이 지속되다 소실로 표면화하고, "탑승 변경"으로 정정 가능하다(침묵 사망 경로 없음).
- **늦은 선택 수용**: 폴링에서 사라진 항목도 마지막 관측 후 3분간 목록 하단에 유지하되, **마지막 관측 시각과 당시 문장을 병기**한다("2분 전 관측: 곧 도착"). 승차 직후 1번째 슬롯이 다음 차로 바뀌어 있는 함정(버스)의 대응.
- **대기 중 자동 낭독은 선택(탑승 선언) 후에만**: 선언 전 목록 갱신은 무낭독(진행 상황 버튼이 답한다). 선언 후에는 그 항목의 완성 문장이 바뀔 때만 polite. 최상단 항목 자동 낭독은 하지 않는다(폴마다 다른 열차 문장이 들리는 혼란 차단).
- **목록 포커스 안정**: 항목 정체성은 복합 키(열차·차량 식별자)로 고정하고, 폴링 갱신이 정렬을 바꾸지 않는다(도착 순 정렬은 각 폴 스냅숏 기준이되 기존 항목의 상대 순서 유지). 포커스가 얹힌 항목이 소실되면 목록 heading으로 선점 복귀(헌장 §5).

### 5.2 하차 카운트다운 (riding)

- **서울 버스**: 하차 정류소 기준 `getArrInfoByRoute`(신규 op) 폴링. `vehId1`/`vehId2` 중 잠금 복합 키 일치 슬롯의 `arrmsg`가 카운트다운 정본("6분47초후[4번째 전]").
  - `ord`(하차 정류소의 노선 내 순번)는 `fetchSeoulRouteStops`(86400 캐시)에서 해석하되, **순환·왕복 중복 정류소 대응으로 "승차 정류소 순번보다 큰 것 중 최소"를 택한다**(승차 순번도 같은 시퀀스에서 해석). 해석 실패(하차 정류소 미발견·순서 역전)면 캐시 우회 재조회 1회, 재실패 시 그 leg는 `untrackable` 강등(잘못된 ord로 반대 방향 차량을 읽는 것보다 정직한 포기가 낫다).
- **지방 버스**: 하차 정류소 TAGO 도착 폴링, 노선 번호 필터의 최근접 차량(`arrprevstationcnt`·`arrtime`).
  - **근사의 소비 한계**: 통지 사다리·표시까지만 쓴다. **arrived(도착 관측) 전이의 근거로 쓰지 않는다** — 앞차 기준일 수 있어 조기 하차 안내가 된다. 잔여 1 도달 시 "곧 하차 지점입니다(같은 노선 접근 차량 기준)"까지 통지하고, 전환은 사용자 확인만 남긴다(arrived 없이 riding에서 직접 "다음 구간" 버튼 상시 노출).
  - 근사 기준 차량이 바뀌면(잔여 역행 관측) "다른 차량 기준으로 바뀌었습니다" 통지(조용한 기준 교체 금지).
  - **하차 정류소 해석은 세션 시작 시 1회**: passStopList 좌표로 TAGO A-2 최근접 정류소를 잡아 `nodeId`·`citycode`를 캐시한다(leg `serviceCityCode`는 ODsay 코드라 TAGO에 못 쓴다). **왕복쌍 모호 가드**: 상위 후보 2개가 모두 그 노선을 보유하고 거리 차가 40m 미만이면 반대편 오선택 위험이 판별 불가이므로 그 leg를 `untrackable`로 강등한다(모호하면 추적하지 않는다). ODsay `localStationID` ↔ TAGO `nodeId` 일치가 실호출로 확정되면 직결로 단순화한다.
- **지하철**: 하차역(정식 표기) 도착조회 폴링, `btrainNo` 복합 키 일치 항목의 `arvlMsg2`가 정본, `arvlMsg3`(현재 역)·`arvlCd` 병용.
- **등장 전**: 도착 API는 근접 차량만 담으므로 멀면 미등장(`notYetVisible`)이 정상. 시트는 ODsay `stationCount` 기반 정적 표시("약 N개 정거장")와 **마지막 갱신 시각·신호 상태**를 상시 유지하고, 등장 시 1회 "추적 시작" 통지. 시간 역산은 하지 않는다(§2).

## 6. 통지·낭독 계약 (a11y)

### 6.1 통지 사다리와 채널

- **낭독**: 등장(추적 시작) 1회, 잔여 정거장 {3, 2, 1} 도달, 도착 관측·추정, 국면·구간 전환, 신호 상태 변화(§4.2 시점 규칙). 잔여 > 3의 감소는 낭독하지 않는다(E4 closer 과빈 교훈).
- **채널**: 기본 polite 단일 채널. **자동 통지의 예외 둘만 interrupting(.high)**: 잔여 1(하차 임박)과 도착 관측·추정. 놓친 하차의 회수 비용이 커서 사용자 여정의 직접 응답으로 정당화된다(헌장 §5 "사용자 행동의 응답" 계열 — 탑승 선언에 대한 응답 흐름). 이 판정은 실승차에서 재검증한다(§8). 진행 상황 버튼 응답은 이 예외 계산 밖이다 — 버튼 활성화의 직접 응답이라 .high가 정본(B1 `announceProgress` 관례 승계, 헌장 §5).
- **낡은 통지 폐기(supersede)**: 게시 전 자체 큐에서 코얼레싱한다. 새 카운트다운 통지는 미발화 카운트다운을 대체하고, 도착 통지는 미발화 카운트다운 전부를 폐기한다(빠른 역간에서 3·2·1·도착이 밀려서 연달아 읽히는 것 차단).
- **문맥 병기(M1 개정 2026-08-06, 피드백 #9 "상태 문구 어색")**: 완성 문장 단독으로는 어느 역 기준인지 알 수 없으므로 **라벨 프레임 "{하차 지점}까지, {message}."**로 병치한다(위원장 결정 방향. ⚠ 초안의 프레임어 "도착"은 접근성 감사 HIGH로 교체 — "여의도 도착, 여의도 도착"처럼 라벨과 실제 도착 사건이 낭독에서 구분 불가). 사다리(countdown)·문장 변화(messageChanged)·재관측(backOnTrack) 통지는 프레임만 쓰고, 종전 고정 문맥 문장("{노선}, {하차 지점} 기준.")의 반복 병치는 폐기한다 — 매 통지마다 같은 문맥 문장이 반복되는 것 자체가 어색함의 원인이었다. 노선·하차 전문(全文) 문맥은 추적 시작(trackingStarted)·진행 상황 버튼·상시 표시가 담당한다(`context` 카피는 "{line} 탑승 중, {stop}에서 하차합니다."로 개선, 대기 국면은 `waitContext`). **문법 결합 금지의 정밀화**: 금지는 완성 문장 *원문 내부 변형*이고, 라벨의 전치 병치(프레임)는 허용이다.
- **시트 상시 표시**(live region 밖, 묶음 A 계약 재사용): 현재 구간, 잔여 정거장, 최신 완성 문장, **신호 상태와 마지막 갱신 시각**. 폴링마다 갱신. 무통지 구간(미등장·실패 초기·빈 목록)에도 이 표시가 "안내가 살아 있고 무엇을 기다리는지"를 답한다.
- 사운드·햅틱: E4 8종·3종 재사용(신설 없음). 사다리 = closer 톤, 하차 임박 = 도착 임박 계열, 하차·완료 = 도착 톤, 신호 끊김 = weak 톤. 톤·햅틱은 보조 수단이고 정본은 통지·표시다(E4 계약).

### 6.2 판정용 신호 추출 ≠ 낭독 재조합

낭독은 완성 문장 그대로다. 그러나 사다리 판정에는 잔여 정거장 **수**가 필요하다. 추출 우선순위:

- 지방 버스: 구조 필드 `arrprevstationcnt`(파싱 불요).
- 서울 버스: 구조 필드(`staOrd`−`sectOrd`, 실호출로 필드 존재 확정) 우선, 부재 시 `arrmsg`의 "[N번째 전]" 패턴.
- 지하철: `arvlMsg2`의 "[N]번째 전역" 패턴 + `arvlCd`.
- **추출 실패는 기능 사망이 아니다**: 잔여 수를 모르면 사다리만 비활성(완성 문장 변화 통지로 폴백)하고 문장 표시는 계속한다.

### 6.3 지하철 역명은 정식 표기로 조회한다 (기존 정합 결함 수정 포함)

조사 §1.3 실측: 도착조회는 부역명 포함 정식 표기가 정본이다("천호" → INFO-200 위장, "천호(풍납토성)" 정상). 그런데 **현행 `fetchSubwayArrivals`는 `stripStationDecorations`로 괄호를 벗겨 조회**하므로, seed 정식 표기가 부역명을 가진 역(천호(풍납토성)·군자(능동) 등)은 기존 "내 주변"·역 상세 실시간도 미커버로 위장 실패했을 개연성이 크다. B2에서 함께 고친다:

- 조회명 결정: seed(`matchStationsByName`, lineHint 병용) 매칭이 **역명·노선 모두 확정될 때만** seed `name` 원문(부역명 포함). 미매칭·모호(복수 매칭에 노선 상이)면 입력 원문에서 노선 토큰·"역" 접미만 벗기고 **괄호는 보존**.
- **호환 폴백**: 정식 표기 조회가 INFO-200이면 벗긴 표기로 1회 재조회한다(정식 표기를 안 받는 역이 있어도 기존 동작을 잃지 않는 fail-open — 공용 provider의 의미 변경을 단방향 도박으로 만들지 않는다).
- 표시명은 현행 유지(벗긴 이름). 조회 키와 표시명을 분리한다. 캐시는 원래 no-store라 키 충돌 축이 없다.
- **회귀 행렬이 머지 게이트**: 천호 1건이 아니라 부역명 유·무, 환승역, 동명이역(양평), 광역철도(경의중앙·수인분당) 대표 표본의 실호출 대조 + 기존 nearby 소비자의 대표 역 상태를 고정하는 행동 계약 테스트(스키마 스냅숏은 의미 회귀를 못 잡는다).
- A축 정합 결함이므로 B2 출하에 편승하되 커밋은 분리한다.

ODsay가 주는 역명(`endName` 등)은 부역명이 없으므로, 하차역·승차역 조회 전에 같은 규칙으로 seed 정식 표기를 해석한다.

## 7. 데이터 계약 (API 확장)

- **`/api/route/transit?includeStops=1`**(옵트인, additive): ODsay `passStopList`를 정규화해 탑승 leg에 `stops?: { name, localId?, arsId?, lat, lng }[]`(양 끝 포함)를 싣는다. 미지정 응답 byte-호환(스키마 스냅숏). provider `OdsaySubPath`에 `passStopList` 선언 추가. 추가 upstream 호출 0(같은 응답에 이미 있다).
- **`/api/transit/track`**(신규 폴링 라우트): 요청 `phase=wait|ride` × `mode=seoulBus|tagoBus|subway` + 대상 식별자(zod 형식·범위 검증). 응답은 **판별 union**: `{ mode, status: "ok" | "empty" | "unsupported", items: [...] }` 형태로 provider·상태를 서버가 확정해 내려보내고(클라가 봉투 차이를 해석하지 않는다), upstream 오류는 502다(empty와 절대 뭉개지 않는다). 서울 슬롯(`vehId`·문장·`staOrd`·`sectOrd`), TAGO 항목(잔여·문장 없음), 지하철 항목(`btrainNo`·`updnLine`·`arvlCd`·문장) 각 스키마 명시. 미등장(빈 결과)과 upstream 오류(502)를 절대 뭉개지 않는다.
  - 서울 wait: `getStationByUid(arsId)` + `busRouteId` 필터. 서울 ride: `getArrInfoByRoute(stId, busRouteId, ord)`(ord 규칙은 §5.2). 지방 wait·ride: TAGO `ArvlInfoInqireService` + `routeno` 필터. 지하철은 기존 subway-arrival 확장을 재사용(아래).
  - no-store. `apis.data.go.kr`·`ws.bus.go.kr`는 https + 타임아웃(조사 §1.2 hang 함정).
- **`/api/station/subway-arrival` 확장**(additive): 각 도착 항목에 `trainNo`(btrainNo)·`arrivalCode`(arvlCd) 추가. 기존 소비자 무영향(스냅숏 + §6.3 행동 계약 테스트). 조회명 정식 표기(§6.3)는 이 라우트·nearby 공용.
- **레이트리밋**: 신규 폴링 라우트 IP 60초 20회(폴링 15초 = 분당 4회 + 수동 조작·복귀 버스트 여유. NAT 공유 IP에서 기존 60초 10회 관례가 과도 차단을 만들 수 있어 폴링 라우트만 상향). **429·일시 실패는 즉시 "신호 끊김"이 아니다**: 다음 폴에서 조용히 재시도하고, 통지는 §4.2 시점 규칙(연속 3회 또는 90초)을 따른다.

## 12. M1 증보 — 추적 정보 품질 배선 (2026-08-06, 피드백 라운드1 #1·#9·#10)

> 출처: 위원장 실승차 피드백 라운드1 계획(`docs/superpowers/plans/2026-08-06-realtime-guidance-feedback-r1.md`)과 외부 API 실측(2026-08-06 00:25 KST, 서울 도착 API·열차 위치 API 실호출 대조). 이 절이 §5.2·§6.1·§7의 해당 계약을 개정한다.

### 12.1 recptnDt 신선도 게이트 (피드백 #1)

실측: upstream 데이터는 폴 시점에 이미 15~25초 낡았고(운영사별 편차 극단 — 서울교통공사 16~33초 / 코레일 계열 최대 19분 / 신분당선 미래값 고장), 여기에 폴 주기가 가산돼 체감 1~2분 지연이 됐다. 대응은 셋이며 전부 **게이트**다(문서식 barvlDt 보정 금지 — 신분당선은 recptnDt 동결 + arvlMsg2 정상 갱신이라 보정이 역방향이 된다):

- **투영**: provider가 `recptnDt` 원문을 `SubwayArrival.receivedAt`으로 싣고, track 서비스가 서버 시각 기준 lag를 계산해 `TrackItem.dataStamp`(원문 문자열)·`dataAgeSeconds`(정수 초)로 내려보낸다. KST 명시 오프셋(+09:00)으로 파싱한다(서버 TZ 무관).
- **게이트 ⓐ**: lag < 0(신분당선 미래값 고장)은 0으로 클램프.
- **게이트 ⓑ**: lag > 120초 ∧ 종착 상태(arvlCd ∈ {1, 2, 5})는 동결 레코드 — `dataAgeSeconds`를 null(판정 불가)로 강등한다. 화면은 null이면 신선도를 표기하지 않는다(틀린 정밀 주장 금지). 미제공(버스)도 null — 소비자 행동이 같아 구분하지 않는다.
- **게이트 ⓒ**: 낭독 정본은 `arvlMsg2` 유지. `barvlDt` 재환산·보정 금지(§2 재조합 금지의 재확인).
- **동일 스냅숏 무정보 폴(재발화 차단)**: 잠금 항목의 `dataStamp`가 직전 커밋과 동일하고 **완성 문장도 동일**하면 그 폴은 "새 정보 없음"이다 — 상태 머신은 lastSeq·pollCount·lastUpdatedAt·dataAgeSeconds·**missCount 리셋**만 기록하고 어떤 이벤트도 내지 않으며 phase·signal도 바꾸지 않는다(동결 레코드의 재등장이 backOnTrack·signalRecovered로 낡은 문장을 재발화하는 경로 차단). ⚠ 문장 동일 조건이 필수다: 신분당선은 stamp가 동결된 채 문장이 정상 갱신되므로 stamp만으로 억제하면 사다리가 죽는다. ⚠ **무정보여도 매칭은 매칭이다** — 연속 미등장 카운터(missCount)는 끊는다. 안 끊으면 미등장↔동결재등장 반복(분기역 근접)에서 §4.2의 "N연속" 계약보다 빨리 signalLost·도착 추정이 오발화된다(독립 리뷰 MAJOR).
- **stamp 동결 감지(나이의 거짓 정밀 차단)**: 같은 stamp인데 문장이 갱신된 커밋은 recptnDt가 고장난 것(신분당선형) — 그 항목의 `dataAgeSeconds`는 null로 강등한다. 코레일 계열의 진짜 지연(stamp 전진 + 큰 lag)은 원값을 유지한다(정직한 큰 수치가 은폐보다 낫다).

### 12.2 arvlCd·arvlMsg3 병용 (피드백 #10)

M3 경유역 탑승 위치 표시가 state.currentLocation을 재사용한다.

### 12.3 상태 문구 조립 계약 (피드백 #9)

- **원인**: 통지 조립기(완성 문장을 공백 연결)와 화면 조립기(`joinText` 쉼표 연결)가 같은 문자열(`context` = "…기준.")을 공유해 "기준., " 이중 구두점이 났고, iOS 상시 표시만 `stationCountAbout` 폴백·`lastUpdated`(§6.1 상시 표시 요구)를 누락하는 드리프트가 있었다.

- 통지 문구 개정: §6.1 문맥 병기(M1 개정) 참조. `context` 카피는 "{line} 탑승 중, {stop}에서 하차합니다.".

## 13. M2 증보 — 대기 국면 탈출구·계측 (2026-08-06, 피드백 라운드1 #4·#2)

> 출처: 피드백 라운드1 계획 M2. 실승차에서 승차 대기 국면이 "탑승 대기"에 고정된 채 탈출구가 없었고(#4, 원인 후보 6경로 — 계측 필요), 탑승 변경에 취소 전이가 없어 오탭 시 복귀 불가였다(#2). 이 절이 §4.2·§5.1의 해당 계약을 증보한다.

### 13.1 탑승 변경 취소 — A안 (피드백 #2)

- **상태 축**: `previousLock`(직전 잠금)을 상태 머신이 보존한다 — `changeBoarding`이 현재 `lock`을 `previousLock`으로 옮기고, `board`·`advance`가 소거한다. 오케스트레이터 재구현 금지(웹·iOS 드리프트 축이라 머신 소유).
- **취소 전이 = `board(previousLock)` 재사용**: 별도 입력을 신설하지 않는다. waiting ∧ `previousLock` 보유 시 "탑승 변경 취소" 버튼을 노출하고, 활성화가 `previousLock`으로 재탑승한다(추적 상태는 초기화 후 재수렴 — 잠금 식별자가 같으므로 다음 폴에서 즉시 재관측된다).
- **§5.1 3분 유지 버퍼 복원**: `changeBoarding`의 소실 항목 버퍼(retained) 소거를 제거한다. 종전 구현이 스스로 버퍼를 비워 "폴링에서 사라진 항목도 3분간 유지"(§5.1 늦은 선택 수용)가 탑승 변경 직후에만 죽어 있었다 — 잘못 잠근 채 이동한 뒤 돌아온 목록에서 원래 열차가 사라지는 바로 그 경로였다. `advance`의 소거는 유지한다(다음 leg는 다른 정류소·역이라 버퍼가 무의미).

### 13.2 대기 국면 탈출구 (피드백 #4)

waiting에서 사용자가 상황을 움직일 수단이 없었다(자동 폴 대기뿐). 둘을 추가한다:

- **새로고침**: 즉시 1폴. 폴 완료 시 결과를 **직접 응답으로 통지**한다(버튼 활성화의 직접 응답이라 iOS는 .high — `announceProgress` 관례). §5.1 "선언 전 목록 갱신은 무낭독"의 예외가 아니다 — 자동 갱신이 아니라 사용자 요청의 응답이다. 응답 계약 셋(접근성 감사 반영 2026-08-06): ①응답은 "탑승 후보 {count}개."(0 포함)이고 **조회 실패·미지원만 사유 문장**이다 — 조회가 실행되지 않았는데 "0개"라고 말하면 3-state 위반이고, 반대로 0건의 *왜*(사유 문장)는 목록 자리 지속 문장이 담당한다(같은 문장을 통지·화면 두 곳에 남기지 않는다 — 감사 M4, 헌장 §5 복제 금지 계열) ②응답 게시는 같은 폴의 상태 머신 이벤트 통지 **뒤**다 — 웹은 배칭의 마지막 승자, iOS는 .high의 큐 절단으로 응답이 최종 발화가 된다(역순이면 응답이 페인트 없이 사라지거나 동어반복 두 문장이 나간다 — 감사 M1) ③조기 unsupported(폴 URL 불성립·해석 실패 캐시)와 fetch 예외 경로에서도 응답을 침묵시키지 않고 플래그를 반드시 소비한다(누수 시 이후 자동 폴이 발화 — 감사 HIGH).
- **"이미 탑승했습니다" — 근사 잠금의 일반화**: 열차·차량을 특정하지 못한 채 이미 탑승한 사용자(#4의 실제 상황)를 위해, tagoBus 근사 계약(§5.2)을 seoulBus·subway로 확장한다. `vehicleId: ""`가 근사 잠금의 판별자다(`isApproxTransitLock`).
  - **매칭**: 하차 지점 도착 목록에서 방향 일치(양측 보유 시 — 지하철은 wayCode ↔ 상행·하행, 판정 불가 표기는 무필터) 항목 중 잔여 최소. tagoBus의 기존 최근접 로직과 단일 구현.
  - **근사의 소비 한계(§5.2)를 그대로 상속**: arrived 전이 금지(관측·추정 모두 — 식별자가 없어 도착 확정이 불가능), advance 상시 노출, 기준 차량 교체(잔여 역행) 통지, 근사 주석 병기. 주석·advance 노출의 판별자는 leg 유형이 아니라 **잠금의 근사 여부**다(tagoBus는 항상 근사라 행동 불변).
- 두 버튼 모두 waiting 전용이다. 근사 잠금 후에도 "탑승 변경"으로 목록 복귀가 가능하다(정정 경로 유지).

### 13.3 0건 사유 3-state (화면·통지)

"도착 예정 차량이 아직 없습니다" 한 문장이 서로 다른 세 상태를 뭉개고 있었다(#4 원인 후보 ①②⑤가 화면에서 구분 불가). 구분한다:

- **서버**: `/api/transit/track` 응답에 `rawCount`(노선·경로 필터 **전** 원시 건수)를 additive로 싣는다(ok·empty 공통). 판별 union 자체는 불변 — empty ∧ rawCount > 0 = "필터 전멸"(그 정류소·역에 도착은 있는데 이 노선이 아니다)을 클라가 판정할 수 있게 하는 최소 투영이다.
- **화면(waiting 목록 영역)**: 후보 0건일 때 사유를 가른다 — ⓐ 진짜 0건(empty ∧ rawCount 0): 현행 "도착 예정 차량이 아직 없습니다" ⓑ 필터 전멸(empty ∧ rawCount > 0): "이 노선이 아닌 차량만 조회되고 있습니다" ⓒ 조회 실패·미지원: "실시간 목록을 조회하지 못했습니다". 신호 상태 상시 표시(§6.1)와 별개로 목록 자리에서 답한다(사용자 시선이 목록에 있다).
- **통지**: 자동 폴은 여전히 무낭독(§5.1). 새로고침 응답은 후보 수로 답하고(실패·미지원만 사유 문장, 13.2 ①), 사유 문장 자체는 목록 자리에만 남는다.
- 0건 사유(즉시 반영)와 신호 상태 상시 표시(3회·90초 래치, §4.2)는 같은 실패를 다른 시점에 반영하는 **별개 표면**이다 — 첫 실패 직후 최대 90초간 목록 자리는 "조회 실패", 상시 표시는 "차량 접근 대기"로 갈릴 수 있다. 목록 자리 문장이 그 폴의 진실이고 래치는 일시 실패의 소음 억제 계약이라 의도된 비대칭이다(감사 L1 기각 근거 — 래치를 즉시 반영으로 바꾸면 §4.2 통지 시점 규칙이 무너진다).

### 13.4 목록 포커스 소실 복귀 (§5.1 미구현분)

폴링 갱신으로 포커스가 얹힌 항목이 소실되면 **목록 라벨("탑승할 차량을 선택하세요")로 선점 복귀**한다(헌장 §5 — body 이탈 방치 금지). 웹은 목록 focus-within 추적 + 갱신 후 activeElement가 body로 떨어졌을 때만 복귀(무관 포커스 강탈 금지), iOS는 항목 정체성 옵셔널 바인딩의 소실 감지 + **정본 시퀀스 전체**(가시화 scrollTo → 지연 → 대입 → 검증 → 1회 재시도 — 동기 대입 한 줄은 List AX 컬링에 조용히 되돌아간다, 감사 M3. 계측 로그는 시도가 아니라 착지 결과를 남긴다).

- **항목 키**: vehId, 없으면 **슬롯 위치 폴백**(`slot-{index}`) — 완성 문장 폴백은 문장 갱신마다 remount를 만들어 커서가 폴마다 튕긴다(감사 L2, §5.1 "폴링 갱신이 포커스를 흔들지 않는다"의 역행). 웹·iOS 동형.
- **탑승 계열 전이(waiting→riding)의 선점**: 후보 탑승·"이미 탑승"·"탑승 변경 취소"는 누르는 순간 자신을 포함한 대기 UI 전체를 제거한다 — riding 컨트롤(근사 잠금이면 "다음 구간", 아니면 "탑승 변경")로 선점 이동한다(헌장 §5, 감사 M2. arrived 진입 선점과 대칭). ⚠ arrived→riding 자동 복귀(backOnTrack)는 사용자 행동이 아니라 선점하지 않는다(강탈 금지).

### 13.5 실험판 계측 (#4 원인 확정)

- iOS `#if DEBUG || EXPERIMENTAL` 전용 파일 로그 `TransitGuideDiag`(ChatFocusDiag 선례 — Documents/transit-guide-diag.log, 2MB 롤오버). ⚠ Experimental 구성은 DEBUG를 정의하지 않으므로 게이트에 EXPERIMENTAL 명시가 필수다.

## 14. M3 증보 — 경유역 목록·도보 핸드오프 (2026-08-06, 피드백 라운드1 #3·#6)

### 14.1 경유역 목록 1단계 (피드백 #3)

`viaStops`(§4.1 기보유 — 추가 upstream 호출 0회)를 disclosure로 정적 표시한다. 웹은 `aria-expanded` 버튼, iOS는 `DisclosureGroup`(펼침 시맨틱 정본 — 시뮬 무라벨 셰브런은 아티팩트). 레퍼런스는 카카오지하철 경유역 UX(위원장 캡처).

- **항목은 무헤딩·단일 텍스트**(도착편 관례): "이름, 승차|하차|현재 위치"를 쉼표로 흡수(joinText). 양 끝(첫·마지막)이 승차·하차이고, 현재 위치는 §12.2의 `state.currentLocation`(arvlMsg3)을 `viaStopCurrentIndex`(웹·Kit 미러, 정규화는 종착 검사 `normalizeStopName` 공용)로 매칭 — 지하철 잠금 추적에서만 성립하고 미매칭·버스는 무표기가 정답(3-state).
- **단계 공개(더 보기·RevealWindow) 비적용 판정**: 항목이 인터랙티브하지 않은 정적 텍스트라 절단 너머 항목이 행동을 바꾸지 않고(교통 목록 비적용 판정 동형), disclosure 펼침 자체가 사용자의 명시 행동이다.
- leg 전환 시 disclosure는 접힌다(다음 구간의 목록은 다른 목록 — 낡은 펼침 상태 이월 금지).
- 2단계(역별 장소 상세 링크)는 1단계 실사용 판정 후(계획 보류 유지).

### 14.2 대중교통 완료 → 도보 핸드오프 A안 (피드백 #6, §4.1 비범위 개정)

§4.1의 "도보 안내 **자동** 연결 비범위"는 유지하되(B안 기각 근거: 지하 역사 GPS 공백 — 하차 직후 fix가 없거나 크게 튄다), **제안형(A안)**을 추가한다: done 전이 시 말미 도보(`walkAfterMinutes`)가 있으면 "남은 도보 안내 시작" 버튼을 노출하고 포커스를 선점한다(사라진 "다음 구간" 버튼의 커서를 다음 행동으로 — 헌장 §5).

- **iOS**: done의 `stop()`이 세션 상태를 소거하므로 모델 `pendingWalkHandoff`(목적지 라벨·도보 분)를 stop() **뒤에** 보존한다(stop()이 이 값까지 지우는 단일 소거 경로라 순서 필수). 시트 presentation을 `isTracking ∨ pendingWalkHandoff`로 확장 — 닫기(스와이프·escape·닫기 버튼)는 제안 소거. 수락 시 시트 dismiss 후 600ms 지연을 두고 `beacon.toggle(dest: tracked.dest, kind: .walk)`(같은 계층 두 시트의 단일 presentation 제약). 목적지 변경은 제안도 무효(무통지 소거 — 시트가 닫힌 상태에선 도달 불가 경로지만 방어).
- **웹**: 훅이 `doneHandoff`를 남기고(다음 시작에서 소거) 패널이 `DistanceBeacon(kind walk, startOnOpen, focusTriggerOnMount)`을 마운트한다 — 세션 스토어 단일성이 상호 배제를 그대로 담당.
- **게이트 없음**: 세션 자체가 `realtimeGuidanceEnabled ∧ ko` 게이트 안에서만 존재하므로 추가 게이트가 잉여다. 도보 경로 실패는 기존 `fallbackToBrief`가 흡수.
- **상태 머신 무변경**: done 의미(§4.2)·fixture 불변. 핸드오프는 오케스트레이터 계층의 세션 밖 수명이다.
