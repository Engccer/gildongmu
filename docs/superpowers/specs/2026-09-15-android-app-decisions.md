### D1. 개인 개발자 계정

**판정**: 개인(personal) 계정으로 등록한다.

**따라오는 의무**: 2023-11-13 이후 생성된 개인 계정이므로 **12명 이상의 테스터가 14일 연속 비공개 테스트에 참여**해야 프로덕션 출시를 신청할 수 있다. 앱 단위로 적용된다. 추가로 Play Console 모바일 앱을 통한 실기기 접근 인증이 요구된다.

**기각된 대안**: 조직(organization) 계정. D-U-N-S 번호로 등록하면 위 12명 요건 범위 밖이 되지만, 단체 명의 계정은 소유권이 단체에 귀속된다. 길동무를 개인 프로젝트로 유지한다는 판단이 앞선다.

---

### D2. 안드로이드 네이티브

**판정**: Kotlin 네이티브 앱으로 만든다.

**기각된 대안 ①: TWA(웹 래퍼)**. 구글이 공식 지원하는 경로이고 요건도 이미 갖춰져 있었다(manifest·아이콘 192/512·maskable·서비스워커 전부 충족, `assetlinks.json` 하나만 부족). 며칠이면 출시 가능했다. 그럼에도 기각한 이유는 D3(실시간 안내 포함)과 양립하지 않기 때문이다. 웹이 못 하는 것은 웹 래퍼도 못 한다.

⚠ **이 기각은 "TWA가 나쁘다"가 아니다.** 요건이 이미 충족돼 있다는 사실은 유효하므로, 만약 일정이 급해져 "일단 뭐라도 올려야 한다"는 상황이 오면 이 선택지는 며칠 거리에 그대로 남아 있다. 되살릴 때 확인할 것은 `assetlinks.json`과 Lighthouse 점수 두 가지뿐이다.

**기각된 대안 ②: Flutter / React Native**. 로직 미러 대상이 하나 더 느는 데다, 접근성이 프레임워크의 접근성 구현에 종속된다. 길동무는 접근성이 단일 최고 가치라 중간 계층을 두지 않는다.

### D3. 기능 등가, 실시간 안내 1차 포함

**판정**: iOS와 최대한 등가. 실시간 안내를 1차 출시에 포함한다.

**기각된 대안**: 실시간 안내를 2차로 미루고 검색·장소·길찾기·내 주변·채팅만 먼저 출시. 기간은 크게 짧아지지만 위원장이 완전 등가를 택했다.

**파급**: 개발 기간이 수개월 단위가 된다. 그리고 **실보행 검증이 필요해져 일반 안드로이드 폰이 M4의 블로킹 조건이 된다**(O1 참조).

### D4. 로직 공유: 세 번째 미러 + 공유 fixture

**판정**: 순수 로직을 웹(TS)·iOS(Swift)·안드로이드(Kotlin) 세 벌로 두고, 같은 fixture JSON을 세 곳에서 모두 돌려 어긋나면 빌드가 깨지게 한다.

**근거**:
1. 웹과 iOS 사이에서 **이미 작동 중인 방식**이라 새로 증명할 것이 없다.
2. `GildongmuKit/Sources` 90파일 11,820줄 중 **89개가 `import Foundation`만** 쓴다. 플랫폼 의존이 없어 Kotlin 이식이 기계적이다.
3. iOS를 한 줄도 건드리지 않는다. 심사 통과하고 실사용 중인 코드를 흔들지 않는다.

**기각된 대안 ①: KMP(Kotlin Multiplatform)로 로직 단일화**. 2026년 기준 프로덕션 준비 단계이고 "로직 한 벌"이라는 목표에는 정공법이다. 기각 이유는 두 가지다. 검증된 iOS 앱의 로직 계층을 전면 수술해야 하고, 웹 TypeScript는 여전히 별개로 남아 결국 두 벌이 된다. 얻는 것이 반쪽인데 위험은 전부다.

⚠ **이 기각은 조건부다.** 만약 장래에 웹을 접거나, iOS를 대규모로 재작성할 일이 생기면 전제가 바뀐다. 그때 재검토한다.

**기각된 대안 ②: 정본 하나에서 나머지 언어를 코드 생성**. 생성기 자체가 별도의 큰 프로젝트가 되고, 생성기가 틀리면 세 플랫폼이 동시에 틀린다. YAGNI.

### D5. 네 계층 구조

**판정**:

```
[1] 서버 라우트 38개       이미 있음. 안드로이드가 그대로 호출. 작업 0
[2] 순수 로직(판정 규칙)    웹 TS ↔ Swift ↔ Kotlin 세 벌. 공유 fixture가 동조 강제
[3] 플랫폼 서비스          위치·음성·TTS·소리·진동·걸음수. 각자 구현, 같은 인터페이스
[4] 화면(Compose)          SwiftUI 75파일에 대응. 새로 작성
```

**[2]와 [3]의 경계가 이 설계의 핵심이다.** [2]는 "무엇을 언제 할지 정하는 곳", [3]은 "실제로 하는 곳"이다.

**경계의 실례**(iOS에 이미 존재):
- `GildongmuKit/Sources/GildongmuKit/GuideSpeechGate.swift`의 `speechDeferStep(now:toneEndsAt:)`는 시각 두 개를 받아 "몇 초 미룰지" 숫자 하나를 반환한다. 오디오 API를 모른다. → **[2], Kotlin으로 이식**
- `Gildongmu/TtsPlayer.swift`는 `UIKit`·`AudioToolbox`·`Accessibility`를 쓴다. → **[3], 이식하지 않고 안드로이드 방식으로 새로 작성**

**이 경계가 지켜지면 iOS 업데이트의 대부분이 [2]에서 일어나므로, 안드로이드는 [2]만 따라가면 된다.**

**규모 실측**(2026-09-15):

| 계층 | iOS 규모 |
|---|---|
| [2] Kit Sources | 90파일 11,820줄 |
| Kit Tests | 78파일 11,612줄 |
| [3]+[4] 앱 | 75파일 21,021줄 |
| 웹 `src/lib` (같은 로직의 TS 판) | 201파일 29,017줄 |

### D6. 동조 강제 장치 3종

**장치 1. 공유 fixture (이미 있음, 소비자를 3으로 늘림)**

`src/lib/__tests__/fixtures/*.json`에 시나리오와 정답이 있다. 현재 웹과 iOS가 함께 읽는다. 안드로이드가 세 번째 응시자로 들어간다. 한 곳만 고치면 나머지 두 곳이 같은 시험에서 틀린다.

**장치 2. 미러 등록부 (새로 만듦)**

fixture가 없는 미러(문구 조립, 표 매핑)를 위해 "이 파일들은 한 몸"이라고 적은 목록을 두고 한쪽만 바뀌면 경고한다. 기존 `format-drift.test.ts`(웹↔Kit 거리 표기 대조) 방식을 세 벌로 넓힌다.

**장치 3. 기능 대조표 (문서 + 릴리스 절차)**

⚠ **장치 1, 2가 잡지 못하는 구멍이 있다.** iOS에 새 화면이 생겼는데 안드로이드에 안 만들면, 시험은 전부 통과하는데 기능만 없다. 이건 자동화가 아니라 규율로 막는다.

- iOS 화면과 안드로이드 화면의 1대1 대조표를 문서로 둔다.
- `ios-release-submit` 스킬의 "직전 아카이브 이후 커밋 재판정" 단계에 **"이 변경이 안드로이드에도 필요한가"** 한 줄을 붙인다.

### D7. 접근성 이중 1급

**판정**: 일반 폰 TalkBack 터치와 점자 단말기 키보드 탐색을 **동등하게** 1급으로 둔다.

**근거**: 길동무 주 사용자층이 시각장애인이고, 국내에서는 한소네 계열 점자 단말기 사용자 비중이 크다. iOS에는 없던 갈래다(아이폰은 사실상 VoiceOver 터치 하나).

**구현 원칙**: 터치와 키보드는 다른 기능이 아니라 **같은 접근성 트리의 두 입구**다. 별도 화면을 만들지 않고 세 가지를 지킨다.
1. 조작 가능한 모든 요소가 포커스를 받는다(터치만 되고 키보드로 못 가는 요소 0).
2. 포커스 이동 순서가 의미 순서와 같다.
3. "한 줄 = 한 접근성 객체"를 지킨다. iOS `joinText`에 대응하는 것은 Compose `Modifier.semantics(mergeDescendants = true)`.

**한소네에서의 낭독 엔진은 확인 불요 사항이다.** 한소네 자체 엔진이든 TalkBack이든 안드로이드 표준 접근성 API(`AccessibilityNodeInfo`)를 읽으므로, 표준을 제대로 채우면 어느 쪽이든 동작한다. 웹에서 NVDA와 VoiceOver가 같은 HTML을 읽는 것과 같은 구조다.

### D8. minSdk 31 (Android 12) / targetSdk 36 (Android 16)

**판정**: minSdk 31, targetSdk 36.

**minSdk 31의 근거 (위원장 당사자 정보)**: **한소네 6이 V2.0 업데이트로 Android 12다.** 한소네 7은 2026년 9월 출시됐으나 아직 배포 전이고 위원장은 베타테스터로 사용 중이다. **많은 사용자가 여전히 한소네 6을 쓴다.** 한소네 6을 지원 대상에서 빼면 주 사용자층의 상당수를 잃는다.

⚠ **초안에서 제시했다가 철회한 근거**: "TalkBack의 점자 디스플레이 지원이 Android 13부터이므로 minSdk 33" 논거는 **한소네에 해당하지 않는다**. 그 기능은 "일반 폰에 외부 점자 디스플레이를 붙이는" 경로이고, 한소네는 점자 디스플레이가 내장된 기기로 자체 엔진을 쓴다. 이 논거를 되살리지 말 것.

**targetSdk 36의 근거**: 2026-08-31부터 신규 앱은 Android 16(API 36) 이상을 대상으로 해야 Google Play에 제출할 수 있다. 이 날짜는 이미 지났다. 선택의 여지가 없다.

**minSdk 31 + targetSdk 36 조합은 정상이며 런타임 분기로 처리한다.**

### D9. 받아쓰기는 API 33 게이트

**판정**: 온디바이스 받아쓰기(`createOnDeviceSpeechRecognizer()`, API 33+)가 가능한 기기에서만 받아쓰기 기능을 노출한다. **Android 12에서는 버튼 자체를 만들지 않는다.**

**따라서 한소네 6에서는 받아쓰기를 쓸 수 없다. 한소네 7(Android 15)에서는 정상 동작한다.**

**기각된 대안: 서버 STT(Deepgram `/api/speech-to-text`)로 우회**. 웹판이 이미 쓰는 경로라 기술적으로는 즉시 가능하다. 기각 이유는 셋이다.
1. 개인정보 3자 일치가 깨진다. iOS는 온디바이스라 "오디오 미수집"으로 신고했는데, 안드로이드만 서버 전송이면 신고 내용이 갈린다.
2. 없는 기능을 가짜로 메우지 않는다는 3-state 원칙에 어긋난다.
3. **점자 단말기는 물리 점자 키보드가 있어 받아쓰기 의존도가 가장 낮다.** 하필 손실이 가장 작은 기능이라는 점이 이 기각을 지지한다.

**게이트 패턴은 길동무 관용구 그대로다**: 조건 미충족이면 버튼·섹션·import 전부 0.

### D10. 오디오는 번역하지 않고 재설계

**판정**: iOS 오디오 세션 코드를 Kotlin으로 옮기지 않는다. 안드로이드는 오디오 포커스(AudioFocus) 기반으로 **같은 목표를 다른 수단으로** 달성한다.

**근거**: iOS 오디오 코드에 쌓인 계약(세션 카테고리 전환, 소유권 이전 `.ownershipTransferred`, 잘림 방지 지연 `endSession()`)은 **iOS 고유의 문제를 푼 것**이다. 안드로이드에는 그 문제가 없다. 번역하면 존재하지 않는 문제에 대한 방어 코드를 옮기게 된다.

**단, 판정은 공유한다.** `speechDeferStep`(톤이 0.6초 이상 남았으면 발화를 미룬다)은 [2]라서 Kotlin으로 이식하고, 실제로 미뤘다가 재생하는 부분만 [3]에서 안드로이드 방식으로 쓴다.

**플랫폼 서비스 대응표**:

| 기능 | iOS | 안드로이드 |
|---|---|---|
| 위치 | CoreLocation | FusedLocationProvider |
| 받아쓰기 | SFSpeechRecognizer (온디바이스 강제) | `createOnDeviceSpeechRecognizer()` (API 33+) |
| 음성 출력 | AVSpeechSynthesizer | TextToSpeech |
| 안내음 | AVAudioPlayer + 세션 카테고리 | SoundPool + AudioFocus |
| 진동 | UIFeedbackGenerator 3종 | VibrationEffect (3종 대응 유지) |
| 걸음 수 | CMPedometer | Step Counter 센서 (`ACTIVITY_RECOGNITION`) |
| 화면 유지 | idleTimerDisabled | FLAG_KEEP_SCREEN_ON |

### D11. 전경 서비스 + 지속 알림

**판정**: 실시간 안내는 전경 서비스(foreground service, `location` 타입)로 구현하고 지속 알림을 띄운다. **`ACCESS_BACKGROUND_LOCATION` 권한은 요청하지 않는다.**

**근거**: 백그라운드 위치 권한은 Play Console 별도 신고 양식과 심사를 거치고 "있으면 좋은" 용도는 거부된다. 반면 길동무 실시간 안내는 **사용자가 앱에서 "안내 시작"을 직접 누르는 순간** 시작되므로, 그 시점에 앱이 전경에 있다. 전경에서 전경 서비스를 시작하는 패턴이면 백그라운드 위치 권한 없이 화면이 꺼져도 위치를 계속 받는다.

**필요 권한**: `ACCESS_FINE_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, `ACTIVITY_RECOGNITION`(걸음수), `RECORD_AUDIO`(받아쓰기, API 33+).

**부수 효과(이득)**: 안드로이드가 강제하는 지속 알림이 스크린 리더 사용자에게는 자산이다. 안내 상태 한 줄과 "안내 종료" 버튼을 알림에 놓으면, 앱으로 돌아가지 않고 알림 그늘에서 종료할 수 있다. iOS에는 없던 자리다.

⚠ **구현 시 실측할 것**: 전경에서 시작하는 전경 서비스가 정말로 백그라운드 위치 권한 없이 동작하는지. 안드로이드 14 이후 규칙이 조여졌으므로 M4 착수 시 실기기로 확인한다.

---

### D12. 내부 테스트 조기 운영, 단 피드백에 일정을 걸지 않는다

**판정**: 계정 개설 직후 뼈대 앱을 내부 테스트 트랙에 올려 배포 파이프라인을 확립하고, 개발 내내 내부 테스트로 올린다. 비공개 테스트 12명은 **형식 요건 충족 목적으로만** 운영한다.

**위원장 판단(2026-09-15)**: 개인 개발자라 테스터에게 보수를 지불할 수 없고 선의에 기댈 수밖에 없다. 대부분은 설치만 하고 정식 출시 전에는 쓰지 않을 것이다. **따라서 전체 개발을 테스터 피드백과 무관하게 진행하고, 피드백은 오는 대로 받는다.**

⚠ **이 판단이 무효화한 것**: 초안에서 "테스터 12명이 곧 일반 안드로이드 폰 검증 채널이 된다"고 설계했으나 **그 전제는 폐기됐다.** 검증 공백은 O1로 다시 열린다.

**12명 요건의 성격**: 14일간 참여 상태를 유지하면 되고 매일 쓸 필요는 없다. 그래서 형식 충족과 실질 검증이 분리 가능하다.

---

### D13. UI는 Jetpack Compose

**판정**: Compose로 작성한다. XML View 시스템을 쓰지 않는다.

**근거**: 2026년 안드로이드 UI 표준이고, 접근성 semantics API가 성숙해 "한 줄 = 한 접근성 객체"를 선언적으로 표현할 수 있다(`mergeDescendants`). Compose 1.8.0부터 Accessibility Test Framework 검사를 Compose 테스트에서 직접 돌릴 수 있어 자동 검증 레인도 선다. SwiftUI와 사고 구조가 비슷해 [4] 화면 이식의 인지 비용도 낮다.

## 3. 열린 판정 (착수 세션 또는 위원장이 정할 것)

### O1. 일반 안드로이드 폰 검증 수단 ⚠ M4 블로킹

**문제**: D12로 테스터 검증 채널 전제가 폐기됐다. 현재 보유 안드로이드 기기는 한소네 7 하나뿐인데, **한소네를 들고 걸을 수는 없다.** 실시간 안내(M4)는 실보행 검증이 필수이므로 주머니에 들어가는 안드로이드 기기가 필요하다.

**이것은 편의 사항이 아니라 블로킹 조건이다.** 접근성 헌장이 "실기기 판정"을 요구하고, 실시간 안내는 특히 실보행 실측 없이는 닫을 수 없다(iOS에서 확립된 규율).

**선택지**:
1. **중고 안드로이드 폰 1대 구입** (권고). 실보행 검증과 일반 폰 TalkBack 검증을 동시에 해결한다. M3까지는 없어도 진행 가능하므로 구입 시점을 미룰 수 있다.
2. 에뮬레이터. 실보행 검증에 쓸 수 없어 M4를 닫지 못한다. 디스크 10GB 이상도 필요하다.
3. 지인·커뮤니티 산발 피드백. 회귀 검출이 안 된다.

**권고**: 선택지 1을 M3 완료 시점까지 확보한다. minSdk가 31이므로 오래된 중고도 쓸 수 있고, TalkBack 검증이 목적이라 고사양이 필요 없다.

### O2. 패키지 이름

iOS 번들 ID는 `space.dodoplanet.gildongmu`(실험판 `.dev`). 안드로이드도 같은 체계를 쓸지, 실험판에 해당하는 분리를 둘지 정한다. **한 번 정하면 바꿀 수 없다**(패키지 이름은 스토어 정체성).

### O3. 스토어 등재 정보

앱 이름, 짧은 설명, 자세한 설명, 스크린샷, 기능 그래픽, 카테고리, 콘텐츠 등급 설문, 데이터 안전성 섹션. iOS App Store 자산을 재활용하되 안드로이드 규격이 다르다.

### O4. 한소네 개발자 옵션 진입 경로 (실기기)

자체 런처(BrailleSense Launcher)를 쓰므로 안드로이드 표준 경로와 다를 수 있다. 무선 디버깅 연결의 전제다.

### O5. Play Console 모바일 앱의 한소네 동작 (실기기)

개인 계정의 실기기 접근 인증 요건을 한소네로 충족할 수 있는지. 한소네 7에 Play 스토어가 있음은 매뉴얼로 확인됐다(제16장).

### O6. 실험 빌드 구성을 둘지

iOS는 `Debug` / `Release` / `Experimental` 세 구성으로 검증 전 기능을 릴리스에서 뺀다. 안드로이드는 build variant(`debug`/`release`/`experimental`)로 같은 구조를 만들 수 있다. M4 이전에 정한다.
