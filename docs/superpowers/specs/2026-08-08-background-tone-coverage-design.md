## 1. 배경

M4(커밋 `b14f141`)가 `UIBackgroundModes: location`을 Experimental 구성에 선언해 **위치 스트림**을 백그라운드로 승격했다. 그때 남긴 관찰 포인트가 있다(PROGRESS.md:115):

> 잠금 중 소리 가청 여부는 별도 축(톤이 `.ambient`라 잠금 시 무음 가능, VO 통지의 백그라운드 발화도 미확정) — 무음이면 오디오 세션 카테고리 재설계가 후속.

**위원장 실측(2026-08-07)으로 이 축이 닫혔다: 백그라운드에서 소리도 음성도 들리지 않는다.** 위치는 살아 있으나 출력이 전부 막혀 있어, M4의 목표("주머니에 넣고 걸어도 안내가 살아야 한다")가 절반만 실현된 상태다.

동시에 조사 과정에서 **같은 `BeaconTone.tick`이 두 모드에서 다른 뜻으로 쓰이고 있음**이 드러났다. 간략(비콘)에서는 정체(`hold`) 신호이고, 상세(경로 추종)에서는 무이벤트 fix마다 3초씩 나는 생존 하트비트다. 사용자에게는 같은 소리이므로 이는 내부 구조가 밖으로 샌 것이다.

## 3. 출력 채널 계약

### 3.1 채널별 가청 범위

| 채널 | 전경 | 백그라운드·잠금 |
|---|---|---|
| 톤(`BeaconTonePlayer`) | 남 | **남**(신규) |
| 음성(`AccessibilityNotification.Announcement`) | 남 | 안 남 |
| 햅틱(`UIFeedbackGenerator`) | 남 | 안 남(플랫폼 제약) |

**음성 억제는 명시적 게이트로 구현한다.** 백그라운드에서 announcement가 발화되지 않는 것은 실측으로 확인했으나, 한 차례 실측은 API 계약이 아니다. OS 버전·VoiceOver 상태에 따라 무시·지연 전달·복귀 후 뒤늦은 발화가 가능하므로 플랫폼 동작에 의존하지 않는다.

- **상태 텍스트 갱신과 발화를 분리한다.** `statusText`·`lastGuidance`는 백그라운드에서도 갱신하고(전경 복귀 시 화면이 최신이어야 한다), `AccessibilityNotification.Announcement.post()` 호출만 앱 활성 상태 게이트로 막는다.
- 게이트 기준은 `scenePhase == .active`다. `.inactive`(제어센터·알림 센터)에서는 발화를 허용한다. 그 상태는 사용자가 화면을 보고 있는 중이다.

### 3.2 오디오 세션 소유권 모델

현재 `BeaconTonePlayer.ensureSession()`이 `.ambient` + `.mixWithOthers`를 선언한다. `.ambient`는 정의상 백그라운드에서 무음이다.

**"세션 시작 시 승격, 종료 시 원복"만으로는 안전하지 않다.** 오디오 세션은 프로세스 전역 자원이고 소비자가 셋(안내 톤·TTS `.playback`·받아쓰기 `.playAndRecord`)이라, 무조건 원복하면 다른 소비자의 카테고리를 파괴한다.

#### 상태 머신

안내 톤 재생기가 다음 세 값을 소유한다.

| 값 | 뜻 |
|---|---|
| `desiredCategory` | 안내가 **원하는** 카테고리(`.playback` 세션 중 / `.ambient` 세션 밖) |
| `didPromote` | 우리가 실제로 승격했는가(원복 자격) |
| `isSuppressed` | 다른 소비자가 세션을 점유 중인가(기존 값 승계) |

규칙:

1. **승격**: 세션 시작 시 `desiredCategory = .playback`. `isSuppressed`면 즉시 적용하지 않고 의도만 저장한다.
2. **재조정**: `isSuppressed`가 해제되는 시점(받아쓰기·TTS 종료)에 `desiredCategory`를 다시 적용한다. **이 재조정 지점이 없으면 "받아쓰기 중 안내 시작"이 영구히 `.ambient`로 남아 잠금 시 무음이 된다.**
3. **원복**: 세션 종료 시 `didPromote`인 경우에만 `.ambient`로 되돌린다. 우리가 승격하지 않았다면(다른 소비자가 이미 `.playback`을 잡았다면) 건드리지 않는다.
4. **인터럽션**: `interruptionNotification .ended`도 같은 재조정 경로를 지난다. 현행처럼 `isSuppressed` 중이면 무시하되, **suppression 해제 시 재조정이 인터럽션 복구를 함께 수행**한다. 두 경로가 하나의 재조정 함수로 합쳐지므로 "인터럽션 종료가 suppression 중에 도착해 영영 복구 못 함"이 성립하지 않는다.
5. **route 변경·media reset**: `routeChangeNotification`·`mediaServicesWereResetNotification`도 재조정 경로에 연결한다. 플레이어 재생성이 필요하므로 `isSilenced` 판정을 함께 갱신한다.

`.mixWithOthers`는 양쪽 카테고리에 유지한다. 기존 주석(`BeaconTonePlayer.swift:18-23`)의 근거가 그대로 유효하다.

#### 승격 실패

카테고리 설정 또는 활성화가 실패하면 **세션은 시작하되 degraded로 표시**한다. 전경에서 `start` 톤은 `.ambient`로도 들리므로, 실패를 알리지 않으면 사용자는 정상 시작으로 믿고 잠근 뒤 무음을 만난다.

- 실패 시 전경에서 음성 통지 1회(신규 문구: 잠금 중에는 소리가 나지 않는다는 뜻).
- `statusText`에도 반영해 화면 탐색으로 확인 가능하게 한다.

### 3.3 백그라운드 모드 선언

`ios/Support/Info-Experimental.plist`의 `UIBackgroundModes`에 `audio`를 추가한다(현재 `location` 단독).

- `Support/Info.plist`(Release)에는 **추가하지 않는다.** 실시간 안내 자체가 `#if EXPERIMENTAL` 게이트라 공식판에는 기능이 없다.
- 플래그 졸업 시 이 키를 Release plist로 옮긴다. 그때 **백그라운드 오디오는 심사 검토 대상**이므로 심사 노트에 용도(시각장애 사용자를 위한 내비게이션 오디오 신호)를 명시해야 한다. `AppConfig.realtimeGuidanceEnabled` 졸업 체크리스트에 추가한다.
- 앱을 깨어 있게 유지하는 것은 여전히 `location` 모드다. `audio`는 재생 허용만 담당한다.

## 4. 톤 의미론 통일

### 4.1 소리 9종

| 소리 | 뜻 | 변경 |
|---|---|---|
| `start` / `stop` | 세션 시작·종료 | |
| `closer` | 목적지와 가까워지는 중 | **상세 모드에도 적용** |
| `farther` | 멀어지는 중 | **상세 모드에도 적용** |
| `tick` | **정지** | **뜻 변경** |
| `ahead` | 결정 지점 40m 전 예고 | |
| `warning` | 경로 이탈 | |
| `nearby` | 도착 | |
| **`unreliable`**(신규) | **현재 안내를 신뢰할 수 없음** | **추가** |

⚠ 신규 소리의 뜻을 "위치 불확실"이 아니라 **"현재 안내를 신뢰할 수 없음"**으로 넓게 잡았다. 원인이 셋(GPS 정확도 불량·fix 부재·경로 재획득)인데 각각에 소리를 배정하면 학습 부담이 소리 수만큼 늘고, 사용자가 취할 행동은 셋 다 같다(기다리거나 하늘이 트인 곳으로 이동). **원인 구분은 전경 음성이 담당한다**(현행 문구 유지·확장).

### 4.3 공용 추출 범위: 추세 판정만

초판은 "상세 모드 거리 입력만 잔여 경로 거리로 바꿔 `beaconStep`을 재사용"이었다. **이 계층 선택을 폐기한다.** `beaconStep`은 추세 판정 외에 도착 판정·`weak` 게이트·음성 마일스톤 정책을 함께 소유하는데, 그 셋이 전부 상세 모드와 충돌한다.

| `beaconStep` 구성요소 | 상세 모드 재사용 |
|---|---|
| 데드밴드 추세 판정 | **공용 추출** |
| 도착 판정(`arrivalThreshold`) | **금지** — 상세는 `arrived` 이벤트가 정본이다. 잔여 40m·accuracy 50m면 beacon이 먼저 도착을 선언해 남은 결정 지점을 삼킨다 |
| `weak` 게이트(100m) | **금지** — 상세 게이트는 50m다. 75m fix가 한쪽은 불확실, 한쪽은 유효가 되어 불확실한 위치에서 방향 톤이 난다 |
| 음성 마일스톤(`speak`) | **금지** — 상세는 턴 안내가 음성을 소유한다. 겹치면 두 음성이 경합한다 |

#### 추출 대상

```
trendStep(anchor: Double, trend: Trend, distance: Double, deadBand: Double)
  -> (kind: .closer | .farther | .hold, anchor: Double, trend: Trend)
```

순수 함수이고 상태를 커밋하지 않는다. 호출부가 결과를 채택할지 결정한다(§4.4).

#### 상세 모드의 데드밴드

**GPS 수평 정확도를 그대로 쓰지 않는다.** 상세 모드의 거리 축은 경로 잔여 거리이고, 그 오차 원인은 GPS 정확도가 아니라 **경로 투영(map matching)의 안정성**이다. accuracy 5m라도 평행 도로로 투영이 점프하면 잔여 거리가 100m 튀고, accuracy 40m라도 투영이 안정적이면 잔여 거리는 매끄럽다.

- 데드밴드 = `max(baseDeadBand, 투영 점프 가드)`.
- 투영 점프 가드: 직전 fix 대비 잔여 거리 변화가 물리적으로 가능한 범위(속도 × 경과 시간 × 여유 계수)를 넘으면 그 fix의 추세 판정을 **버린다**(추세·앵커 불변). 이는 리듀서가 이미 갖고 있는 `uncertain`·`reacquiring` 국면과 별개의, 추세 축 전용 가드다.

### 4.4 톤 선택: 중재기가 아니라 계층 순서

초판은 4단계 우선순위 중재기를 두었다. **폐기한다.** 중재기는 후보 생성·상태 커밋 분리, 선점 정책, 시간축 억제, lifecycle 톤 포함까지 딸려오는 큰 컴포넌트인데, 그 복잡도 전부가 "상세 모드에 추세 톤을 추가한다"는 결정이 새로 만든 문제였다.

**기존 코드 구조가 이미 답을 갖고 있다.** `handleDetail`은 `out.tone` → `out.event` → (없으면) 하트비트 순으로 흐른다. 하트비트 자리에 추세 톤을 놓으면 중재가 필요 없다.

#### 상세 모드

```
1. 국면이 uncertain·reacquiring     → unreliable 톤 (간격 §7)
2. out.tone (ahead / warning)      → 그 톤
3. out.event (arrived 등)          → 이벤트가 소유
4. 그 외                            → 추세 축 (§4.5)
```

각 단계는 **배타적**이다. 위 단계가 톤을 내면 아래 단계의 `trendStep`을 **호출하지 않는다.** 호출하지 않으므로 앵커·추세·타이머가 갱신되지 않고, 따라서 "억제된 후보의 latch가 커밋되어 다음 fix에서 사라지는" 문제가 구조적으로 성립하지 않는다. 별도의 2단계 커밋 계약이 불필요하다.

⚠ 이 배타성은 추세 앵커가 **정지한다**는 뜻이다. 이탈 구간이 길면 앵커가 낡는다. 그래서 이탈·불확실에서 복귀할 때 앵커를 현재 거리로 **재기준화**한다(§8과 같은 규칙).

#### 간략 모드

```
1. fix 부재 워치독 발동 또는 weak   → unreliable 톤
2. 도착 존 진입                     → nearby 톤 (현행 래치)
3. 그 외                            → 추세 축 (§4.5)
```

#### 시간축: 행동 안내 후 정숙 구간

`ahead`·`warning` 재생 후 **3초간 추세 톤을 억제**한다. 사용자가 행동해야 하는 안내 직후에 배경 톤이 끼어들면 의미가 흐려진다. 억제 중에도 `trendStep`은 호출하지 않는다(위 배타성과 같은 이유).

#### 재생 선점

톤은 전부 1초 미만의 짧은 파일이다. 재생 중 새 톤 요청이 오면 **기존 재생을 중단하고 새 톤을 재생한다**(겹침 금지). 겹치면 두 소리가 섞여 어느 쪽도 식별되지 않는다.

`start`·`stop`은 세션 경계라 다른 톤과 같은 fix에서 발생하지 않는다. 우선순위 표에 넣지 않는다.

### 4.5 추세 축 내부 순서

| 순서 | 조건 | 톤 |
|---|---|---|
| 1 | 정지 확정(§5) | `tick` |

| 3 | 그 외 | 없음 |

## 5. 정지 판정

### 5.1 현행 `hold`를 그대로 쓸 수 없는 이유

`Beacon.swift:138`의 데드밴드는 `max(15m, fix.accuracy)`다. 그래서 `hold`는 "정지"가 아니라 **"아직 데드밴드를 못 넘음"**이다.

| 수단 | 15m 소요 | 결과 |
|---|---|---|
| 도보(1.4m/s) | 약 11초 | closer 1회당 tick 3~4회 — **걷는 중에 정지 톤이 지배적** |
| 차량 | 1초 미만 | tick 거의 없음 |

같은 소리가 수단에 따라 정반대 빈도가 된다.

### 5.2 3-state 판정

**정지·이동 이진화는 3-state 불변식 위반이다.** "속도를 모름"은 "정지"도 "이동"도 아니다.

```
MotionState = stopped | moving | speedUnknown
```

#### 신뢰 조건

`LocationService.BeaconFixPayload`에 `speed`·`speedAccuracy`(둘 다 `CLLocation`에서 그대로) 추가.

| 조건 | 판정 |
|---|---|
| `speed >= 0 && speedAccuracy >= 0 && speedAccuracy <= speedAccuracyCeiling` | speed 채택 |
| 위 조건 불성립 + 거리 미분 폴백 유효(아래) | 폴백 채택 |
| 둘 다 불가 | `speedUnknown` |

⚠ **음수 여부만으로 신뢰도를 판정하지 않는다.** `speed = 0.2`인데 `speedAccuracy`가 매우 크면 그 값은 정지 근거가 못 된다.

#### 거리 미분 폴백의 유효 조건

전부 충족할 때만 쓴다.

| 조건 | 값 |
|---|---|
| 두 fix 시간 간격 | 1.0초 이상 5.0초 이하 |
| 두 fix 정확도 | 각각 20m 이하 |
| 산출 속도 | 물리 상한(수단별) 이하 |

간격이 너무 짧으면 GPS 지터가 속도로 증폭되고(40m 정확도 두 fix가 1초에 20m 흔들리면 20m/s), 너무 길면 실제 이동이 평균화되어 정지로 보인다.

#### 히스테리시스

단일 임계값은 정차 중 speed가 임계 근처를 오갈 때 tick과 침묵을 번갈아 내어 리듬이 고장처럼 들린다.

| 상수 | 뜻 |
|---|---|
| `stopEnterMps` | 이 값 **미만**이 `stopEnterHoldS` 이상 지속되면 `stopped` 진입 |
| `stopExitMps` | 이 값 **초과**면 즉시 `moving` (진입보다 높게 잡는다) |
| `stopEnterHoldS` | 진입 유지 시간 |

이탈이 즉시인 것은 비대칭이 의도이기 때문이다. 정지 오판은 계속 들리는 거짓 tick을 만들고, 이동 오판은 한 번의 침묵으로 끝난다.

#### 임계값

**초판의 `0.5m/s` 및 그 근거("보행 최저 0.8~1.0m/s")를 철회한다.** 그것은 비장애 보행 **평균**을 최저값으로 잘못 옮긴 것이었다.

기준은 **위원장 판정(2026-08-08): 비장애 보행 속도의 90%**다. 실측 대신 이 비율을 근거로 삼는다.

| 값 | 산출 | 결과 |
|---|---|---|
| 비장애 성인 평상 보행 | 보수적 중앙값 | 1.3 m/s |
| **평상 보행** | 1.3 × 0.9 | **1.17 m/s** |
| **느린 구간**(혼잡·계단·경사로·장애물 탐색) | 평상의 60% | **0.7 m/s** |

임계 3종:

| 상수 | 값 | 근거 |
|---|---|---|
| `stopEnterMps` | **0.4 m/s** | 느린 구간(0.7)의 57%. 정상 보행 중 가장 느린 구간보다 확실히 아래라 오판 여유가 있다 |
| `stopExitMps` | **0.6 m/s** | 진입보다 높다(§히스테리시스). 느린 구간에 근접하므로 이동 복귀가 빠르다 |
| `stopEnterHoldS` | **2.0초** | 신호 대기 같은 실제 정지는 2초를 넘고, 보행 중 순간 감속은 넘지 않는다 |

⚠ **이 값들은 계산이지 측정이 아니다.** 비율 근거(90%)는 위원장 판정이고 나머지 두 단계(평상 1.3, 느린 구간 60%)는 일반 통계다. 실사용에서 거짓 tick 또는 정지 미감지가 나오면 이 표를 먼저 의심한다(§14).

### 5.3 왜 기존 속도 표본을 쓰지 않는가

상세 모드에 `GuideSpeedSample`·`estimateSpeedMps`(`RouteGuide.swift:79-86`)가 있으나 **경로 진행거리의 미분**이다. 간략 모드에는 경로가 없어 그대로 못 쓴다.

직선거리를 미분하는 대안은 틀린다. 그것은 "목적지 접근 속도"이지 "이동 속도"가 아니다. 목적지를 옆으로 지나쳐 걸으면 직선거리가 거의 안 변해도 실제로는 이동 중이다. **도플러 속도는 경로와 목적지 양쪽에 독립이라 두 모드에 같은 판정을 쓸 수 있는 유일한 축이다.**

기존 속도 표본 기계(`speedGuardActive` 등)는 **건드리지 않는다.** 그것은 "속도 빠름" 오판 가드라는 다른 목적을 가지며, M4 리뷰에서 표본 고갈 회귀까지 정리해 둔 상태다.

### 5.4 상태별 톤

| MotionState | 데드밴드 | 톤 |
|---|---|---|
| `stopped` | (무관) | `tick` |
| `moving` | 넘음 | `closer` / `farther` |
| `moving` | 못 넘음 | 없음(허용, 아래) |
| `speedUnknown` | 넘음 | `closer` / `farther` |
| `speedUnknown` | 못 넘음 | **없음** |

⚠ `speedUnknown`에서는 **`tick`을 내지 않는다.** 속도를 모르는데 정지 톤을 내면 거짓이다. 침묵이 늘지만, 거짓 정지보다 낫다. 이 상태가 오래 지속되면 fix 워치독(§6.2)이 `unreliable`로 잡는다.

**`moving`인데 데드밴드 미달인 침묵은 허용한다.** 직전 톤이 closer였다면 사용자는 "가까워지는 중"이라는 상태를 이미 알고 있고, 도보 기준 최대 11초는 그 상태가 유지되는 시간이다. 여기를 채우면 도보에서 2초마다 소리가 나 결정 3(빈도 절제)과 충돌한다.

### 5.5 도착은 종단 상태

도착(`nearby`) 이후에는 `tick`·추세 톤·`unreliable`을 **전부 억제**한다. 억제하지 않으면 목적지에 서 있는 동안 정지 tick이 계속 난다(도착 래치가 `nearby` 재생만 막고 정지 판정은 그대로 통과하기 때문).

억제는 세션 종료 또는 도착 존 이탈(히스테리시스 경계)까지 유지한다.

## 6. 신뢰 불가 상태 커버리지

### 6.1 메워야 하는 구멍

톤이 없는 상태를 전부 열거한다.

| 상태 | 조건 | 초판 | 개정 |
|---|---|---|---|
| 간략 `weak` | 정확도 무효 또는 > 100m | `uncertain` 톤 | `unreliable` |
| 상세 `uncertain` | 정확도 > 50m | `uncertain` 톤 | `unreliable` |
| 상세 `reacquiring` | 경로 재획득 중 | `uncertain` 톤 | `unreliable` |
| **fix 부재** | 콜백 자체가 안 옴 | **누락** | `unreliable`(워치독) |
| **상세 stale fix** | `age > 10`으로 조용히 폐기 | **누락** | `unreliable`(워치독) |
| **세션 시작 후 첫 fix 대기** | | **누락** | `unreliable`(워치독) |
| `speedUnknown` 지속 | | **누락** | 워치독 대상 아님(§5.4) |
| 재생기 사망 | `tones.isSilenced` | 한계 | §6.3 |

⚠ **초판의 최대 결함은 fix 부재였다.** 권한 철회·위치 서비스 비활성화·Core Location 정지·백그라운드 업데이트 중단이면 새 fix가 오지 않고, 그러면 `weak`·`uncertain` 판정 자체가 실행되지 않는다. 톤을 fix 처리 경로에만 걸면 **마지막 정상 톤 이후 영구 침묵**이 된다.

### 6.2 fix 워치독

**기존 채널을 재사용한다.** 모델에 이미 `lastFixAt`·`lastStaleNoticeAt`과 약신호 통지 경로가 있다(M4 노트: "선언 빌드의 fix 공백은 워치독 약신호 채널이 잡는다"). 초판은 그 채널을 톤에 연결하지 않았을 뿐이다.

- **타이머 구동**이지 fix 구동이 아니다. fix가 안 와도 돈다는 것이 요점이다.
- 마지막 **수용된** fix로부터 `noFixSeconds` 경과 시 `unreliable` 상태 진입.
- 상세 모드의 `age > 10` 폐기도 `lastFixAt`을 갱신하지 않으므로 같은 워치독이 잡는다. 별도 `staleFix` 상태가 불필요하다.
- 세션 시작 후 첫 fix 대기도 같은 타이머로 덮인다(`lastFixAt`을 세션 시작 시각으로 초기화).

### 6.3 `unreliable` 톤 계약

| 항목 | 값 |
|---|---|
| 진입 | **즉시 1회** 재생 |
| 지속 | `unreliableIntervalS` 간격 반복 |
| 회복 | **즉시 현재 상태 톤 1회**(추세 또는 tick), 앵커 재기준화 후 |

⚠ 진입·회복 즉시 재생이 계약의 핵심이다. 간격 타이머만 두면 GPS 상실 후 최대 `unreliableIntervalS`만큼 침묵하고, 회복 후에도 데드밴드 미달로 추가 침묵해 사용자가 회복 여부를 모른다.

전경 음성은 현행대로 원인을 구분해 알린다(`beacon.weak` 등). 톤은 추가 채널이지 대체가 아니다.

### 6.4 재생기 사망과 무음

`tones.isSilenced`는 정의상 톤을 못 내는 상태이므로 백그라운드에서 통지 불가다. 여기에 더해 **카테고리 설정은 성공했으나 실제로 소리가 안 나는 경로**가 있다(출력 route 상실, 시스템 볼륨 0, 디코드 실패).

가능한 범위:

- `AVAudioPlayer` 재생 완료 델리게이트 실패, route 부재, `mediaServicesWereReset`을 `isSilenced` 판정에 포함한다(현행은 재생기 생성 실패만 본다).
- 세션 시작 시 `start` 톤 재생 성공을 **전경에서 확인**하고, 실패면 그 자리에서 음성 통지(§3.2 degraded).
- 세션 중 사망은 백그라운드에서 침묵으로 남는다. **이것은 수용하는 한계다.** 햅틱은 백그라운드에서 동작하지 않아 대안이 되지 못한다.

**허용 최대 정상 침묵**: 정상 상태의 침묵에는 두 원인이 있고, 계약값은 그 둘의 최대값이다.

| 원인 | 최대 지속 |
|---|---|
| `moving`인데 데드밴드 미달(§5.4) | 데드밴드 ÷ 느린 구간 속도. 도보 15m ÷ 0.7m/s ≈ **21초** |
| `unreliable` 간격 사이 | `unreliableIntervalS` |

**데드밴드 미달 침묵이 지배적이다.** 평상 보행(1.17m/s)이면 13초, 느린 구간(0.7m/s)이면 21초 동안 톤이 없다. 초판이 "도보 최대 11초"로 잡은 것은 1.4m/s 기준이었다.

계약:

- `maxNormalSilenceS` = `max(데드밴드 통과 최대 시간, unreliableIntervalS)` = **21초**(도보 기준).
- 이 값이 "이보다 오래 조용하면 고장"이라는 사용자 계약이 된다. 백그라운드에서 톤이 유일한 채널이므로, 이 값이 곧 **이상을 알아채기까지 걸리는 시간**이다.

**위원장 판정(2026-08-08): 21초를 그대로 계약값으로 둔다.** 최소 재확인 간격 추가(15초마다 추세 톤 1회)와 데드밴드 축소(15m → 10m) 두 대안을 기각했다.

기각 근거:

- 직전 톤이 `closer`였다면 사용자는 상태를 이미 알고 있고, 21초는 그 상태가 유지되는 시간이다.
- **최소 재확인 간격은 폐기한 하트비트가 이름만 바꿔 돌아오는 것이다.** "일정 시간마다 소리를 낸다"는 구조가 같고, 다른 점은 그 소리에 뜻이 있다는 것뿐이다. 위원장 가정 3(하트비트 폐기)과 정면으로 어긋난다.
- 데드밴드 축소는 GPS 지터 내성을 깎아 제자리에서도 추세 톤이 나게 만든다. 15m는 그 내성의 근거값이다.

§11에 상태 전수 테스트로 못 박는다(계약값 21초 확정).

### 6.5 전경 복귀 재동기화

백그라운드에서 음성이 억제된 동안 상태가 여러 번 바뀌었을 수 있다. 복귀 시 **누적 이벤트를 재생하지 않고 현재 상태 하나를 즉시 낭독**한다. 누적 재생은 낡은 정보를 순서대로 읽어 혼란만 준다.

## 7. 빈도 정책

### 7.1 수단별 간격

| 수단 | closer | farther | tick | unreliable |
|---|---|---|---|---|
| 도보 | 2초(현행) | 2초 | 3초 | `unreliableIntervalS` |
| 차량 | **10초** | 2초 | 3초 | `unreliableIntervalS` |

- `farther`를 수단별로 가르지 않는 것은 **경고 축이기 때문**이다. 정상 진행 통지와 경고 통지의 빈도 비대칭은 이미 확립된 정책이다(음성 쪽 `closerSpeakInterval` 사다리 대 `speakInterval` 50m 고정).
- 차량 10초, `unreliableIntervalS`는 **초기값**이며 실사용 판정 대상이다(§14).

### 7.2 톤 간격을 음성처럼 거리 사다리로 만들지 않는 이유

음성은 `closerSpeakInterval`(5km↑ 1000m ~ 근거리 100m)이라는 거리 적응형 사다리를 쓴다. 톤에 같은 사다리를 적용하면 차량으로 5km 밖에서는 약 1분마다 톤이 난다. 이는 §6.4의 "허용 최대 정상 침묵" 계약을 무너뜨린다.

**톤과 음성은 축이 다르다.** 톤은 연속 상태 신호이므로 시간 기반이 맞고, 음성은 이정표이므로 거리 기반이 맞다.

### 7.3 배터리

`.playback` 세션을 수십 분 활성 유지하면 오디오 하드웨어·Bluetooth route가 절전에 들지 못한다. **증분 크기를 설계 전제로 삼지 않는다.** 정량 측정 항목으로만 남긴다(§11.2).

## 8. handoff와 축 전환 (가정 1)

현재 `GuideEvent.handoff` 처리(`BeaconModel.swift:659-666`)가 `beaconState = .initial`, `gateState = .initial`로 리셋해, 전환 후 첫 판정이 `first`(톤 없음)가 되어 톤이 끊긴다.

### 8.1 재기준화

상세의 잔여 거리는 **경로 거리**, 간략은 **직선거리**라 값이 불연속으로 줄어든다(경로 500m가 직선 120m가 되는 식).

- **승계**: 추세 방향(`trend`)만.
- **재기준화**: `anchorDistance`와 `lastSpokenDistance`를 **둘 다** 새 축의 현재값으로 재설정한다.

⚠ 초판은 앵커만 재설정했다. `lastSpokenDistance`를 옛 축 값(500m)으로 두면 새 축 현재값(120m)과의 차이 380m가 즉시 마일스톤을 넘겨 **전환 직후 거짓 closer 음성**이 나간다. 반대 방향 전환에서는 필요한 음성이 장기 억제된다.

### 8.2 전제 조건

handoff는 다음이 **모두** 성립할 때만 커밋한다.

- 유효 fix(정확도 게이트 통과)
- 국면이 `following` 또는 `bundle`(`uncertain`·`reacquiring`·`offRoute`가 아님)
- 잔여 거리가 투영 점프 가드(§4.3)를 통과

신뢰 불가 상태의 잔여 거리가 순간적으로 handoff 거리 아래로 튀는 것만으로 전환하면, 실제 경로가 남았는데 결정 지점 안내가 사라진다.

### 8.3 비정상 상태에서의 전환

직전 상태가 `unreliable`·`offRoute`였다면 전환 후 **새 축의 현재 상태 톤을 즉시 1회** 낸다(§6.3 회복 규칙과 동일). 그러지 않으면 전환 직후 데드밴드 미달 침묵이 "비가시화 성공"인지 "이상 지속"인지 구분되지 않는다.

## 10. 신규 사운드 선정

2026-08-03 8종 청취 선정과 같은 절차를 따른다.

1. 후보 2~3종 생성(ElevenLabs 또는 합성).
2. **배경 미디어 위에서 청취**한다. `.mixWithOthers`이므로 팟캐스트·음악이 재생 중일 때 저이득 톤(`tick` 0.3, 신규 톤 예정 0.3)이 묻히면 그 톤은 사실상 없는 것이다. 공존 확인만으로는 이 결함이 안 잡힌다.
3. 위원장 청취 후 1종 확정. `warning`과 확실히 구분될 것(이탈은 사용자 행동, 신뢰 불가는 기기 사정이라 취할 행동이 다르다).
4. 확정본을 `public/sounds/guide/unreliable.mp3` + 앱 리소스 `guide-unreliable.mp3`로 동시 배치.
5. `BeaconTonePlayer.gains`에 등록.

**이 단계는 구현 계획의 블로킹 태스크다.**

## 11. 테스트·게이트

### 11.1 게이트 테스트 (매 커밋)

- **계층 순서**: 상세 4단계·간략 3단계의 배타성. 위 단계가 톤을 낼 때 `trendStep`이 **호출되지 않음**(앵커·타이머 불변)을 단언한다.
- **정지 3-state**: `speed` 음수, `speedAccuracy` 초과, 폴백 유효 조건 각 경계, 히스테리시스 진입·이탈, `speedUnknown`에서 tick 미발생.
- **워치독**: fix 부재·stale fix·첫 fix 대기 각각에서 `unreliable` 진입, 진입 즉시 1회, 회복 즉시 1회.
- **허용 최대 침묵**: 모든 정상 상태 조합에서 `unreliableIntervalS`를 넘는 침묵이 없음(도착 제외).
- **handoff**: 앵커·`lastSpokenDistance` 동시 재기준화, 전제 조건 3종 각각의 차단.
- **오디오 상태 머신**: suppression 중 시작 → 해제 시 승격, `didPromote` 아닐 때 원복 안 함, 인터럽션 종료가 suppression 중 도착.
- **웹 미러**: 같은 계약을 `src/lib/__tests__/beacon.test.ts`에. 특히 `speed: null` → `speedUnknown`.
- **드리프트**: 웹↔Kit 상수 동조(`format-drift.test.ts` 선례).

## 15. 적대적 리뷰 반영 기록 (2026-08-08, codex gpt-5.6-sol·high, 39건)

**4개 계층에서 지적이 반복됐다**(우선순위 6건·리듀서 재사용 4건·정지 판정 6건·fix 부재 4건). CLAUDE.md 규칙에 따라 지엽 패치가 아니라 계층 선택을 재검토했고, 그 결과 2개 계층을 교체하고 2개를 확장했다.
