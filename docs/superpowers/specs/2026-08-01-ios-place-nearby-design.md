# iOS 장소 상세 "이 장소 주변" 설계 (2026-08-01)

> 백로그 B1. 웹 장소 상세에 있고 iOS엔 없는 3섹션(버스 도착·따릉이·날씨/공기질)을
> iOS 장소 상세에서 도달 가능하게 한다. 같은 마일스톤에 편승 예정이던 B2·B3은
> 착수 전 코드 대조에서 전제 소멸이 확인되어 §6으로 이관한다.

## 1. 문제

주 사용 창구가 iOS인데 같은 장소를 열어도 정보량이 다르다.

| 정보 | 웹 장소 상세 | iOS 장소 상세 |
|---|---|---|
| 역 4종(메타·도착·시간표·시설) | 있음 | 있음 |
| 무장애 편의시설 | 있음 | 있음 |
| **근처 버스 정류소·도착** | `BusArrivals mode="place"` | **없음** |
| **근처 따릉이 대여소** | `BikeStations mode="place"` | **없음** |
| **날씨·공기질** | `LocalConditions lat lng` | **없음** |

데이터 계층은 이미 있다. iOS `BusNearbyView`·`BikeNearbyView`·`ConditionsView`가
완성 화면으로 존재하고 Kit `NearbyService`·`ConditionsService`가 그 뒤를 받친다.
**없는 것은 단 하나 — 현재 위치가 아니라 이 장소 좌표로 앵커하는 길이다.**

## 2. 설계 결정

### 2-1. 진입 형태 = NavigationLink 3행(단일 섹션)

장소 상세에 `이 장소 주변` 섹션 하나를 추가하고 그 안에 3행을 둔다. 각 행은
기존 화면을 **장소 좌표로 앵커해** push한다.

섹션 위치는 **길찾기 다음, 역 4종 앞**이다. 웹(역 4종 뒤)과 반대이고 리뷰에서 지적이
나왔으므로 근거를 남긴다 — 두 플랫폼의 역 섹션 구조가 다르다.

| | 웹 | iOS |
|---|---|---|
| 역 시설 2종(`StationFacilities`·`SeoulMetroFacilities`) | **버튼으로 펼치는 접힌 패널** | `StationSectionsView`가 전부 인라인 전개 |
| 뒤에 둘 때 선형 주파 비용 | 없음(접혀 있다) | 천호역 실측 **수백 행**(음향유도기 38개·엘리베이터 목록 등) |

앞에 둘 때의 비용은 어느 쪽이든 3행이고, heading 점프로는 두 배치가 동등하다. 즉 선형
주파에서만 차이가 나는데 그 차이가 3행 대 수백 행으로 비대칭이다. **순서를 웹에 맞추려면
iOS 역 시설을 접히는 형태로 바꾸는 것이 선행**이며, 그 전엔 이 배치가 맞다.

인라인 섹션(무장애 편의시설처럼 자동 등장)이 아니라 push를 택한 근거:

- **기존 화면 전량 재사용.** pull-to-refresh, 8종 상태 오버레이, VO 완료 통지,
  버스 도착의 경유 정류소 push까지 계약이 그대로 따라온다. 인라인으로 다시 그리면
  같은 계약을 3벌 복제하게 된다(웹 `NearbyPanelShell` 추출과 같은 이유의 반대편).
- **장소 상세를 짧게 유지.** 스크린 리더 사용자는 상세를 선형 주파한다. 날씨·공기질만
  자동 삽입해도 8행이 늘고, 그 뒤의 무장애 편의시설이 그만큼 멀어진다.
- **발견 경로가 명확하다.** 접근성 헌장 §3의 "버튼으로 펼치는 건 버튼이 발견 경로".
  섹션 헤더 heading(`.isHeader`)이 3행 묶음을 알리고, 각 행이 자기 화면의 진입점이다.

웹이 날씨·공기질을 자동 등장 region으로 내는 것과 표현이 다르지만, 미러링 대상은
**정보 도달성과 접근성 계약**이지 화면 구조가 아니다(웹은 스크롤 문서, iOS는 List 스택).

### 2-2. 좌표 소스 = Kit `NearbyCoordinateSource.fixed` 신설

현행 2종은 `.current`(위치 어댑터 주입)와 `.none`(좌표 단계 생략, 파라미터를 fetch
클로저가 캡처 — `BusRouteStopsModel` 선례)뿐이다. 장소 앵커에 `.none`을 쓰면 좌표가
있는데도 **커버리지 선분기를 건너뛴다**. 웹 `LocalConditions`는 장소 좌표에 대해
`isInKorea(lat, lng)` 선분기를 그대로 적용하므로, 같은 보호를 잃는 선택이다.

```swift
public enum NearbyCoordinateSource {
    case current(@MainActor (_ force: Bool) async throws -> NearbyCoord)
    case fixed(NearbyCoord)   // 신설 — 앵커 좌표 고정, 위치 취득 단계 없음
    case none
}
```

전이표(스펙 `2026-07-31-ios-nearby-skeleton-design.md` §5)에 **새 상태·새 전이가 없다.**
`.fixed`가 낼 수 있는 전이는 `.current`의 진부분집합이다:

| 전이 | `.current` | `.fixed` |
|---|---|---|
| 커버리지 밖 선분기 → `.outOfCoverage` | 있음 | **있음** |
| `denied` / `failedLocation` | 있음 | 없음(위치 취득이 없다) |
| fetch 성공·0건·실패·취소 | 있음 | 있음(동일) |

`force`는 `.fixed`에서 재측위 의미가 없다 — 새로고침은 fetch만 다시 돈다.

### 2-3. 게이트·빈 결과는 현행 계약 그대로

- **키 게이트 없음.** iOS는 내 주변 허브도 10행을 무조건 노출하고 서버 응답으로
  판정한다(웹의 `canShow*` prop은 서버 컴포넌트가 있어 가능한 구조). 같은 관례를 따른다.
- **따릉이는 서울 전용이라 지방 장소에서 0건이 정상**이다. 조회 실패가 아니라
  "주변에 따릉이 대여소가 없습니다"(기존 카피). 3-state 불변식 유지.
- 통지 문구·오버레이 카피는 **한 글자도 바꾸지 않는다**. 앵커가 바뀌었을 뿐 데이터의 성격은 같다.
- **단, 화면 제목엔 기준 장소명을 병기한다**(`nearbyTitle`, 앵커일 때만). 앵커 화면의 문구는
  전부 "주변 …"인데 그 기준점이 현재 위치가 아니라는 사실이 화면 어디에도 없으면 스크린 리더
  사용자는 "주변에 대여소가 없습니다"를 자기 주변으로 읽는다(뒤로 가기 라벨은 되돌아가야 얻는
  맥락이다). 카피를 손대지 않고 기준점만 확보하는 최소 보정이다. 앵커를 좌표가 아니라
  `PlaceAnchor{coord,name}`으로 옮기는 이유가 이것이다.

## 4. 테스트 계약

Kit `NearbyLoadCoreTests`에 `.fixed` 3케이스:

1. **좌표 전달** — `.fixed(x)`로 만든 코어의 fetch가 받는 coord가 정확히 x이고,
   `force: true` 재호출에도 같은 좌표가 간다(재측위 개념 부재).
2. **커버리지 선분기** — 한국 밖 좌표면 fetch를 **호출하지 않고** `.outOfCoverage`.
   (이 단언이 없으면 `.fixed`에서 선분기를 빼도 서버 마커가 가려 테스트가 통과한다.)
3. **위치 실패 경로 부재** — 위치 어댑터를 아예 쓰지 않으므로 `denied`·`failedLocation`에
   도달할 수 없다. 실패는 fetch throw → `failedServer`뿐임을 고정.

변이 주입으로 검출력을 실측한다(케이스 2의 커버리지 분기 제거 → 실패해야 한다).

앱 타깃엔 테스트 레인이 없다. 뷰 조립은 빌드 + 시뮬레이터 접근성 트리 실측으로 판정한다.

## 5. 범위 밖

- **웹 변경 없음.** 이 마일스톤은 iOS 갭 해소만 다룬다.
- **거리 비컨(B4)** — 웹 실보행 스모크가 선행 게이트(백로그 유지).
- **역 4종·무장애의 push 전환** — 이미 인라인으로 동작하고, 자동 등장 계약이 다르다.

## 6. B2·B3 폐기 — 착수 전 코드 대조 결과

백로그가 이 마일스톤에 편승시키려던 두 항목은 **작성 시점 이후 전제가 소멸**했다.

| 항목 | 백로그 서술 | 실제 코드 | 판정 |
|---|---|---|---|
| B2 딥링크 수단 선택 | "iOS 도보 고정, 웹은 수단별 링크 제공" | 웹 `RouteLinks.tsx`는 `buildPlaceDeeplink`(장소 핀)·`buildKakaoWebMapUrl` 2개뿐이고 주석에 "모드 선택은 길찾기 뷰의 책임"(2026-07-30 스펙 §4) 명시 — **웹에 수단별 링크가 없다**. ⚠ 다만 웹=장소 핀, iOS=도보 경로 딥링크로 **여는 화면 자체는 다르다**(수단 선택 갭이 없을 뿐 동형은 아니다) | 폐기 |
| B3 대중교통 브리핑 출발지 변경 | "웹 `DirectionsView`엔 있음" | iOS `DirectionsTabView`에 출발지 필드(`searchTarget = .from`)와 스왑(`model.swap()`)이 이미 있다 | 이미 구현 |

두 항목 모두 갭이 아니므로 구현하지 않고 백로그에서 근거와 함께 내린다.

## 7. 동반 수정 — 카탈로그 수기 편집 잠복 결함

카탈로그 재생성이 잠복 결함 하나를 드러냈다.

`ios.route.serviceOutside`(대중교통 운행 밖 낭독 문구, 커밋 66df22a)가 **생성물인
`Localizable.xcstrings`에만** 존재했다. `ios/i18n/ios-extra/`·`messages/` 어디에도 없으므로
변환 스크립트가 만들어낼 수 없는 키다 — 이전 세션이 생성 카탈로그를 손으로 편집했다는 뜻이고,
**다음 재생성 때 조용히 사라져 화면에 키 문자열이 그대로 낭독되는** 상태였다. 이번 재생성이
실제로 그것을 지웠다.

수정은 사본 복원이 아니라 **중복 제거**다. 마일스톤 1이 웹 정본에 같은 뜻의
`route.transit.legServiceOutside`를 추가했으므로(단 **그 커밋이 카탈로그를 재생성하지 않아
HEAD 카탈로그엔 없었다** — 이번 재생성이 처음 수록했다) `RouteBriefing.swift`가 웹 정본 키를
직접 쓰도록 바꾸고 사본을 없앴다. 교체가 안전한 근거는 값 동일성이 아니라 **플레이스홀더
계약 동일성**이다: 6로케일 전부 `%1$@`=first, `%2$@`=last로 순서·개수가 같다.

같이 잡힌 카피 결함: 이 키의 en·es·fr·it 문구가 `First bus`처럼 **버스로 못박혀** 있었는데
마일스톤 1이 같은 키를 지하철 구간까지 확장해(웹 `TransitRouteBriefing.tsx`의 leg 루프는
수단 무관) 지하철에 "First bus"가 낭독되고 있었다. 수단 중립으로 고쳤다(ko `첫차`·ja `始発`는
원래 중립이라 무변경).

## 8. 검증 (시뮬레이터 실측 2026-08-01)

| 항목 | 결과 |
|---|---|
| 섹션 노출·순서 | 길찾기 → **Near this place**(3행) → 역 4종 → 무장애. 역 장소(천호역)에서 확인 |
| 앵커 제목 | 앵커 화면 제목이 `Bike stations, 해운대해수욕장`. 시각은 말줄임되지만 **접근성 라벨은 완전**(전체 문자열 일치 확인) |
| 앵커 실동작 | 현재 위치 캐시가 서울인 상태에서 **해운대해수욕장**(321km) 앵커 버스 도착이 부산 노선(185·1003·307)을 냈다 |
| 앵커 실동작(공기질) | 같은 조건에서 측정소가 **부산 좌동 1.8km** |
| 3-state | 해운대 앵커 따릉이 = "No bike stations nearby"(0건 안내, 오류 아님). 서울 전용 서비스의 정직한 0건 |
| 회귀 | 내 주변 허브 3행(현재 위치)·역 4종·무장애 섹션 정상 |

⚠ **위치 캐시 주의**: `LocationService`는 직전 좌표를 캐시하므로 시뮬레이터 좌표만 바꾼
대조 실험은 결론이 나지 않는다(도쿄로 옮겨도 현재 위치 화면이 서울 데이터를 냈다).
앵커 판정은 **먼 장소를 열어 그 지역 데이터가 나오는지**로 해야 한다.

실기기 VoiceOver 확인(섹션 heading 발견 경로·push 후 뒤로가기 맥락)은 백로그 F로 이관한다.

## 9. 리뷰 처리 (별도 컨텍스트, 요구사항+diff만 전달)

Critical 0 · Important 0 · Minor 5. 리뷰어가 변이 4종을 독립 주입해 이 마일스톤의 핵심 주장
(선분기 이동이 기존 두 소스에 무영향)을 기계적으로 재증명했다.

| # | 지적 | 처리 |
|---|---|---|
| 1 | `.fixed` 위치 실패 테스트의 `coordCallCount == 0`이 반증 불가능(그 소스엔 어댑터를 설치조차 하지 않는다) | **수용** — 삭제하고 "타입 구조가 보증, 이 테스트가 고정하는 축은 실패 분류 한 줄" 주석으로 정정 |
| 2 | 앵커 화면이 기준점을 밝히지 않아 "주변에 없습니다"가 자기 주변으로 읽힌다 | **수용** — §2-3의 제목 병기(`PlaceAnchor`·`nearbyTitle`). 설계 때 파라미터 표면을 이유로 접었던 판단인데, 기준점 부재는 SR 사용자가 되돌아가야만 회수되는 정보라 정확성 논거가 더 강하다 |
