# E88. 채팅 도구 보강 다섯 설계

2026-11-14. BACKLOG E88. 서버 전용(채팅 `/api/chat`). 클라이언트 코드는 iOS 진행 통지 라벨 한 줄만 바뀐다. 묶음 ⓐ → ⓑ → ⓒ 순서로 따로 커밋한다.

서버에는 있는데 채팅 도구로 열리지 않은 기능 다섯을 붙인다. 공통 원칙은 기존 도구와 같다.

- 지명을 좌표로 푸는 자리는 `resolveCoord` 하나다. 못 풀면 `placeNotFound`이고 현재 위치로 대신하지 않는다.
- 0건, 정보 없음, 조회 실패를 다른 모양으로 돌려준다. 조회 실패는 throw이고 에이전트 루프가 실패로 전한다.
- 새 인자를 쓰지 않은 호출의 결과는 종전과 글자 단위로 같다.

## 묶음 ⓐ 경로 도구

### A1. 출발지 인자 `origin`

대상은 `get_walk_route`, `get_car_route`, `get_transit_route`다. `plan_journey`는 건드리지 않는다.

| 항목 | 계약 |
|---|---|
| 인자 | `origin`(선택, 문자열). 사용자가 현재 위치가 아닌 출발지를 말했을 때만 넣는다. |
| 해석 | `resolveCoord(origin)`. 못 풀면 `placeNotFound(origin)`. 현재 위치로 대신하지 않는다. |
| 우선순위 | 말한 출발지 > 실제 `userLocation`. 장소 채팅의 앵커는 출발지가 되지 않는다(종전과 같다). |
| 위치 없음 | 출발지를 말했으면 위치 권한이 없어도 조회한다. |
| 커버리지 | 출발지 좌표가 한국 밖이면 종전 `outOfCoverage` 안내를 돌려준다. |
| 결과 | `data.origin`에 실제로 고른 장소(이름과 주소)를 싣는다. 키워드 검색 첫 결과라 사용자가 말한 곳과 다를 수 있어 모델이 그 이름을 말할 수 있어야 한다. |
| 렌더 | 출발지를 말한 답에는 렌더를 하나도 내지 않는다. |
| 인자 없음 | 응답이 종전과 같다(`origin` 키도 없다). |

렌더를 내지 않는 까닭은 둘이다.

1. `route-start`(E83 [안내 시작])는 실제 위치에서만 안내를 시작한다. 다른 곳에서 출발하는 경로의 답에 그 버튼을 달면 답과 다른 경로의 안내가 시작된다.
2. 능력을 신고하지 않은 클라이언트의 종전 카드 `car-route`와 `transit-route`는 기기 위치로 경로를 다시 조회하는 카드다(`CarRouteBriefing`이 `awaitGeolocation`으로 출발지를 정한다). 답은 서울역 출발인데 카드는 현재 위치 출발 경로를 보여 주게 되므로 내지 않는다. 도보는 원래 종전 카드가 없다.

출발지를 말한 대중교통 조회는 카드용 조회(`includeStops`·`includeLanes`)를 하지 않는다.

경유지(`via`), 계단 회피(`accessible`)와 함께 쓸 수 있다. 대중교통의 경유지 미지원과 영어 자동차 경로의 경유지 미지원은 종전 순서 그대로 출발지 해석보다 먼저 판정한다.

### A2. 대중교통 수단 한정 `mode`

| 항목 | 계약 |
|---|---|
| 인자 | `get_transit_route`의 `mode`(선택, `"subway"` 또는 `"bus"`). 사용자가 지하철만, 버스만이라고 했을 때만 넣는다. |
| provider | `getTransitRoute`의 `modeAxis`(`subwayOnly`·`busOnly`). `/api/route/transit`의 `pathType`과 같은 축이다. |
| 찾음 | `route`에 그 수단만 타는 1순위 경로 하나, `data.mode`에 한정한 수단. |
| 없음 | `route: null` + `noRouteWithMode: true` + `mode` + 안내 문장. 「그 수단만으로 가는 경로가 없다」이고 「경로가 없다」가 아니다. |
| 조회 실패 | throw(종전과 같다). |
| 모르는 값 | `mode`가 두 값이 아니면 무시하고 종전 조회를 한다. |
| 렌더 | `route-start`를 신고한 요청에는 같은 수단 한정으로 받은 결과를 카드에 싣는다(답과 카드가 같은 경로). 신고하지 않은 요청의 종전 카드 `transit-route`는 수단을 모르는 채 다시 조회하므로 내지 않는다. |

ODsay 호출 수: 수단을 한정한 조회는 URL에 `SearchPathType`이 붙어 캐시 항목이 따로다(1시간 캐시). 그래서 수단을 한정한 질문 하나에 ODsay 호출이 1회 나간다. 모델이 한정 없는 조회를 함께 부르면 2회다. 카드용 조회는 한국어 데이터 로케일에서 같은 URL이라 캐시를 타고(추가 0), 영어 데이터 로케일에서는 `lang`이 달라 1회 더 나간다(E83과 같다). 새 호출 자리는 `fetchOdsay` 한 곳이고 캐시 뒤에 있다.

### A3. 베르길리우스

베르길리우스는 세 경로 도구를 그대로 연다. 그 끝점의 버튼은 실제 위치에서 시작하는 안내뿐이므로 출발지 인자를 닫는다.

- 선언 변환층(`vergiliusToolSpecs`)이 세 경로 도구의 스키마에서 `origin` 속성을 뗀다.
- 루프가 실행 직전에 호출 인자에서 `origin`을 뗀다(모델이 스키마에 없는 인자를 보내도 현재 위치 출발로 조회한다).

수단 한정 `mode`는 답과 버튼이 같은 경로라 그대로 둔다. 베르길리우스 도구 목록에는 이번에 도구를 더하지 않는다.

### A4. 지침

선언 문구만으로 실호출에서 인자가 맞게 채워지면 시스템 지침은 고치지 않는다. 부족하면 긍정 조건 한두 줄만 더한다.

## 묶음 ⓑ 장소 정보

### B1. 전화번호

- `placesToData`(장소 검색 `search_places`가 모델에 주는 재료)가 번호가 있는 곳에만 `phone`을 싣는다. 없는 곳은 키가 없다.
- 화면 카드(`placesToRender`)는 바꾸지 않는다.
- 그 밖에 장소를 모델에 주는 자리: 아이 놀 곳·주변(`get_surroundings`)·야간 진료는 원래 provider 객체를 그대로 실어 전화번호가 이미 간다. 한눈에 보기와 현재 위치 정위의 기준점은 이름·거리·방위만 주는 요약이라 그대로 둔다(번호는 장소 검색으로 묻는다). 무장애 관광지는 원천에 전화번호가 없다.

빼 둔 것이 의도였는지: 첫 구현(2026-06-20)의 근거는 「토큰 절약을 위해 핵심 필드만」 하나였다. 개인정보나 약관을 이유로 뺀 기록은 `git log -S`, INTEGRATIONS, PATTERNS, spec 어디에도 없다. 「도구 결과 `data`는 LLM에만」은 원문 재료를 클라이언트로 흘리지 않는다는 규칙이고, 사업장 대표 전화는 이미 화면 카드에 나온다.

### B2. 이름으로 무장애 정보 찾기

새 도구를 만들지 않고 `get_barrier_free_detail`에 `name` 인자를 더한다(도구 수 불변).

| 항목 | 계약 |
|---|---|
| 인자 | `contentId`(주변 무장애 목록에서 이어 갈 때) 또는 `name`(장소 이름). 둘 다 선택이다. |
| 기본 | 둘 다 없고 장소 채팅이면 앵커 장소(이름과 좌표)로 찾는다. 둘 다 없고 앵커도 없으면 오류. |
| 이름 해석 | 장소 검색 첫 결과의 좌표와 이름. 못 풀면 `placeNotFound`. 앵커 이름과 같으면 앵커 좌표를 쓴다. |
| 매칭 | `findBarrierFreeByName`. 먼저 장소 상세 화면과 같은 판정 `matchBarrierFreePlace`(좌표 50m 안 ∩ 이름 일치)를 보고, 없으면 관광공사 이름 검색(`searchKeyword2`)에서 이름이 같고 1km 안인 곳을 고른다. 좌표 목록이 등록 장소를 빠뜨리는 때가 있고(덕수궁 좌표 조회에 덕수궁이 없었다), 넓은 부지는 카카오 좌표와 관광공사 좌표가 수백 m 어긋난다(경복궁 약 400m, 실호출 2026-11-14). |
| 찾음 | `matched: true` + `searchedPlace` + `detail`(편의시설 목록, 등록 이름). |
| 찾지 못함 | `matched: false` + `searchedPlace` + 안내 문장. 「이 이름으로 등록된 무장애 정보가 없다」이고 「편의시설이 없다」가 아니다. 이름 검색에 걸린 1km 안의 다른 등록 장소가 있으면 `similar`(이름·거리, 최대 3곳)를 싣고 상세는 대신 주지 않는다(모델이 되묻는다). |
| 찾았는데 항목 없음 | `detail.facilities`에 그 항목이 없다. 등록된 정보가 없는 것이라고 선언 문구가 가르친다. |
| 조회 실패 | throw. |

`contentId` 호출의 결과는 종전과 같다.

## 묶음 ⓒ 입구 기준 왼쪽·오른쪽·맞은편

새 도구 `get_entrance_sides`(채팅 도구 26 → 27). 게이트는 카카오 키다.

| 항목 | 계약 |
|---|---|
| 인자 | `place`(필수). 인자 없이 현재 위치로는 부르지 못한다. 보도 위 GPS 좌표에서는 방향 축이 거의 서지 않기 때문이다. |
| 해석 | 장소 채팅에서 `place`가 앵커 이름과 같으면 앵커 좌표, 아니면 장소 검색 첫 결과. 못 풀면 `placeNotFound`. |
| 조립 | `assembleScene`(장소 상세의 「주변 확인」과 같은 조립, 반경 150m). |
| 축이 섬 | `frame: "entrance"` + 묶음(`left`·`right`·`across`·`beyond`)별 이름·분류·거리·다른 도로명. 기준은 「입구를 마주 보고 섰을 때」다. 묶음마다 가까운 순 여덟 곳까지, 묶음의 전체 수를 함께 싣는다. |
| 축이 안 섬 | `frame: "compass"` + `sidesUnavailable: true` + 안내 문장. 좌우 묶음을 싣지 않는다. 방위로 답하려면 `get_surroundings`를 쓰라고 알린다. |
| 0건 | `total: 0`(150m 안에 등록된 가게나 시설이 없다). |
| 조회 실패 | throw. |
| 재료 | 좌표·전화번호·링크·id는 싣지 않는다. |
| 렌더 | 없다. 산문이 정본이다. |

진행 통지 문자열 `chat.progress.tool.get_entrance_sides`를 여섯 언어에 더하고 iOS·안드로이드 생성물을 다시 만든다. iOS `toolLabel`에 case 한 줄을 더한다.
