# 도보 경로 대안 제시와 안내 중 전환 (M3 + E10ⓑ) 설계

2026-08-12 확정. 백로그 M3(2026-08-11 위원장 요청)과 E10(이탈 시 자동 재탐색, 판정 대기)을 한 마일스톤으로 묶는다.

## 0. 위원장 판정 (2026-08-12, 설계의 전제)

1. **범위**: M3(출발 전 경로 선택 + 안내 중 수동 전환) + **E10 ⓑ안**(이탈 확정 시 자동 조회 후 *제안*, 전환은 사용자 수락). ⓐ안(자동 전환)은 채택하지 않는다 — "자동 재설정이 도로 중앙으로 안내했다"는 실사고 근거(스펙 2026-08-03 §5.6)는 그대로 유효하며, 이 설계는 그것을 뒤집지 않는다.
2. **제시 형태**: 길찾기 조회 시 두 경로(추천·최단)를 **항상 함께** 제시한다(대중교통 대안 동형). 옵트인 버튼 방식 기각 — 이 마일스톤의 출발점이 "대안의 존재 자체를 알 수 없다"였다.
3. **계단 회피와의 곱**: 계단 회피를 켠 상태에서도 최단 경로를 **보여주되 경고**한다("계단 회피 미적용" 문장). 숨김 기각.

## 1. 데이터 근거 (2026-08-11 실호출, BACKLOG M3)

- Tmap `searchOption=10`(최단)이 등굣길 880m(카카오 기본)→715m 이면도로를 준다. 그 길은 데이터에 있고, 탐색 옵션이 안 고를 뿐이다.
- ⚠ `searchOption=30`("최단+계단제외")은 실측상 추천과 동일(868m) — **최단이면서 계단을 피하는 경로는 어느 API도 제공하지 못한다.** 판정 3(경고 병기)의 근거.
- ⚠ 카카오에는 이 축의 옵션이 없다(`route_mode=ACCESSIBLE`뿐). 최단은 **Tmap 전용**이다.
- ⚠ 현 코드는 Tmap에 `searchOption`을 보내지 않는다(미전송=0 추천과 실측 동일). 폴백 경로의 동작은 바꾸지 않는다(미전송 유지).

## 2. 아키텍처 선택

**서버가 한 번 조회에 두 경로를 반환한다**(A안). 쿼터·캐시·문장 파이프라인 제어가 `walk-route.ts` 한 곳에 남고, 소비자 전부가 같은 계약을 공유한다(대중교통 5경로 응답 동형).

- 기각 B(클라이언트 2회 호출): 병렬 호출·실패 흡수를 클라마다 중복 구현.
- 기각 C(両경로 Tmap 통일): "ko 기본 카카오" 위원장 판정(2026-07-29)을 뒤집고, 계단 회피·`rewriteWalkGuidance`·음향신호기 주석이 카카오 중심이라 회귀가 크다.

## 3. API·서비스 계약

### 3.1 `/api/route/walk` 파라미터 2종 추가 (모두 옵트인, additive)

- **`variant`**: 부재(기본, 현행 파이프라인 그대로) | `shortest`. `shortest`는 Tmap `searchOption=10` 단독 호출(폴백 없음 — 카카오에 동등 축이 없다. Tmap 실패는 502, 키 부재는 최단 축 자체가 성립 안 하므로 조회 화면에서 미노출). 응답 모양은 현행과 동일(`{ result }`).
- **`alternatives=1`**: 기본 경로와 최단 경로를 병렬 조회해 `{ result, shortest }`로 반환. **부분 성공은 비대칭이다**(적대적 리뷰 #5 반영): **기본 경로 실패는 현행대로 전체 502**(`result` 필수 계약을 깨는 응답 모양을 만들지 않는다 — 하위 호환이 부분 성공보다 우선), **최단 실패만 흡수**해 `shortest: null`로 현행과 동일한 화면이 성립한다. `hasTmapKey()` 불통과 시 최단 조회 자체를 생략(`shortest` 필드 부재).
- **파라미터 조합표**(리뷰 #10 반영 — 허용 밖 조합은 400):

  | 조합 | 판정 | 근거 |
  |---|---|---|
  | `variant` + `alternatives` 동시 지정 | 400 | 상호 배타 — 単경로 조회와 복수 조회는 다른 소비자다 |
  | `alternatives=1` + `includeGeometry=1` | 400 | 조회 화면은 기하가 불필요하고, 両경로 기하는 응답만 키운다. 기하는 안내 시작 시 `variant` 단일 조회로 |
  | `variant=shortest` + `includeGeometry=1` | 허용 | 최단 경로 안내 시작·전환·제안 경로 |
  | `variant=shortest` + `accessible=true` | 허용 | §3.2 경고 병기 |

- 옵트인 값 검증은 `includeGeometry` 관례 동형(정확한 값만 허용, 그 외 400 — 조용한 무시 금지).
- **옛 클라이언트 호환**: `shortest`는 additive 필드다. Swift Codable·기존 웹 코드 모두 미지 필드를 무시한다(대중교통 `routeKey` 실사고의 역방향 점검 — 이번엔 필수 디코딩을 요구하지 않는다).
- ⚠ **채팅·CLI/MCP는 옵트인하지 않으므로 Tmap 추가 호출이 0이다.** 이것이 쿼터 방어의 실질이다: [[nextjs-fetch-cache-route-handler-contract]]에 따라 **POST fetch의 `revalidate`는 실효가 없어 Tmap 호출은 사실상 비캐시**다(provider 주석의 "1시간 캐시" 서술은 카카오 GET에만 참). `alternatives`는 길찾기 화면(iOS, 후속 웹)만 요청한다.
- ⚠ **`alternatives=1` 한 요청의 Tmap 최악 비용은 2건이다**(리뷰 #7 반영): 최단 1건 + 기본 경로의 카카오 실패 폴백 1건. 방어는 현행 IP 레이트리밋(60초 10회) 유지 + 옵트인 축소(위)로 하고, 서버 일일 예산·가중 레이트리밋은 신설하지 않는다(기각 근거는 §9).

### 3.2 `walk-route.ts` (서비스 진입점 — provider 직접 호출 금지 유지)

- `getWalkRoute(params)`에 `variant?: "shortest"` 추가. `shortest`면 `getWalkRouteBriefing`(tmap)을 `searchOption: "10"`으로 호출하고 동일 파이프라인(재작성→음향신호기 주석 순서 계약 유지)을 태운다. Tmap 문장은 재작성 정규식에 거의 걸리지 않으나 순서 계약은 동일하게 지난다(MERGED_CROSSWALK가 両형태를 받는 기존 설계 그대로).
- **계단 회피×최단**: `accessible=true`이고 `variant=shortest`면 경로는 그대로 조회하되 `stepFree: "unavailable"` + **`stepFreeNotice` 전용 문장**을 싣는다: "최단 경로에는 계단 회피가 적용되지 않습니다. 계단이 포함될 수 있습니다." 새 `StepFreeStatus` 값을 추가하지 않는다 — 옛 iOS enum 디코딩을 깨지 않으면서 문장은 서버 정본 필드(`stepFreeNotice`)로 전달되는 기존 계약을 재사용한다.
- `tmap-pedestrian.ts`: `searchOption?: "10"` 파라미터 추가(미지정이면 현행대로 미전송 — 폴백 동작 불변).
- **경로 정체성은 세션 인자가 고정한다**(리뷰 #9 부분 반영): 안내 중 전환·이탈 제안의 재조회는 세션의 `dest`·`accessible`·`includeGeometry`를 그대로 쓰고 **variant만 축**이다. 별도 복합 키(RouteIntent류)는 만들지 않는다 — 진입점이 좌표·옵션을 인자로 받지 않는 구조가 1선 방어라는 기존 원칙 그대로, 세션 파라미터는 세션 수명 동안 불변이다. ⚠ 전환 시 `accessible`이 조용히 탈락하지 않는지 게이트 테스트로 고정한다.

### 3.3 Tmap 기하 보존 (최단 경로 실시간 안내의 성립 조건)

현행 normalize는 LineString feature를 버리고 Point 좌표만 남긴다. 안내 지점 사이를 직선으로 이으면 이탈 판정(수직거리 축)이 실경로 곡률에서 헛경고를 낸다. **`includeGeometry` 요청 시 LineString 좌표를 스텝별 `pathCoords`로 보존**하도록 `normalizeTmapWalkRoute`를 확장한다(Tmap GeoJSON은 Point·LineString이 교대로 오므로 직전 Point의 스텝에 후속 LineString을 귀속). 기본 응답(기하 미요청)은 현행과 byte 동일 유지.

- 이 확장은 기존 Tmap **폴백** 경로의 실시간 안내 품질도 함께 올린다(부수 효과, 회귀 아님).
- ⚠ **기하는 normalize 출력이 아니라 파이프라인 종단에서 보존을 검증한다**(리뷰 #11 반영): `rewriteWalkBriefing`·`annotateAudioSignals`가 스텝을 다듬은 **뒤에도** `pathCoords`가 유실·오귀속되지 않아야 한다. 기하 없는 스텝을 만나면 `buildGuideRoute`가 경로 전체를 거부해 상세 안내가 **조용히 간략으로 강등**되는 것이 기존 계약(§1.2)이라, 유실은 오류 없이 실시간 안내를 죽인다. Tmap 기하 경로의 파이프라인 통과 fixture 가드를 게이트 테스트로 둔다.
- 실호출 게이트: 등굣길 최단 경로에서 LineString 귀속이 스텝 순서와 일치하는지 확인.

## 4. iOS 조회 화면 (`DirectionsTabView` 도보 섹션)

- 도보 카드가 요약 라벨 2행이 된다. 대중교통 대안 disclosure 동형(`DisclosureGroup`, 펼침 본문은 단계 안내 + 안내 시작 버튼). 한 줄 = 한 접근성 객체, 구분자 쉼표, 거리는 `Format.swift` `formatDistance` 정본:
  - "추천 경로, 880m, 도보 약 13분"
  - "최단 경로, 715m, 도보 약 11분" (+계단 회피 시 `stepFreeNotice` 문장을 요약 뒤 병기)
- 라벨은 "추천"·"최단"으로 짓는다. "큰길 우선"은 어느 provider도 계약으로 보장하지 않는 성질이라 라벨로 약속하지 않는다(정직성 원칙). 판단 재료는 거리·시간 숫자가 담당한다 — 실측상 두 경로의 차이도 거리로 드러난다(18%). "큰길 비중" 파생 수치는 데이터 근거가 없어 만들지 않는다.
- 최단 조회 실패(`shortest: null`·필드 부재) 시 최단 행 자체를 그리지 않는다(현행 화면과 동일 — 死행 금지).
- **응답은 스냅샷 교체다**(리뷰 #13 반영): 새 조회 시작 시 이전 대안을 지우고, 추천·최단은 **같은 응답에서 온 쌍만** 함께 그린다(기존 request-id stale 폐기 관례 동형 — 다른 조회 세대의 결과를 조합하지 않는다).
- i18n: 도보 경로는 V1 ko 전용(현행 유지). 신규 문구는 ko 네임스페이스만.
- **빌드 구성(위원장 지시 2026-08-12)**: 조회 화면의 복수 경로 제시(요약 2행·단계 안내 브리핑·계단 회피 경고)는 **Release(App Store)·Experimental 両구성에 반영**한다 — `#if EXPERIMENTAL` 게이트를 걸지 않는다. 반면 §5(안내 중 전환)·§6(이탈 시 제안)은 실시간 안내 계층이라 현행 `AppConfig.realtimeGuidanceEnabled`(`#if EXPERIMENTAL`) 게이트를 그대로 따른다. 따라서 Release에서는 두 경로의 브리핑(요약·단계 낭독)까지 제공되고, 안내 시작 버튼과 그 이후 계층은 현행처럼 실험판에만 나타난다.

## 5. 안내 중 수동 전환

- `BeaconModel`(iOS)·`useRouteGuide`(웹, 후속 이식)이 세션의 `variant`를 보유한다. 안내 시작 시 선택한 경로의 variant로 `includeGeometry=1` 조회(현행 흐름에 파라미터 하나 추가).
- 안내 시트에 "다른 경로로 전환" 버튼: **현위치 기준으로 반대 variant 재조회**. `performReroute`에 variant 인자를 추가하는 것이 전부다 — 위치 강제 재취득(`{force:true}` 동형)·상태 리셋(`resetFinalApproach`·`rebaseForAxisChange`·래치)·latest-wins 응답 폐기·전환 성공 통지 `.high`가 전부 기존 검증 계약이다. 출발 전에 받아 둔 대안 경로를 재사용하지 않는 이유: 걷는 중이라 그 경로의 출발점이 낡았다.
- 전환 성공 통지에 variant를 밝힌다: "최단 경로로 전환했습니다. 전체 715m." (새 경로임을 알리는 기존 재조회 문구 계약의 확장).

## 6. 이탈 시 제안 (E10 ⓑ)

- **트리거**: 이탈 **확정**(표결 확정 이벤트, 리듀서 기존 이벤트 소비 — 판정 순수 계층은 변경하지 않고 모델 계층에서 구독). 확정 회차당 **1회만** 세션 variant·`accessible`로 경로를 자동 조회해 보관한다. 출발점은 **확정 시점의 최신 세션 fix**다(안내 세션은 연속 fix 수신 중이라 싱글턴 TTL 함정과 다른 층이지만, 명시한다 — 리뷰 #3 반영). 제안에는 취득 좌표·취득 시각을 함께 저장한다(신선도 판정의 기준값).
- **latest-wins 토큰**(리뷰 #1 반영): 제안 조회는 기존 재조회와 같은 토큰 계층을 쓴다. 폐기·수락·목적지 변경·세션 종료·새 확정 회차 시작 시 토큰이 증가하고, **토큰이 일치하고 이탈이 지속 중일 때만** 응답을 보관 상태로 커밋한다 — 복귀 후 늦게 도착한 첫 회차 응답이 폐기된 제안을 되살리는 경로를 차단한다.
- **상태는 넷으로 가른다**(리뷰 #2·#12 반영): `없음` → `조회 중` → `준비됨` → (`수락`·`폐기`·`만료`). **조회 실패는 그 회차 종결이다**(재시도 없음 — 쿼터 방어. 다음 확정 회차가 새 기회다. 명시적 트레이드오프). **만료는 수락을 기다리지 않는 능동 전이다**: 신선도 한계(아래) 도달 시 `준비됨`을 즉시 해제하고 버튼 라벨을 원복한다 — 라벨이 "준비된 새 경로로 안내"인데 눌러 보니 일반 재조회가 시작되는 어긋남을 만들지 않는다(수락 시점 검사는 최후 안전망으로만 남는다).
- **통지(polite, 1회 best-effort)**: `준비됨` 진입 시 요약을 들려주되 전환하지 않는다. 문안 시안: "새 경로가 준비되었습니다. {첫 스텝 요약}, 전체 {distance}." 재발화하지 않으며, **지속 신호의 정본은 통지가 아니라 버튼 라벨이다**(리뷰 #2 반영 — 이탈 경고 반복 채널에 통지가 잠식돼도 시트의 라벨이 발견 경로로 남는다. [[once-only-warning-delivery-contract]]의 "신호는 문장의 존재로" 원칙의 버튼 판).
- **수락**: 이탈 중 시트의 "경로 다시 조회" 버튼이 "준비된 새 경로로 안내"로 바뀐다(별도 버튼 추가 금지 — SR 읽기 순서 비용). 누르면 보관 경로를 즉시 채택(왕복 없음). **채택은 `performReroute`의 성공 커밋 경로를 그대로 지난다**(리뷰 #4 반영 — 별도 채택 전이 신설 금지. 경로·기준선·이탈 표결·finalApproach·래치를 한 커밋 지점에서 바꾸는 원자성은 그 계층이 이미 보장하고, 검증도 그쪽에 있다). 채택 성공 통지는 `.high`(버튼 활성화의 결과 통지 계약).
- **신선도 한계**: 제안 취득 위치에서 30m 초과 이동 또는 120초 경과(잠정값, 실보행 판정 대상). 도달 시 위 `만료` 전이.
- **폐기**: 이탈 복귀(활성 축 전체 해제)·세션 종료·목적지 변경 시 제안과 버튼 라벨을 조용히 원복한다(통지 없음 — 근거가 사라지면 표시도 사라진다).
- **활성 조건**(리뷰 #14 반영): 제안의 트리거·커밋·수락은 **활성 안내 세션이고 최종 접근 진입 전**일 때만 성립한다. 이탈 표결이 최종 접근(6a)보다 앞이라는 기존 불변식 순서에 제안도 그대로 걸리고, 도착·종료는 폐기와 동일하게 모든 보관·대기 상태를 무효화한다.
- **쿼터**(리뷰 #8 반영): 확정 회차당 1회(이탈 지속 중 재조회 없음) + **세션당 제안 조회 상한 5회**(잠정값). GPS 오차로 복귀·재확정이 진동하면 회차가 반복 생성될 수 있어, 상한이 쿼터·통지 폭주의 마지막 방어선이다. 상한 도달 후에도 수동 재조회 버튼은 현행대로 동작한다(자동 축만 멈춘다).
- ⚠ **A6 한계 명시**: 이탈 확정 지연(실보행 82초, 방위 축 재설계 후 재판정 미완)은 이 마일스톤이 고치지 않는다. 확정이 늦으면 제안도 늦는다. 실보행 판정 항목으로 이월하며, 이 한계가 확인되더라도 제안 계층의 설계는 유효하다(확정이 빨라지면 제안이 그만큼 앞당겨진다).

## 7. 이번에 하지 않는 것

- **자동 전환(E10 ⓐ)**: §0 판정 1.
- **웹 UI**: 서버 계약은 이번에 완성되므로 웹은 UI만 남는다. PORTS.md에 등록(iOS 먼저·웹 후속 — M4 단계 분리 선례).
- **CLI/MCP·채팅 노출**: 옵트인 미요청으로 현행 동작 byte-identical. 후속 판단(노출하려면 CLI는 `FORMATTERS` 등록 필수 — [[cli-formatter-registration-gap]]).
- **경로 3개 이상**(Tmap 계단제외 30 등): 30은 실측상 추천과 동일해 죽은 선택지다. 목록 과잉 금지.

## 8. 검증

- **실호출 머지 게이트**: 등굣길 구간 両경로 실호출 — 최단이 715m 이면도로를 재현하는가, `alternatives=1` 응답에 両경로가 실리는가, 계단 회피 시 `stepFreeNotice` 전용 문장이 실리는가. fixture green으로 닫지 않는다.
- **서버 실호출 게이트 결과(2026-08-12, 집 37.53657,127.14732 → 신명중 본관)**:
  - `alternatives=1`: `result` 956m/7스텝(명일로 447m 직진 — 카카오 추천, 08-11 실측과 동일 성격. 총거리 차이는 origin이 실측 세션과 미세하게 다른 탓) + `shortest` 689m/12스텝(세븐일레븐·코사할인마트 경유 이면도로 — 실측 715m 계열 재현). 両경로 문장 정상 한국어.
  - `variant=shortest&includeGeometry=1`: 전 스텝 `pathCoords` 존재, 인접 스텝 기하 전부 이어짐(단절 0), `finalApproach` 존재(오프셋 48.6m).
  - `variant=shortest&accessible=true`: `stepFree: "unavailable"` + 전용 문장("최단 경로에는 계단 회피가 적용되지 않습니다…") + 비기하 스텝 0번 삽입 확인.
  - 금지 조합 2건(`alternatives+includeGeometry`, `variant+alternatives`) 実HTTP 400 확인.
  - ⚠ **게이트가 검출한 결함 1건(수정 완료)**: Tmap 종점 "도착" Point는 후속 LineString이 없는 0길이 단일점이라 `buildGuideRoute` 유령 스텝 가드가 **경로 전체를 거부** → `finalApproach` 소실·상세 안내가 조용히 간략 강등(§3.3이 경고한 바로 그 유형). 카카오는 도착 스텝 자체를 내지 않으므로, 기하 모드의 `normalizeTmapWalkRoute`가 기하 없는 후행 마커를 떨구는 것으로 수정(비기하 브리핑은 "도착" 유지 — byte 동일). fixture green이었고 실호출에서만 드러났다.
- **게이트 테스트**: 라우트 파라미터 검증(옵트인 오값·금지 조합 400), 부분 실패 비대칭(기본 실패 502·최단 실패만 흡수), Tmap LineString 귀속 순서 + 파이프라인 종단 기하 보존(fixture), 전환 시 `accessible` 보존, 기본 응답 byte 동일(기하 미요청·옵트인 미요청 시 현행과 무변).
- **하위 호환 계약 테스트**(리뷰 #17 반영): 직전 App Store 배포판의 `WalkRouteEnvelope` 디코더 형태 fixture로 새 응답 6종(기본·`shortest` 객체·`shortest: null`·필드 부재·기본 실패 502·최단 실패)을 디코딩 검증한다. "Codable은 미지 필드를 무시한다"를 가정이 아니라 테스트로 확정한다.
- **구성별 확인**: Release 빌드에서 복수 경로 제시가 보이고 안내 시작·전환·제안 계층은 나타나지 않는지, Experimental에서 전부 나타나는지 両구성 산출물로 확인한다(§4 빌드 구성 계약).
- **실보행 판정(F-a 계열)**: ①최단 경로 실안내 품질(이면도로 실보행) ②이탈 제안 발화 시점·신선도 게이트 잠정값 ③A6 재판정과의 상호작용. 등굣길이 시험 코스다.

## 9. 설계 리뷰 게이트 판정

**실시한다** — 조건 ④(실보행 안내 안전 크리티컬) 해당: 이탈 시 제안은 종전 명시 금지(§5.6)의 경계 위에 새 상태(보관 경로·버튼 라벨 전환·신선도 게이트)를 얹는다. (조건 ①~③은 비해당: 새 판정 계층·새 외부 계약·비가역 파급 없음.)

**실시 완료(2026-08-12, codex adversarial-review raw exec 주입 방식, 17건).** 수용분은 위 각 절에 `리뷰 #n 반영`으로 표기: 부분 성공 비대칭(#5), latest-wins 토큰(#1), 조회·발화 래치 분리와 버튼 라벨 지속 신호(#2), 제안 fix 신선도(#3), 채택의 기존 커밋 경로 재사용(#4), 회차 상한(#8), accessible 보존(#9), 조합표(#10), 파이프라인 종단 기하 가드(#11), 만료 능동 전이(#12), 스냅샷 교체(#13), 활성 조건(#14), 하위 호환 fixture(#17), 쿼터 최악 비용 명시(#7 일부). **기각 5건과 근거**:

- 서버 일일 예산·가중 레이트리밋(#7 본안): 개인 규모 트래픽에 과설계. 현행 IP 리밋 + 옵트인 축소가 방어선이고 소진 감시는 `usage-report.mjs`가 정본.
- RouteIntent 복합 키 신설(#9 본안): 진입점이 좌표·옵션을 인자로 받지 않는 **구조가 1선 방어**라는 기존 원칙으로 이미 성립. 세션 인자 불변 + `accessible` 보존 테스트로 충분.
- 캐시 키 variant 확장(#15): Tmap은 POST 비캐시(revalidate 실효)이고 카카오 옵션(`route_mode`)은 URL 파라미터라 캐시 키가 이미 갈린다. 실질 갭 없음.
- 통지 큐 취소·우선순위 토큰 체계(#6 본안): iOS 통지에 대기 큐 취소 API가 없다. 단일 polite 채널 + 버튼 라벨 지속 신호 + 채택 `.high`로 대체(#2·#4 수용분이 같은 증상을 다른 계층에서 막는다).
- Release 명령 경계 게이트 신설(#16): 기존 `realtimeGuidanceEnabled`가 이미 모델 명령 경계 게이트다(신규 UI는 전부 그 게이트 안쪽 뷰에만 존재). §8 구성별 산출물 확인이 검증을 담당.
