# 길찾기 화면 재편 (도보 강등·대안 축·도보 구간 정보) 설계

> 2026-08-07. 위원장 제기: "모든 길찾기 조회에 획일적으로 3수단 결과를 주는 것이 최선인가". 원설계는 `2026-07-21-walk-route-directions-tab-design.md`(3수단 병렬 비교), 대중교통 정규화는 `2026-06-18-odsay-transit-routing-design.md`, 운행시간 강등은 `2026-08-01-odsay-service-hours-design.md`, 안내 진입점은 `2026-08-03-mode-entrypoints-car-guidance-design.md`·`2026-08-04-transit-guidance-design.md`가 정본이다.
>
> **전제 교정 하나를 먼저 기록한다.** 착수 전 가설은 "대중교통과 도보를 통합하려면 여러 API를 앱이 조합 계산해야 한다"였으나, ODsay `searchPubTransPathT`가 이미 도보·버스·지하철 조합 경로를 계산해 준다. 재편은 API 조합이 아니라 **이미 받고 있는 데이터의 노출 방식** 문제다. 경로 대안 데이터원 확장(백로그 E6)은 위원장 보류 상태이고 이 스펙은 그 판정을 건드리지 않는다.

## 1. 배경과 목표

세 가지 관찰에서 출발한다.

1. **장거리에서 도보 상세는 정보가 아니라 장애물이다.** 자택에서 서울역까지 도보 경로는 12.8km, 약 3시간이고 턴바이턴 스텝이 수백 행이다. 채택 가능성이 사실상 0인 이 목록이 수단 heading 사이를 채운다. 원설계가 도보를 최하단에 둔 것(2026-07-22 위원장 결정, "분량 최다·검색 빈도 최저")은 이미 같은 문제 인식의 소프트 대응이었다.
2. **의미 있는 대안이 잘려 나가고 있다.** ODsay는 길동에서 서울역까지 경로를 9개 주는데 `normalizeOdsayRoute`가 앞 3개만 취한다. 실호출 확인 결과 7번째 경로가 **370번 버스 직통, 환승 0회**다. 시각장애 사용자에게 환승은 낯선 역에서 방향을 다시 잡는 가장 비싼 동작이므로 26분을 더 쓰더라도 택할 이유가 있는데, 이 선택지는 화면에 도달할 수 없다.
3. **도보 구간이 "도보 N분"으로만 표현된다.** ODsay는 도보 구간마다 거리를 주지만 정규화가 분만 남긴다. 어디까지 걷는지, 몇 미터인지가 UI에 존재하지 않아 대중교통 경로의 실제 부담을 판단할 수 없다.

**측정 가능한 성과**: ①장거리 조회에서 대중교통 heading부터 자동차 heading까지 스와이프 수가 도보 상세 행수만큼 줄고 ②무환승 경로가 존재하는 조회에서 그 경로가 화면에 오르며 ③각 도보 구간의 행선지와 거리가 낭독된다.

## 2. 확정 판단

| 사안 | 확정 | 근거 |
|---|---|---|
| 도보 강등 판정 축 | **이미 조회한 도보 경로의 소요 시간** | 직선거리는 육교·우회로를 반영하지 못한다. 소요 시간은 병렬 조회 결과에 이미 있어 **추가 API 호출 0**이고 사용자가 실제로 판단하는 값과 같다 |
| 문턱 | **30분 초과** (위원장 판정) | 잘못 접은 비용(스와이프 1회)이 잘못 펼친 비용(수백 행)보다 훨씬 작은 비대칭. 낮은 쪽이 기대손실 최소 |
| 도보 배치 | **제자리(최하단) 유지, 내용만 접는다** | 수단 h3 3개가 heading 로터 점프 경로다(원설계 §5). 대중교통 하위로 옮기면 그 경로가 사라지고, 대중교통이 경로 없음일 때 실패한 섹션 안에서 성공한 수단을 찾게 된다. 접힘은 **깊이**를 조절하는 도구이지 **소속**을 바꾸는 도구가 아니다 |
| 대안 개수 | **추천 1 + 최대 4 = 최대 5** (위원장 판정) | 축 경로가 묻히지 않으면서 접힘 버튼이 자동차·도보 heading을 밀어내지 않는 선 |
| 대안 축 | **최단 시간·최소 환승 2개** (위원장 판정) | "도보 최소" 3번째 축은 실사용 판정 후로 미룬다(§9) |
| 축 선정과 운행시간 강등의 순서 | **축 선정이 먼저, 강등이 나중** | 역순이면 9경로 전부의 노선 시간표를 조회해야 해서 TAGO·TOPIS 호출이 3배가 된다. 대가는 §3.3에 명시 |
| 도보 구간 행선지 | **다음 탑승 구간의 `startName`에서 유도** | ODsay 도보 subPath는 `trafficType`·`distance`·`sectionTime` 3필드뿐이다(2026-08-07 실호출 확정, 아래 §3.1). 이름은 응답에 없다 |
| 마지막 도보의 행선지 | **클라이언트가 목적지 이름으로 채운다** | provider는 목적지 이름을 모른다. 이름을 모르는 소비자는 이름 없는 형태로 낭독한다(3-state 정신: 없는 것을 지어내지 않는다) |
| 거리 표기 | **`formatDistance` 정본 경유, 직접 조립 금지** | 지역 사본 4곳이 갈려 850m를 "0.8km"로 낸 실사고. `format-drift.test.ts`가 강제 |
| 획일성 완화의 범위 | **도보 섹션만** | 자동차 브리핑은 요약 중심이라 분량 문제가 없고, 위원장이 제기한 것도 도보다. YAGNI |

원설계의 유효 계약을 전부 승계한다: 3수단 `Promise.allSettled` 병렬, 수단별 독립 3-state, 단일 polite 합산 통지, 수단 순서 대중교통→자동차→도보, en 로케일 도보 미노출.

## 3. 데이터 계층 (ODsay 정규화)

### 3.1 실호출로 확정된 응답 계약 (2026-08-07)

자택(127.1420, 37.5380) → 서울역(126.9707, 37.5547) 실호출:

```
path[0] info: totalWalk=399, totalTime=45, payment=1750,
              busTransitCount=0, subwayTransitCount=2, totalWalkTime=-1
subPath: [
  {trafficType:3, distance:178, sectionTime:3},                    ← 도보 3필드뿐
  {trafficType:1, distance:14200, sectionTime:26, startName:"길동", endName:"동대문역사문화공원", stationCount:13},
  {trafficType:3, distance:0,   sectionTime:3},                    ← 환승 통로(기존 필터로 제외)
  {trafficType:1, distance:3600,  sectionTime:7,  startName:"동대문역사문화공원", endName:"서울역", stationCount:4},
  {trafficType:3, distance:221, sectionTime:3}                     ← 마지막 도보
]
```

확정 사항 넷:

- **도보 subPath의 키는 `trafficType`·`distance`·`sectionTime` 셋뿐이다.** `startName`/`endName`이 없다. 행선지는 유도해야 한다.
- `totalWalk`(399m)는 거리 합이고 환승 통로(0m)를 포함하지 않는다. `totalWalkTime`은 `-1`(정보 없음 마커)이므로 **쓰지 않는다**. 총 도보 시간은 현행대로 `sectionTime` 합으로 센다.
- `subwayTransitCount:2`는 탑승 구간 수이지 환승 횟수가 아니다(탑승 leg 2개, 환승 1회). **환승 횟수를 leg 수에서 계산하는 기존 결정을 유지**하고 `*TransitCount`를 쓰지 않는다.
- ODsay는 이 좌표쌍에 **경로 9개**를 준다.

### 3.2 도보 구간에 거리와 행선지를 싣는다

`TransitLeg`에 `distanceMeters?: number`를 더한다. 도보 구간 전용이고 탑승 구간에는 싣지 않는다(탑승 거리는 정거장 수가 이미 표현하며, 낭독에 더할 값이 아니다).

행선지는 기존 `toName` 필드를 재사용한다. 이 필드의 의미는 이미 "이 구간의 끝"이라 도보에도 그대로 성립한다. 유도 규칙은 하나다:

> **도보 구간의 `toName` = 그 뒤 첫 탑승 구간의 `fromName`. 뒤에 탑승 구간이 없으면 설정하지 않는다.**

이 한 규칙이 첫 도보(출발지→첫 승차역)와 환승 도보(하차역→다음 승차역)를 함께 처리한다. 유도는 환승 통로 필터링 **뒤**의 legs 배열에서 수행한다.

`fromName`은 도보에 설정하지 않는다. "○○까지 도보 N분"이 성립하는 데 출발점 이름이 필요하지 않고, 첫 도보의 출발점은 provider가 이름을 모른다.

### 3.3 대안 선정을 축 기반으로 바꾼다

`paths.slice(0, 3)`을 **순수 함수 3단계**로 교체한다. 선정과 라벨 부여를 갈라 놓는 것이 핵심이며, 이유는 `annotateServiceStatus`가 1순위 자체를 바꿀 수 있기 때문이다(아래 "왜 3단계인가").

**1단계 `selectTransitRoutes(routes): TransitRoute[]`** (축 기반 후보 선정, 라벨 없음)

```
base = routes[0]                                (ODsay 추천 1위, 선정의 비교 기준)
pool = routes[1..]
minTransfers = pool 중 transfers < base.transfers 인 것들의 transfers 최소값.
               동률이면 pool 앞선 것(추천순 보존)
minMinutes   = pool 중 totalMinutes < base.totalMinutes 인 것들의 totalMinutes 최소값.
               동률이면 pool 앞선 것
결과 = [base] + [뽑힌 축 경로(중복 제거)] + [나머지를 추천순으로 채워 총 5개까지]
```

pool이 비면 결과는 `[base]` 하나다(대안 0개).

**2단계 `annotateServiceStatus(...)`** (기존 함수, 무변경): 5개에 운행 상태를 싣고 안정 정렬로 강등한다.

**3단계 `annotateHighlights(routes): TransitRouteResult`** (최종 순서 확정 후 라벨 부여)

```
recommended = routes[0]                         (강등 정렬 뒤의 1순위)
alternatives = routes[1..]
fewestTransfers = alternatives 중 transfers < recommended.transfers 인 것들의
                  transfers 최소값. 동률이면 앞선 것
fastest         = alternatives 중 totalMinutes < recommended.totalMinutes 인 것들의
                  totalMinutes 최소값. 동률이면 앞선 것
두 축이 같은 경로를 가리키면 fewestTransfers 라벨만 부여한다
  (환승이 더 강한 신호이고, 라벨 2개를 한 줄에 붙이면 분절이 는다)
```

`TransitRoute`에 `highlight?: "fastest" | "fewestTransfers"`를 더한다. **판정은 서버가 하고 클라이언트는 표시만 한다.** 세 플랫폼이 같은 비교 로직을 복제하지 않게 하는 것이 목적이며, 커버리지 마커·`serviceStatus`와 같은 계층 결정이다.

**왜 3단계인가.** 라벨을 1단계에서 붙이면 축의 기준점이 낡는다. `annotateServiceStatus`는 원래 추천이 운행 밖이고 무환승 대안이 운행 중일 때 **그 대안을 1순위로 승격**시킨다. 그러면 승격된 경로는 렌더되지 않는 자리(추천)에서 라벨을 들고 있고, 남은 대안들의 축은 이미 사라진 기준으로 계산된 값이 된다. 라벨 부여를 최종 순서 뒤로 미루면 **"축 라벨은 언제나 현재 1순위보다 나은 것"**이라는 불변식이 성립한다.

축은 **1순위보다 나을 때만** 생긴다. 1순위가 이미 최단이면 `fastest` 라벨은 존재하지 않고, 모든 경로의 환승이 같으면 `fewestTransfers`도 없다(길동→강동역 실측: 9경로 전부 환승 0회라 환승 축 없음, 최단 축은 추천 16분과 다른 13분 경로에 생김).

**선정이 강등보다 먼저인 이유.** 역순(9경로 전부에 운행 상태를 실은 뒤 선정)은 9경로 전 구간의 노선 시간표 조회를 요구해 TAGO·TOPIS 호출이 3배가 된다. 이 순서의 대가는 축 경로가 막차 끊긴 노선일 수 있다는 것인데, 그때 그 경로는 2단계에서 아래로 내려가고 해당 구간에 "첫차 …, 막차 …, 지금은 운행하지 않습니다"가 붙으므로 오인할 여지가 없다. 또한 1단계의 비교 기준(`base`)은 ODsay 추천 1위이므로 운행 상태와 무관하게 결정적이다.

**응답 크기.** `includeStops=1` 옵트인 소비자(웹·iOS)에서 경로 3개가 5개로 늘어 경유역 배열이 약 67% 증가한다. 경로당 경유역이 17개 안팎이므로 절대량은 수 KB 수준이고, 대안 어느 것으로도 안내를 시작할 수 있어야 하므로(M5 계약) 선택적 로딩은 두지 않는다. CLI/MCP는 `includeStops`를 요청하지 않아 영향이 없다.

### 3.4 잘못된 위치의 도착 문구를 제거한다

현재 구간 목록 뒤에 항상 `arrive`("○○ 도착", `summary.arriveName ?? dest`) 문단이 붙는다. 그런데 마지막 구간이 도보일 때 그 도보는 **마지막 하차역에서 목적지로** 걷는 것이므로, 그 뒤에 하차역 이름으로 "도착"을 말하면 순서가 거꾸로다. §3.2로 마지막 도보가 목적지 이름을 갖게 되면 이 문단은 잉여이기까지 하다.

> **`arrive` 문단은 마지막 leg가 탑승일 때만 렌더한다.** 마지막이 도보면 그 구간 문장이 이미 도착을 말한다.

이는 재편이 만든 결함이 아니라 재편이 드러낸 기존 결함이며, 같은 줄을 건드리므로 함께 고친다.

## 4. 표시 계층

### 4.1 대안 표시 이름 (단일 함수)

세 곳(disclosure 라벨, 안내 시작 버튼 라벨, 스크린 리더 로터)이 같은 이름을 써야 하므로 이름 산출을 한 함수로 모은다.

| 조건 | 이름 |
|---|---|
| `highlight === "fewestTransfers"` | `route.transit.alternativeFewestTransfers` = "환승이 가장 적은 경로" |
| `highlight === "fastest"` | `route.transit.alternativeFastest` = "가장 빠른 경로" |
| 없음 | `route.transit.alternativeHeading` = "대안 경로 {index}" |

**번호는 축 라벨이 없는 대안들 사이에서만 1부터 센다.** 배열 인덱스를 그대로 쓰면 축 경로가 1번을 소비해 "대안 경로 2"부터 시작하는 어색함이 생긴다.

disclosure 라벨은 현행대로 `joinText(이름, 요약, 도보 요약)`이다. 라벨이 곧 요약 전문이므로 펼침 본문은 `includeSummary=false`를 유지한다.

### 4.2 안내 시작 버튼 라벨

`beacon.guideStartTransitAlt`를 `"대안 경로 {index} 안내 시작"`에서 **`"{name} 안내 시작"`**으로 바꾸고 §4.1의 이름을 주입한다. 결과는 "환승이 가장 적은 경로 안내 시작"·"대안 경로 2 안내 시작"이다. 스크린 리더 버튼 목록·항목 선택기가 heading 문맥 없이 이름만 나열한다는 2026-08-06 판정의 연장이며, 번호보다 축 이름이 구분에 강하다.

### 4.3 도보 구간 문장

| 조건 | 메시지 |
|---|---|
| `toName` 있음 | `legWalkTo` = "{name}까지 도보 {minutes}분, {distance}" |
| `toName` 없고 소비자가 목적지 이름을 앎 | `legWalkTo`에 목적지 이름 주입 |
| 둘 다 없음 | `legWalk` = "도보 {minutes}분, {distance}" |

거리는 `formatDistance`를 지난다. 한 구간은 한 텍스트로 합쳐 쉼표로 잇는다(인라인 span 분절 금지).

### 4.4 도보 섹션 조건부 접힘

- **판정**: 도보 조회가 `done`이고 `durationSeconds > 30 * 60`이면 접힌 상태로 시작한다. `error`·`empty`는 접을 상세가 없으므로 현행 그대로 한 줄 문구를 낸다.
- **접히는 것은 상세뿐이다.** 계단 회피 토글과 도보 안내 시작 버튼은 접힘 **밖**에 남는다. 접힘 안에 넣으면 접힌 상태에서 도달할 수 없고, 계단 회피 재조회 후 도보 heading으로 가는 포커스 이동이 접힌 대상을 향해 조용히 실패한다.
- **라벨**은 기존 `route.pedestrian.summary`("총 {distance}, 약 {minutes}분")를 그대로 쓴다. 새 문구를 만들지 않는다.
- **펼침 상태는 사용자 조작이 이긴다.** 상태를 `자동 | 펼침 | 접힘` 3값으로 두고, 자동일 때만 문턱 판정을 적용한다. 계단 회피 재조회는 상태를 보존한다(경로가 바뀌며 문턱을 넘나들 때 사용자가 펼쳐 둔 것이 닫히면 조작이 배신당한다). **새 조회(조회 버튼)는 자동으로 되돌린다**(목적지가 달라질 수 있다).

## 5. 접근성 계약 (승계 + 신규)

승계(변경 금지):

1. **조회 완료 후 포커스를 옮기지 않는다**(2026-08-02 위원장 판정). 계단 회피 토글 재조회만 예외로 도보 heading 이동을 유지한다.
2. **세션 단일성**과 패널 언마운트 전이의 명시 중지·`beacon.stopped` 통지.
3. **안내 세션이 살아 있는 대안의 접힘 클릭은 무시한다**(접힘 unmount가 세션을 조용히 죽인다). 대안이 5개로 늘어도 동일하다.
4. 수단 h3 3개 구조와 순서 불변.
5. 한 줄은 한 접근성 객체. 거리·축 라벨은 쉼표로 이어 붙이고 시각용 span으로 쪼개지 않는다.

신규:

6. **도보 disclosure는 버튼이 발견 경로이므로 본문은 `<div>`**(region·heading 부여 금지, 헌장 §3). iOS는 `DisclosureGroup`이 정본이다.
7. **접힘·펼침에 별도 live region 통지를 두지 않는다.** `aria-expanded`(iOS는 DisclosureGroup 상태)가 이미 상태를 말한다.
8. **축 라벨은 통지가 아니라 이름이다.** 조회 완료 통지는 현행 단일 합산 문장을 유지하고 "무환승 경로가 있습니다" 같은 문장을 더하지 않는다.

## 7. 테스트·게이트

**순수 함수(fixture 단위)**
- `selectTransitRoutes`: 9경로 fixture에서 5개 선정(무환승 7번째 경로가 뽑히는가), 후보가 5개 미만인 경우, pool이 빈 경우.
- `annotateHighlights`: 축 없음(전부 동일 환승이고 1순위가 최단), 두 축이 같은 경로를 가리키는 경우, **강등이 1순위를 바꾼 뒤 라벨이 새 1순위 기준으로 다시 계산되는 경우**(3단계 분리의 이유를 지키는 축).
- 도보 `toName` 유도: 첫 도보·환승 도보에 이름이 붙고 **마지막 도보에는 붙지 않는다**. 환승 통로 필터 뒤에 유도가 도는지.
- `arrive` 조건: 마지막이 도보인 경로와 탑승인 경로.

**컴포넌트**
- 도보 30분 경계(초과 시 접힘, 이하 펼침), `error`·`empty`에 disclosure 부재.
- 계단 회피 재조회 후 사용자 펼침 상태 보존, 새 조회 후 자동 복귀.
- 대안 번호 매기기(축 경로가 번호를 소비하지 않음).
- 안내 세션 활성 대안의 접힘 클릭 무시가 5개 목록에서도 성립.

**실호출(머지 게이트)**
- 자택→서울역: 무환승 370번 경로가 대안 목록에 오르고 `highlight`가 붙는가.
- 자택→강동역: 최단 축이 추천과 다른 경로에 붙는가, 환승 축은 생기지 않는가.
- 700m 이내 좌표쌍: `-98`로 대중교통 경로 없음이 유지되는가(단거리에서 도보가 자동으로 1차 수단이 되는 경로).

**기존 게이트**: `format-drift.test.ts`(거리 표기 3벌 동조), `i18n-messages.test.ts`, `check-xcstrings-keys.mjs`, `formatter-coverage.test.ts`.

## 8. 변이 주입 점검

계약 테스트가 있다는 사실과 그 축이 실제로 지켜진다는 사실은 다르다. 최소 네 곳에 변이를 주입해 검출력을 확인한다: ①`selectTransitRoutes`에서 축 선정을 제거하고 추천순 5개로 되돌린다 ②`annotateHighlights`를 강등 **앞**으로 옮겨 낡은 기준으로 라벨을 붙이게 한다 ③도보 `toName` 유도를 한 칸 밀어 잘못된 역 이름을 붙인다 ④도보 접힘 문턱을 무한대로 만들어 항상 펼침이 되게 한다. 넷 다 테스트가 잡지 못하면 그 테스트는 축을 지키지 않는다.

## 9. 비범위 (백로그 후보)

- **"도보가 가장 짧은 경로" 3번째 축**: 위원장 판정으로 2축 시작. 실사용에서 필요가 확인되면 더한다.
- **대안 5개 초과**: 접힘 버튼이 자동차·도보 heading을 밀어내는 선을 실사용으로 확인한 뒤.
- **도보 요약의 시간 표기**("약 190분" → "약 3시간 10분"): 3벌 미러(웹·iOS·CLI)를 건드리는 별개 축이고, 이번 변경으로 회귀하지 않는다(접힘 라벨이 기존 문구를 그대로 쓴다).
- **경로 대안 데이터원 확장(E6)**: 위원장 보류 유지. 이 스펙은 ODsay 단일 데이터원으로 성립한다. 덧붙이면, 통합 경로 관점에서 후보 비교는 오히려 ODsay 유지에 유리하다(카카오 publictraffic은 첫·끝 도보 leg가 없고 서교공 path2는 지하철 전용이라, 첫·끝 도보를 포함한 조합 경로를 주는 것은 ODsay뿐이다).
- **계단 회피 상태가 실시간 도보 안내에 미전달(백로그 A4)**: 재편과 독립된 정합 결함이라 별도로 처리한다.
- **자동차 섹션 강등**: 브리핑이 요약 중심이라 분량 문제가 없다.

## 10. 리뷰 포커스

- 축 선정과 운행시간 강등의 **순서**가 만드는 상태(운행 밖 경로에 축 라벨이 붙는 경우)가 사용자에게 정직하게 보이는가.
- 도보 접힘의 3값 상태(자동·펼침·접힘)가 계단 회피 재조회·새 조회·목적지 편집·스왑 전이에서 일관된가.
- 대안 번호 재매김이 안내 시작 버튼의 포커스 복귀 대상(`GuideStartButton.transitAlt(Int)`)과 어긋나지 않는가.
- 마지막 도보의 목적지 이름 주입이 소비자마다 갈리지 않는가(웹·iOS는 이름 있음, CLI는 없을 수 있음).
