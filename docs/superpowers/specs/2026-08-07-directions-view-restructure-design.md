# 길찾기 화면 재편 (도보 강등·대안 축·도보 구간 정보) 설계

> 2026-08-07. 위원장 제기: "모든 길찾기 조회에 획일적으로 3수단 결과를 주는 것이 최선인가". 원설계는 `2026-07-21-walk-route-directions-tab-design.md`(3수단 병렬 비교), 대중교통 정규화는 `2026-06-18-odsay-transit-routing-design.md`, 운행시간 강등은 `2026-08-01-odsay-service-hours-design.md`, 안내 진입점은 `2026-08-03-mode-entrypoints-car-guidance-design.md`·`2026-08-04-transit-guidance-design.md`가 정본이다. **codex 적대적 리뷰(gpt-5.6-sol·high, 21건) 반영본이며 반영·기각 내역은 §11.**
>
> **전제 교정 하나를 먼저 기록한다.** 착수 전 가설은 "대중교통과 도보를 통합하려면 여러 API를 앱이 조합 계산해야 한다"였으나, ODsay `searchPubTransPathT`가 이미 도보·버스·지하철 조합 경로를 계산해 준다. 재편은 API 조합이 아니라 **이미 받고 있는 데이터의 노출 방식** 문제다. 경로 대안 데이터원 확장(백로그 E6)은 위원장 보류 상태이고 이 스펙은 그 판정을 건드리지 않는다.

## 1. 배경과 목표

세 가지 관찰에서 출발한다.

1. **장거리에서 도보 상세는 정보가 아니라 장애물이다.** 자택에서 서울역까지 도보 경로는 12.8km, 약 3시간이고 턴바이턴 스텝이 수백 행이다. 채택 가능성이 사실상 0인 이 목록이 화면 끝까지를 채운다. 원설계가 도보를 최하단에 둔 것(2026-07-22 위원장 결정, "분량 최다·검색 빈도 최저")은 이미 같은 문제 인식의 소프트 대응이었다.
2. **의미 있는 대안이 잘려 나가고 있다.** ODsay는 길동에서 서울역까지 경로를 9개 주는데 `normalizeOdsayRoute`가 앞 3개만 취한다. 실호출 확인 결과 7번째 경로가 **370번 버스 직통, 환승 0회**다. 시각장애 사용자에게 환승은 낯선 역에서 방향을 다시 잡는 가장 비싼 동작이므로 26분을 더 쓰더라도 택할 이유가 있는데, 이 선택지는 화면에 도달할 수 없다.
3. **도보 구간이 "도보 N분"으로만 표현된다.** ODsay는 도보 구간마다 거리를 주지만 정규화가 분만 남긴다. 어디까지 걷는지, 몇 미터인지가 UI에 존재하지 않아 대중교통 경로의 실제 부담을 판단할 수 없다.

**측정 가능한 성과**

1. 장거리 조회에서 **도보 섹션이 차지하는 접근성 객체 수가 수백에서 한 자리로 줄어**, 도보 heading에 착지한 사용자가 요약만 듣고 판단을 끝낼 수 있다(펼치지 않는 한 상세를 지나칠 필요가 없다).
2. 무환승 경로가 존재하는 조회에서 **그 경로가 화면에 오르고 축 이름으로 발견된다**(길동→서울역 370번이 현재는 도달 불가).
3. 각 도보 구간의 **행선지와 거리가 낭독된다**("길동역까지 도보 3분, 178m").

⚠ 성과 1을 "대중교통 heading에서 자동차 heading까지의 스와이프 감소"로 서술하면 **거짓이다.** 도보는 최하단이라 그 사이를 지나가지 않는다. 이득은 페이지 끝단의 부피이지 수단 간 이동 비용이 아니다(적대적 리뷰 #12).

## 2. 확정 판단

| 사안 | 확정 | 근거 |
|---|---|---|
| 도보 강등 판정 축 | **이미 조회한 도보 경로의 소요 시간** | 직선거리는 육교·우회로를 반영하지 못한다. 소요 시간은 병렬 조회 결과에 이미 있어 **추가 API 호출 0**이고 사용자가 실제로 판단하는 값과 같다 |
| 문턱 | **표시 분 값 > 30** (위원장 판정) | 잘못 접은 비용(스와이프 1회)이 잘못 펼친 비용(수백 행)보다 훨씬 작은 비대칭. **판정과 표시가 같은 분 값을 써야** 경계에서 "약 30분인데 접혔다"가 안 생긴다(리뷰 #20) |
| 도보 배치 | **제자리(최하단) 유지, 내용만 접는다** | 수단 h3 3개가 heading 로터 점프 경로다(원설계 §5). 대중교통 하위로 옮기면 그 경로가 사라지고, 대중교통이 경로 없음일 때 실패한 섹션 안에서 성공한 수단을 찾게 된다. 접힘은 **깊이**를 조절하는 도구이지 **소속**을 바꾸는 도구가 아니다 |
| 대안 개수 | **추천 1 + 최대 4 = 최대 5** (위원장 판정) | 축 경로가 묻히지 않으면서 접힘 버튼이 화면을 채우지 않는 선 |
| 대안 축 | **최단 시간·최소 환승 2개** (위원장 판정) | "도보 최소" 3번째 축은 실사용 판정 후로 미룬다(§10) |
| **파이프라인 순서** | **정규화(전체) → 운행상태 강등(전체) → 선정(5) → 축 라벨** | 선정을 강등보다 앞에 두면 **선정 밖의 유일한 운행 중 경로를 영영 못 본다**(리뷰 #2). 비용 우려는 실측으로 기각: 시간표 조회는 노선·역 단위 **중복 제거 + 24시간 revalidate 캐시**라 상한이 4콜에서 12콜이고 재사용률이 높다(§3.3) |
| 축 라벨과 운행 상태 | **`outside` 경로에는 축 라벨을 주지 않는다** | 접힌 disclosure의 접근명에는 운행 상태가 없어, 버튼 목록에서 "가장 빠른 경로"만 듣고 펼쳐야 운행 종료를 안다(리뷰 #4). 권할 수 없는 경로에 권유 라벨을 붙이지 않는다 |
| 도보 구간 행선지 | **다음 탑승 구간의 `startName`에서 유도** | ODsay 도보 subPath는 `trafficType`·`distance`·`sectionTime` 3필드뿐이다(2026-08-07 실호출, §3.1). 이름은 응답에 없다. 유도의 일반성은 두 지역 25경로 실호출로 확정했다(§7 통과) |
| 마지막 도보의 의미 | **이름을 몰라도 "목적지까지"는 안다** | 이름 부재와 구간 의미 부재는 다른 층이다(리뷰 #9). 이름을 아는 소비자는 이름을, 모르는 소비자는 "목적지까지"를 쓴다 |
| 거리 표기 | **`formatDistance` 정본 경유, 직접 조립 금지** | 지역 사본 4곳이 갈려 850m를 "0.8km"로 낸 실사고. `format-drift.test.ts`가 강제 |
| 절단 노출 | **응답에 `totalCandidates`를 싣는다. UI 표기는 하지 않는다** | 조용한 절단 금지(리뷰 #1). 다만 표기 심사는 "사용자 행동을 바꾸는가"이고 후보 총수는 바꾸지 않는다(소아진료 `total` 선례, 정직성 표기는 API 계층 계약) |
| 획일성 완화의 범위 | **도보 섹션만** | 자동차 브리핑은 요약 중심이라 분량 문제가 없고, 위원장이 제기한 것도 도보다. YAGNI |

원설계의 유효 계약을 전부 승계한다: 3수단 `Promise.allSettled` 병렬, 수단별 독립 3-state, 단일 polite 합산 통지, 수단 순서 대중교통→자동차→도보, en 로케일 도보 미노출.

## 3. 데이터 계층 (ODsay 정규화)

### 3.1 실호출로 확정된 응답 계약 (2026-08-07)

자택(127.1420, 37.5380) → 서울역(126.9707, 37.5547):

```
path[0] info: totalWalk=399, totalTime=45, payment=1750,
              busTransitCount=0, subwayTransitCount=2, totalWalkTime=-1
subPath: [
  {trafficType:3, distance:178, sectionTime:3},                    ← 도보 3필드뿐
  {trafficType:1, distance:14200, sectionTime:26, startName:"길동", endName:"동대문역사문화공원", stationCount:13},
  {trafficType:3, distance:0,   sectionTime:3},                    ← 환승 통로
  {trafficType:1, distance:3600,  sectionTime:7,  startName:"동대문역사문화공원", endName:"서울역", stationCount:4},
  {trafficType:3, distance:221, sectionTime:3}                     ← 마지막 도보
]
```

확정 사항 넷:

- **도보 subPath의 키는 `trafficType`·`distance`·`sectionTime` 셋뿐이다.** `startName`/`endName`이 없다.
- `totalWalk`(399m)는 거리 합이고 환승 통로(0m)를 포함하지 않는다. `totalWalkTime`은 `-1`(정보 없음 마커)이므로 **쓰지 않는다**. 총 도보 시간은 현행대로 `sectionTime` 합으로 센다.
- `subwayTransitCount:2`는 탑승 구간 수이지 환승 횟수가 아니다(탑승 leg 2개, 환승 1회). **환승 횟수를 leg 수에서 계산하는 기존 결정을 유지**하고 `*TransitCount`를 쓰지 않는다.
- ODsay는 이 좌표쌍에 **경로 9개**를 준다.

⚠ **이 관찰은 지하철 전용 경로 하나에서 나왔다.** 버스 단독, 버스 간 환승, 버스·지하철 혼합, 연속 도보, 첫·끝 구간 0m 같은 패턴에서 같은 계약이 성립하는지는 **미확정**이다(리뷰 #7·#8). §7의 실호출 게이트가 이를 확정했다(2026-08-07 통과). 다만 관측되지 않은 모양에 대한 방어는 유지한다.

### 3.2 도보 구간에 거리와 행선지를 싣는다

`TransitLeg`에 `distanceMeters?: number`를 더한다. 도보 구간 전용이고 탑승 구간에는 싣지 않는다(탑승 거리는 정거장 수가 이미 표현하며 낭독에 더할 값이 아니다).

**3-state를 지킨다**(리뷰 #5). `distance`가 없거나 유한한 0 이상 수가 아니면 **필드를 싣지 않는다**. 0을 넣거나 `NaN`을 흘리면 "정보 없음"이 "0m"로 둔갑한다. 표시 계층은 필드 부재 시 거리 없는 문구로 떨어진다(§4.3).

⚠ `sectionTime`(분)에는 같은 처리를 하지 않는다. `TransitLeg.minutes`가 **필수 필드**라 3-state를 표현하려면 타입과 전 소비자를 바꿔야 하는데, §7에서 결측이 0건이었고 이 재편의 목적과 무관한 확장이다. 현행 `sectionTime ?? 0`을 유지하고, 결측이 관측되면 그때 별도로 다룬다(YAGNI).

행선지는 기존 `toName` 필드를 재사용한다. 이 필드의 의미는 이미 "이 구간의 끝"이라 도보에도 그대로 성립한다. 유도 규칙은 하나다:

> **도보 구간의 `toName` = 그 뒤 첫 탑승 구간의 `fromName`. 뒤에 탑승 구간이 없으면 설정하지 않는다.**

이 한 규칙이 첫 도보(출발지→첫 승차역)와 환승 도보(하차역→다음 승차역)를 함께 처리한다. 유도는 환승 통로 필터링 **뒤**의 legs 배열에서 수행한다.

`fromName`은 도보에 설정하지 않는다. "○○까지 도보 N분"이 성립하는 데 출발점 이름이 필요하지 않고, 첫 도보의 출발점은 provider가 이름을 모른다.

### 3.3 파이프라인: 강등 → 선정 → 라벨

`paths.slice(0, 3)`을 **순수 함수 3단계 + 기존 강등**으로 교체한다. 순서가 계약이다.

**0단계 정규화**: ODsay 응답의 **모든** path를 `TransitRoute`로 정규화한다.

⚠ **응답 스키마 위반은 throw한다**(리뷰 #3). 현행 `data.result?.path ?? []`는 `result` 자체가 없는 응답을 "경로 없음"(null)으로 바꿔 **조회 실패와 0건을 합친다.** 3-state 위반이며, 인증 게이트웨이 변화나 부분 장애가 사용자에게 "대중교통 경로가 없습니다"로 도달한다. 계약을 가른다:

| 응답 | 처리 |
|---|---|
| error 코드가 `-98` 등 경로 없음류 | `null` (graceful) |
| error 그 외 | throw (기존) |
| `result.path`가 배열이고 길이 0 | `null` (진짜 0건) |
| `result` 또는 `result.path`가 없거나 배열이 아님 | **throw** (스키마 위반 = 장애) |

⚠⚠ **ODsay error 봉투는 두 모양이고 키 이름도 갈린다**(2026-08-07 실호출 신규 발견, 리뷰 밖):

```
객체: {"error": {"code":"-98", "msg":"출, 도착지가 700m이내입니다."}}        경로 없음
배열: {"error": [{"code":"500","message":"[ApiKeyAuthFailed] ..."}]}        인증 실패
```

현행 `data.error.code`는 배열에서 `undefined`가 되어 코드 판정이 통째로 무력화된다. 지금은 배열로 오는 것이 인증 실패뿐이라 throw가 정답이지만, **배열 모양으로 경로 없음류 코드가 오는 순간 그것이 502 장애로 둔갑한다.** `datagokr-envelope`가 "단건 응답 모양이 기관마다 다르다"를 공용 파서로 흡수한 것과 같은 계열이다. 두 모양을 다 받는 판독 함수를 두고(배열이면 첫 원소, `msg ?? message`), 코드 판정은 그 결과로만 한다. 무효 키가 **HTTP 200**으로 온다는 점도 함께 기록한다(HTTP 상태로는 인증 실패를 못 가른다).

**1단계 강등** (`annotateServiceStatus`, 기존 함수 재사용): 정규화된 **전체** 경로에 운행 상태를 싣고 안정 정렬한다.

비용 실측(2026-08-07, 길동→서울역 9경로): 시간표 조회 키는 3경로 4개, 5경로 7개, 9경로 12개다. 겉보기 3배지만 **`fetchServiceHoursMap`·`fetchSubwayServiceHoursMap`이 노선·역 키로 중복을 제거하고 각 조회에 `revalidate: 86400`이 걸려 있어**, 12는 캐시 완전 미스 상한이고 실사용 재사용률이 높다. 이 비용으로 "선정 밖의 유일한 운행 중 경로를 못 보는" 결함(리뷰 #2)을 사는 것은 타당하지 않다.

**2단계 선정** (`selectTransitRoutes(routes): { selected, totalCandidates }`)

```
base = routes[0]                      (강등 후 1순위)
pool = routes[1..]
축 후보는 serviceStatus가 outside가 아닌 경로로 제한한다(리뷰 #4)
minTransfers = 축 후보 중 transfers < base.transfers 인 것들의 transfers 최소값.
               동률이면 pool 앞선 것(정렬 순서 보존)
minMinutes   = 축 후보 중 totalMinutes < base.totalMinutes 인 것들의 totalMinutes 최소값.
               동률이면 pool 앞선 것
selected = [base] + [뽑힌 축 경로(중복 제거)] + [나머지를 정렬순으로 채워 총 5개까지]
totalCandidates = routes.length
```

pool이 비면 `selected`는 `[base]` 하나다(대안 0개).

**3단계 라벨** (`annotateHighlights(selected): TransitRouteResult`)

최종 순서가 확정된 뒤 `selected[0]`을 기준으로 축을 다시 판정해 `highlight`를 싣는다. 2단계의 축 판정은 **후보를 뽑기 위한 것**이고 3단계는 **표시할 이름을 정하는 것**이라, 두 곳에서 같은 비교를 하는 것이 중복이 아니라 역할 분리다(2단계는 5개 밖을 보고, 3단계는 5개 안만 본다).

**`highlight`는 enum이 아니라 축 집합이다**(리뷰 #6). 한 경로가 최단이면서 최소 환승일 수 있고, 그때 한쪽을 버리면 가장 유용한 조합을 숨긴다. 종전 근거였던 "라벨 2개는 분절을 늘린다"는 **틀렸다**: 쉼표로 이은 단일 텍스트 노드는 하나의 접근성 객체이고, 분절을 만드는 것은 시각 스타일용 별도 `span`이다.

**표시 번호도 서버가 정한다**(리뷰 #15). 축 없는 대안에 `displayIndex`(1부터)를 싣는다. 번호 계산을 클라이언트에 두면 웹·iOS·CLI 세 벌이 갈리고, 그 갈림을 잡는 테스트가 없다(`format-drift.test.ts`는 거리만 본다).

**안정 식별자**를 싣는다(리뷰 #14). 각 경로에 `routeKey`(응답 안에서 유일)를 부여하고, 활성 안내 세션 추적·강제 펼침·포커스 복귀는 **배열 인덱스가 아니라 이 키로** 한다. 인덱스는 표시 순서가 바뀌면 다른 경로를 가리킨다.

### 3.4 잘못된 위치의 도착 문구를 제거한다

현재 구간 목록 뒤에 항상 `arrive`("○○ 도착", `summary.arriveName ?? dest`) 문단이 붙는다. 마지막 구간이 도보일 때 그 도보는 **마지막 하차역에서 목적지로** 걷는 것이므로, 그 뒤에 하차역 이름으로 "도착"을 말하면 순서가 거꾸로다. §3.2로 마지막 도보가 목적지 의미를 갖게 되면 이 문단은 잉여이기까지 하다.

> **`arrive` 문단은 마지막 leg가 탑승일 때만 렌더한다.**

⚠ 이 판정이 **`distance === 0` 도보 필터에 의존한다**(리뷰 #8). 첫·끝 구간이 0m인데 시간이 있는 응답이 존재하면, 그 도보가 필터에 제거되어 마지막이 탑승이 되고 목적지가 아닌 하차역 이름으로 "도착"을 말한다. §7 게이트에서 25경로를 조사한 결과 0m 도보는 전부 중간(지하철 환승 통로)이었고 첫·끝 0m는 없었다. 전제가 성립하지만, 이후 관측되면 위치(첫·끝)를 필터 조건에 더한다.

이는 재편이 만든 결함이 아니라 재편이 드러낸 기존 결함이며, 같은 줄을 건드리므로 함께 고친다.

## 4. 표시 계층

### 4.1 대안 표시 이름

서버가 준 `highlight`(축 집합)와 `displayIndex`를 문구로 옮기기만 한다.

| 조건 | 이름 |
|---|---|
| 축에 `fewestTransfers`와 `fastest`가 모두 있음 | `alternativeFastestFewestTransfers` = "가장 빠르고 환승도 가장 적은 경로" |
| `fewestTransfers`만 | `alternativeFewestTransfers` = "환승이 가장 적은 경로" |
| `fastest`만 | `alternativeFastest` = "가장 빠른 경로" |
| 없음 | `alternativeHeading` = "대안 경로 {index}" (`displayIndex` 주입) |

disclosure 라벨은 현행대로 `joinText(이름, 요약, 도보 요약)`이다. 라벨이 곧 요약 전문이므로 펼침 본문은 `includeSummary=false`를 유지한다.

### 4.2 안내 시작 버튼 라벨

`beacon.guideStartTransitAlt`를 `"대안 경로 {index} 안내 시작"`에서 **`"{name} 안내 시작"`**으로 바꾸고 §4.1의 이름을 주입한다. 스크린 리더 버튼 목록·항목 선택기가 heading 문맥 없이 이름만 나열한다는 2026-08-06 판정의 연장이며, 번호보다 축 이름이 구분에 강하다.

포커스 복귀 대상(`GuideStartButton.transitAlt`)은 **`routeKey`를 키로 쓴다**(리뷰 #13·#14). 표시 번호와 배열 인덱스가 다른 좌표계이므로 둘 중 어느 것도 포커스 키로 쓰지 않는다.

### 4.3 도보 구간 문장

| `toName` | 거리 필드 | 소비자가 목적지 이름을 앎 | 문구 |
|---|---|---|---|
| 있음 | 있음 | 무관 | `legWalkTo` = "{name}까지 도보 {minutes}분, {distance}" |
| 있음 | 없음 | 무관 | `legWalkToNoDistance` = "{name}까지 도보 {minutes}분" |
| 없음(마지막) | 있음 | 예 | `legWalkTo`에 목적지 이름 주입 |
| 없음(마지막) | 없음 | 예 | `legWalkToNoDistance`에 목적지 이름 주입 |
| 없음(마지막) | 있음 | 아니오 | `legWalkToDest` = "목적지까지 도보 {minutes}분, {distance}" |
| 없음(마지막) | 없음 | 아니오 | `legWalkToDestNoDistance` = "목적지까지 도보 {minutes}분" |

이름을 몰라도 **"목적지까지"라는 구간 의미는 항상 안다**(리뷰 #9). 거리는 `formatDistance`를 지난다. 한 구간은 한 텍스트로 합쳐 쉼표로 잇는다(인라인 span 분절 금지).

### 4.4 도보 섹션 조건부 접힘

- **판정**: 도보 조회가 `done`이고 **표시 분 값이 30을 넘으면** 접힌 상태로 시작한다. 판정과 라벨이 같은 분 값을 써야 경계에서 모순이 안 생긴다(리뷰 #20). `error`·`empty`는 접을 상세가 없으므로 현행 그대로 한 줄 문구를 낸다.
- **접히는 것은 상세뿐이다.** 계단 회피 토글과 도보 안내 시작 버튼은 접힘 **밖**에 남는다.
- **안내 세션 계약**(리뷰 #10): 도보 안내 세션의 상태와 세션 UI는 **접힘 바깥 계층이 소유**한다. 접힘 본문의 마운트·언마운트가 세션 수명에 영향을 주어서는 안 된다. 대중교통 대안에서 "접힘 unmount가 세션을 조용히 죽인" 결함을 이미 겪었으므로 같은 함정을 도보에서 반복하지 않는다. 이 불변식은 테스트로 못 박는다(§8).
- **라벨**은 기존 `route.pedestrian.summary`("총 {distance}, 약 {minutes}분")를 그대로 쓴다.
- **상태는 3값**(`자동`·`펼침`·`접힘`)이고 자동일 때만 문턱 판정을 적용한다. 전이표(리뷰 #11):

| 전이 | 상태 |
|---|---|
| 새 조회(조회 버튼) | `자동`으로 복귀 |
| 계단 회피 토글 재조회 | 보존 |
| 출발지·도착지 편집, 스왑, 최근 장소 선택 | `자동`으로 복귀 (결과도 함께 비워진다) |
| 사용자가 disclosure를 조작 | `펼침` 또는 `접힘` |
| 이전 요청의 늦은 완료 | **무시**(기존 요청 ID latest-wins 가드를 따른다. 늦게 도착한 응답이 현재 상태를 바꾸지 않는다) |

## 5. 접근성 계약 (승계 + 신규)

승계(변경 금지):

1. **조회 완료 후 포커스를 옮기지 않는다**(2026-08-02 위원장 판정). 계단 회피 토글 재조회만 예외로 도보 heading 이동을 유지한다.
2. **세션 단일성**과 패널 언마운트 전이의 명시 중지·`beacon.stopped` 통지.
3. **안내 세션이 살아 있는 대안의 접힘 클릭은 무시한다.** 대안이 5개로 늘어도 동일하며, 대상 판정은 `routeKey`로 한다.
4. 수단 h3 3개 구조와 순서 불변.
5. 한 줄은 한 접근성 객체. 거리·축 라벨은 쉼표로 이어 붙이고 시각용 span으로 쪼개지 않는다.

신규:

6. **도보 disclosure는 버튼이 발견 경로이므로 본문은 `<div>`**(region·heading 부여 금지, 헌장 §3). iOS는 `DisclosureGroup`이 정본이다.
7. **접힘·펼침에 별도 live region 통지를 두지 않는다.** `aria-expanded`(iOS는 `DisclosureGroup` 상태)가 이미 상태를 말한다.
8. **축 라벨은 통지가 아니라 이름이다.** 조회 완료 통지는 현행 단일 합산 문장을 유지하고 "무환승 경로가 있습니다" 같은 문장을 더하지 않는다.
9. **운행하지 않는 경로에 권유 라벨을 붙이지 않는다**(§2). 접힌 상태의 접근명이 그 경로를 권하는 것처럼 들려서는 안 된다.

## 7. 착수 전 실호출 확정: **통과** (2026-08-07)

§3.1의 관찰이 한 경로 패턴에서 나왔으므로 구현 전에 확정했다. 대상은 자택→서울역 9경로(지하철 전용·버스 전용·버스 간 환승·버스와 지하철 혼합 전 패턴 포함)와 부산 서면→해운대 16경로다.

| # | 확인 | 결과 |
|---|---|---|
| 1 | 전 패턴에서 도보 subPath가 같은 3필드인가 | **그렇다.** 두 지역 25경로의 도보 키 합집합이 `trafficType,distance,sectionTime`뿐 |
| 1 | 뒤 첫 탑승의 `startName`이 실제 도보 행선지와 맞는가 | **맞다.** 결측 0건이고 의미도 정확하다: `도보(182m) > 버스[130: 길동역1번출구→동대문구청] > 도보(371m) > 지하철[1호선: 제기동→서울역]`에서 중간 도보의 유도 행선지 "제기동"은 실제로 동대문구청에서 제기동역까지 걷는 구간이다. 버스 정류장 이름도 그대로 성립한다 |
| 2 | 연속 도보 subPath가 존재하는가 | **없다**(25경로 0쌍). 유도 규칙에 예외가 필요 없다 |
| 3 | 첫·끝 구간이 `distance:0`인 응답이 있는가 | **없다.** 0m 도보 4건은 전부 중간이고 모두 지하철 사이 환승 통로다. §3.4의 `arrive` 판정 전제가 성립한다 |
| 4 | `distance`·`sectionTime` 필드 자체가 없는 도보가 있는가 | **관측되지 않았다.** §3.2의 3-state 분기는 도달하지 않을 수 있으나 **방어는 유지한다**(관측되지 않음 ≠ 없음) |
| 5 | `result` 누락 응답의 실재 | **무효 키로 재현.** HTTP 200 + error 배열이고 `result`가 없다. 이 경로는 error 분기가 먼저 잡지만, 그 과정에서 **error 봉투 2형**을 발견해 §3.3에 반영했다 |

⚠ **부산은 경로를 16개 준다**(수도권 9개보다 많다). 5개 선정 시 11개를 버리므로 `totalCandidates` 노출(§2)의 무게가 더 크다.

⚠ 버스 정류장 이름은 "길동주민센터.둔촌2동주민센터"처럼 마침표로 이은 복합명이 온다. 도보 문구에 그대로 들어가므로 낭독이 길어지지만, 같은 이름이 이미 `legBoard`("○○에서 △△ 승차")에 쓰이고 있어 신규 회귀가 아니다. 원문 통과가 정본이며 축약하지 않는다.

## 8. 테스트·게이트

**순수 함수(fixture 단위)**
- `selectTransitRoutes`: 9경로 fixture에서 5개 선정(무환승 7번째가 뽑히는가), `outside` 경로가 축 후보에서 빠지는가, 후보 5개 미만, pool 빈 경우, `totalCandidates` 정확성.
- `annotateHighlights`: 축 없음, 두 축 동시 만족(조합 라벨), 축 동률, `displayIndex` 부여.
- 강등이 1순위를 바꾼 뒤 축이 **새 1순위 기준**으로 계산되는가.
- 도보 `toName` 유도(첫·환승 도보에 붙고 마지막엔 안 붙음), 환승 통로 필터 뒤에 도는가.
- `distanceMeters` 3-state: 필드 없음·비수치·음수에서 필드를 싣지 않는가.
- 스키마 위반 throw vs 0건 null 분기.
- `arrive` 조건(마지막이 도보/탑승).

**합성(배선) 테스트**: 순수 함수 개별 통과가 배선을 보장하지 않는다(리뷰 #16). 원시 ODsay 응답 + 시간표 조회 스텁을 넣어 **최종 직렬화 응답까지** 검증한다: 단계 호출 순서, 반환값 소비, 5개 상한, 라벨이 강등 뒤 기준인가.

**컴포넌트**
- 도보 30분 경계(초과 접힘, 이하 펼침), `error`·`empty`에 disclosure 부재.
- §4.4 전이표 전항목.
- **접힘·펼침이 도보 안내 세션을 죽이지 않는다**(§4.4 계약).
- 대안 번호(`displayIndex`)와 `routeKey` 기반 세션 추적·강제 펼침·포커스 복귀.

**접근성 실측**(리뷰 #17): 구조 테스트로는 증명되지 않는 축이다.
- 웹: Chrome 접근성 트리로 disclosure 접근명 실측(축 라벨 + 요약이 한 객체인가, 분절이 없는가).
- iOS: **실기기 VoiceOver**로 도보 `DisclosureGroup` 상태 낭독, 대안 버튼 목록 순서, 안내 시작 후 포커스 복귀 착지점. SwiftUI 접근성 포커스는 시뮬레이터로 검출되지 않는다는 기존 계약을 따른다.

**실호출(머지 게이트)**
- §7의 5개 항목.
- 길동→서울역: 무환승 370번이 대안 목록에 오르고 축 라벨이 붙는가.
- 길동→강동역: 최단 축이 추천과 다른 경로에 붙는가, 환승 축은 생기지 않는가.
- 700m 이내: `-98`로 대중교통 경로 없음이 유지되는가.
- **심야 시간대**: 강등 후 1순위가 바뀌고 축 라벨이 새 1순위 기준으로 계산되는가, `outside` 경로에 축 라벨이 없는가.

**기존 게이트**: `format-drift.test.ts`, `i18n-messages.test.ts`, `check-xcstrings-keys.mjs`, `formatter-coverage.test.ts`.

## 9. 변이 주입 점검

계약 테스트가 있다는 사실과 그 축이 지켜진다는 사실은 다르다. **생산 코드 경로에** 변이를 주입해 검출력을 확인한다(순수 함수만 변이시키면 배선을 못 본다).

1. `selectTransitRoutes`에서 축 선정을 제거하고 정렬순 5개로 되돌린다.
2. `annotateHighlights` 호출을 강등 **앞**으로 옮긴다.
3. 축 후보의 `outside` 제외를 없앤다.
4. 도보 `toName` 유도를 한 칸 밀어 잘못된 역 이름을 붙인다.
5. `distanceMeters`에 `distance ?? 0`을 넣어 3-state를 뭉갠다.
6. 도보 접힘 문턱을 무한대로 만든다.
7. 세션 추적을 `routeKey`에서 배열 인덱스로 되돌린다.

일곱 중 하나라도 테스트가 잡지 못하면 그 축은 지켜지지 않는다.

## 10. 비범위 (백로그 후보)

- **"도보가 가장 짧은 경로" 3번째 축**: 위원장 판정으로 2축 시작. 실사용에서 필요가 확인되면 더한다.
- **축 동률 경로 전부에 라벨 부여**(리뷰 #21): 현재는 동률 중 앞선 하나만 라벨을 받는다. 요약에 환승 수·시간이 있어 판별 가능하므로 수용하되, 실사용에서 혼동이 확인되면 다시 본다.
- **대안 5개 초과**와 **절단 사실의 UI 표기**: `totalCandidates`는 응답에 있으므로 판단 재료는 남아 있다.
- **도보 요약의 시간 표기**("약 190분" → "약 3시간 10분"): 3벌 미러를 건드리는 별개 축이고 이번 변경으로 회귀하지 않는다.
- **경로 대안 데이터원 확장(E6)**: 위원장 보류 유지. 통합 경로 관점에서 후보 비교는 오히려 ODsay 유지에 유리하다(카카오 publictraffic은 첫·끝 도보 leg가 없고 서교공 path2는 지하철 전용이라, 첫·끝 도보를 포함한 조합 경로를 주는 것은 ODsay뿐이다).
- **계단 회피 상태가 실시간 도보 안내에 미전달(백로그 A4)**: 재편과 독립된 정합 결함.
- **자동차 섹션 강등**: 브리핑이 요약 중심이라 분량 문제가 없다.
