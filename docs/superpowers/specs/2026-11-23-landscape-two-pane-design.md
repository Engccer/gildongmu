# E91·B30. 가로 화면 지원과 두 칸 배치 (설계)

- 접수: BACKLOG E91(iOS)·B30(안드로이드), 2026-11-22 위원장 판정으로 등록. 계기는 한소네 7(가로 약 1024×576dp)에서 검색 탭의 고정 줄이 결과 칸을 잠식한 것(A82).
- 위원장 판정 2026-11-23(착수 세션, 네 건):
  1. 범위: 검색 탭 하나가 아니라 모든 탭에 가로 지원을 적용한다. 가로 지원으로 잃는 것이 적고 한 화면만 다루는 것은 통상적이지 않다.
  2. 순서: 설계는 한 번에, 구현은 iOS 먼저. 위원장의 실기기 VoiceOver 확인을 기다리지 않고 이어서 안드로이드로 옮기고 한소네에서 확인한다.
  3. 안내 중 회전: 실시간 안내 중에도 화면이 돌게 둔다(안드로이드와 같은 동작). 회전을 원하지 않는 사용자는 iOS 세로 방향 고정을 쓴다.
  4. 나눌 화면: 「입력하는 부분」과 「목록」 두 부분으로 된 검색·길찾기·채팅만 두 칸으로 나눈다. 내 주변·장소 상세·설정·안내 시트는 목록 하나라 지금 배치 그대로 가로에서 동작하게 한다.
- 설계 리뷰: 판별 기준 네 조건(새 불변식·상태 머신, 외부 연동, 되돌리기 어려운 변경, 안전·낭독 정확성)에 해당하지 않아 생략한다. 배치만 바꾸고 문장·판정·세션은 건드리지 않는다.

## 1. 지금 상태 (2026-11-23 조사)

- iOS는 아이폰 전용·세로 전용이다(`INFOPLIST_KEY_UISupportedInterfaceOrientations = UIInterfaceOrientationPortrait`, 세 구성 모두). 창 크기에 반응하는 코드는 없다.
- 안드로이드는 방향 잠금이 없어 지금도 화면이 돈다. 창 크기에 반응하는 코드는 안내 시트의 `BoxWithConstraints` 한 곳뿐이다.
- 검색·길찾기는 두 플랫폼 모두 화면 전체가 한 스크롤이다(안드로이드 검색만 결과 수 줄을 스크롤 밖 맨 위에 고정, A82). 채팅은 위치 표시줄·대화(스크롤)·입력줄 세 층이다.

## 2. 결정

### 2.1 가르는 기준 (창 크기, 기기 이름 아님)

- iOS: `verticalSizeClass == .compact`. 아이폰을 가로로 눕힌 모든 경우가 여기 들고 세로는 들지 않는다.
- 안드로이드: 창의 가로가 세로보다 길고 가로가 600dp 이상. 한소네 7(1024×576dp)과 가로로 눕힌 폰(약 800~900×360~410dp)이 함께 든다. Material의 높이 등급(480dp 미만이 compact)은 한소네가 빠지므로 쓰지 않는다. 판정은 순수 함수 한 곳(`isWideLowWindow`)에 두고 단위 테스트로 잠근다.

### 2.2 두 칸 배치 (검색·길찾기·채팅)

훑는 순서는 왼쪽 칸 다음 오른쪽 칸이고, 세로 배치와 같은 순서를 지킨다.

| 탭 | 왼쪽 칸 | 오른쪽 칸 |
|---|---|---|
| 검색 | 검색창, (안드로이드) 검색 버튼, 받아쓰기, 위치 표시줄, 정렬 버튼, (안드로이드) 결과 수 줄 | 최근 검색 또는 결과 목록. 이 칸만 결과에 따라 스크롤 |
| 길찾기 | 출발·도착·경유지·역 칸, 조회 버튼, 상태 문장, 해결 버튼 | 최근 경로, 안내 중 섹션, 여정 결과, 수단별 결과 |
| 채팅 | 위치 표시줄, 대화(스크롤) | (안드로이드) 통지 줄, 입력창과 버튼들 |

- 칸 너비: 검색·길찾기는 왼쪽 40%, 채팅은 대화 60%.
- iOS 검색창은 시스템 검색창(`.searchable`)이라 내비게이션 바에 그대로 있다. iOS에는 결과 수 줄이 없고 새로 만들지 않는다(결과 수는 종전처럼 통지).
- 안드로이드 검색의 결과 수 줄은 넓고 낮은 창에서 왼쪽 칸 맨 아래 스크롤 밖에 고정한다. 그래서 순서가 E91이 정한 검색창 → 검색 버튼 → 받아쓰기 → 결과 수 → 결과가 된다. 세로 창에서는 A82 배치(상단 고정)를 그대로 둔다.
- 왼쪽 칸은 내용이 넘치면 그 칸 안에서 스크롤한다(안드로이드 검색은 결과 수 줄만 스크롤 밖).
- 두 칸 사이를 오가는 포커스 착지(첫 결과 착지, 조회 뒤 착지, 답변 완료 착지)의 판정과 순서는 바꾸지 않는다.

### 2.3 한 칸 그대로 두는 화면

내 주변(허브·종류별), 장소 상세, 설정, 안내 시트, 그 밖의 시트는 배치를 바꾸지 않는다. 가로에서 잘리거나 가려지는 요소가 없는지만 확인하고, 있으면 그 자리만 고친다.

### 2.4 iOS 방향

- 세 구성(Debug·Release·Experimental) 모두 세로 + 가로 왼쪽·오른쪽을 지원한다. 거꾸로 세로는 넣지 않는다. 아이폰 전용은 그대로다.
- 화면별 방향 잠금은 두지 않는다(판정 3).

## 3. 구현

### 3.1 iOS

- `ios/Gildongmu/TwoPaneList.swift`: 앞 칸·뒤 칸 내용을 받아, 가로이면 `HStack { List(앞) ; List(뒤) }`, 아니면 `List { 앞 ; 뒤 }` 하나로 그리는 틀. 뒤 칸에만 얹는 덮개(검색 중·실패·0건)를 따로 받는다.
- `SearchView`·`DirectionsTabView`는 `List {`를 이 틀로 바꾸고 나누는 자리 한 곳을 표시한다. 행 내용·수식어·포커스 코드는 옮기지 않는다.
- `ChatConversationView`는 가로일 때 `HStack { 위치 표시줄 + 대화 ; 입력줄 }`로 그린다.
- `project.pbxproj`의 방향 설정 세 곳을 고친다.

### 3.2 안드로이드

- `a11y/WindowLayout.kt`: `isWideLowWindow(widthDp, heightDp)` 순수 함수와 현재 창에서 그 값을 읽는 컴포저블.
- `SearchScreen`·`DirectionsScreen`·`ChatScreen`은 넓고 낮은 창에서 `Row { 왼쪽 칸 ; 오른쪽 칸 }`로 그린다. 세로 창의 배치·계측 테스트는 그대로다.

## 4. 검증

- iOS: 시뮬레이터를 가로로 돌려 세 탭의 요소 순서(왼쪽 칸 → 오른쪽 칸)와 나머지 화면이 잘리지 않는지 확인한다. 세로에서 종전 순서가 그대로인지도 확인한다. 실기기에는 정식판·실험판 둘 다 설치한다.
- 안드로이드: `isWideLowWindow` 단위 테스트, 세 화면의 계측 테스트(넓고 낮은 창에서 순서와 결과 수 줄에 스크롤 조상이 없음), 한소네 7 대본(B30이 요구한 것: 「다음 줄」로 결과 끝까지 도달, 결과 수 통지 뒤 첫 결과 착지).
- 위원장 실기기 확인으로 남는 것: VoiceOver로 가로에서 세 탭을 훑는 순서, 회전 직후 커서 위치, 안내 중 회전 시 안내 음성. TalkBack 폰 가로.

## 5. 알려진 위험

- 한소네는 화면에 보이는 편집창이 커서를 붙잡을 때가 있다(PATTERNS 「스크롤 영역을 좁히거나 낭독 순서를 바꾸는 배치는…」 ②). 두 칸에서는 검색창이 늘 화면에 있으므로 첫 결과 착지를 한소네에서 반드시 잰다.
- 왼쪽 칸이 넘쳐 스크롤이 생기면 한소네에서 그 칸의 화면 밖 행에 「다음 줄」로 닿는지 잰다(같은 절 ①).
- iOS에서 회전하면 두 칸과 한 칸 사이에서 목록이 새로 그려져 스크롤 위치와 VoiceOver 커서가 처음으로 돌아갈 수 있다. 첫 판에서는 보존 장치를 넣지 않고 위원장 실기기 확인에서 거슬리는지 판정받는다.
