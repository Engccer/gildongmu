# 승차 중 현재역을 실제 열차 위치로 채운다 (E35)

> 판정 한 줄(리뷰 게이트): 새 외부 계약(서울 `realtimePosition`)과 승차 상태 머신 옆에 붙는 표시 상태라 **설계 단계 적대적 리뷰 대상**이다(글로벌 codex 운영 ①·②). 리뷰 결과는 §10.

## 0. 요지

승차(riding) 중 경유역 목록의 "현재 위치" 표식은 지금 하차역 **도착** 정보의 `arvlMsg3`에서만 나온다. 그 값은 내 열차가 하차역 도착 목록에 실린 뒤에야 생기므로 승차 초반 10분 안팎은 표식이 없다(2026-09-09 실측 10분 54초). 서울 실시간 **열차 위치**(`realtimePosition`)는 노선 단위로 운행 중 열차의 현재역을 주고, 그 열차번호(`trainNo`)는 도착 API `btrainNo`와 같은 식별자다. 잠근 열차를 열차번호로 찾아 **표식만** 채운다.

**표시 전용 계약**: 승차 상태 머신(`transitGuideReduce`)의 입력·상태·전이는 한 줄도 바뀌지 않는다. 도착·riding 승격·하차·`neverSeen` 판정은 도착 API가 그대로 한다. 위치는 상태 머신 밖의 별도 표시 상태가 들고, 화면·문장이 그것을 읽는다(판정서 `2026-08-23-express-stop-data-verdict-design.md` §3 기각 사유 1~11은 전부 "판정을 위치로 대체"에서 나왔다 — 이 설계는 그 경로를 만들지 않는다).

## 1. 범위

| 면 | 무엇이 바뀌나 |

## 2. 외부 계약 (실측)

**2026-09-23 14:50 KST 탐색 실호출 4건**(위치 5호선·2호선, 도착 강동·강남):

- 호출: `http://swopenapi.seoul.go.kr/api/subway/{KEY}/json/realtimePosition/{start}/{end}/{노선명}` — 도착 API와 같은 호스트·키(`SEOUL_SUBWAY_REALTIME_KEY`)·http 전용.
- 봉투: 정상 `{ errorMessage:{ code:"INFO-000", total }, realtimePositionList:[…] }`, 데이터 없음은 평면 `{ status, code:"INFO-200", message }` — **도착 API와 같은 봉투 계열**이라 결과 코드 판독(중첩 → 평면)을 공유한다. 서울 열린데이터 일반(`readSeoulOpenJson`)·data.go.kr(`datagokr-envelope`) 파서와는 다른 봉투라 그쪽에 넣지 않는다.
- 행: `trainNo` · `statnNm`(부역명 포함, 예 `군자(능동)`) · `trainSttus` · `recptnDt`(KST `yyyy-MM-dd HH:mm:ss`) · `updnLine` · `directAt` · `lstcarAt` · `subwayId` · `statnTid`/`statnTnm`(종착).
- 건수: 5호선 33행(total 33), 2호선 36행(total 36). ⚠ **창 끝 번호가 곧 행 수다**(`0/5` → 5행, total 36).
- **노선별 제공(15:11 KST, 매핑표 20노선 × 1건, 설계 리뷰 M5)**: 19노선 INFO-000 — 1호선 69·4호선 37·2호선 36·5호선 34·7호선 33·수인분당선 32·9호선 26·3호선 25·경의중앙선 25·공항철도 20·6호선 19·8호선 14·GTX-A 12·경춘선 11·신분당선 11·우이신설선 11·서해선 8·신림선 6·경강선 5행. **`중앙선`만 INFO-200**(0행). 열차번호에 선행 0(`0106`)·영문(`A2123`)이 있다.
- **조인 8/8**: 강동 도착 5호선 4편성·강남 도착 2호선 4편성의 `btrainNo`가 전부 해당 노선 위치 목록의 `trainNo`에 있었다. 신분당선(1077) 3편성은 2호선 목록에 없는 것이 정상(노선이 다르다).
- `trainSttus`: 0 진입 · 1 도착 · 2 출발 · **3 전역 출발**(직전 역을 떠나 `statnNm`으로 가는 중). 3은 2026-08-03 조사에 없던 값이다. 같은 순간 도착 API `arvlMsg3`는 직전 역을 말하고 위치 API는 3으로 다음 역을 말하는 사례가 있었다(5128: 도착 `굽은다리` / 위치 `길동`, 3) — **위치 피드가 도착 피드보다 한 역 앞서 바뀐다.** 2026-09-09 위원장 요청 ①("역간 중간 지점에서 바뀌면 좋겠음")이 표식을 `statnNm`에 두는 것만으로 채워진다.
- `recptnDt` 나이: 조회 시각 대비 0~2분(도착 API보다 늦을 수 있다).
- `updnLine`: 이번 표본의 대응은 상행·내선=`0`, 하행·외선=`1`(8편성). 규격 문언과의 대조는 하지 않았다 — 2026-08-03 조사가 "규격과 반대"로 기록했고, **쓰지 않으므로 다시 판정할 필요가 없다**. 조인은 노선 + 열차번호로 충분하다.

## 3. 서버

### 3.1 provider `src/lib/providers/seoul-subway-position.ts`

- `fetchSubwayLinePositions(line: string): Promise<SubwayLinePositions | null>` — `line`은 서울 표기(`5호선`). 키 없음 → `null`. INFO-000 → `{ trains, total, truncated }`. **INFO-200 → `{ trains: [], total: 0 }`**(운행 밖과 노선 미제공이 같은 코드 — 도착 추적의 4-state 교훈과 같은 이유로 "0행"으로 둔다, 아래 라우트가 `notFound`로 말한다). 그 밖의 코드·HTTP 오류 → throw.
- 행 정규화는 `trainNo`·`statnNm`·`trainSttus`·`recptnDt` 넷만 싣는다(`updnLine`은 파싱하지 않는다 — 소스에 이름이 없으면 나중에도 못 쓴다).
- 조회 창 `0/200`(200행 — 비혼잡 1호선이 이미 69행이다). `total > 받은 행 수`면 `truncated: true`를 싣고 서버 로그 1줄 — 그때 못 찾은 열차는 `notFound`다(조용한 은폐가 아니라 로그로 드러나는 한계). 러시아워 1호선이 창을 넘는지는 그 로그가 말한다(§9).
- **노선 단위 캐시**: 모듈 수명 `Map<노선, {at, value}>`, TTL **20초**, 비행 중 요청 공유(`inFlight` Map — `odsay-express-stops.ts` 선례). 실패는 캐시하지 않는다(일시 장애가 굳지 않게). Next 데이터 캐시(`fetch` `revalidate`·`unstable_cache`)를 쓰지 않는 이유: stale-while-revalidate라 한동안 조회가 없던 노선의 첫 요청이 **낡은 목록**을 받는다 — 실시간 표식에선 그것이 곧 거짓 위치다. 인스턴스 간 공유는 없다(Fluid 인스턴스 재사용 범위 안에서만 공유 — 현 규모에서 충분하고, 부족하면 쿼터 계측이 먼저 말한다).

### 3.2 라우트 `GET /api/transit/position?line={ODsay 노선명}&train={열차번호}`

- `dynamic = "force-dynamic"`, 응답 캐시 없음. 레이트 리밋 전용 저장소 60초 20회(세션당 분당 1~2회, 추적 라우트와 같은 NAT 공유 근거 — 429는 조용한 표식 부재가 된다).
- 파싱(zod: `line` 1~30자, `train` `^[0-9A-Za-z]{1,10}$`) → 노선 매핑(`subwayIdForOdsayLine` → `subwayLineNameForId`, 추적 라우트와 같은 표) → 키 게이트 → upstream. 좌표 입력이 없어 커버리지 마커는 해당 없다.
- 응답(판별 union, 3-state + 조인):

| 응답 | 뜻 |
|---|---|
| `200 {status:"found", station, trainStatus, dataStamp, dataAgeSeconds}` | 그 열차가 목록에 있다. `dataAgeSeconds`는 서버 계산(`parseRecptnDt` 재사용, 미래값 0 클램프, 파싱 불가 `null`) |
| `200 {status:"notFound", total}` | 목록은 받았는데 그 열차가 없다(INFO-200 포함, `total: 0`) — "정보 없음". 클라이언트는 `total: 0`을 "노선 0행"으로 따로 센다 |
| `200 {status:"unsupported"}` | 노선이 매핑표 밖이거나 키가 없다 — 이 leg에선 다시 묻지 않는다 |
| `502 {error}` | upstream 실패 — "조회 실패" |

`lang`은 받지 않는다: 역명은 조인 키로만 쓰이고 화면 라벨은 leg의 경유역 표시 투영(영문 포함)에서 고른다.

## 4. 순수 계층 (웹 ↔ Kit 미러, 공유 fixture)

```
TransitPositionOutcome = found(station, dataAgeSeconds?) | notFound(lineEmpty) | unsupported | failed
TransitPositionBinding  = { legIndex, phaseGen, vehicleId }   // 이 riding 진입 × 이 열차
TransitRidingPosition   = binding + { stopIndex?, lastFoundAt?, lookups, behind, emptyLine, stopped }
```

1. **`lookupDue(state, leg, position)`** — 켜는 조건(§5 ①). 전부 참일 때만:
   `phase == riding` ∧ `leg.trackMode == subway` ∧ 식별 잠금(`lock.vehicleId` 비어 있지 않음 — 근사·비관측 잠금 제외) ∧ `signal ∈ {notYetVisible, neverSeen}` ∧ (결박이 같으면) `!stopped ∧ lookups < cap(leg)`. **`cap(leg) = max(30, 2 × leg.minutes)`** — 구간 소요에 비례(E36 유휴 상한과 같은 모양, 설계 리뷰 M4).
2. **`step(prev, state, leg, requested, outcome, now)`**:
   - **`requested`(요청 시점 결박)가 지금 결박과 다르면 응답을 버린다**(늦은 응답, 설계 리뷰 M1). 결박이 prev와 다르면 새로 시작.
   - **보존 창이 지난 래치는 먼저 버린다**(설계 리뷰 M2 — 표시되지 않는 래치가 뒤의 진짜 관측을 막지 않게).
   - `failed`(429·5xx·네트워크): 아무것도 세지 않는다(쿼터 소비가 없다 — 리듀서 `ridingPolls`와 같은 규칙, 설계 리뷰 m11).
   - `unsupported`(매핑 밖·키 없음·그 밖의 4xx): `stopped`.
   - `notFound`: 횟수 +1. `lineEmpty`(노선 0행)가 **3회 연속**이면 `stopped`(중앙선처럼 제공 안 하는 노선이 매 폴 헛조회하지 않게, 설계 리뷰 M5).
   - `found`: 나이가 `null`이거나 300초 초과면 관측이 아니다(동결). `uniqueViaStopIndex`(조망과 같은 유일 매칭)가 없으면 관측이 아니다(승차역 전·하차역 너머·동명 반복). 래치보다 **뒤 역**이면 1회는 무시하고 **2회 연속이면 그 역에서 다시 시작**(튄 값 하나가 구간을 잠그지 않게, M2). 같거나 앞이면 `stopIndex`·`lastFoundAt` 갱신.
3. **`shownIndex(state, position, now)`** — 결박이 같고 `phase == riding`이고 `now − lastFoundAt ≤ 180초`일 때만 `stopIndex`. **보존 창 180초 = riding 미관측 주기 60초 × 3**.
4. **`viaHereIndex`** — 경유역 목록 표식. 도착 유래 `viaStopCurrentIndex`(현행)와 위치 항 중 **큰 값**. 위치 항은 보존 창 안이면 그 값이고, **인계 뒤(`tracking`)에는 도착 쪽이 래치를 따라잡을 때까지 창과 무관하게 래치**다(조회가 꺼진 뒤 창이 지나 표식이 한 칸 뒤로 튀던 경로, 설계 리뷰 m1).
5. **`statusIndex`** — 상태 문장이 위치를 말할 index. `signal ∈ {notYetVisible, neverSeen}`이고 `shownIndex`가 있을 때만.
6. **`overviewApplyingPosition`** — 조망 후처리. 기존 `transitProgressOverview`와 그 fixture는 **그대로** 두고 결과에 얹는다(안드로이드 이식본을 흔들지 않는다):
   - `here == .station(a)`이고 위치 항 `p > a` → `.station(p)`.
   - `here == .unknown(.noObservation)`이고 `statusIndex = p` → `.station(p)`.
   - 그 밖(`signalLost`·`upstreamFailed`·`ambiguous`·국면 밖)은 불변.
   - 현재 leg 정차역 행의 `here` 플래그를 맞춘다. silence 행·`reboardOffered`는 **불변**(탈출구를 지우지 않는다 — 판정서 §3 4번).
   - iOS는 모델의 `overview` 계산 속성 자체가 이 후처리본이다 — 조망 행·다른 경로 출발점·근거 변화 판정이 한 값을 읽는다(설계 리뷰 m8).
7. **`neverSeenWarningDeferred` · `neverSeenPendingStep`** — §6 판정 2의 보류 규칙(아래).
8. 응답 분류: `positionOutcomeFromBody`·`positionOutcomeFromHttpStatus`(웹) ↔ `TransitPositionService.outcome(from:)`(Kit, 봉투·오류 두 판). 429·5xx·네트워크 = `failed`, 그 밖의 4xx = `unsupported`(형식 밖 열차번호가 30번 400을 받던 경로, 설계 리뷰 m4).

상수(웹·Kit 동일값, **전부 잠정값** — 실승차 판정 대상, §9): 조회 상한 하한 30회 · 보존 창 180초 · 동결 300초 · 뒤 역 재시작 2회 · 노선 0행 중단 3회 · 클라이언트 조회 예산 8초(서버 upstream 예산 5초보다 길게 — 서버가 먼저 502로 답하게).

**시간 상한(구현 리뷰 M1)**: 위치 조회는 도착 폴과 같은 단일 비행 안에 직렬로 끼므로 상한이 없으면 느린 upstream이 다음 도착 폴(첫 관측·카운트다운)을 그만큼 민다. 서버 upstream `AbortSignal.timeout(5초)`, 웹 `AbortSignal.timeout(8초)`, iOS `APIClient.get(timeout: 8)`. 초과는 `failed`(세지 않는다). iOS는 위치 조회를 `pollOnce` 밖(폴 루프, 도착 폴 뒤)에서 불러 `pollEnd elapsed` 계측에 섞이지 않게 하고, `posPoll` 줄이 위치 조회 소요를 따로 싣는다(구현 리뷰 m4).

**렌더 시계**: 웹은 렌더 중 시계를 읽지 않는다 — 조회 시점에 `positionClock`을 state로 굳히고(폴이 매번 새 state를 낸다) 화면·상시 문장·착지 폴백 라벨이 그것을 쓴다. 렌더 밖에서 판정하는 자리(진행 상황 통지·복귀 통지)는 **지금 시각**을 쓴다 — 숨김·백그라운드·폴 사이에 창이 지났을 수 있고, 사용자가 묻는 순간의 답은 참이어야 한다. 통지 때 화면 시계(`positionClock`)도 같은 틱에 앞당겨 화면 줄과 답이 어긋나지 않게 한다(검증 리뷰 n4). 예외: iOS "다른 경로" 출발점·근거 변화 판정은 후처리된 `overview`(화면 시계)를 읽는다 — GPS가 우선이고 120초 stale 가드가 있어 창이 최대 60초 늘어나는 영향이 작다(검증 리뷰 n1). iOS `statusLineText(state:leg:now:speaksLocated:)`는 `now`에 기본값이 없다(생략이 한쪽을 조용히 다른 시계로 돌린다). (설계 리뷰 m2, 구현 리뷰 m1 — 접근성 감사 m3는 통지를 화면 시계로 맞추자고 했으나 통지의 참을 택했다.)

## 5. 설계 결정

### ① 언제 위치 조회를 켜는가 — 도착 피드가 아직 열차를 못 본 riding 구간에서만

- 켜는 구간이 곧 **표식이 없던 구간**이다: riding 진입 뒤 하차역 도착 목록에 내 열차가 실리기 전(`notYetVisible`, 10폴 뒤 `neverSeen`). 도착 피드가 열차를 보기 시작하면(`tracking`) 끈다 — 그때부터 표식은 현행대로 도착 `arvlMsg3`가 채우고, 위치 조회는 새 정보를 주지 않는 추가 호출일 뿐이다.
- 정상 초기 미관측과의 구분: **상태 머신의 신호는 그대로 `notYetVisible`이다**. 구분은 신호가 아니라 표시 계층에서 한다 — 위치가 잡혔으면 상태 문장의 신호 자리를 위치 문장이 차지한다(§6 판정 1). 그렇지 않으면 A33 문장("하차역에 가까워지면 열차 위치가 표시됩니다.")이 바로 옆 경유역 목록의 "현재 위치"와 모순된다.
- **표식이 있다가 없어지는 경로를 구조로 줄인다**: ⓐ인계 — 도착 쪽이 잡히는 순간 위치 조회를 끄지만 보존 창(180초) 동안 위치 표식이 남고, 경유역 표식은 두 출처 중 큰 값이라 도착 `arvlMsg3`가 한 역 뒤여도 뒤로 튀지 않는다 ⓑ일시 누락·실패 — 보존 창 안에서는 표식 유지 ⓒ단조 래치 — 흔들린 레코드가 표식을 뒤로 끌지 않는다. 남는 소멸은 "세 번 연속 위치를 못 받았고 도착 쪽도 아직 못 봤다"뿐이고, 그때 낡은 역을 계속 말하는 것은 거짓이라 소멸이 정직하다(상태 문장은 A33 문장으로 돌아간다).
- 근사·비관측 잠금은 켜지 않는다: 열차번호가 없다(A34 ① "어느 열차인지 모르므로 폴하지 않는다"와 같은 선).
- 첫 조회는 riding 진입 뒤 첫 폴에 같이 나간다 — 관측 승격은 15초 뒤, 선언 진입(이미 탔어요·선택한 열차에 탔어요·탑승 변경 취소)은 즉폴이라 곧바로(설계 리뷰 m5).

### ② 쿼터 — 노선 캐시 + 결박당 max(30, 2×구간 소요)회 상한

- `SEOUL_SUBWAY_REALTIME_KEY` 일 1,000회를 도착 API와 나눈다. 위치 조회는 **별도 타이머가 없다** — riding 폴 한 번에 최대 1회 얹힌다(도착 조회·dispatch 뒤, 갱신된 상태로 `lookupDue`를 판정). 그래서 주기는 riding 미관측 주기(첫 15초, 이후 60초)를 따르고, E36 유휴 폴 정지·백그라운드 폴·세션 폴 상한(240)·즉폴 금지 규칙을 전부 자동 상속한다.
- **세션당 증분 상한(수치)**: riding 결박 하나당 위치 조회 ≤ **max(30, 2 × 구간 소요 분)회**. 전형은 미관측 구간 10분 안팎(09-09 실측 10분 54초)이라 **결박당 10~12회**, 도착 쪽 같은 구간 호출 수와 1:1이다. 실패(429·5xx)는 세지 않지만 upstream을 쓰지 않거나(429) 실패한(5xx) 호출이라 쿼터 산수에 들지 않는다. 한 세션의 증분 상한은 "riding 폴 수"를 넘지 못한다(폴 한 번에 최대 1회) — 세션 폴 상한 240·유휴 정지가 그대로 덮는다. 노선 0행 3회 연속이면 그 결박은 멈춘다(제공 안 하는 노선의 헛조회 상한 3회).
- 서버 노선 캐시(20초)가 같은 노선을 동시에 타는 세션들의 호출을 하나로 합친다. 도착 조회는 역 단위라 합칠 수 없지만 위치는 노선 단위라 합칠 수 있다 — 이것이 "쿼터 배증"에 대한 구조적 답이다(사용자가 늘수록 증분 비율이 준다).
- 상한에 닿으면 조회를 멈추고 보존 창이 지나면 표식이 사라진다(상태 문장은 A33 문장으로). 상한이 구간 소요에 비례하므로 이 소멸은 "구간 소요의 두 배가 지나도록 도착 피드가 못 잡은" 이상 상황에서만 난다.

### ③ 웹·iOS 동조

웹 `TransitGuidePanel`에 같은 표식이 있다(경유역 목록 `viaStopCurrentIndex`). 그래서 **순수 계층 미러 + 공유 fixture**, 웹 훅·패널과 iOS 모델·시트를 함께 고친다. iOS에만 있는 소비자(조망·다른 경로 출발점)는 iOS만(주변 확인 앵커는 §5 ⑤로 읽지 않는다). 웹은 전경 전용 폴이라 백그라운드 위치 조회도 없다(현행 웹 폴 계약 그대로).

### ④ 3-state — 조인 실패·결측·조회 실패를 뭉개지 않는다

- 라우트가 `found`/`notFound`/`unsupported`/502를 가른다. 클라이언트 순수 계층은 결과를 `TransitPositionOutcome` 넷으로 받고, 조인 실패(매칭 없음·모호)와 동결(나이 초과)을 "관측 아님"으로 따로 판정한다.
- **표식은 "있다"만 주장한다.** 없는 표식은 "모른다"이지 "없다"가 아니다(조망 불변식 "없는 표식은 거짓이 아니지만 있는 표식은 거짓일 수 있다"). 그래서 네 사유 모두 화면에서는 표식 부재 + 현행 신호 문장으로 나가고 **새 문구를 만들지 않는다** — 사유를 사용자에게 가르는 문장은 행동을 바꾸지 않는다(위치 조회 실패에 사용자가 할 일이 없다).
- 사유는 계측 로그에 남긴다(iOS `transitGuideLog` `posPoll seq= outcome= station= idx= age=` 1줄/조회) — 실승차 사후 판정에서 "결측이었나 조인 실패였나"를 가를 유일한 증거다.

### ⑤ 주변 확인 앵커는 위치를 따르지 않는다 (접근성 감사 M1)

앵커가 위치 유래 현재역을 따르면 승차 내내 약 2분마다 앵커가 바뀌고, `SurroundingsSceneSection`이 앵커 변경 때 불러 둔 장면을 버린다 — 사용자가 연 장면을 읽는 도중 VoiceOver 커서가 얹힌 행이 사라지고, "승차 중 하차역 주변을 미리 들어 둔다"는 사용이 막힌다. 그래서 앵커는 종전 도착 유래 판정(`transitSurroundingsAnchor(state:leg:)`)을 그대로 쓴다(도착 피드가 잡히는 마지막 몇 정거장에서만 현재역). 대안(장면은 유지하고 헤더만 바꾸기)은 새 동작이라 채택하지 않았다.

**새 문구 키는 없다.** 기존 키 `transitGuide.currentStation`("현재 위치 {station}.")·`viaCurrent`("현재 위치")를 새 자리에서 쓴다.

**판정 1 — 상태 문장의 신호 자리**(승인): 위치가 잡혀 있으면(`statusIndex`) 신호 문장(`stateRidingNotYetVisible`·`stateNeverSeen`) 자리에 `현재 위치 {역}.`을 쓴다. 조망 silence 행·백그라운드 복귀 낭독의 상태 문장도 같은 선택기를 지난다.

**판정 2 — `neverSeen` 1회성 경고**(승인): 위치가 잡혀 있는 동안 `neverSeen` 전이가 일어나면 그 경고(통지 "탑승하신 차량을 찾지 못하고 있습니다. 다른 차량을 타셨다면 탑승 변경을 눌러 주세요." + 경고음)를 **내지 않고 결박째 보류**한다. 상태 머신의 `neverSeen`·탈출구([탑승 변경])는 그대로다. 보류 규칙(설계 리뷰 M3):
- ⓐ 보류는 위치 상태와 **같은 결박**(`legIndex`·`phaseGen`·`vehicleId`)에 묶인다. 결박이 바뀌면(탑승 변경·취소·다음 구간·선언 도착·새 riding 진입·세션 종료) **버린다**(발화 없음).
- ⓑ 폴마다 처분한다: 신호가 `neverSeen`이 아니게 됐으면(추적 시작·소실·실패) 또는 국면이 riding이 아니면 **버린다**(추적 중에 "찾지 못하고 있습니다"는 거짓). 신호가 그대로 `neverSeen`인데 현재역이 사라졌으면(보존 창 경과·조회 상한·노선 0행 중단) **그때 낸다** — 이벤트와 같은 경로(`handle(event:)`, 약한 톤 포함). 그 밖은 계속 보류.
- ⓒ 이벤트 밖에서 경고 문장을 고르는 자리 — iOS 복귀 낭독(`returnStatusText`)·조망 silence 행·웹 탭 복귀 통지 — 는 **같은 선택기**를 지난다: 현재역이 잡혀 있으면 현재역 문장, 아니면 종전 그대로(`neverSeen`이면 행동 문장). 근거: 그 문장의 전제("찾지 못하고 있습니다")가 거짓이 된다 — 잠근 열차가 우리 경로를 따라 움직이는 것이 보이는데 "못 찾는다"고 말하게 된다. 도착 목록 미등장은 대부분 "아직 멀다"(A33)였고, 위치가 그 경우를 가려낸다. 대안은 "그대로 낸다"(표식과 경고가 동시에 들린다).

**조망 안의 반복(설계 리뷰 m6 → 위원장 판정)**: 조망 머리 문장(상태 문장)·silence 행·정차역 행이 같은 현재역을 세 번 말하던 것을, 머리 문장에서 현재역 문장을 빼서 두 곳으로 줄였다(iOS `statusLineText(…, speaksLocated: false)` — 조망 머리만). 빠진 자리에 신호 문장을 되살리지 않는다(아래 두 줄과 모순된다). silence 행은 래치 계약(spec 2026-08-23 §4.1)상 지울 수 없어 같은 선택기를 지난다. 소스 가드가 조망 머리의 `speaksLocated: false`를 잠근다.

## 7. 비채택안

- **상태 머신 입력으로 위치를 넣기**: 판정서 §3이 기각(11건). 이 설계의 위치 상태는 리듀서 밖에 있고 리듀서는 그 존재를 모른다.
- **클라이언트가 노선 목록 전부 받기**: 50행을 매 폴 내려받아 열차를 찾는 것은 서버 필터와 결과가 같고 전송만 크다.
- **`trainSttus`별 문장**("길동 진입 중."·"다음 역 길동." — 기존 키 `subwayArriving`·`subwayNextStop`): 더 세밀하지만 그 키들은 A27에서 **하차역**을 말하는 자리라 같은 틀로 다른 역을 말하면 "다음 역"이 하차 신호로 오독될 수 있다. 요청 ①은 표식이 `statnNm`(전역 출발 시 다음 역)으로 앞서 바뀌는 것으로 채워진다. 필요해지면 별건.
- **시간표 평균 나누기**: 어림이고 어긋남을 알 수 없다(BACKLOG E35). 실데이터가 있으니 쓰지 않는다.
- **별도 위치 폴 타이머**: 주기·유휴·백그라운드·상한 규칙을 전부 다시 짜야 한다. 폴 한 번에 얹으면 상속된다.

- **보류가 지우는 것**(구현 리뷰 m6·접근성 감사 참고): 위치는 **잠근 열차**의 위치다. 사용자가 실제로 다른 열차에 탔다면 잠근 열차가 경로를 따라 움직이는 동안 "현재 위치 {역}."이 사용자 위치처럼 들리고, 보류가 없애는 경고가 바로 "다른 차량을 타셨다면"이다. 도착 추적도 같은 가정 위에 있고 [탑승 변경]은 남아 있다. 판정 2를 받을 때 "경고의 역할이 '오래 못 봤다'인가 '다른 열차일 수 있다'인가"를 함께 묻는다.
- **완행 잠금 × 급행 구간에서 표식이 깜박일 수 있다**(설계 리뷰 m10): 급행 구간의 경유역은 급행 정차역뿐이라 완행의 현재역은 대부분 조인되지 않고, 급행 정차역 사이가 3분을 넘으면 표식이 사라졌다 나타난다. 정직한 동작이라 두었다.
- **열차번호 재사용**(설계 리뷰 m12): 같은 `trainNo`가 하루에 여러 운행으로 재사용되는지는 미실측이다. 결박이 riding 진입 단위라 한 구간 안의 재사용만 문제가 되고, 그때도 조인은 경유역 안의 유일 매칭이어야 표식이 선다.
