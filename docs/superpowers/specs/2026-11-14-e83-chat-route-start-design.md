# E83 채팅 경로 카드의 [안내 시작] 범용화: 설계

2026-11-14 · 서버 + 웹(여섯 언어) + iOS 실험판 · 앞 설계: `2026-11-12-e70b-chat-journey-design.md`(여정 카드, 이 문서의 D번호 참조는 그 문서의 것이다)

## 1. 목표와 성과

채팅에서 도보·자동차·대중교통 길을 물으면 답 아래에 버튼만 있는 카드가 붙고, 수단 이름이 든 버튼 한 번으로 그 수단의 실시간 안내가 시작된다. 지금은 단일 수단을 물은 뒤 안내를 받으려면 길찾기 탭에서 도착지를 다시 넣어야 한다.

**움직일 성과**: 채팅 답에서 안내 시작까지 재입력 0회, 수단 하나를 물은 답은 넘길 줄이 둘(수단 버튼, 길찾기에서 열기), 셋을 견준 답은 넷. 확인은 웹 VoiceOver와 iOS 실험판 실기기.

**비목표**: 장소 상세에서 연 채팅(여정 카드와 같은 범위: 웹 옴니박스 채팅과 iOS 채팅 탭만), 안드로이드, iOS 정식판, 카드 안에서 대중교통 경로 고르기, 대중교통 경유지(ODsay 미지원 그대로), **웹 자동차 경유지 안내**(§3 R9).

## 2. 위원장 판정 (2026-11-14, BACKLOG E83)

1. 대중교통 버튼은 추천 순서 첫 경로로 바로 시작한다. 다른 경로는 [길찾기에서 열기]로 가서 고른다.
2. 답에서 조회한 수단마다 버튼을 단다.
3. 카드는 제목·합계 줄 없이 버튼만 둔다. 「도보 안내 시작」·「자동차 안내 시작」·「대중교통 안내 시작」, 맨 끝에 「길찾기에서 열기」 하나. 웹의 버튼 없는 요약 카드는 이 카드로 바꾼다.
4. 여섯 언어 모두에 연다.
5. 「도착지와 수단으로 안내 시작」을 한 곳에 만들어 채팅 버튼이 먼저 쓰고 베르길리우스(E82)가 나중에 같은 곳을 부른다.
6. 웹은 검증 뒤 바로 배포하고, iOS는 실험판에 먼저 넣는다.
7. 자동차에 경유지를 넣어 물은 답은 버튼이 경유지를 실어 넘긴다.

## 3. 설계 결정

| # | 결정 | 근거 |
|---|---|---|
| R1 | 새 렌더 `route-start` 하나를 세 도구(`get_walk_route`·`get_car_route`·`get_transit_route`)가 낸다. 도구 호출 하나가 렌더 하나이고, **클라이언트가 한 답의 `route-start` 렌더를 도착지별로 묶어 카드 하나로 그린다** | 판정 2·3. 서버 루프는 도구별 렌더를 모으기만 한다(기존 구조 유지) |
| R2 | 능력 신고 `"route-start"`로 연다. 신고한 요청에는 세 도구가 `route-start`만 내고(옛 `car-route`·`transit-route`는 내지 않는다), 신고하지 않은 요청은 종전과 byte-identical이다. 로케일 제한 없음, 장소 채팅은 닫힘(여정과 같은 자리) | 카드를 못 그리는 클라이언트(안드로이드·iOS 정식판)의 동작을 바꾸지 않는다. 판정 4 |
| R3 | 렌더는 **경로를 찾은 때에만** 낸다. 위치 없음·경로 없음·실패·미지원 마커에는 렌더가 없다 | 버튼은 「이 답이 말한 길로 안내를 시작한다」는 약속이다(3-state: 못 찾은 길에 시작 버튼을 달지 않는다) |
| R4 | 도보·자동차 렌더는 도착지(와 경유지·계단 회피 여부)만 싣는다. 신선도 판정이 없다 | 두 안내는 시작할 때 지금 위치에서 경로를 새로 받는다 |
| R5 | 대중교통 렌더는 조회 결과 전체와 출발 좌표·조회 시각·수동 위치 여부를 싣는다(여정 카드 D8과 같은 props-driven). 시작하는 경로는 길찾기 화면이 기본으로 펼치는 추천 첫 경로다 | 판정 1. 다시 조회하면 답이 말한 경로와 달라질 수 있다 |
| R6 | 대중교통 신선도는 여정 카드와 같은 함수·같은 수치(10분·100m, D16)를 쓴다. 낡았거나 수동 위치에서 조회한 카드는 그 결과로 시작하지 않고, 길찾기에서 기기 위치로 다시 조회한 뒤 「위치가 바뀌어 경로를 다시 찾습니다.」를 통지한다(자동 시작 없음) | 위원장이 실사용에서 확정한 수치다. 판정 함수 하나를 둘이 쓴다 |
| R7 | 도보·자동차 버튼에는 위치가 바뀐 경우의 고지를 두지 않는다 | 안내가 시작하며 새 경로의 요약을 스스로 말한다. 런타임 판정 위에 상시 고지를 얹지 않는다 |
| R8 | [길찾기에서 열기]는 도착지(와 경유지)를 채우고 길찾기 화면의 평소 조회(전 수단)를 돌린다. 착지는 길찾기 화면의 평소 규칙(첫 성공 수단 제목)이다 | 웹·iOS 길찾기에는 수단 탭이 없고 한 화면에 수단별 제목이 있다. 수단을 고르는 자리는 그 화면 하나다 |
| R9 | **자동차 + 경유지**: iOS는 버튼이 경유지를 실어 안내를 시작한다(판정 7). 웹은 자동차 안내가 경유지를 싣지 못하므로(길찾기 화면도 같은 조건에서 버튼이 없다, `carGuideStartable`) 「자동차 안내 시작」을 내지 않고 [길찾기에서 열기]가 경유지를 실어 넘긴다. 웹 자동차 경유지 안내는 별건으로 BACKLOG에 올린다 | 웹 안내 훅에 경유지를 싣는 일은 안내 엔진 변경이고 실주행 판정이 따로 필요하다 |
| R10 | 수단 버튼은 그 클라이언트·로케일에서 그 수단의 안내를 시작할 수 있을 때만 낸다(길찾기 화면의 시작 버튼과 같은 조건: 자동차는 Tmap 경로 ∧ 한국어 데이터). 조건이 안 되면 그 버튼만 빠지고 [길찾기에서 열기]는 남는다 | 눌러도 시작되지 않는 버튼을 두지 않는다 |
| R11 | iOS 「한 곳」: `GuideSession`에 도착지와 수단을 받는 시작 함수 하나를 두고 카드가 그것만 부른다 | 판정 5. E82가 같은 함수를 부른다 |
| R12 | 카드에 heading을 두지 않는다. 답에 도착지가 둘 이상이면 카드가 도착지마다 하나이고 각 카드 첫 줄에 도착지 이름을 평문 한 줄로 둔다. 도착지가 하나면 그 줄이 없다 | 판정 3, 여정 카드 D15. 같은 이름의 버튼이 두 벌이면 어느 도착지인지 가를 줄이 필요하다 |
| R13 | 시스템 지침은 고치지 않고 시작한다. 실호출에서 모델이 「길찾기 탭에서 도착지를 넣으라」처럼 버튼과 어긋나는 말을 하면 그때 긍정 문장 하나를 더한다 | 프롬프트 최소판 먼저 |

## 4. 렌더 계약 (서버 ↔ 웹 ↔ iOS)

```ts
type RouteStartMode = "walk" | "car" | "transit";

interface RouteStartRenderPayload {
  type: "route-start";
  mode: RouteStartMode;
  dest: { lat: number; lng: number };
  destLabel: string;
  destRoman: string | null;          // 영문 원천이 없을 때의 서버 로마자(여정 카드와 같은 규칙)
  via: { lat: number; lng: number; label: string } | null;   // 도보·자동차만. 대중교통은 늘 null
  accessible: boolean;               // 도보의 계단 회피. 그 밖의 수단은 false
  carProvider: string | null;        // 자동차 경로의 provider(예: "tmap"). 그 밖의 수단은 null
  transit: {                         // 대중교통만. 그 밖의 수단은 null
    result: /* 길찾기 화면이 쓰는 대중교통 조회 결과와 같은 모양 */;
    origin: { lat: number; lng: number };
    queriedAt: number;               // epoch ms
    manualOrigin: boolean;
  } | null;
}
```

- 모든 키는 늘 있다(없는 값은 `null`·`false`). Kit 디코딩 실패는 `.unsupported`로 접는다.
- `transit.result`는 길찾기 화면의 대중교통 결과로 그대로 세울 수 있어야 한다. 채팅 도구의 조회 옵션이 길찾기 화면과 다르면(차로 정보 등) 신고한 요청에서는 길찾기 화면과 같은 옵션으로 조회한다.
- 요청의 `capabilities`에 `"route-start"`를 싣고, 신고한 요청은 `userLocationManual`도 싣는다(여정과 같은 필드).
- 공유 fixture: `ios/GildongmuKit/Tests/GildongmuKitTests/Fixtures/chat-route-start-render.json`(수단 셋 각 1건, 자동차는 경유지 포함). 웹 테스트가 fixture 키 = 타입 키 = 서버 렌더 리터럴 키를 잠근다(`chat-journey-render-fixture.test.ts`와 같은 모양).

## 5. 서버

- `types.ts`: `RouteStartRenderPayload`, `ChatCapability`에 `"route-start"`. `ExecutionContext`에 신고 능력을 읽을 자리(여정의 `ctx.journey`와 같은 층, 수동 위치 여부 포함).
- `route.ts`의 능력 거름: `"journey"`는 종전대로 ko, `"route-start"`는 전 로케일. 장소 채팅은 빈 집합.
- `router.ts` 세 도구: 신고가 있고 경로를 찾았으면 `route-start` 렌더. 자동차는 경유지가 있어도 낸다(`via` 실음). 도보는 `accessible`·`via` 실음. 모델에 주는 `data`는 바꾸지 않는다.
- 신고가 없으면 종전 렌더·종전 `data` 그대로(선언 목록도 그대로: 이 능력은 도구를 새로 열지 않는다).

## 6. 웹

- `MessageBubble`: 한 답의 `route-start` 렌더를 도착지 좌표로 묶어 `RouteStartCard`를 묶음마다 하나 그린다. 버튼 순서는 도보·자동차·대중교통·길찾기에서 열기. 같은 수단이 둘이면 첫 것만 쓴다.
- `RouteStartCard`: 버튼만(R12의 도착지 줄 예외). 버튼마다 `min-h-11`, `aria-disabled` + in-flight ref 가드. 통로(`onAction`)가 없으면 그리지 않는다.
- 채팅의 `CarRouteBriefing`·`TransitRouteBriefing` 사용을 걷어 낸다(다른 화면이 쓰면 컴포넌트는 남긴다).
- 통로는 여정 카드와 같은 사슬(`ChatInterface` → `ChatOverlay` → `PlaceSearch`)이고 대화 보존(E70-b2)도 같다. 범용 채팅만 신고한다.
- `DirectionsView`에 진입 하나를 더한다(`initialGuide`): `{ mode, via, accessible, action: "open" | "start" | "requery", transit? }`.
  - `open`: 도착지·경유지를 채우고 평소 조회(전 수단, 프리필 조회와 같은 길).
  - `start` 도보·자동차: **그 수단만** 기기 위치(`realOrigin`, `force`)에서 조회하고, 결과가 서면 그 수단의 시작 버튼을 `autoStart`로 시작한다. 수단 제한은 이 첫 조회에만 걸리고 사용자가 [경로 조회]를 누르면 평소대로 전 수단이다.
  - `start` 대중교통(신선): 조회 없이 카드의 결과로 대중교통 결과만 세우고 추천 첫 경로의 안내 패널을 `autoStart`로 시작한다.
  - `requery` 대중교통(낡음·수동 위치): 기기 위치에서 평소 조회, 통지 `journey.cardStaleRequery`, 자동 시작 없음.
  - 착지: `start`는 안내 패널이 자기 트리거로 착지하고 화면 제목 착지를 건너뛴다(D17). 그 밖은 평소 규칙.
  - 안내 세션이 이미 살아 있으면 길찾기 화면의 평소 거절을 따른다.
- 신선도 판정은 `journeyCardFreshness`를 그대로 쓴다(인자가 `{origin, queriedAt}`).
- `realOrigin: true` 호출 자리가 늘어난다. `e70b2-chat-card-guard.test.ts`의 「정확히 하나」를 새 자리 수로 고치고 각 자리의 모양을 잠근다.
- 문자열: `beacon.guideStartWalk`·`beacon.guideStartCar`·`beacon.guideStartTransit`(신규, 여섯 언어)·`journey.openInDirections`·`journey.cardStaleRequery`.

## 7. iOS 실험판

- 봉인: `AppConfig.experimentalChatGuideEnabled`(`#if EXPERIMENTAL`). 능력 신고와 카드 그리기가 이 플래그 뒤에 있다(가드로 잠근다). 채팅 탭만(장소 채팅 시트 제외).
- Kit: `ChatRenderPayload.routeStart(RouteStartChatPayload)` 디코딩, 실패는 `.unsupported`. 한 답의 렌더를 도착지별로 묶는 순수 함수(웹과 같은 규칙)를 Kit에 둔다.
- `GuideSession`에 시작 함수 하나(R11): 도착지(좌표·이름·로마자)와 수단(도보: 계단 회피·경유지 / 자동차: 경유지 / 대중교통: 경로·계단 회피)을 받아 기존 `startBeacon`·`startTransit`으로 보낸다. 도보의 경로 종류 기본값은 길찾기 화면의 첫 도보 시작 버튼과 같다. 점유 중 거절은 기존 `refuseStartIfOccupied`.
- 카드: 버튼만. 도보·자동차는 측위·신선도 없이 바로 시작 함수. 대중교통은 여정 카드와 같은 순서(점유 확인 → `force` 측위 → `journeyCardFreshness` → 신선하고 수동 위치가 아니면 시작, 아니면 길찾기로 넘겨 재조회·통지).
- [길찾기에서 열기]: `DirectionsPrefill`에 경유지 칸을 더해 도착지·경유지를 채우고 평소 조회.
- 자동차 버튼 조건은 길찾기 화면과 같다(`dataLocale == "ko"` ∧ `carProvider == "tmap"`).
- 가드 갱신: `guidance-gate-drift.test.ts`의 시작 호출 수·호출 파일 목록·`capabilities:` 문자열, 새 플래그의 봉인 단언.
- 문자열은 웹과 같은 키를 쓰고 `node ios/scripts/messages-to-xcstrings.mjs all`로 다시 만든다.

## 8. 불변식과 테스트

- 신고가 없으면 요청·응답이 종전과 byte-identical(서버·웹 훅·Kit 요청 본문).
- 렌더는 경로를 찾은 때에만(R3), 세 도구 각각.
- 카드: 버튼 순서, 한 줄 한 객체, heading 없음, 통로 없으면 버튼 없음, 조건이 안 되는 수단 버튼 없음(R10), 도착지 둘이면 카드 둘과 이름 줄.
- 웹 진입: `open`·`start`(수단별)·`requery`, 수단 제한이 첫 조회에만 걸리는지, 수동 위치를 건너뛰는지.
- 대중교통 신선도 갈래(신선·만료·이동·측위 실패·수동 위치).
- iOS: Kit 디코딩 fixture, 묶기 함수, 시작 함수의 수단별 분기, 봉인 가드, 시뮬레이터에서 카드 표시. 실기기 판정은 위원장.
- **실호출 게이트(머지 조건)**: 실제 채팅 API에 신고를 실어 ①도보 질문 → `route-start` 도보 1건 ②세 수단 비교 질문 → 수단 셋 ③자동차 경유지 질문 → `via`가 실린 자동차 1건 ④같은 질문을 신고 없이 → 종전 렌더. 각 3회. 술어는 렌더의 `mode`·`via`·`transit.result`의 경로 수(1 이상)를 본다.
- 웹 실브라우저 접근성 게이트(`npm run test:a11y`).

## 9. 구현 방식과 리뷰 판정

- 서버·웹과 iOS는 §4 계약만 공유하고 파일이 겹치지 않아 worktree 둘에서 서브에이전트가 나란히 구현한다(겹치는 것은 가드 테스트 두 파일의 서로 다른 단언과 문서). 문자열 키와 이 문서는 먼저 main에 넣는다.
- 설계 단계 적대적 리뷰는 생략한다: 새 불변식·판정 계층이 없고(능력 신고·신선도·시작 함수는 E70-b에서 검증된 계약의 재조합), 새 외부 통합·비가역 변경이 없으며, 안내 엔진을 고치지 않는다. 구현 뒤 묶음별 리뷰와 실호출 게이트가 잔여 위험을 맡는다.
