# 수단별 실시간 길 안내(묶음 B) 데이터·신호 조사

> 2026-08-03. 위원장 실사용 피드백(진입점을 대중교통·자동차·도보 3종으로 분리)에 따른 착수 조사. 실호출 프로브 2건(대중교통 신호·자동차 기하) + 웹 선례 조사 1건의 종합. 표기: [실측]=이 조사의 직접 호출, [공식]=사업자·기관 공개 문서, [2차]=외부 정리·보도. 선행 문서 `RESEARCH-2026-08-02-realtime-walk-navigation.md`(도보·약관·MKDirections)는 유효하며 재조사 금지.

## 결론

**세 수단 모두 새 키·새 활용신청 없이 성립한다.** 신호 정본은 수단마다 다르다:

| 수단 | 신호 정본 | 근거 |
|---|---|---|
| 도보 | 기기 GPS + 카카오 도보 폴리라인 투영 (E4 기출하) | 기존 |
| 자동차 | 기기 GPS + Tmap 자동차 폴리라인 투영 + 주기 재호출 ETA | §2 [실측] |
| 버스(서울) | 승차 정류소에서 `vehId` 잠금 → 하차 정류소 도착 API 폴링의 `arrmsg` | §1.1 [실측] |
| 버스(지방) | TAGO 하차 정류소 도착 API의 `arrprevstationcnt`(차량 잠금 불가 근사) | §1.2 [실측] |
| 지하철(수도권) | 승차역에서 `btrainNo` 잠금 → 하차역 도착 API 폴링의 `arvlMsg2` | §1.3 [실측] |
| 지하철(비수도권) | 실시간 부재 — 시간표 타이머만 가능(제공 시 열화 명시) | §3.3 [2차] |

**iOS에서 지하철 하차 판정에 기기 위치를 쓰는 설계는 착수 금지.** 네이버·서울교통공사·Tmap이 각각 독립적으로 같은 결론을 공개했다(§3.1). 유일하게 실전 검증된 iOS 경로는 네이버지도의 "탑승 열차 선택 → 그 열차의 실시간 운행정보 기준"이다.

## 1. 대중교통 [실측]

### 1.1 버스(서울): 차량 잠금 하차 카운트다운이 이미 승인된 API로 성립

- **ODsay 경로 응답에 전 경유 정류장 목록이 있고 현재 provider가 통째로 버린다.** `subPath[].passStopList.stations[]`: 이름·좌표·`localStationID`·`arsID`(양 끝 포함, `stationCount`는 홉 수라 배열보다 1 작다). `src/lib/providers/odsay.ts`의 `OdsaySubPath`에 선언조차 없다. **추가 API 호출 0회**로 하차 카운트다운의 뼈대가 나온다.
- **조인 키 검증 완료**: ODsay `localStationID`("123000017") = TOPIS `stId`(동일 값). 문자열 매칭 없이 정류소 ID 직결.
- **차량 잠금**: 승차 정류소 `getStationByUid`가 `vehId1`·`sectOrd1`·`arrmsg1`을 준다. 승차 시점에 `vehId`를 잠그고, 하차 정류소에 `arrive/getArrInfoByRoute`를 폴링해 같은 `vehId`가 `vehId1`/`vehId2`로 나타나면 `arrmsg1`("6분47초후[4번째 전]")이 곧 하차 카운트다운 완성 문장이다(재조합 금지 규칙과 정합). 뒤차 오인이 구조적으로 없다.
- ⚠ **TOPIS 버스위치 API(`buspos/getBusPosByRtid`)는 미승인**(headerCd 7, 키 무효 아님 — 같은 키로 도착·정류소 API 정상). **신청 불필요**: 위치 좌표는 정류소 순번으로 재환산해야 하는데 도착 API가 이미 순번·완성 문장으로 준다.

### 1.2 버스(지방): 근사 카운트다운만 성립

- 이미 쓰는 TAGO `ArvlInfoInqireService`가 `arrprevstationcnt`(N번째 전)·`arrtime`(초)을 준다(`tago-bus.ts:77`이 이미 파싱). 하차 정류소 폴링으로 같은 안내 성립.
- ⚠ **TAGO에는 차량 식별자가 없다**(vehId 대응 부재) — "그 노선의 최근접 접근 차량" 근사이고, 배차가 촘촘하면 뒤차를 볼 수 있다. 이 열화는 숨기지 말고 상태로 구분한다.
- TAGO 버스위치 API는 v2 폐기 + 구버전 미승인. 승인받아도 차량 식별자 문제가 해소되지 않아 신청 실익 없음.
- ⚠ `apis.data.go.kr`를 http로 호출하면 행이 걸린다(2분 타임아웃 실측). https + 타임아웃 필수.

### 1.3 지하철(수도권): 열차번호 잠금이 정본, 위치 API는 보조

- **열차번호 조인 검증 완료(4/4)**: 도착 API `btrainNo` = 위치 API `trainNo`. 승차역 도착조회에서 탄 열차의 `btrainNo`를 잠그면 그 열차만 추적된다. "내가 탄 열차" 특정의 유일한 확실한 수단.
- **하차 카운트다운 완성 문장이 이미 온다**: 하차역 도착조회 `arvlMsg2` = "[2]번째 전역 (몽촌토성(평화의문))" / "4분 후 (길동)". `arvlMsg3`=열차 현재 역, `arvlCd`(1 도착·2 출발·99 운행중). 새 조립 불필요.
- **갱신은 역 통과 이벤트 단위**(40초간 2호선 54편성 중 52% 갱신 = 역·상태가 바뀐 편성): 폴링 10~15초면 충분, 더 짧아도 새 정보 없음.
- **`realtimePosition`은 보유 키로 동작하나 ⚠ 5호선이 결측**(INFO-200, 2회 재현). 위원장 생활권(천호·길동)이 5호선이므로 위치 API 단독 의존 금지. **도착 API에는 5호선 열차가 정상**(천호역 응답에 5184·5662)이라 도착 API 기반이면 공백이 우회된다. `trainSttus`는 0=진입·1=도착·2=출발(전이 관측으로 확정).
- ⚠ **역명은 부역명 포함이 정본(함정)**: `천호`로 조회하면 INFO-200이 "부재"로 위장하고 `천호(풍납토성)`이어야 정상. ODsay는 부역명 없이 주므로 양방향 정규화 필요 — 벗기기는 `station-match.ts` 재사용, **조회용 정식 표기는 seed에 필요**.
- 서울 실시간 API의 수도권 커버리지(경의중앙 1063·공항철도 1065·경춘 1067·수인분당 1075·신분당 1077, GTX-A·서해·신림 포함) [2차]. 문서화된 결함 둘: 급행 열차 위치 부정확, 코레일 구간 "출발 후에도 도착 표시" — 3-state 정직 표기 대상.
- ODsay 지하철 `sectionTime`은 역당 약 2분 균등 추정의 산출물(대부분 정확히 2.00분/역) [실측] — **경로 총 소요 추정에는 쓰되 하차 임박 판정에 역산 금지**(정차·지연·급행 미반영).

## 2. 자동차 [실측]

- **Tmap 단독으로 진행 브리핑 성립.** 길동역→강남역 12,104m 실측: LineString 321점(38.9m/점), 이음매 10곳 전부 0.00m(`SEAM_TOLERANCE_M` 5m 무조건 통과), 턴 Point 10개 전부 폴리라인 정점과 0.00m, 링크별 `name`(도로명)·`distance`·`time`. 도로명 시퀀스 조립 확인(올림픽로→천호대로→올림픽대로→…). **현 `tmap-car.ts`가 LineString을 버리고 guide 수치를 0으로 하드코딩하는데 짝 LineString에 실수치가 있다** — "0=미제공"은 upstream 사실이 아니라 우리가 만든 것.
- **실시간 ETA 확인**: 같은 좌표 재호출에 거리 바이트 동일·totalTime −56초 변동. 단 `trafficInfo:"Y"`로도 정체 등급 필드는 0/11 — Tmap은 실시간 *시간*만 주고 *정체 등급*은 안 준다. 정체 등급(`traffic_state`/`traffic_speed`)은 카카오만 제공.
- **카카오는 폴백 유지**: 기하가 성기고(56.8m/점, max 494m) 출발지 유턴 스냅으로 자기근접 24.8m·재투영 모호율 8%(Tmap 2%). 고유 가치는 정체 등급과 `guides[].road_index`뿐.
- **쿼터 산술**(Tmap 일 1,000건 도보 폴백 공유): 25분 주행에 10분 주기 재호출 = 세션 3회(일 ~330세션 여유). 1분 미만 폴링은 불성립. **10분 주기 또는 이벤트 구동(스텝 전진·이탈 시) 갱신이 정답.**
- ⚠ **description의 거리를 "다음 분기까지"로 읽지 말 것**: Point 없이 LineString이 연속되는 자리가 있어 9개 안내 중 2개가 어긋났다("299m 이동"인데 다음 안내 지점까지 실제 4,068m). 분기 간 거리는 반드시 기하에서 계산(문장 파싱 금지).
- **기존 도보 리듀서(`route-guide.ts`)는 속도 인지 상수 주입 없이 재사용 불가** — 4건:
  1. `ANNOUNCE_AHEAD_M=40`: 80km/h에서 1.8초 전 통지(교차로 진입 후 도착). 시간 기반(T−15초) 또는 속도 스케일 필요, 승객 브리핑은 2단("2km 앞"/"곧")이 적합.
  2. `WINDOW_AHEAD_MIN_M=50`+`EDGE_HITS_MAX=3`: fix 2.3초 공백이면 창 경계 클램프 + 직선 도로 저수직거리로 edgeHit 누적 → 멀쩡한 주행 중 거짓 "재확보". 지하차도·교량 하부에서 상시. 리듀서가 이미 계산하는 10초 중앙값 속도를 `ahead`에 되먹이면 해소.
  3. `OFF_ROUTE_BASE_M=30`: 두 provider 폴리라인 상호 어긋남 p95 28.6m·max 41.4m — 임계가 기하 불확실성 안에 있다. `OFF_ROUTE_HOLD_S=20`은 80km/h에서 444m 주행 후 확정.
  4. `REACQUIRE_GAP_S=10` 복구가 램프·입체교차에서 모호 정체(후보 복수 거부) — heading 또는 직전 d 연속성 타이브레이크 필요.
- ⚠ **조립 함정**: Tmap 도착 Point(`pointType:"E"`)는 뒤따르는 LineString이 없어 순진하게 스텝화하면 0-길이 스텝 → `buildGuideRoute` null → 상세 전체가 조용히 간략 강등. 도착은 스텝이 아니라 종점 마커로.
- **API 확장 지점은 한 곳**: `/api/route/car`에 도보 선례 그대로 `includeGeometry` 옵트인(`CarRouteGuide.pathCoords?` 추가, 기본 응답 byte-호환).

## 3. 선례·플랫폼 제약 [공식·2차]

### 3.1 iOS 지하철 내 기기 위치는 사실상 없다 (3사 독립 일치)

- 네이버지도: "iOS는 지하 구간 실시간 위치 파악에 제약" → **탑승 열차 선택 방식으로 우회**(하차까지 남은 역 수·출입문 위치·출구 번호 제공) [공식, 2023-12 보도].
- Tmap 기술 블로그: 지하 WiFi 스캔은 안드로이드 경로. iOS는 구간별 예상시간 **타이머**가 남는다. Geofence는 100~150m 한계 [공식].
- 서울교통공사 또타지하철: 도착역 알림·차내 비콘 안내 모두 안드로이드 전제(iOS 추후) [공식].
- 원인: iOS 앱은 주변 WiFi 스캔 API 접근 불가. 지상 구간(1호선 지상·경의중앙 일부 등)에서만 부분 가용 — 부분 가용성 의존은 같은 노선 안 동작 분기를 만들어 SR 사용자에게 원인 불명 불안정이 되므로 채택 금지.

### 3.2 하차 알림 선례 수치

- Tmap 버스 하차 임박 임계: **"구간의 약 75% 지점"** — 공개된 유일한 구체 수치 [공식].
- 카카오맵: "이용자 위치 + 실시간 운행정보" 병용이라고만 공개(비중 미상) [공식].

### 3.3 비수도권 도시철도 실시간은 없다

부산·대구·대전·광주·인천 전부 공공 실시간 위치·도착 API 미확인(부산 15000522는 시간표 명시, 광주 자체 API도 정적). 어디GO 앱·DarkTornado repo 2차 소스가 "시간표 기반"으로 일치 분류. ⚠ 갈리는 지점: 인천 1·2호선의 서울 API 커버 여부(어디GO는 실시간 목록에 포함) — 채택 시 실호출로 판정.

### 3.4 기타

- **Live Activities(잠금화면)는 이번 범위 제외 권고**: 공식 백그라운드 갱신 경로가 APNs 푸시뿐(서버 인프라 필요), 로컬 갱신은 심사 위험, `NSSupportsLiveActivitiesFrequentUpdates`도 사용자가 끌 수 있음. 국내 선례는 네이버지도. "지속 위치로 앱 실행 중 로컬 갱신"은 미검증 추정.
- **Apple MapKit transit은 한국 미제공**(도보·자동차는 정상이라는 기존 실측과 별개 축, `.transit` 실호출 미검증) [2차].
- **시각장애인 특화 선례**: BlindSquare 탑승 중 모드(GPS 기반 교차로·정류장 낭독 — 지상 한정), 국내 실증은 버스 승하차 집중(데이지: 비콘 하차벨). **지하철 탑승 중 안내의 시각장애인 특화 선례는 부재** — 선례 없이 설계하는 영역.
